Part 1Foundations

01How to Think About System Design

  • HLD decides the components, their responsibilities, how they communicate and where data lives; LLD designs the inside of one component.
  • Interviewers grade the process: scoping, structure, depth, trade-offs, numbers and communication. There is no single reference answer.
  • Systems scale in stages, and each building block (load balancer, cache, CDN, replicas, shards, queues, regions) removes one bottleneck and introduces a new problem.
  • Stateless app servers are the precondition for horizontal scaling; shared state belongs in a database, a cache or a signed token.
  • Non-functional requirements drive architecture more than features do; turn each one into a number (QPS, p99 latency, nines, staleness window).
  • State latency targets as percentiles such as p99, not averages, because the slow tail is what users feel.
  • Use a time-boxed plan: clarify (5), estimate (5), API and data model (5–10), high-level design (10–15), deep dives (10), wrap-up (5).
  • Tie every choice to a requirement or an estimate, and say what you give up.
  • Lead the conversation: announce transitions, propose deep dives, and point out your own design's weaknesses.

02Networking and How the Web Works

  • Typing a URL triggers: DNS lookup, TCP handshake, TLS handshake, HTTP request through a load balancer or reverse proxy to an app server, then rendering and fetching sub-resources.
  • DNS is hierarchical and cached: recursive resolver, root, TLD, authoritative. The TTL trades lookup cost against how fast changes propagate.
  • GeoDNS steers users to a nearby region but sees the resolver's location and is limited by caching; use load balancers for fine-grained balancing and fast failover.
  • A fresh HTTPS connection costs about 3 RTTs with TLS 1.3 (TCP, TLS, request); reuse connections and terminate TLS near users to cut latency.
  • HTTP/2 multiplexes streams on one TCP connection but still suffers TCP head-of-line blocking; HTTP/3 over QUIC fixes this and survives network changes.
  • REST for public and cacheable APIs, gRPC for internal high-QPS calls, GraphQL for flexible client-driven data needs.
  • GET, PUT and DELETE are idempotent; POST is not. Make POST retries safe with idempotency keys.
  • Pick real-time transport by direction and scale: SSE for server-to-client streams, WebSockets for bidirectional, WebRTC for peer media, polling as the simple fallback.
  • Persistent connections are cheap individually but stateful at scale: you need a registry or pub/sub to route messages, heartbeats, draining, and jittered reconnects.
  • A forward proxy acts for clients; a reverse proxy acts for servers and handles TLS termination, routing, load balancing, caching and protection.

03Back-of-the-Envelope Estimation

  • Estimates exist to drive decisions: round hard, state assumptions, carry units, and finish each number with what it implies.
  • 2^10 ≈ 10^3, so KB, MB, GB, TB and PB step by about 1,000. Signed 32-bit integers overflow at about 2.1 billion; use 64-bit IDs and counters.
  • A day has 86,400 ≈ 10^5 seconds: 1M events/day ≈ 12/s and 1B/day ≈ 12k/s. Multiply by about 2–3x for global peak, more for regional apps and events.
  • Memory ~100 ns, SSD random read ~100 µs, same-data-center round trip ~0.5 ms, disk seek ~10 ms, cross-continent round trip ~100–200 ms.
  • Storage = new objects per day × size × retention × overheads (replication, indexes, disk headroom). Media usually dwarfs metadata.
  • Networks are measured in bits: 1 Gbps = 125 MB/s. Egress = read rate × response size; large egress calls for a CDN and a cost estimate.
  • Size caches by distinct hot items (often ~20% of what is read daily) times entry size times ~1.5 overhead; many caches fit on one node.
  • Servers = peak load ÷ per-server capacity at ~60% utilization, plus headroom to lose a zone. Check CPU, connections, memory, network and disk; the largest wins.
  • 99.9% ≈ 43 minutes of downtime per month, 99.99% ≈ 4.3 minutes, 99.999% ≈ 26 seconds.
  • Little's Law, L = λ × W, sizes thread pools, connection pools and queues, and explains why a slow dependency exhausts them.

Part 2Core Building Blocks

04Scaling and Load Balancing

  • Scale up first when it's simple; scale out when you need more than one machine's capacity or need to survive a machine failure.
  • Keep the app tier stateless: sessions in Redis or a signed token, files in object storage. Stateless tiers scale by adding boxes.
  • L4 balancers see IPs and ports and decide per connection; L7 balancers parse HTTP and decide per request, enabling path routing, retries and gRPC balancing.
  • Terminate TLS at the L7 balancer by default; re-encrypt (or use mTLS) when the internal network must be encrypted too; passthrough loses L7 routing.
  • Round robin for uniform requests, least connections for variable or long-lived ones, power of two choices with many LB nodes, consistent hashing only when you need affinity.
  • Use readiness checks with hysteresis for routing, never let a shared dependency fail every instance's health check, and drain connections on deploy and scale-in.
  • Avoid sticky sessions: they cause uneven load, lost sessions on failure, and fight autoscaling.
  • Remove the LB as a SPOF in layers: multi-AZ managed LBs or VRRP pairs inside a site, GSLB or anycast across regions.
  • Autoscaling takes minutes: scale out fast, scale in slowly, and use warm pools or scheduled scaling for spikes you can predict.
  • When the fleet grows, check what breaks next: DB connections, downstream rate limits, LB capacity, account quotas.

05Caching and CDNs

  • Backend load is proportional to the miss ratio: going from 90% to 99% hits cuts database load 10x.
  • Cache-aside is the default: read cache, on miss read DB and set with a TTL; on write, update DB then delete the key rather than setting it.
  • Write-through keeps the cache warm at the cost of write latency; write-behind is fast but loses unflushed writes, so use it only for data like counters.
  • LRU is a hash map plus a doubly linked list for O(1) get and put; LFU or W-TinyLFU resists scans; set Redis to an allkeys-* policy for caches.
  • Every cache entry needs a TTL as a safety net; drive invalidation from the commit log (CDC) when correctness matters, and never decide payments on cached data.
  • Stampede: coalesce or lock per key and serve stale while refreshing. Penetration: negative caching and Bloom filters. Avalanche: TTL jitter and replicas. Hot key: local cache and key replication.
  • Pick Redis for data structures, replication and clustering; Redis Cluster hashes keys into 16,384 slots and needs hash tags for multi-key operations.
  • Use versioned URLs with max-age one year and immutable for static assets; use s-maxage, stale-while-revalidate and tag purges for content at the CDN.
  • Normalize CDN cache keys and avoid Vary on high-cardinality headers; add an origin shield so the origin sees about one fetch per object.
  • Always ask what happens at a 0% hit ratio: if the database falls over, you need warm-up, rate-limited fallbacks and a replicated cache.

06Databases: SQL, NoSQL and Indexing

  • ACID is four separate promises: atomicity (all-or-nothing via the log), consistency (your invariants, helped by constraints), isolation (concurrency control) and durability (WAL fsync before COMMIT returns).
  • PostgreSQL defaults to Read Committed and MySQL InnoDB to Repeatable Read. Neither prevents write skew; only Serializable, explicit row locks or constraints do.
  • Lost update: fix with an atomic UPDATE ... SET n = n + 1, SELECT ... FOR UPDATE or a version check. Write skew: fix with Serializable, locking the rows you read, or a unique or exclusion constraint.
  • MVCC lets readers and writers proceed without blocking each other; long-running transactions pay for it in bloat.
  • Use pessimistic locks for short, highly contended transactions, and optimistic version checks for low contention or anything that spans user think time.
  • Composite indexes follow the leftmost-prefix rule: equality columns first, then the sort column, then range columns. A covering index answers a query without touching the table.
  • Every index speeds up some reads and slows down every write; name the query each index serves.
  • B-trees update in place, giving predictable reads and random writes. LSM-trees append and compact, giving high write throughput at the cost of read and space amplification.
  • Pick NoSQL by access pattern: key-value for key lookups, document for self-contained aggregates, wide-column for huge append-heavy partitions, graph for multi-hop traversals, time-series for metrics, search for text.
  • Default to a normalized relational database, denormalize specific hot read paths, and name the requirement that pushes any data to another store.

Part 3Distributed Data

07Replication, Partitioning and Consistent Hashing

  • Replicate for availability, read scale, latency and durability. The hard part is propagating changes, done with single-leader, multi-leader or leaderless replication.
  • Async replication is fast but loses acknowledged writes on failover. Semi-sync (wait for one follower or a majority) keeps every acknowledged write on two machines for one extra round trip.
  • Replica lag anomalies have targeted fixes: read-your-writes (read own data from the leader or require a caught-up replica), monotonic reads (stick a user to one replica), consistent prefix (keep causally related writes in one partition).
  • Failover means detect, elect the most up-to-date replica, reroute and fence. Prevent split brain with majority-based leases and epoch fencing, not shorter timeouts.
  • In multi-leader setups, avoid conflicts first with a home leader per record. LWW silently drops concurrent writes, version vectors detect concurrency, and CRDTs merge automatically.
  • Quorums: with R + W > N, reads overlap the latest write. N = 3, W = 2, R = 2 tolerates one node down, but quorums are not linearizable (sloppy quorums, LWW clocks, partial writes).
  • Range partitioning gives cheap scans but hot-spots sequential keys; hash partitioning spreads load but scatters range queries; directory partitioning gives flexible placement at the cost of a lookup service.
  • Hashing never fixes a single hot key: split it into sub-keys, cache it, or handle celebrities and whale tenants specially.
  • Local secondary indexes keep writes cheap but make reads scatter-gather; global indexes give one-partition reads but asynchronous or transactional writes.
  • Never use hash % N over nodes: consistent hashing moves about 1/N of keys when a node joins, and virtual nodes even out load and spread recovery.

08Distributed Systems: CAP, Consistency and Consensus

  • Partial failure defines distributed systems: a timeout means 'no answer yet', never 'it did not happen', so every retried operation must be idempotent.
  • CAP, stated correctly: while a partition lasts, choose linearizability or availability. P is not optional, and 'CA' is not a real option for a multi-node system.
  • PACELC: even with a healthy network, strong consistency costs latency because it needs coordination. Choose per kind of data, not per system.
  • Linearizability is single-object, real-time recency; serializability is transaction isolation without a real-time promise; strict serializability (Spanner) is both.
  • Causal consistency is roughly the strongest model that stays available during partitions; eventual consistency guarantees only convergence.
  • Wall clocks drift and jump, so LWW can silently drop writes. Lamport clocks order events, vector clocks detect concurrency, HLCs add physical time, TrueTime bounds the error and waits it out.
  • Raft: randomized election timeouts, one vote per term, votes only for up-to-date logs, entries committed once a majority stores them. 2f + 1 nodes tolerate f failures.
  • Use etcd or ZooKeeper for small, critical coordination data (leaders, locks, config, membership), never for bulk data.
  • 2PC blocks when the coordinator dies after participants vote YES. Across services use sagas with idempotent steps and compensations, orchestrated when the flow is complex.
  • Never dual-write to a database and a broker; use a transactional outbox. Correctness locks need leases plus fencing tokens checked by the resource.

Part 4Communication and Architecture

09Message Queues, Streams and Event-Driven Design

  • Queue work that can happen after the response; keep calls synchronous when the user is waiting for the result. Queues buy decoupling, buffering, load leveling and fan-out, at the price of eventual consistency and duplicates.
  • Point-to-point queues split messages among competing consumers; pub/sub gives every subscriber its own copy. SNS-to-SQS and Kafka consumer groups combine both.
  • Kafka orders records only within a partition. Key by the entity whose events must stay ordered, choosing a high-cardinality key to avoid hot partitions.
  • A consumer group has at most one active consumer per partition, so the partition count caps parallelism. Adding partitions later remaps keys and breaks per-key ordering across the change.
  • Durable Kafka: replication factor 3, acks=all, min.insync.replicas=2, unclean leader election off. Consumers read only up to the high watermark.
  • Process then commit gives at-least-once; commit then process gives at-most-once. Exactly-once delivery is impossible; exactly-once effect is achievable.
  • Idempotent producers dedupe client retries per partition and session; Kafka transactions give exactly-once only for Kafka-to-Kafka pipelines. External side effects need idempotent consumers or dedupe tables.
  • Route poison messages to a DLQ, retry transient failures through delayed retry tiers with backoff, and alert on DLQ depth and on consumer lag measured in time.
  • Event notification, event-carried state transfer, event sourcing and CQRS are different patterns. Name the one you use and its consistency cost.
  • Never dual-write a database and a broker: use a transactional outbox, published by a poller or by CDC with Debezium.

10Storage, Search and Data Processing

  • Block storage is a raw disk for one host, file storage is a shared POSIX tree, object storage is an HTTP key to blob store that scales without limit and is cheapest per GB.
  • Object stores split a strongly consistent metadata service from a bulk data service; durability comes from multi-zone placement, checksums, scrubbing and fast repair.
  • 3x replication costs 200% overhead and survives 2 losses; RS(6,3) erasure coding costs 50% and survives any 3, at the price of CPU and costly repairs. Replicate hot data, erasure-code cold data.
  • Upload large media straight from the client to object storage with presigned URLs and multipart upload; your servers only handle metadata.
  • An inverted index maps each analyzed term to a sorted postings list; queries intersect lists, and positions enable phrase matching.
  • BM25 is the default relevance function: IDF weighting, saturating term frequency and document-length normalization.
  • Elasticsearch is near-real-time (refresh about every 1 s), routes documents by hash modulo a fixed primary shard count, and should be fed from the database by CDC, never treated as the source of truth.
  • Use event time, not processing time, for windowed aggregation; watermarks decide when a window is complete and how late data is handled.
  • Tumbling windows do not overlap, sliding windows put each event in size/slide windows, session windows close after an inactivity gap.
  • Columnar storage reads only the columns a query touches and compresses well, which is why OLAP engines and Parquet use it; ELT on a lakehouse is the modern default.

11Microservices, API Design and Rate Limiting

  • Start as a modular monolith; extract microservices only for a concrete reason such as independent scaling, team autonomy or a distinct reliability need.
  • Split services by business capability and bounded context, not by technical layer, and give each service its own database reachable only through its API or events.
  • Service discovery needs a registry kept current by health checks; client-side discovery saves a hop, server-side keeps clients simple.
  • The API gateway handles north-south cross-cutting concerns (TLS, auth, rate limits, routing); BFFs shape responses per client; a service mesh handles east-west retries, timeouts and mTLS through sidecars.
  • Make every non-idempotent create safe to retry with a client-generated Idempotency-Key stored atomically with the result.
  • Use cursor (keyset) pagination for large or changing collections: it seeks via an index instead of scanning and discarding offset rows.
  • Version with /v1 in the path, make only additive changes within a version, and return one consistent error format with a machine-readable code and request id.
  • Token bucket allows bursts up to capacity with a sustained refill rate in two numbers per key; fixed windows allow 2x bursts at edges; sliding window counter approximates a true sliding window with two counters.
  • Distributed rate limiting needs atomic check-and-update, typically a Redis Lua script, and an explicit fail-open or fail-closed decision.
  • Reject with 429 plus Retry-After, and send limit, remaining and reset headers on every response.

Part 5Production Readiness

12Reliability, Availability and Fault Tolerance

  • Components in series multiply availabilities (0.999 × 0.999 ≈ 99.8%); redundant components in parallel multiply unavailabilities (1 − 0.001² = 99.9999%).
  • End-to-end availability is capped by the weakest series component, so find and remove single points of failure, including DNS, auth, config and certificates.
  • Availability = MTBF / (MTBF + MTTR): fast detection, automated failover and quick rollback often buy more than more reliable hardware.
  • Size for failure: with k zones and peak need N, provision N × k / (k − 1), and keep active-active nodes below the utilization the survivors can absorb.
  • Active-passive suits single-writer state such as a database primary; active-active suits stateless tiers and data that is partitioned by owner or mergeable.
  • Multi-AZ with synchronous replication is the default (RPO zero, failover in seconds); multi-region costs far more and must be justified by requirements.
  • Every remote call needs a timeout derived from the remaining deadline; retry only transient errors on idempotent operations, with capped exponential backoff and full jitter.
  • Retries multiply across layers (3 × 3 × 3 = 27): retry at one layer, cap attempts, and enforce a retry budget to prevent retry storms.
  • Circuit breakers fail fast when a dependency is down, bulkheads stop one dependency from exhausting shared resources, and load shedding keeps goodput up under overload.
  • RPO is acceptable data loss, RTO is acceptable downtime; pick backup-restore, pilot light, warm standby or active-active per service tier, and test restores and failovers regularly.

13Observability and Security

  • Metrics tell you that something is wrong, traces tell you where, logs tell you why; link all three with a trace or correlation ID propagated on every hop.
  • Use structured JSON logs, RED metrics for services and USE metrics for resources; keep high-cardinality fields like user IDs out of metric labels.
  • Measure latency with percentiles from histograms, never averages, and never average percentiles across instances; merge histogram buckets instead.
  • SLI is the measurement, SLO the internal target, SLA the contract with penalties; a 99.9% SLO leaves about 43.8 minutes a month of error budget.
  • Spend the error budget on releases and experiments; when it runs out, the error budget policy shifts the team to reliability work.
  • Page on symptoms users feel, using multi-window burn-rate alerts (for example 14.4x over 1 hour and 5 minutes), not on CPU or other causes.
  • Sessions are instantly revocable but need a lookup; JWTs verify locally but cannot be revoked before expiry, so pair short-lived access tokens with revocable refresh tokens and a denylist.
  • Use OAuth 2.0 authorization code with PKCE for every user-facing client, OIDC ID tokens for login and SSO, and check iss, aud and exp on every token.
  • RBAC for simple roles, ABAC for contextual policies, ReBAC (Zanzibar-style tuples) for sharing and nested resources; enforce coarse checks at the gateway and fine-grained checks in services.
  • TLS outside and mTLS inside, envelope encryption with KMS at rest, secrets in a vault with workload identity, passwords hashed with Argon2id or bcrypt, and layered DDoS defense at the edge.

Part 6Advanced Toolkit

14Advanced Techniques and Data Structures

  • Snowflake IDs pack 1 sign bit, a 41-bit millisecond timestamp (about 69 years from a custom epoch), a 10-bit machine ID (1,024 workers) and a 12-bit sequence (4,096 IDs per ms per worker) into 64 bits. They stay unique only if worker IDs are unique and clocks never run backwards.
  • Time-ordered keys (Snowflake, UUID v7, ULID) keep B-tree inserts at the right-hand edge of the index; random UUID v4 keys scatter inserts across it. On range-partitioned stores such as Bigtable and Spanner the rule flips: sequential keys create a hot tablet.
  • A Bloom filter never gives false negatives. Size it with m = −n·ln p / (ln 2)² and k = (m/n)·ln 2: about 9.6 bits and 7 hashes per item for 1%, no matter how large the items are.
  • A Count-Min Sketch estimates frequencies in fixed memory and only overestimates, by at most εN with probability 1 − δ. Use it to find heavy hitters, not to report exact long-tail counts.
  • HyperLogLog counts distinct items in 12 KB in Redis with about 0.81% standard error. Merge sketches with PFMERGE to get unions, and never add daily unique counts together.
  • Merkle trees find the ranges where replicas differ in O(log n) hash comparisons. Gossip spreads membership in O(log N) rounds. Failure detectors such as SWIM and phi accrual can only suspect a node, so pair them with fencing.
  • For nearby search, a geohash prefix is a cell (6 characters is about 1.2 × 0.6 km, 5 is about 4.9 km). Always query the 8 neighbouring cells and re-rank by true distance. Quadtrees adapt to density, S2 handles precise region coverings, and H3 hexagons suit area aggregation.
  • OT transforms position-based edits through a central server, which is how Google Docs works. CRDTs converge without coordination but carry extra metadata and tombstones; they suit offline-first and peer-to-peer apps.
  • For distributed Top-K, partition events by key before counting, keep per-minute buckets for sliding windows and serve precomputed results from a cache. Merging local top-K lists computed from unpartitioned data gives wrong answers.
  • Fan-out on write makes reads cheap but costs one write per follower; fan-out on read makes writes cheap but amplifies tail latency. Use a hybrid to handle celebrity accounts.

Part 7Case Studies

15Case Studies I: Core Services

  • Do the code-length arithmetic out loud: 62^7 ≈ 3.5 trillion covers 182B links with room to spare, so seven base62 characters are enough.
  • At high write rates, pre-generate short keys (KGS) so the write path never does collision checks; keep a conditional put as the safety net and for custom aliases.
  • Pick 302 when you need per-visit analytics or the ability to disable links; 301 lets browsers cache the redirect, so you lose both.
  • Keep hot read paths read-only: emit analytics events to Kafka and aggregate offline instead of incrementing counters per request.
  • Dynamo-style stores map one technique to each problem: consistent hashing with vnodes, N replicas with R + W > N, vector clocks, sloppy quorum with hinted handoff, Merkle-tree anti-entropy, gossip.
  • R + W > N gives overlapping quorums, not linearizability; sloppy quorums, failed partial writes and concurrent updates still surface stale or conflicting data.
  • A crawler's frontier does two jobs, priority and politeness; partition by hostname so robots.txt, DNS and rate-limit state live on one node.
  • Crawler dedupe happens at three levels: URL normalization, a URL-seen set of fingerprints, and content fingerprints (SimHash for near-duplicates); per-host budgets stop spider traps.
  • Autocomplete: cache the top K completions at every trie node so lookups cost O(prefix length), rebuild offline from search logs with time decay, and add a streaming overlay for trending queries.
  • Size before you shard: a ~10 GB trie or a 15 GB hot-link cache fits in RAM, so replicate it; shard by prefix range only when it no longer fits.

16Case Studies II: Social and Communication

  • Chat: one WebSocket per device on gateways that only hold connections; a Redis session registry maps user and device to gateway, and the chat service owns message logic.
  • Order messages by a per-conversation sequence number assigned by the single owner of that conversation, and dedupe retries with a client-generated message ID. Never order by client clocks.
  • Ack the sender only after a durable quorum write. Delivery is at-least-once with client dedupe by seq, and receipts are per-member cursors (last_delivered_seq, last_read_seq), not per-message rows.
  • Presence is heartbeats plus a TTL key plus subscribe-on-view; push notifications are a wake-up hint, and offline devices catch up by syncing from the server-side log.
  • Feed: fan out post IDs, not bodies. Push to followers for normal authors, pull celebrity posts at read time and merge, skip inactive users, and treat the home timeline as a rebuildable cache.
  • Ranked feeds are candidate generation plus scoring at read time; paginate with an opaque cursor over a per-session ranked list, and use keyset cursors on time-sortable IDs for chronological feeds.
  • Notifications: accept with 202 and an idempotency key, apply preferences, quiet hours, caps and templates once, then use separate queues and workers per channel and priority so OTPs never wait behind campaigns.
  • Exactly-once delivery to APNs, FCM, SMS or email providers is impossible; aim for at-least-once with dedupe keys and collapse IDs, retry only transient errors, and disable dead tokens.
  • Video calls have three planes: control (REST), signaling (your own WebSocket service carrying SDP and ICE candidates) and media (SRTP over UDP). ICE tries host, STUN server-reflexive and TURN relay candidates; TURN over TLS on 443 rescues UDP-blocked networks.
  • An SFU with simulcast is the default for group calls: each sender uploads once in several qualities and the SFU picks a layer per receiver. Mesh suits 1:1, an MCU suits dial-in and composited output, and SFUs cascade across regions.

17Case Studies III: Media, Location and Commerce

  • Video streaming splits a control plane (metadata, auth, signed manifest URLs) from a data plane (segments from the CDN). App servers never stream video bytes, and egress bandwidth is the design.
  • Transcoding is an asynchronous DAG: split at keyframes, encode chunk-and-rendition tasks in parallel, stitch and package. Tasks are idempotent, and low renditions are published first.
  • Adaptive bitrate is a client decision. Keyframe-aligned segments plus HLS/DASH manifests let the player switch quality at any segment boundary, and CMAF lets one set of segments serve both formats.
  • Pre-position a predictable catalog on ISP-embedded caches during off-peak fill windows (Netflix Open Connect); use pull-through tiered caching with an origin shield for the long tail.
  • Ride-hailing has two data paths: a firehose of disposable locations held in memory and logged to Kafka, and a trickle of trips that must be correct, held in a transactional store with a state machine.
  • Index moving drivers with cells (H3 or geohash) for O(1) updates, search ring by ring, rank by road ETA, and guarantee one driver per trip with a compare-and-set reservation. Shard by city.
  • File sync is content-addressed immutable blocks plus a per-namespace metadata journal: send hashes, upload only missing blocks, then commit. Metadata is never committed before its blocks are durable.
  • Sync notifications are hints; clients pull changes by cursor. Detect conflicts with a compare-and-set on the parent revision and keep a conflicted copy, never last-writer-wins on device clocks.
  • A seat hold is a conditional UPDATE with an expiry, the unique constraint on (show, seat) is the last guard, and payment confirmation is conditional and idempotent, with an automatic refund if the hold was lost.
  • A flash sale is solved at the edge: a virtual waiting room meters admission to what inventory needs, so the booking database sees hundreds of writes per second instead of a million requests.
