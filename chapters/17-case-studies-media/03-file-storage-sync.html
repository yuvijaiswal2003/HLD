Design file storage and sync (Dropbox / Google Drive)

Dropbox and Google Drive feel like one folder that exists everywhere at once. Underneath are two very different systems: a block store holding immutable chunks of files, each named by the hash of its content, and a metadata service that records which chunks make up each file at each revision and the order in which changes happened. The client does real work too. It watches the file system, chunks and hashes files, and reconciles local state with the server's. Almost all the bandwidth savings come from one rule: never upload a chunk the server already has.

1. Requirements

  • Sync: upload, download and sync files and folders across a user's desktop, mobile and web clients; a change on one device appears on the others within seconds.
  • Offline: edit while offline and reconcile on reconnect, without losing anyone's work.
  • History: keep version history and let users restore deleted files for, say, 30 days.
  • Sharing: share folders with other users as viewer or editor, and share files by link. Out of scope: real-time co-editing of documents and full-text search.
  • Durability: an acknowledged file is never lost; target 11 nines for stored blocks (Chapter 10).
  • Consistency: revisions of a file are strictly ordered, and a device never sees a revision whose blocks aren't all stored. Propagation to other devices is eventual (seconds).
  • Efficiency: minimize bytes over the wire with delta sync, dedupe and compression; many users are on slow or metered links.
  • Scale: hundreds of millions of users, an exabyte of data, hundreds of billions of files; metadata operations under ~200 ms.

2. Estimates

  erasure coding at 1.5x                         ~ 1.05 EB raw disk (3x replicas: 2.1 EB)

  x ~300 B each (path, revision, block list)     ~ 150 TB, sharded by namespace
Commits: 100M DAU x 20 file changes/day          = 2B commits/day
  2B / 86,400                                    ~ 23k commits/s, ~70k/s at peak
Upload after delta sync: 100M x 30 MB/day        = 3 PB/day ~ 35 GB/s ~ 280 Gbps
Devices online at peak ~50M; ~100k idle long-polls per server -> ~500 servers

Storage, not request rate, is the cost center. At an exabyte, 1% better storage efficiency is 10 PB of disks, which is why dedupe, compression and erasure coding instead of triple replication matter so much. Metadata is large (~150 TB) and transactional (~70k commits/s at peak), so it needs a sharded relational store with a shard key that keeps each commit on one shard. The 50M connected devices are idle almost all the time, so notifications must be cheap per connection and carry no data.

5. High-level design

Upload path. The desktop client's watcher (inotify, FSEvents or ReadDirectoryChangesW) sees a file change. The chunker splits the file into 4 MB blocks, hashes each with SHA-256, and records the result in a local SQLite index. It sends the metadata service a commit with the path, the parent revision it edited, and the ordered list of hashes. The service answers with the hashes it doesn't have. The client uploads only those to the block service, which re-hashes each block on arrival, so a buggy or malicious client can't store bytes under the wrong name. The client then repeats the commit, and the metadata service applies it atomically: append a journal entry to the namespace and update the latest-state row. Download path. The journal append emits an event. The notification service wakes every device long-polling on that namespace; each one asks for changes since its cursor, gets the new block list, and fetches only the blocks it doesn't already have locally. Sharing. A shared folder is its own namespace mounted into each member's tree, so a single commit becomes visible to every member, and permissions are checked per namespace. Share links are random 128-bit tokens mapped to a namespace, path, role and expiry, and downloads go through short-lived signed URLs.

6. Deep dives

Deep dive A: chunking and dedupe. Splitting files into blocks buys three things. Uploads become resumable: a failure retries one 4 MB block, not a 2 GB file. Sync becomes a delta: an edit re-uploads only the changed blocks. And storage dedupes: a block is stored once however many files contain it, because its name is its hash. Fixed-size blocks are simple and work well for files edited in place, but inserting bytes near the start shifts every later boundary and changes every hash. Content-defined chunking (CDC) instead cuts wherever a rolling hash over a small sliding window (a Rabin fingerprint, or Gear hashing in FastCDC) matches a bit pattern, so boundaries move with the content and an insertion changes only the chunk it lands in; backup tools such as restic and Borg chunk this way. Dedupe scope is a policy decision. Deduping within a user or team is safe. Global cross-user dedupe saves more but leaks information: if an upload finishes instantly, the uploader learns that someone already has that exact file. Because blocks are immutable, deleting a file only removes references to them, and a background mark-and-sweep collector frees blocks that no revision within the retention window still references. That is safer than synchronous reference counts, which drift when a crash lands between two steps.

Fixed-size blocks (e.g. 4 MB)

Strengths
  • Trivial to compute and to seek: block k starts at byte k times 4 MB
  • Predictable metadata size per file
  • Great for files modified in place: databases, VM images, many media edits
Weaknesses
  • An insertion shifts every later boundary, so all later hashes change
  • Poor dedupe across slightly different versions of documents
Use whenThe default for a sync product with a simple, fast client; Dropbox uses 4 MB blocks.

Content-defined chunking

Strengths
  • Boundaries follow content, so inserts and deletes touch one or two chunks
  • Much better dedupe across versions and similar files
Weaknesses
  • Variable chunk sizes need min and max limits
  • Rolling-hash CPU cost on every byte
  • Can't jump to byte offset N without the chunk list
Use whenBackup and archival systems, or sync where edits often insert into the middle of large files.

Deep dive B: the sync protocol. Each namespace has an append-only journal with a monotonically increasing journal_id, and a client's cursor is the last journal_id it has applied for each namespace it mounts. Sync is just: fetch changes since the cursor, apply them, advance the cursor. Notifications are hints: the long-poll returns only that namespace 42 changed, and the client pulls the details. That makes them cheap to fan out to 50M idle connections and harmless to lose or duplicate, because the journal is the source of truth and the same code path handles a laptop that was offline for a week. If a cursor is older than the journal's compaction horizon, the server tells the client to do a full re-list. One ordering rule is non-negotiable: never commit metadata before every block it references is durably stored, or another device could fetch a revision it can't download. The check, upload, commit loop enforces exactly that.

Deep dive C: conflicts. Every commit carries the parent revision the client edited, and the metadata service applies it only if the file's latest revision still equals that parent. That is optimistic concurrency: a compare-and-set on the latest-state row. If two laptops edit the same file offline, the first to reconnect wins. The second gets a 409, and its client keeps both versions by committing its copy under a new name such as report (Bob's conflicted copy 2026-10-22).docx. Last-writer-wins by device timestamp would silently throw away someone's work, and device clocks drift (Chapter 8). Automatic merging only works when the system understands the format; real-time co-editing uses operational transformation (as Google Docs does) or CRDTs (Chapter 14), not file sync. On the client, every decision comes from a three-way comparison of the local tree, the remote tree and the last synced state, which serves as the merge base. Only local differs from base: upload. Only remote differs: download. Both differ: conflict. Without the base you can't tell a local delete from a remote create.

In production
How Dropbox does it
Dropbox stores file content as 4 MB blocks addressed by their SHA-256 hash, so unchanged blocks are never uploaded again. In 2016 it finished moving the bulk of user data off Amazon S3 onto Magic Pocket, its own exabyte-scale, erasure-coded block storage system. In 2020 it described rewriting its desktop sync engine, Nucleus, in Rust, built around reconciling a remote tree, a local tree and a synced tree.
In the interview
What to say first
State the split in the first two minutes: content-addressed immutable blocks, plus a per-namespace metadata journal. Then walk through the commit protocol (send hashes, the server answers with what's missing, upload those, commit with a parent revision). That one exchange shows dedupe, delta sync, the blocks-before-metadata rule and conflict detection together. Expect follow-ups on two devices editing the same file, how devices learn about changes, and how a one-line edit avoids re-uploading 2 GB.
