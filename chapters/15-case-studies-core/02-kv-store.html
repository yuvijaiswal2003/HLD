Design a Distributed Key-Value Store

A Dynamo-style key-value store is where Chapter 7 (replication, partitioning, quorums), Chapter 8 (consistency, clocks) and Chapter 14 (gossip, Merkle trees) come together. Nobody expects you to invent anything; the interviewer wants to see you assemble known techniques, each chosen for a specific failure or scaling problem, and say what each costs. We design for the requirement behind Amazon's 2007 Dynamo paper: keep accepting writes while nodes, racks or links fail. Cassandra and Riak are its best-known descendants. The managed DynamoDB service is a different design despite the name: each partition is replicated by a Multi-Paxos group with a leader.

1. Requirements

  • Operations: put(key, value), get(key), delete(key). Keys up to 256 bytes, values up to 1 MB, typically ~10 KB.
  • Always writable: a put succeeds even with some replicas or a whole rack down. Think shopping cart: rejecting “add to cart” loses money.
  • Tunable consistency: callers trade latency and availability against freshness per request.
  • Incremental scale: grow from tens to hundreds of nodes by adding machines, with no downtime and no manual resharding.
  • Latency and durability: p99 under 10 ms inside a data center; an acknowledged write survives node loss; no master and no single point of failure.
  • Not required: multi-key transactions, secondary indexes, range scans.

2. Estimates

Assume 1B keys × ~10 KB = 10 TB of raw data, 30 TB with 3 replicas. Keeping each node at ~1 TB on a 2 TB SSD (headroom for compaction and rebalancing) needs ~30 nodes for storage alone. Peak traffic is 500k reads/s and 100k writes/s. With N = 3, every write goes to all 3 replicas (the coordinator just waits for W of them): 300k replica writes/s. With R = 2, each read touches 2 replicas: 1M replica reads/s. If one node sustains ~20k replica operations/s on an LSM engine, 1.3M / 20k ≈ 65 nodes. Throughput, not storage, sizes this cluster; plan ~80 nodes so it survives losing a rack at peak.

5. High-level design

We are building the database itself, so every node runs the same code, holds the structures in the table above and can coordinate any request. There is no master or metadata server, which removes single points of failure but means membership must itself be replicated, by gossip. The client library caches the ring (learned from any node) and sends a request to the first node of the key's preference list. Write: the coordinator writes locally, forwards to the other N−1 replicas in parallel, and replies once W replicas (counting itself) have acknowledged. Read: it asks R replicas; if versions differ, it returns the newest version (or the concurrent siblings) and repairs stale replicas in the background. Hinted handoff, anti-entropy and gossip run off the request path and keep replicas converging.

6. Deep dives

A. Partitioning. Keys are hashed (e.g. Murmur3) onto a ring, and each physical node owns many virtual nodes (tokens) scattered around it (Chapter 7). Vnodes smooth out load, let a new node take small slices from many existing nodes instead of one big slice from a neighbor, and let bigger machines own more tokens. A key's preference list is the first N distinct physical nodes clockwise from its hash, skipping extra vnodes of nodes already chosen and, in production, spreading replicas across racks or availability zones. Token-aware clients send each request straight to a replica, saving the hop through a random node that would forward it.

B. Quorums: the consistency knob. If R + W > N, every read set intersects every write set, so a read reaches at least one replica holding the latest acknowledged write. That is still not linearizability (Chapter 8): a write that failed after reaching one replica may surface later, concurrent writes still need resolution, and sloppy quorums (below) break the overlap during failures. If the interviewer demands strict consistency, the honest answer is consensus per partition (Raft, as in CockroachDB or TiKV), which gives up availability on the minority side of a partition.

C. Concurrent writes and vector clocks. Any replica can accept a write during a partition, so two clients can update one key without seeing each other. Last-write-wins by timestamp (Cassandra's choice) silently drops one of them and trusts clocks. Dynamo instead attaches a vector clock, a list of (node, counter) pairs, to each version. Version X descends from Y if every counter in X is at least the matching counter in Y; if neither descends from the other, they are concurrent and both are kept as siblings for the application to merge. The opaque X-Context token in the API is this clock: every get returns it and the next put sends it back, which tells the store which version the writer had seen. A cart merges by set union, which has a known flaw: an item removed on one side comes back after the merge. CRDTs such as observed-remove sets (Chapter 7) fix that. Clocks also grow with the number of coordinators, so Dynamo truncated the oldest entries past a threshold of about 10.

D. Failure handling. Each mechanism targets a different kind of failure; naming the pairing is what interviewers listen for.

Pitfall
Deletes are writes, and they can come back
A delete writes a tombstone that must reach every replica before it is purged. Cassandra keeps tombstones for gc_grace_seconds, 10 days by default. If a replica is down longer than that, the others purge the tombstone, the old replica returns still holding the value, and anti-entropy dutifully copies the “deleted” data back everywhere. The fix is operational: run repair more often than the grace period, and rebuild rather than restart a node that has been gone longer than it.

In the interview
Map every mechanism to the problem it solves
Strong candidates organize the answer as problem to technique: partitioning to consistent hashing with vnodes; replication to a rack-aware preference list of N nodes; the consistency knob to R and W; concurrent writes to vector clocks (or LWW, with its cost stated); temporary failures to sloppy quorum and hinted handoff; permanent divergence to Merkle-tree anti-entropy; membership to gossip. Then they say, unprompted, what R = W = 2 still does not guarantee.
