Remember for the interview

  1. 01Do the code-length arithmetic out loud: 62^7 ≈ 3.5 trillion covers 182B links with room to spare, so seven base62 characters are enough.
  2. 02At high write rates, pre-generate short keys (KGS) so the write path never does collision checks; keep a conditional put as the safety net and for custom aliases.
  3. 03Pick 302 when you need per-visit analytics or the ability to disable links; 301 lets browsers cache the redirect, so you lose both.
  4. 04Keep hot read paths read-only: emit analytics events to Kafka and aggregate offline instead of incrementing counters per request.
  5. 05Dynamo-style stores map one technique to each problem: consistent hashing with vnodes, N replicas with R + W > N, vector clocks, sloppy quorum with hinted handoff, Merkle-tree anti-entropy, gossip.
  6. 06R + W > N gives overlapping quorums, not linearizability; sloppy quorums, failed partial writes and concurrent updates still surface stale or conflicting data.
  7. 07A crawler's frontier does two jobs, priority and politeness; partition by hostname so robots.txt, DNS and rate-limit state live on one node.
  8. 08Crawler dedupe happens at three levels: URL normalization, a URL-seen set of fingerprints, and content fingerprints (SimHash for near-duplicates); per-host budgets stop spider traps.
  9. 09Autocomplete: cache the top K completions at every trie node so lookups cost O(prefix length), rebuild offline from search logs with time decay, and add a streaming overlay for trending queries.
  10. 10Size before you shard: a ~10 GB trie or a 15 GB hot-link cache fits in RAM, so replicate it; shard by prefix range only when it no longer fits.
