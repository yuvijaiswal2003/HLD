Design a Web Crawler

A web crawler (spider) starts from seed URLs, downloads pages, extracts their links and repeats. Search engines, web archives such as the Internet Archive and Common Crawl, SEO tools and training-data pipelines all run one. The core algorithm is a breadth-first traversal you could write in twenty lines. The design problem is running it over billions of pages without overloading any single website, without getting stuck in infinite link mazes, and without downloading the same content again and again.

1. Requirements

  • Crawl: from seed URLs, fetch HTML over HTTP and HTTPS, extract links, and store page content for a downstream indexer (this chapter's news-indexer design problem consumes it).
  • Recrawl: revisit pages based on how often they change; important pages (high PageRank, news front pages, sitemaps) much more often.
  • Politeness: obey robots.txt; by default at most one connection per host and a delay between requests to it.
  • Scale: 3B pages per month, with no duplicate storage of identical content.
  • Robustness and extensibility: survive spider traps, malformed HTML, slow or hostile servers; make it easy to add PDF parsing or image fetching later.
  • Out of scope unless asked: JavaScript rendering (a headless browser costs an order of magnitude or more CPU and memory per page), ranking, and the search index itself.

2. Estimates

A 30-day month is ~2.6M seconds, so 3B pages / 2.6M s ≈ 1,150 pages/s average, ~2,300/s at a 2x peak. At ~100 KB of uncompressed HTML per page, download bandwidth is 1,150 × 100 KB ≈ 115 MB/s, roughly 1 Gbps. Storage is 3B × 100 KB = 300 TB per month raw, ~75 TB compressed at 4:1; keeping 12 monthly snapshots is ~0.9 PB of object storage. With ~50 links per page, the link extractor emits ~58k URLs/s that must be checked against the set of ~10B known URLs. If an average fetch takes ~1 s including slow servers, Little's Law (Chapter 3) says 2,300 pages/s × 1 s = 2,300 requests in flight. Async I/O handles that easily; CPU for decompression, parsing and fingerprinting is the real limit. At ~100 pages/s per node end to end, peak needs ~23 nodes, so plan ~30.

Content fingerprints64-bit text hash and SimHashFirst URL seen with this contentRocksDB on each node

URL state is ~10B rows, rewritten on every fetch and read by key, which suits a wide-column store. Google's Bigtable paper describes exactly this “webtable”, with rows keyed by reversed hostname (com.cnn.www/index.html) so that one site's pages sort together and per-site scans are cheap. Page bodies go into WARC files, the archive format used by the Internet Archive and Common Crawl: large, append-only, compressed files are the cheapest thing to put in object storage, and each event carries a file-and-offset pointer to its record.

5. High-level design

  1. Pick
    A fetcher asks the frontier for the next URL whose host may be contacted now.
  2. Resolve and check
    Look up the host's IP in the local DNS cache and its rules in the robots.txt cache; disallowed URLs are dropped.
  3. Fetch
    Issue the request with connect and total timeouts, a 10 MB size cap and a conditional header (If-None-Match or If-Modified-Since) so unchanged pages return a cheap 304.
  4. Store and publish
    Append the response to a WARC file and publish a page-crawled event for the indexer.
  5. Parse and dedupe
    Extract text and links; if the text fingerprint was seen before, record the duplicate and stop processing this page.
  6. Extract and route
    Normalize each link, apply filters (scheme, length, blocklists), test it against the URL-seen set, and send new URLs to the node that owns their host.
  7. Reschedule
    Update the URL's state and compute its next fetch time from its observed change rate.

6. Deep dives

A. The URL frontier. The frontier is not a FIFO queue. It answers two questions at once: which URL is most valuable to fetch next (priority), and which hosts may be contacted right now (politeness). The Mercator crawler's design, still the standard answer, gives each question its own layer. Front queues are one per priority level; a prioritizer assigns each URL a level from signals like PageRank, past change frequency and whether it is a news page or sitemap. Back queues each hold URLs of exactly one host. When a back queue empties, a router refills it from the front queues, biased toward high priority. A min-heap keyed by each host's next allowed fetch time hands hosts to fetcher threads; after a fetch the host goes back into the heap at now plus a delay. A common rule is about 10 times the last response time, and never less than the non-standard Crawl-delay directive where a site sets one and the crawler honors it. Most of the frontier lives on disk with only the queue heads in memory: 10B queued URLs × ~100 B is ~1 TB.

B. Dedupe at three levels. URL variants: the same page is reached as http and https, with and without a trailing slash, with fragments, reordered query parameters or tracking parameters, so normalize before anything else. URL-seen test: 10B known URLs × 8-byte fingerprints is 80 GB, about 2.7 GB per node across 30 nodes, which fits in RAM, and 64-bit fingerprints expect only about three collisions among 10B URLs (n² / 2^65). A Bloom filter (Chapter 14) needs ~12 GB for 10B URLs at 1% false positives; it is the choice when memory is tight, at the cost of silently never crawling ~1% of new URLs. Content duplicates: mirrors, print versions and syndicated copies have different URLs but the same text. Hash the extracted text, not the raw HTML (which differs in ads and timestamps), to catch exact copies; for near-duplicates use SimHash, a 64-bit fingerprint in which similar documents differ in only a few bits. Google published its use of SimHash with a Hamming-distance threshold of 3 to detect near-duplicates among 8 billion pages.

python
from urllib.parse import urlsplit, urlunsplit, parse_qsl, urlencode
import hashlib

TRACKING = {"utm_source", "utm_medium", "utm_campaign", "gclid", "fbclid"}
DEFAULT_PORT = {"http": 80, "https": 443}

def normalize(url: str) -> str:
    s = urlsplit(url.strip())
    scheme = s.scheme.lower()
    host = (s.hostname or "").lower().rstrip(".")
    if s.port and s.port != DEFAULT_PORT.get(scheme):
        host = host + ":" + str(s.port)
    query = sorted((k, v) for k, v in parse_qsl(s.query) if k not in TRACKING)
    return urlunsplit((scheme, host, s.path or "/", urlencode(query), ""))  # drop the fragment

def fingerprint(text: str) -> int:
    return int.from_bytes(hashlib.blake2b(text.encode(), digest_size=8).digest(), "big")

def owner(url: str, ring) -> str:
    # Every URL of a host goes to one node, so politeness state never leaves that node.
    return ring.lookup(urlsplit(url).hostname)

C. Distributing the crawl. Partition by hostname with consistent hashing (Chapter 7), not by URL. Every URL of a host then lands on one node, which owns that host's back queue, robots.txt rules, DNS entry and delay timer, so politeness needs no cross-node coordination. Links found for other hosts go into a Kafka topic partitioned by host, and the owning node consumes them; batching keeps this cheap at 58k links/s. When a node dies, its hosts move to ring neighbors, which rebuild state from the URL store. DNS deserves its own component: a crawler resolves far more distinct hostnames than a normal client, and the Mercator team found synchronous lookups through the standard library to be one of their biggest bottlenecks. Run a caching resolver on every node, resolve asynchronously, honor TTLs and pre-resolve hosts as their URLs enter the frontier. Placing crawler pools in several regions and assigning hosts to the nearest pool cuts fetch latency, which by Little's Law cuts the number of open connections needed.

D. robots.txt and freshness. Fetch robots.txt before a host's first page and cache it for at most 24 hours, the limit RFC 9309 sets. A 4xx on robots.txt means no restrictions; a 5xx or network error means assume everything is disallowed until it can be fetched. Back off on 429 and 503 responses and when a host's latency rises. For freshness, each URL carries a next_fetch_at computed from its observed change rate: pages that changed on recent visits come back sooner, pages that never change drift toward monthly. Conditional GETs make unchanged revisits cost a few hundred bytes. News front pages, RSS feeds and sitemaps are polled every few minutes, because that is where new URLs appear first.

Pitfall
Spider traps: dedupe will not save you
Some sites generate unbounded URL spaces: calendars that link to the next month forever, faceted search that produces every filter combination, session IDs embedded in paths, or deliberately malicious traps. Every URL really is new, so the URL-seen set never fires. Defend with a per-host page budget per crawl cycle, a maximum URL length (~2,000 characters) and path depth, detection of repeating path segments such as /a/b/a/b/a/b, and stripping known session parameters. The budget is the backstop: a trap then wastes a bounded slice of the crawl instead of all of it.

In the interview
What strong candidates say
Name the frontier's two jobs, priority and politeness, before drawing boxes, then say “I'll partition by host so politeness is local to one node.” Do the Little's Law calculation for in-flight fetches out loud, and list the three dedupe levels: URL normalization, the URL-seen set, content fingerprints. Interviewers routinely probe spider traps, robots.txt failures and DNS as the hidden bottleneck; raising them yourself shows you have thought about the real web, not an idealized graph.
