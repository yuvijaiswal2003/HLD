Design a QR-Code and Link-in-Bio Service with Click Analytics

Design a service that gives creators and businesses two products: a link-in-bio page (sho.rt/@handle) listing their links, and dynamic QR codes for print whose destination the owner can change at any time. Owners see near-real-time analytics: page views, clicks and scans by link, country, device and referrer, plus unique visitors. Assume 20M creators and about 300M page views per day.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • How fresh must the dashboard be: seconds, minutes or a day?
  • Do owners need unique visitors, and over which windows: day, week, all time?
  • How quickly must a changed QR destination take effect?
  • Should bots and link-preview fetches be excluded from counts, or shown separately?
  • What privacy rules apply: may we store IP addresses, and for how long?
  • How large are traffic spikes when a big creator posts?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1A printed QR code can never be changed, so it must encode a short URL you control. What does that force about the redirect status code and caching?
H2Bio pages are the same for every visitor and change rarely, so serve them from a CDN. Your servers then never see the page views; how do you still count them?
H3Counting is the crux. Separate the event path (Kafka and a stream processor) from the query path (a columnar store), and decide where bots, double taps and duplicate deliveries are filtered.
H4Unique visitors per link per day across billions of events: which Chapter 14 structure gives this in a few KB, and why does it matter that it is mergeable?
H5When a celebrity posts, one link gets 50k clicks/s. Which part of your pipeline is keyed in a way that turns that into a single hot partition?

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

1. Requirements

  • Bio pages: GET /@handle renders the owner's links; owners edit links, order and theme.
  • Dynamic QR: create a code for a destination, download PNG or SVG, change the destination at any time; changes visible within about a minute.
  • Tracking: every bio-link click and QR scan redirects through us and is counted; page views are counted too.
  • Analytics: views, clicks, scans and click-through rate by link, hour or day, country, device and referrer, plus unique visitors; dashboard lag under ~1 minute.
  • Non-functional: redirects p99 under 50 ms and 99.99% available, because printed codes in the wild cannot be reissued; counts within ~1% of the truth; no raw IP addresses stored.

2. Estimates

Page views: 300M/day ≈ 3,500/s. Clicks at a 20% click-through rate: 60M/day ≈ 700/s. QR scans: 40M/day ≈ 460/s. Total ~400M events/day ≈ 4,600/s average, ~15k/s at a 3x daily peak, with single-creator spikes of ~50k/s on top. At ~300 B per event that is 120 GB/day of raw JSON; in a columnar store with ~10x compression on repetitive fields, ~12 GB/day or ~4.4 TB/year, which is a few ClickHouse nodes. Links: 20M creators × 10 links + 50M QR codes = 250M rows × ~500 B ≈ 125 GB. Unique visitors: a HyperLogLog sketch with 4,096 six-bit registers is ~3 KB and has ~1.6% standard error (1.04 / √4096), so a per-link daily sketch is far cheaper than storing visitor IDs.

3. API

http
POST /api/v1/qr
{"destination": "https://cafe.example/menu", "label": "table tents"}
-> 201 {"code": "q7Tb2", "short_url": "https://sho.rt/q/q7Tb2",
        "svg_url": "https://cdn.sho.rt/qr/q7Tb2.svg"}

PATCH /api/v1/links/{link_id}
{"destination": "https://cafe.example/winter-menu"}
-> 200 OK

GET /@{handle}                       -> 200 static HTML from the CDN
GET /r/{link_id}   and   GET /q/{code}
-> 302 Found, Location: destination, Cache-Control: no-store

GET /api/v1/analytics?from=2026-10-01&to=2026-10-21&metric=clicks&group_by=link,country
-> 200 {"rows": [...], "uniques": 48211, "as_of": "2026-10-21T14:03:00Z"}

4. Data model

StoreKeyFields
Links (PostgreSQL sharded by owner_id)link_idowner_id, kind (bio or qr), destination, position, status, updated_at
Pageshandleowner_id, theme, published_version
Events (ClickHouse)ORDER BY owner_id, link_id, tsevent_id, ts, type (view, click, scan), country, device, referrer_domain, visitor_hash, is_bot
Rollups (ClickHouse materialized view)owner_id, link_id, hour, country, devicecount, HyperLogLog state of visitor_hash

Links are relational and small, edited by their owner, so PostgreSQL sharded by owner_id keeps a creator's links together. Events are append-only and queried as aggregates over one owner's rows, which is exactly what a columnar OLAP store is for (Chapter 10). Ordering the ClickHouse table by (owner_id, link_id, ts) means a dashboard query reads only that owner's slice of the data.

5. High-level design

Click or scan: the redirect service resolves the destination from its local LRU, then Redis, then the links DB, returns a 302, and buffers an event to Kafka asynchronously. Page view: the CDN serves the static page, and the page sends a small beacon (navigator.sendBeacon) to the event service; CDN access logs streamed into Kafka are a second source that also catches visitors who block scripts. Dashboard: the API queries ClickHouse rollups for charts and raw events for drill-downs.

6. Deep dives

A. Mutable destinations. The QR code encodes sho.rt/q/q7Tb2, never the destination, and the redirect is always a 302 with no-store; a cached 301 on a phone would pin last season's menu forever. On an edit, the API updates the row, deletes the Redis key, and redirect nodes' local LRUs hold entries for at most 30 seconds, which meets the one-minute requirement. Bio pages are rendered to static HTML on every edit and purged from the CDN by URL. QR images are generated once from the short URL and served from the CDN; a short URL keeps the QR version low (fewer, larger modules), so it scans reliably when printed small, and error-correction level Q or H (25% or 30% recoverable) tolerates damage or a logo in the middle.

B. Counting correctly. Most analytics complaints come from counts that are inflated, deflated or impossible to reconcile. Each source of error gets an explicit fix:

ProblemFixWhere
Bots and crawlersUser-agent lists, data-center IP ranges, no beacon; flag is_bot rather than dropFlink enrich step
Link previews from Slack, WhatsApp, iMessageKnown preview user agents flagged as previews, not visitsFlink enrich step
Double taps and refreshesSame visitor and link within 30 s counts onceFlink keyed state with a TTL
Duplicate delivery from retriesevent_id set at the edge; dedupe in Flink, ReplacingMergeTree as a backstopFlink and ClickHouse
Unique visitors without raw IPsvisitor_hash = hash of IP, user agent and a salt rotated daily; HyperLogLog per link per dayEdge and rollups

The daily salt means no visitor can be tracked across days, which simplifies the privacy story. The price: the same person on two days produces two hashes, so weekly uniques computed by merging daily sketches overcount repeat visitors. Products that need cross-day uniques use a consented first-party cookie as the visitor ID instead. Say this trade-off out loud; it is the kind of detail that separates a strong answer.

C. Hot creators. A celebrity post can send 50k clicks/s to one link. The redirect tier is stateless and scales horizontally, and the hot destination sits in every node's local LRU, so no Redis key gets hot. The pipeline is the trap: partitioning Kafka by link_id would put the whole spike on one partition and one Flink task. Partition raw events by event_id instead, pre-aggregate per link per second inside each task, and merge the partial counts by link_id downstream; this is the two-stage aggregation from Chapter 10's ad-click design. ClickHouse wants inserts in batches of thousands of rows, so Flink flushes every second or so rather than per event.

5Follow-up questions

  • An owner's own site analytics shows 30% fewer visits than your click counts. How do you explain and reconcile the gap?
  • How would you support A/B testing two destinations behind one QR code?
  • A brand prints a unique QR code on each of 10M packages and wants scans per package. What changes?
  • How do redirects and counts behave if Kafka is unavailable for an hour?
  • How would you offer exact all-time unique visitors, and what would it cost?
