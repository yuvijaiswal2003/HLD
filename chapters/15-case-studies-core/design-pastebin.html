Design Pastebin

Design a service like Pastebin where users paste text or code, optionally choose an expiry time and visibility, and get a short link that anyone holding it can open. Assume about 1M new pastes per day and that most pastes are read a handful of times.

45:00Mock interview timer. Start it when you begin talking.
Clarify requirements5 min
Estimate scale5 min
API and data model8 min
High-level design12 min
Deep dives10 min
Wrap up and bottlenecks5 min

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • What is the maximum paste size, and what is a typical one?
  • What is the read:write ratio, and how long are pastes kept when no expiry is set?
  • Which visibility modes are needed: public and listed, unlisted (anyone with the link), private (owner only)?
  • Do we need burn-after-read, editing, or version history?
  • Can anonymous users create pastes, or only signed-in users?
  • Is syntax highlighting rendered on the server, or can the client do it?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1Compared with a URL shortener, the value is now a blob of up to megabytes rather than a 200-byte URL. Where should blobs live, and what stays in the database?
H2At ~35 writes/s, do you still need a key generation service? Think about what a random ID plus a conditional put costs at this rate.
H3Unlisted pastes are protected only by how hard their ID is to guess. How long must the ID be so that an attacker making a million guesses finds almost nothing?
H4Expiry has two halves: never serve an expired paste, and eventually reclaim its storage. Which mechanism handles each half?
H5Public pastes never change after creation. What does that let a CDN do, and what does burn-after-read break?

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

1. Requirements

  • Functional: create a paste (up to 10 MB of UTF-8 text) with optional language, expiry (10 minutes to never) and visibility (public, unlisted, private); read it as a page or as raw text; delete it; optional burn-after-read.
  • Non-functional: reads p99 under 100 ms; 99.9% availability; a paste is durable until it expires; expired or deleted pastes are never served; unlisted IDs are unguessable; abuse (malware, leaked credentials) can be found and taken down.

2. Estimates

Writes: 1M/day / 86,400 ≈ 12/s, ~35/s at peak. Reads at 10:1: 10M/day ≈ 116/s, ~350/s at peak. With a 10 KB average, new content is 1M × 10 KB = 10 GB/day, 3.65 TB/year, and text compresses ~4:1, so ~0.9 TB/year in object storage before expiry removes anything. Metadata over 10 years: 3.65B pastes × ~300 B ≈ 1.1 TB. Peak egress: 350 × 10 KB = 3.5 MB/s, mostly absorbed by the CDN. ID length: the database is tiny, so the ID is sized for secrecy, not storage. With 3.65B pastes among 62^8 ≈ 2.2 × 10^14 possible 8-character IDs, a random guess hits with probability ~1.7 × 10^-5, so a million guesses would find ~17 pastes. With 10 characters (62^10 ≈ 8.4 × 10^17, ~59.5 bits) a million guesses find ~0.004. Use 10-character random IDs and rate-limit clients that produce many 404s.

3. API

http
POST /api/v1/pastes
{"content": "def main(): ...", "language": "python",
 "expires_in": "7d", "visibility": "unlisted", "burn_after_read": false}
-> 201 {"id": "Xk29fQa0Lm", "url": "https://paste.example/Xk29fQa0Lm"}
-> 413 if content is over 10 MB, 429 if the caller is over its create limit

GET /{id}            -> 200 HTML page, highlighting done in the browser
GET /raw/{id}        -> 200 Content-Type: text/plain; charset=utf-8
                     -> 404 unknown, 410 expired or deleted

DELETE /api/v1/pastes/{id}
-> 204 No Content

4. Data model

FieldTypeNotes
idstring, 10 charsPartition key; random base62
owner_idint64, nullableNull for anonymous pastes
visibility, burn_after_readenum, boolControl caching and access checks
language, size_bytesstring, intShown on the page
inline_content or content_keybytes or stringSmall pastes inline, larger ones as an S3 key
created_at, expires_at, statustimestamps, enumstatus: active, burned, deleted, blocked

Metadata goes in DynamoDB (single-key access, built-in TTL, change streams); content goes in S3 under pastes/{id}, compressed. Pastes under ~16 KB, the large majority, are stored inline in the metadata row, which is well inside DynamoDB's 400 KB item limit and saves an S3 request on most reads. A pastes_by_owner index serves “my pastes” and is the only secondary access pattern.

5. High-level design

Write: the paste service validates size, generates a random ID, uploads large content to S3 first, then writes the metadata row with put if not exists. Writing the row last means a crash leaves at worst an orphaned S3 object, which a periodic sweep removes, never a row pointing at missing content. It then enqueues the paste for scanning. Read: the CDN serves cached public and unlisted pastes; on a miss the service reads the row (through Redis for hot pastes), checks status and expires_at, fetches S3 content if not inline, and sets cache headers according to visibility.

6. Deep dives

A. No key service needed. The URL shortener needed a KGS because codes had to be short and the write rate was high. Here IDs are long and writes are ~35/s: with 3.65B pastes in a space of 8.4 × 10^17, each insert collides with probability ~4 × 10^-9, so a random ID with a conditional put almost never retries. Recognizing when a component from a related design is unnecessary is a signal interviewers look for.

B. Expiry in two halves. Correctness: every read compares expires_at with now, so an expired paste returns 410 the moment it expires. Reclamation: DynamoDB TTL deletes expired rows in the background, sometimes days late, which is fine because reads never rely on it. Each TTL delete appears in DynamoDB Streams, and a cleanup worker deletes the matching S3 object. An alternative for content is S3 lifecycle rules, which expire objects by age and can filter by tag, so uploads are tagged with an expiry class (1d, 7d, 30d). Cached copies are bounded by setting the CDN max-age to at most the time left before expiry.

C. Caching versus burn-after-read and privacy. Public and unlisted pastes are immutable, so the CDN can cache them for up to an hour (or until expiry); a delete triggers a CDN purge for both URLs. Private pastes need an authorization check, so they are served with Cache-Control: private, no-store and never reach shared caches. Burn-after-read cannot be cached at all, and the read must be atomic: a conditional update set status = burned if status = active lets exactly one reader win. Messaging apps fetch link previews automatically, which would burn a paste before its recipient sees it, so the GET shows a “click to reveal” page and the content is released only by a POST.

DecisionChosenAlternativeWhy

5Follow-up questions

  • How would you add edit history, so a revised paste keeps every version reachable by its own link?
  • A paste goes viral and gets 20k reads/s. Walk through which layer absorbs the load.
  • How would you detect and take down pastes containing leaked API keys within a minute?
  • How would you support pastes of up to 1 GB?
  • Legal requires takedowns to take effect worldwide within 5 minutes. What changes in your caching?
