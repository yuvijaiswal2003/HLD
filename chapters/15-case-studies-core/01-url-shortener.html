Design a URL Shortener

A URL shortener maps a long URL to a short code such as sho.rt/aZ3k9Qx and redirects anyone who opens it. It looks trivial, which is exactly why interviewers like it: the interesting parts hide in the numbers (how long must the code be?), in key generation (how do many servers mint unique codes without coordinating on every write?), and in a read path that must answer in a few milliseconds at hundreds of thousands of requests per second. The walkthrough follows the 45-minute framework from Chapter 1, told the way you would say it in the room.

1. Requirements

  • Create: given a long URL, return a short URL. Optional custom alias (sho.rt/spring-sale) and optional expiry date.
  • Redirect: opening the short URL sends the browser to the long URL.
  • Analytics: owners see visits per day, top referrers, countries and devices. A few minutes of delay is fine.
  • Manage: owners can disable or delete a link; destinations are immutable by default.
  • Non-functional: redirects are the product, so p99 under ~20 ms server-side and 99.99% availability; link creation may be slower and can briefly degrade. Links must last for years, codes must never collide, and codes should not be trivially enumerable.
  • Clarify early: read:write ratio (drives caching), whether analytics is needed (drives 301 vs 302), whether the same long URL must always get the same code (adds a second index), and whether codes may be guessable (rules out raw sequential IDs).

2. Estimates

Assume 50M new links per day and a 100:1 read:write ratio. Writes: 50M / 86,400 ≈ 580/s average, ~1,800/s at a 3x peak. Reads: 5B/day ≈ 58k/s average, ~175k/s at peak. Over 10 years: 50M × 365 × 10 ≈ 182.5B links. At ~500 bytes per row (a ~200-byte URL plus code, owner, timestamps and index overhead) that is 182.5B × 500 B ≈ 91 TB, ~275 TB with 3 replicas. Cache: if 300M distinct codes are opened per day and the hottest 20% carry 80% of traffic, caching 60M entries × ~250 B ≈ 15 GB, a small Redis cluster. A redirect response is ~500 bytes of headers, so peak egress is only 175k × 500 B ≈ 88 MB/s. Code length: with base62 (0-9a-zA-Z), 62^6 ≈ 56.8B is less than 182.5B, while 62^7 ≈ 3.5 trillion gives ~19x headroom, so codes are 7 characters. Saying this calculation out loud is one of the cheapest points in the interview.

4. Data model

FieldTypeNotes
codestring, 7 to 30 charsPartition key. 7 chars when generated, longer for custom aliases.
long_urlstring, up to 2 KBValidated and checked against a malware blocklist at creation.
owner_idint64Who may see stats, disable or delete.
created_at, expires_attimestampexpires_at null means never.
statusenumactive, disabled, deleted. Checked on every redirect.

The hot access pattern is a single-key lookup by code, with no joins, on a table that grows to ~90 TB. That is a textbook fit for a horizontally partitioned key-value or wide-column store: DynamoDB or Cassandra with code as the partition key, which spreads load evenly because generated codes are random. Sharded PostgreSQL (hash of code) is also a fine answer if you say how you shard. The dashboard's “my links” view is a second table, links_by_owner(owner_id, created_at, code), written alongside the main row (the denormalization pattern from Chapter 6). Analytics never touches this store.

5. High-level design

Read path: the redirect service checks a small in-process LRU, then Redis, then the links table; it checks status and expiry, returns a 302, and hands a visit event to the Kafka producer's local buffer without waiting on the critical path. With a ~90% Redis hit rate the database sees ~17k reads/s at peak, which a modest DynamoDB table or Cassandra cluster handles easily. Write path: the API service validates the URL, pops a pre-generated key from its local batch, and writes the row with a conditional put so nothing can ever overwrite an existing link. Redirect and API are separate deployments, so a surge in link creation or a bad dashboard deploy cannot slow redirects.

6. Deep dives

A. Generating unique codes. The three families of answers are compared below, and the interviewer wants to hear why you reject two of them. We use a key generation service (KGS). A background job generates random 7-character strings into an unused_keys table, discarding the rare duplicate there, off the request path. It keeps about a year of supply ready: 18B keys × 7 B ≈ 128 GB. When an API server asks for a batch, the KGS moves 1,000 keys from unused to used in one transaction before returning them, so no two servers can ever receive the same key. Every API server holds a buffer, so a KGS outage of a few minutes is invisible. The conditional put on the links table stays as a cheap safety net and is also how custom aliases are claimed: put if not exists, else 409. If a generated key ever equals an existing custom alias, its put fails and the server simply takes the next key.

Hash and truncate

Strengths
  • Stateless: any server computes the code
  • Same URL gives the same code, so dedupe is free
Weaknesses
  • Truncated MD5 or SHA-256 collides, so each create needs a check or conditional write plus a retry loop
  • Collisions grow as the table fills: by year 10 about 5% of inserts collide (182.5B used of 3.5T)
  • Two users shortening the same URL share one code and one set of stats unless you salt the hash
Use whenSmall scale, or when identical URLs must map to one code.

Counter, base62-encoded

Strengths
  • Unique by construction, no collision checks
  • Servers can lease ranges of a million IDs (Chapter 14 ticket servers)
Weaknesses
  • One global counter is a bottleneck and a single point of failure
  • Sequential codes are enumerable unless scrambled with a keyed permutation first
Use whenWhen you lease ID ranges per server and scramble them before encoding.

Pre-generated key service (KGS)

Strengths
  • Random-looking unique keys with zero uniqueness work on the write path
  • Batches of ~1,000 keys mean the KGS sees only a few requests per second
Weaknesses
  • Another service to store, replicate and operate
  • Keys held by a crashed server are lost, which is harmless in a 3.5T space
Use whenThe default at high write rates: uniqueness is solved offline, not per request.
python
import secrets

ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

def to_base62(n: int, width: int = 7) -> str:
    """Encode a non-negative integer, e.g. a leased and scrambled counter value."""
    out = []
    while n:
        n, r = divmod(n, 62)
        out.append(ALPHABET[r])
    return "".join(reversed(out)).rjust(width, "0")

def random_key(length: int = 7) -> str:
    """What the KGS background job generates: about 41.7 bits of randomness."""
    return "".join(secrets.choice(ALPHABET) for _ in range(length))

def create_link(long_url, owner_id, allocator, table):
    while True:
        code = allocator.next_key()        # local pop; refills from the KGS when empty
        if table.put_if_absent(code, long_url, owner_id):
            return code                    # succeeds on the first try in practice

B. 301 or 302? This is the question interviewers ask most about this design, and the answer follows from the requirements. Because we sell analytics and let owners disable links, we return 302 (307 is equivalent for GET). If a customer later wants to cut redirect traffic and does not need analytics, a 301 with an explicit Cache-Control: max-age bounds how long browsers keep it.

Aspect301 Moved Permanently302 Found
Browser cachingCached; without explicit headers browsers may keep it indefinitelyNot cached by default; every visit reaches the service
Visit analyticsRepeat visits from the same browser are invisibleEvery visit is counted
Disabling a linkBrowsers holding the cached redirect keep going to the old targetTakes effect on the next visit
Load on the serviceLowerHigher: one request per visit
Search enginesStrong signal that the target is the canonical URLTreated as temporary, a weaker signal

C. Caching and hot links. The mapping is effectively immutable, so cache-aside with a long TTL (days) is safe; on disable or delete, the API deletes the Redis key. Two failure modes from Chapter 5 matter. A viral link can push 50k requests/s at a single Redis shard, and adding shards does not help a single key; give every redirect server an in-process LRU (say 100k entries, 60-second TTL) so hot codes are served from local memory, accepting that a disabled link may keep working for up to a minute. And scanners probing random codes miss in both cache and database every time: cache negative results briefly, or keep a Bloom filter of existing codes in front of the table.

D. Analytics without slowing redirects. Writing a row or incrementing a counter per visit would turn a read-heavy system into one doing 175k writes/s on hot partitions. Instead the redirect server emits an event (code, timestamp, referrer, user agent, country derived from the IP) to Kafka. A Flink job drops bots and link-preview fetchers, aggregates per code per minute and writes rollups to ClickHouse; raw events land in S3 for reprocessing. Unique visitors per day use a HyperLogLog sketch (Chapter 14) rather than storing every visitor. At ~200 bytes per event, 5B events/day is ~1 TB/day raw, which is why raw data goes to object storage and the dashboard reads only rollups.

In the interview
What strong candidates say
“Seven base62 characters give 3.5 trillion codes, about 19 times what ten years need. I'll pre-generate keys so creates never check for collisions. Redirects are 302 because the product sells analytics, and the redirect path only reads: local LRU, Redis, then a key-value store, with visit events going to Kafka asynchronously.” That is four decisions, each tied to a number or a requirement, in under thirty seconds. Then name the bottlenecks yourself: hot links, abuse (rate-limit creates, scan URLs for malware), and the KGS as a dependency.
