Design Search Autocomplete

Typeahead suggests completions as the user types: “new yo” becomes “new york times”, “new york weather”, “new york knicks”. Every keystroke can be a request, so suggestion traffic is several times search traffic, and a suggestion that arrives after the next keystroke is useless. The design splits cleanly into two systems with opposite needs: a serving path that answers a prefix lookup in about a millisecond, and a data path that turns billions of logged searches into a ranked index every day.

1. Requirements

  • Suggest: return the top 5 completions for a prefix, ranked by popularity with recent searches weighted more heavily.
  • Freshness: newly popular queries appear within a day; breaking-news queries within minutes.
  • Safety and privacy: filter offensive suggestions and never suggest a query typed by only a handful of people.
  • Locales: separate suggestions per language and region.
  • Non-functional: suggestions visible within ~100 ms of a keystroke, so p99 server time under ~10 ms; highly available but allowed to fail silently, since search still works without it; eventual consistency is fine.
  • Clarify: personalization (blend the user's own history), spelling correction, and matching in the middle of words are separate features. Ask before assuming them.

2. Estimates

Assume 100M DAU × 5 searches = 500M searches/day ≈ 5,800/s. With a 100 ms debounce a search sends ~8 suggestion requests, so 4B requests/day ≈ 46k/s average and ~100k/s at peak. Logged searches at ~100 B each are 50 GB/day. Index size: keep the top 10M queries per locale (prune the long tail) at ~25 characters average. That is at most 250M trie nodes, perhaps 100M after prefix sharing. Each node stores its top 5 as 4-byte query IDs plus 4-byte scores (40 B) plus ~60 B for the node and its child pointers, so ~100 B × 100M ≈ 10 GB, plus 10M strings × ~30 B = 300 MB. That fits in one server's RAM, so replicate rather than shard. A lookup takes microseconds, so a server is limited by networking at roughly 20–50k requests/s: ~5 servers cover the peak, and ~12 across three regions leave room to lose a zone. Responses are ~300 B, so 100k/s × 300 B is only 30 MB/s.

4. Data model

DataContentsWhere it lives
Query logquery, timestamp, locale, hashed user idKafka, then Parquet files in S3 kept 30 days
Daily aggregates(locale, query, day) to count and distinct usersWarehouse table written by Spark
Trie snapshotSerialized trie per locale with top 5 per nodeVersioned files in S3; loaded into RAM by every suggest server
Trending overlayprefix to spiking queries, refreshed every minuteRedis
BlocklistBanned terms and patternsConfig store pushed to servers

There is no database on the hot path. The serving index is an immutable in-memory snapshot: it is rebuilt from logs, never edited in place, so readers need no locks, every server with the same version gives the same answers, and rollback means loading the previous version. Durable state lives upstream, in logs, aggregates and versioned snapshot files.

5. High-level design

Serving path: the browser debounces keystrokes and checks its cache; cache misses for popular short prefixes are served by the CDN; the rest reach a suggest server, which walks its in-memory trie, merges any trending entries for the prefix, removes blocklisted items and responds. Data path: executed searches flow into Kafka; a daily Spark job aggregates and scores them, the trie builder writes a new snapshot, and servers load it in the background and swap a pointer. A Flink job watches the same stream for spikes and keeps the trending overlay current.

6. Deep dives

A. A trie with top-K cached at every node. A plain trie finds the node for a prefix in O(p) steps, where p is the prefix length, but then has to walk the whole subtree to find the best completions, and the subtree under “s” holds millions of queries. The fix is to precompute: store at every node the top K completions of its subtree. A lookup becomes p pointer hops plus copying K entries, however many queries share the prefix. The price is memory (the K entries per node dominate the 10 GB estimate) and expensive updates: changing one query's score can change the lists of all its ancestors. That is why the trie is built offline and served read-only.

python
import heapq
K = 5

class Node:
    __slots__ = ("children", "score", "top")
    def __init__(self):
        self.children, self.score, self.top = {}, 0.0, []

def insert(root, query, score):
    node = root
    for ch in query:
        node = node.children.setdefault(ch, Node())
    node.score = score                   # decayed popularity of the complete query

def fill_top(node, prefix=""):
    """Offline, bottom-up: best K of this node's own query and its children's lists."""
    cands = [(node.score, prefix)] if node.score else []
    for ch, child in node.children.items():
        fill_top(child, prefix + ch)
        cands.extend(child.top)
    node.top = heapq.nlargest(K, cands)

def suggest(root, prefix):
    node = root
    for ch in prefix:
        node = node.children.get(ch)
        if node is None:
            return []
    return [q for _, q in node.top]      # O(len(prefix)), no subtree walk

B. The data collection pipeline. Count executed searches (and clicked suggestions), not keystrokes: what people type mid-word is noise, what they submit is intent. The daily job aggregates logs into counts and distinct users per query, then scores with exponential decay, for example a 7-day half-life: score = sum of count_d × 0.5^(age_d / 7). Filters run before the build: a minimum distinct-user threshold, so a query typed by a few people (which may contain names or addresses) can never be suggested to strangers; the blocklist; case and whitespace normalization. A daily build is too slow for breaking news, so a Flink job counts queries over 5-minute sliding windows (a Count-Min Sketch plus a heap, Chapter 14, bounds memory), compares each count to the query's usual rate, and writes spiking queries into the trending overlay. The suggest service merges the overlay into the trie's results for matching prefixes.

C. Sharding the trie. At ~10 GB, full replication is the right first answer. Shard only when the index outgrows memory, for example with dozens of locales or a much longer tail. Two naive schemes fail. Sharding by first letter is badly skewed, because far more English queries start with s or c than with x or q. Hashing whole queries breaks prefix lookups, because the completions of one prefix would scatter across every shard. The workable options are compared below.

Replicate the full trie

Strengths
  • Any server answers any prefix
  • No routing layer or shard map
Weaknesses
  • Every server must hold the whole index
  • Each rebuild ships the full snapshot to every server
Use whenDefault while the index fits comfortably in RAM, around tens of GB.

Shard by prefix range

Strengths
  • Ranges such as a to am and an to az are sized from traffic histograms, so load is balanced
  • Hot ranges get extra replicas
Weaknesses
  • A shard map to build, store and update (directory-based partitioning, Chapter 7)
  • The router must parse the prefix
Use whenWhen one locale's trie no longer fits on one machine.

Prefix to top-K in a key-value store

Strengths
  • Each lookup is one get, hash-sharded evenly
  • Scales with standard Redis or Cassandra operations
Weaknesses
  • Stores every prefix with its own list, with no shared structure
  • A network hop per request; a rebuild rewrites hundreds of millions of keys
Use whenWhen you already run a large key-value fleet and can spare the extra ~1 ms.

D. Client and caching. Most of the latency budget goes to the network, so the cheapest wins are on the client. Debounce: wait ~100 ms after the last keystroke, which cuts requests several-fold for fast typists. Drop stale responses: echo the prefix in the response so the client ignores answers that arrive out of order. Cache: suggestions for a prefix are identical for every user in a locale and change at most a few times a day, so mark them cacheable for 15 minutes in the browser and at the CDN. Short prefixes are both the hottest and the fewest (26 single letters and 676 two-letter pairs in English), so the CDN absorbs a large share of the traffic. Keep personalization in a separate small request or on the client so the generic response stays cacheable.

In the interview
What strong candidates say
“There are two systems here: a read-only serving path that must answer in about a millisecond, and an offline pipeline that rebuilds the index from search logs. I'll cache the top 5 at every trie node so a lookup is O(prefix length), rebuild daily with time decay, and add a streaming trending overlay for breaking news.” Then the sizing (~10 GB, so replicate rather than shard), and unprompted: client debounce, CDN caching of short prefixes, and a distinct-user threshold so private queries never leak.
