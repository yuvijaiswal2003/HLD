Latency numbers every engineer should know

Jeff Dean at Google popularized a list of latency figures that engineers should know by heart. Hardware has improved since, but the ratios between memory, disk and network have stayed roughly the same, and the ratios are what drive design decisions. The figures below are rounded, modern approximations.

OperationApproximate timeScaled: if an L1 hit took 1 second
L1 cache reference~1 ns1 s
Branch mispredict~3 ns3 s
L2 cache reference~4 ns4 s
Mutex lock and unlock, uncontended~20 ns20 s
Main memory reference~100 ns~1.7 minutes
Send 1 KB over a 10 Gbps link~1 µs~17 minutes
Compress 1 KB with a fast codec like Snappy~2 µs~33 minutes
Read 1 MB sequentially from memory~50 µs~14 hours
Random 4 KB read from an SSD~20–100 µs~6–28 hours
Read 1 MB sequentially from an NVMe SSD~300 µs~3.5 days
Round trip within one data center~0.5 ms~6 days
Read 1 MB sequentially from a hard disk~5 ms~2 months
Hard disk seek~10 ms~4 months
Round trip US East to US West~65 ms~2 years
Round trip US East to Western Europe~80 ms~2.5 years
Round trip US to Asia or Australia~150–200 ms~5–6 years

What the numbers tell you

  • Memory is about 1,000x faster than an SSD random read and about 100,000x faster than a disk seek. That is the whole case for caches and in-memory stores like Redis.
  • Sequential beats random. A hard disk does ~100–200 random reads per second but streams 100–250 MB/s sequentially. That is why Kafka, write-ahead logs and LSM-tree databases append instead of updating in place.
  • A same-data-center network hop is cheap but not free. A 0.5 ms Redis round trip is worth about 5,000 memory references. Thirty sequential cache calls in one request add 15 ms.
  • Distance is physics. Light in fiber covers about 200,000 km/s, so every 100 km of fiber adds about 1 ms of round trip, and real routes are longer than straight lines. No software change makes New York to Sydney faster than about 160 ms round trip.
  • Cross-region calls belong outside the request path. One synchronous call from Virginia to Frankfurt costs about 90 ms; three of them blow a 200 ms budget.

Throughput numbers

Latency is how long one operation takes; throughput is how many operations or bytes per second a component sustains. These rough single-node figures are good enough for sizing. Always say they are assumptions, and that you would load-test.

ComponentRough single-node capacityNotes
Memory bandwidth~10–20 GB/s for one thread; 100+ GB/s per socketMany memory channels in parallel
NVMe SSD~2–7 GB/s sequential; hundreds of thousands of random IOPSSATA SSDs: ~500 MB/s
Hard disk~100–250 MB/s sequential; ~100–200 random IOPSCheap capacity, terrible random access
10 Gbps network card~1.25 GB/sPlan to use ~70% of it
Redis~100k simple ops/sMuch more with pipelining; one main thread per instance
PostgreSQL or MySQLThousands of transactional writes/s; tens of thousands of simple indexed reads/sDepends heavily on hardware, query shape and durability settings
Kafka brokerHundreds of MB/sSequential disk I/O and batching
Nginx serving static or cached contentTens of thousands of requests/sPer server, mostly bound by network and TLS

Building a latency budget

Add up the hops a request makes to see where time goes. For a user far from the data center, the network usually dwarfs the server's work, which is why CDNs and regional deployments matter more than micro-optimizing code.

In the interview
Use latency numbers to reject designs
“Rendering this page calls the database once per item, 200 times, at about 1 ms each: 200 ms just in round trips. I'll batch it into one query with WHERE id IN (...), or precompute the page.” Quick arithmetic like this shows the interviewer you can spot a slow design before building it.
Pitfall
Don't confuse latency and throughput
A hard disk has a seek time of ~10 ms but can still stream 200 MB/s. A cross-continent link has 150 ms of latency but can carry gigabits per second. Adding servers raises throughput; it never lowers the latency of a single round trip.
