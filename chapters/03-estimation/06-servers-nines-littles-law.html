Server counts, availability nines and Little's Law

How many servers?

Server count is peak load divided by what one server can sustainably handle, plus headroom for failures and deploys. Per-server capacity comes from a load test in real life; in an interview, derive it from CPU time per request, or state an assumption like “a server handles about 1,000 requests per second for this workload”.

text
Assumptions
  peak load:            60,000 requests/s
  CPU per request:      ~20 ms
  server:               32 cores, target ~60% CPU at peak

Per-server capacity
  1 core:  1 s / 20 ms         = 50 requests/s
  32 cores                     = 1,600 requests/s at 100% CPU
  at 60% target                = ~960, call it 1,000 requests/s

Server count
  60,000 / 1,000               = 60 servers at peak
  spread over 3 availability zones; must survive losing one zone:
  60 / (2/3)                   = 90 servers

CPU is not always the limit. Compute the count for each resource the workload stresses and take the largest: that is the binding constraint, and naming it is half the value of the exercise.

Bound byFormulaExample
CPUpeak QPS × CPU time per request ÷ (cores × target utilization)60k/s × 20 ms ÷ (32 × 0.6) ≈ 63, then ÷ (2/3) for zone loss ≈ 95
Connectionsconcurrent connections ÷ connections per server2M WebSockets ÷ 100k per server = 20 servers
Memoryworking set ÷ usable RAM per node600 GB of timelines ÷ 50 GB = 12 nodes
Networkpeak egress ÷ (NIC speed × ~70%)240 Gbit/s ÷ 7 Gbit/s ≈ 35 servers
Disk capacitystored bytes ÷ (disk per node × fill ratio)1.1 PB ÷ (20 TB × 0.7) ≈ 80 nodes

Why not run servers at 100%?

Requests don't arrive evenly, so a busy server builds a queue. In the simplest queueing model (one server, random arrivals), average response time is the service time divided by (1 − utilization). Servers with many cores tolerate higher utilization before the knee, but the knee is just as sharp. That is why capacity plans target roughly 50–70%.

UtilizationResponse time as a multiple of service time
50%2x
70%~3.3x
80%5x
90%10x
95%20x
99%100x

Availability nines

Availability is the fraction of time (or of requests) a system serves successfully, usually written in “nines”. Each extra nine allows 10x less downtime and typically costs much more to reach.

AvailabilityDowntime per yearPer 30-day monthPer day
99% (two nines)~3.65 days~7.2 hours~14.4 minutes
99.9% (three nines)~8.76 hours~43.2 minutes~1.44 minutes
99.95%~4.38 hours~21.6 minutes~43 seconds
99.99% (four nines)~52.6 minutes~4.32 minutes~8.6 seconds
99.999% (five nines)~5.26 minutes~26 seconds~0.86 seconds

The math is just the unavailable fraction times the period: a year has 525,600 minutes, so 99.9% allows 0.001 × 525,600 ≈ 526 minutes ≈ 8.76 hours. At four nines, the monthly budget of about 4 minutes is shorter than the time it takes to page an engineer and diagnose a problem, so it requires automatic failover. Dependencies multiply: a request that needs three services in series, each at 99.9%, is at most 0.999^3 ≈ 99.7% available. Chapter 12 covers this math in depth.

Little's Law

Little's Law says that in any stable system, the average number of items inside equals the average arrival rate times the average time each spends inside: L = λ × W. It holds whatever the arrival pattern, which makes it the most useful formula in capacity planning. It turns a request rate and a latency into concurrency: how many threads, connections or queue slots you need.

text
L = λ x W

1. Concurrency of an API
   2,000 req/s x 0.05 s           = 100 requests in flight

2. Thread pool on a blocking server
   normal:  2,000 x 0.05 s        = 100 busy threads
   DB slows, W = 0.5 s:  2,000 x 0.5 = 1,000 busy threads
   -> a 200-thread pool is exhausted and requests queue

3. Database connection pool
   3,000 queries/s x 0.004 s each = 12 connections busy on average
   -> a pool of ~30 covers bursts; 500 would be wasteful

4. Time spent waiting in a queue
   queue holds ~600,000 messages, 2,000 msg/s flow through
   W = L / λ = 600,000 / 2,000    = 300 s per message
Pitfall
Latency spikes become concurrency spikes
Example 2 is how outages spread. A slow dependency doesn't reduce traffic; it raises W, so L rises with it until thread pools, connection pools or memory run out, and the healthy service in front fails too. Timeouts, bounded pools and circuit breakers (Chapter 12) keep W bounded.
In the interview
Chain the estimates
Strong answers connect the numbers: “Peak is 60k requests per second at 50 ms, so about 3,000 in flight; at 1,000 requests per second per server we need 60, or 90 to survive a zone loss; with that redundancy and automatic failover, 99.95% is a realistic target.”
