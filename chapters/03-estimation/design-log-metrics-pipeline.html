Estimate and design a log and metrics ingestion pipeline

Your company runs 50,000 hosts. An agent on each host ships application logs and system and application metrics. Engineers must be able to search logs within a minute of emission for the last 7 days, and logs must be archived for 90 days for audits. Metrics feed dashboards and alerts, kept at full resolution for 15 days and downsampled for a year. Estimate the load on every tier and design an ingestion pipeline that does not lose data when an incident triples log volume for hours.

45:00Mock interview timer. Start it when you begin talking.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • How many log lines per second does a typical host emit, and how large is a line?
  • How many metric series does each host emit, and how often is each sampled?
  • How fresh must data be: queryable within seconds, or within a minute?
  • Is losing some debug logs acceptable during spikes? Are some logs (audit, security) never droppable?
  • How large and how long are traffic spikes during incidents and deploys?
  • Are hosts in one region or several? Must data stay in its region?
  • Is there a budget target, or a current cost we must beat?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1Start per host: lines per second × bytes per line × hosts. Then convert the per-second rate to per-day storage with 86,400.
H2A durable log like Kafka between agents and stores absorbs spikes. Size it four ways: ingress, disk writes with replication, retention storage, and consumer parallelism. Which one is binding?
H3Metrics are tiny values but there are many series. Compute samples per second, then bytes per sample before and after time-series compression.
H4During an incident, input triples while consumers keep their normal speed. How fast does the backlog grow, and how long does it take to drain?
H5Compression ratios and replication factors change the answers by 3–10x. Write each one down as an explicit assumption.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: agents ship structured log lines and metric samples from every host; logs are searchable by time, service, host, level and text; metrics are queryable for dashboards and alert rules; logs are archived for 90 days; metrics are kept for 15 days at 10 s resolution and 1 year at 5 min resolution.
  • Non-functional: 50,000 hosts; at-least-once delivery, so acknowledged data is never lost; tolerate 3x log volume for several hours; freshness p99 under 60 s for errors; agents use bounded CPU and memory on production hosts; cost-conscious.

Estimates

text
Logs: volume
  50,000 hosts x 50 lines/s             = 2.5M lines/s
  2.5M x 500 B                          = 1.25 GB/s raw  (= 10 Gbit/s)
  1.25 GB/s x 86,400 s                  = ~108 TB/day raw
  incident peak, 3x                     = 7.5M lines/s, 3.75 GB/s raw

Logs: on the wire (agents batch and compress ~5x with zstd)
  1.25 GB/s / 5                         = 250 MB/s avg, 750 MB/s peak

Logs: storage
  hot, searchable 7 days in a columnar store at ~5x net compression
    108 TB / 5 = ~22 TB/day x 7 days    = ~150 TB, x 2 replicas = ~300 TB
    nodes with 8 TB disk at 70% fill    = 300 / 5.6 = ~54 nodes
  archive 90 days in object storage at ~10x
    108 TB / 10 = ~11 TB/day x 90 days  = ~1 PB, ~$20k/month at S3 Standard prices

Agent buffer
  per host: 50 lines/s x 500 B          = 25 KB/s
  1 hour of pipeline outage             = 25 KB/s x 3,600 = ~90 MB of local disk
text
Metrics
  50,000 hosts x 1,000 series           = 50M active series
  one sample per series every 10 s      = 5M samples/s
  raw: 16 B per sample                  = 80 MB/s = ~6.9 TB/day
  compressed: ~1.5 B per sample         = 7.5 MB/s = ~650 GB/day
  15 days at full resolution            = ~10 TB, x 2 replicas = ~20 TB
  1-year rollups at 5 min, 4 values each (min, max, sum, count):
    50M x 288 points/day x 4 x 1.5 B    = ~86 GB/day = ~31 TB/year
  ingester memory at ~3 KB per active series:
    50M x 3 KB = 150 GB, x 3 replicas   = ~450 GB of RAM
text
Kafka for logs: replication factor 3, 24-hour replay buffer
  disk writes = ingress x 3             = 750 MB/s avg, 2.25 GB/s peak
  retention: 250 MB/s x 86,400 s x 3    = ~65 TB

  storage bound:   65 TB / ~7 TB usable per broker      = ~10 brokers
  disk bound:      2.25 GB/s / ~300 MB/s per broker      = ~8 brokers
  network bound:   peak out = replication 1.5 GB/s
                   + 2 consumer groups 1.5 GB/s = 3 GB/s
                   / ~500 MB/s per broker                = ~6 brokers
  binding constraint: retention storage -> 12 brokers with headroom

Partitions, set by the maximum consumer parallelism
  one indexer thread handles ~20k lines/s
  to index a full 3x peak: 7.5M / 20k   = 375 consumer threads
  partitions must be >= consumers       -> 512 partitions

High-level design

Write path: each agent tails local log files and scrapes local metrics, batches about one second of data, compresses it and POSTs it to a gateway. If the gateway is unreachable or returns 429, the agent spills to its local disk buffer (~90 MB per hour of outage) and retries with backoff. Gateways authenticate, enforce per-service quotas and produce to Kafka; they acknowledge the agent only after Kafka confirms the write with all in-sync replicas. Two consumer groups read the log topics: indexers write batches into the columnar store, and the archiver writes hourly compressed files to object storage. Metrics ingesters keep recent samples in memory, flush compressed 2-hour chunks to the time-series DB, and a background job computes 5-minute rollups. Read path: the query API sends log searches to the columnar store (or to the archive for older data) and metric queries to the TSDB.

Deep dives

Finding the binding constraint in Kafka. The four estimates give 6 to 10 brokers. The largest, retention storage for a 24-hour replay buffer, wins, so we run 12 brokers to leave headroom for a broker failure. Partition count is driven by something else entirely: consumers in a group can't exceed partitions, and indexing 7.5M lines/s at 20k lines per thread needs 375 threads, so 512 partitions. Metrics add about 100 MB/s on the wire (assuming ~20 B per sample after batching and compression) and are sized the same way on a smaller topic.

Surviving a 3x incident spike. The partitions allow indexing a full 3x peak, but running that many indexers (and the columnar store write capacity behind them) all the time is expensive. Suppose they normally run at 1.5x average, 375 MB/s compressed, and scaling up takes longer than the spike. During a 2-hour spike, input is 750 MB/s, so the backlog grows at 375 MB/s: 1.35 TB per hour, 2.7 TB after 2 hours, far inside the 21.6 TB a day of retention, so nothing is lost. But when traffic returns to normal, spare capacity is only 375 − 250 = 125 MB/s, so draining 2.7 TB takes 2.7 × 10^6 MB ÷ 125 MB/s ≈ 21,600 s = 6 hours. Logs would be 6 hours stale exactly when engineers are debugging. Fixes: split topics by priority so logs-high has its own, over-provisioned indexers and stays fresh; sample debug logs at the agent during spikes; and enforce per-service quotas so one noisy service can't consume everyone's capacity.

Metric cardinality. Metrics are cheap per sample but expensive per series, because each active series costs memory in the ingesters. One histogram with 10 buckets × 20 endpoints × 5 status codes × 2,000 pods is already 2 million series. A developer who adds a user_id label with a million values makes it unbounded. Enforce a per-service limit on active series at the ingesters, reject new series beyond it with a clear error, and alert service owners when they approach the limit.

5Follow-up questions

  • A team adds a request_id label to a high-traffic metric. What happens to the ingesters, and how do you protect the system?
  • Legal now requires one year of searchable audit logs for the payments service. Estimate the added cost.
  • A Kafka broker fails during an incident peak. What happens to throughput, durability and the brokers that remain?
  • How would you cut the hot log storage cost in half without losing the ability to search errors?
  • Should three regions ship everything to one central region? Estimate the transfer volume and its monthly cost.
