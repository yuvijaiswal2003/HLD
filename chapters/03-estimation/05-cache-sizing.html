Sizing a cache with the 80/20 rule

Access patterns are skewed: a few items are wildly popular and most are rarely touched. The 80/20 rule (Pareto principle) is the standard rule of thumb: about 20% of items receive about 80% of reads. Real skew is often stronger, closer to a Zipf distribution where the top 1% may get half the traffic. The practical consequence: caching a small hot set captures most of the reads.

  1. Count the distinct items read per day
    Not the number of reads. One viral post read 10 million times is still one cache entry.
  2. Take the hot fraction
    Start with 20% unless you know the skew. For sessions or other data where every active item must be found, take 100% of the active set.
  3. Multiply by the size of a cached entry
    Use the size of what you actually cache, such as a rendered fragment or a serialized object, not the database row.
  4. Add memory overhead
    Redis spends roughly 50–100 bytes of bookkeeping per key, plus allocator fragmentation. Multiply by about 1.5, or 2 for very small values.
  5. Divide by usable memory per node
    Plan to use about 75% of RAM; replication buffers and snapshot forks need the rest. Add replicas for availability.

  distinct articles read per day   1M
  hot 20%                          200k articles
  x 20 KB rendered fragment        = 4 GB
  x 1.5 overhead                   = 6 GB  -> one node, plus a replica

Example 2: session store (every active session must be present)
  50M DAU x 1 KB                   = 50 GB
  x 1.5 overhead                   = 75 GB -> 2 nodes of 64 GB, plus replicas

Example 3: precomputed home timelines
  100M DAU x 500 post IDs x 8 B    = 400 GB
  x 1.5 overhead                   = 600 GB
  / ~50 GB usable per 64 GB node   = 12 shards, x 2 with replicas = 24 nodes

Sizing by distinct items, not by read volume

A common shortcut is “cache 20% of the daily read volume”: 5 billion reads/day × 1 KB = 5 TB, so 1 TB of cache. That counts each popular item once per read and overestimates badly. If those 5 billion reads touch only 200 million distinct posts, the hot set is 0.2 × 200M × 1 KB = 40 GB, 25x smaller. If you only know read volume, say the result is an upper bound.

What the hit ratio buys

The hit ratio is the fraction of reads served from the cache. With 150,000 reads/s at peak, a 90% hit ratio sends 15,000/s to the database; 99% sends only 1,500/s. Going from 90% to 99% looks small but cuts database load 10x, which is why a modest increase in cache memory can remove the need for read replicas. Chapter 5 covers caching patterns in depth.

In the interview
Small caches are a finding
Saying “the hot set is about 6 GB, so a single Redis node holds it, with one replica for failover” is a better answer than drawing a 20-node cluster. Interviewers like seeing estimates shrink a design as much as grow it.
Pitfall
Small values are mostly overhead
Caching 100 million 8-byte counters as separate Redis keys costs far more than 800 MB, because per-key overhead is many times the value. Grouping small values into Redis hashes, which are stored compactly while small, can cut memory several-fold.
