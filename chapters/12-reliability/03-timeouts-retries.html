Timeouts, retries, backoff and jitter

Most failures in distributed systems are not clean crashes but slowness: a dependency that takes 30 seconds instead of 30 milliseconds. A hung dependency is worse than a dead one, because every caller waiting on it holds a thread, a connection and memory. The first defense is a timeout; the second is a careful retry.

Timeouts

  • Every remote call gets a timeout. Many clients default to none: Python requests waits forever unless you pass timeout=.
  • Set separate connect and request timeouts. Inside a data center a connect timeout of a few hundred milliseconds is plenty.
  • Base the request timeout on the dependency's measured latency, a bit above its p99.9. If p99.9 is 400 ms, start around 500 ms, not 30 seconds.
  • Propagate deadlines. If the user-facing budget is 1 second and 700 ms are spent, the next hop gets at most 300 ms. gRPC deadlines do this automatically. Never keep working for a caller that has already given up.

Which failures to retry

Retries turn transient failures (a dropped packet, a node restarting, a leader election) into successes. They are only correct for errors that might succeed next time, and only for operations that are safe to repeat.

FailureRetry?Why
Connection refused or reset, DNS blipYes, with backoffLikely transient; request probably never reached the app
503 Service UnavailableYes, with backoff; honor Retry-AfterServer is overloaded or restarting
429 Too Many RequestsYes, after Retry-AfterYou are being rate limited (Chapter 11); hammering makes it worse
Timeout on an idempotent callYes, a limited number of timesRepeating it has the same effect
Timeout on a non-idempotent callOnly with an idempotency keyThe first attempt may have succeeded
400, 401, 403, 404, 422NoThe request itself is wrong; it will fail the same way
Pitfall
Idempotency is a prerequisite for retries
A timeout tells you nothing about whether the server did the work. Retrying POST /charges after a timeout can charge the customer twice. Make the operation idempotent with an idempotency key that the server stores and dedupes on (Chapter 11), or do not retry it automatically.

Exponential backoff with full jitter

If thousands of clients retry on a fixed schedule, their retries arrive in synchronized waves that knock the recovering server back down. Exponential backoff doubles the wait each attempt so pressure drops over time. Jitter randomizes the wait so clients spread out instead of moving in lockstep. With full jitter, each wait is a random value between zero and the capped exponential: sleep = random(0, min(cap, base × 2^attempt)). AWS's published analysis of backoff strategies found that adding jitter sharply cuts the total number of calls clients make while competing for a contended resource.

python
import random
import time

class TransientError(Exception):
    """Timeouts, connection resets, 503s, 429s: safe to retry."""

def call_with_backoff(op, max_attempts=5, base=0.1, cap=5.0):
    """Run op() with capped exponential backoff and full jitter.

    Only wrap idempotent operations, or ones carrying an idempotency key.
    """
    for attempt in range(max_attempts):
        try:
            return op()
        except TransientError:
            if attempt == max_attempts - 1:
                raise                                # out of attempts
            ceiling = min(cap, base * 2 ** attempt)  # 0.1, 0.2, 0.4, 0.8 ...
            time.sleep(random.uniform(0, ceiling))   # full jitter

# usage: call_with_backoff(lambda: inventory.reserve(sku, qty, key=order_id))

Retry storms and amplification

Retries multiply across layers. If every layer makes up to 3 attempts and the bottom dependency is down, one user request becomes 3 × 3 × 3 = 27 calls at the database, at the exact moment it is struggling. That positive feedback loop is a retry storm, and it is a classic way a brief blip becomes a long outage.

  • Retry at one layer, usually the one closest to the failing dependency. Other layers fail fast.
  • Cap attempts per request (2–3 total) and keep a retry budget per client: retries may be at most about 10% of requests in a window. When the dependency is truly down, retries stop instead of tripling traffic.
  • Let an overloaded server answer "overloaded, do not retry" so upstream layers stop retrying.
  • Combine with a circuit breaker (next lesson) so a dead dependency gets near-zero traffic until it recovers.
Tip
Hedged requests for tail latency
For idempotent reads, send a second copy to another replica if the first has not answered by the p95 latency, and use whichever answers first. Google's "The Tail at Scale" paper popularized this. It adds only a few percent extra load but cuts p99 sharply. Never hedge non-idempotent writes.
In the interview
The sentence interviewers want
"Every call has a timeout from the remaining deadline; we retry only transient errors on idempotent operations, with capped exponential backoff and full jitter, at a single layer, under a retry budget." Then mention idempotency keys for writes. That one line covers most of what they probe.
