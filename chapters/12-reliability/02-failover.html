Failover: active-passive, active-active, zones and regions

Redundancy only helps if traffic actually moves off the broken part. Failover is that move. There are two basic shapes, and the choice depends mostly on whether the component holds state that can be written in only one place at a time.

Active-passive

One node serves traffic while a standby waits. A hot standby is running and continuously replicating, and takes over in seconds. A warm standby is running but scaled down or lagging, and takes minutes. A cold standby is provisioned from backups when needed, and takes hours. This is the default for databases: one primary accepts writes, so there is never a write conflict, and the standby is a full-size copy so it can absorb the load.

  1. Detect
    Health checks or heartbeats miss several times in a row, for example 3 misses at a 5-second interval, so about 15 seconds. Too aggressive and a GC pause triggers a false failover; too lax and you burn downtime.
  2. Fence the old primary
    Make sure the old node cannot keep accepting writes: revoke its lease, cut it off at the network or storage layer, or use fencing tokens. Without this you get split brain, two primaries diverging (Chapter 8 covers leases and fencing).
  3. Promote
    The standby applies any replicated log it has and becomes primary. With asynchronous replication, writes the old primary acknowledged but had not shipped are lost.
  4. Redirect traffic
    Move a virtual IP, update DNS (with a low TTL), or update service discovery so clients find the new primary. Clients must reconnect and retry.
  5. Recover and rebuild
    Rebuild the old node as the new standby. Avoid automatic failback, which can cause flapping between nodes.

Active-active

In active-active every node serves live traffic. Stateless tiers behind a load balancer are naturally active-active. Nothing sits idle, and the "failover path" is exercised every second, so it is known to work. The catches: the survivors must absorb the failed node's share, so with two nodes each must stay under about 50% utilization at peak (three nodes: about 66%). And if the nodes hold writable state, concurrent writes in two places create conflicts that need resolution strategies (multi-leader replication and CRDTs, Chapter 7).

Active-passive

Strengths
  • No write conflicts: one writer at a time
  • Simple mental model for stateful systems
  • Standby has full capacity for the failover
Weaknesses
  • Standby capacity sits idle
  • Failover path is rarely exercised and may not work when needed
  • Seconds to minutes of downtime per failover
Use whenDatabases and other stateful components with a single writer, such as a PostgreSQL primary with a hot standby.

Active-active

Strengths
  • All capacity serves traffic
  • Failover is just rerouting; often near-instant
  • Can serve users from the closest site
Weaknesses
  • Each node must keep headroom to absorb the others
  • Writable state needs conflict handling
  • Harder to reason about consistency
Use whenStateless tiers everywhere; stateful data only when it is partitioned by owner or mergeable (counters, sets, append-only logs).

Multi-AZ vs multi-region

An availability zone (AZ) is one or more data centers with independent power, cooling and networking, separated from other AZs in the same region by kilometers but close enough for low single-digit millisecond round trips. That is fast enough for synchronous replication. Regions are hundreds to thousands of kilometers apart, with 60–150 ms cross-region RTT, which pushes you toward asynchronous replication.

AspectMulti-AZ (one region)Multi-region
Protects againstData center fire, power or network loss in one AZRegional outage, regional control-plane failure, natural disaster
ReplicationSynchronous is practical (1–2 ms per commit)Usually asynchronous (60–150 ms RTT)
RPO on failureZero with sync replicationSeconds of writes, the replication lag
Failover timeSeconds to a couple of minutesMinutes (warm standby) to near zero (active-active)
Extra latencyNegligibleLarge if a request crosses regions
Cost and complexityModest; managed databases do it for youHigh: duplicate stacks, data sync, routing, testing
In production
Multi-AZ is not multi-region
In the December 2021 AWS us-east-1 outage, an automated scaling activity caused congestion on AWS's internal network and impaired many AWS services and APIs across the region. The impact did not respect AZ boundaries, so applications that depended on those regional services were affected even when they were spread across several AZs.

One more principle: static stability. During large incidents the control plane (APIs that launch instances, change DNS, scale clusters) is often the first thing to degrade. A design that needs to launch 100 new servers to survive an AZ loss may not be able to. Pre-provision the headroom so the data plane keeps working with no changes.

Pitfall
Untested failover does not work
DNS-based failover is slowed by resolvers and clients that cache records beyond the TTL. Connection pools hold sockets to the dead primary. Runbooks go stale. Schedule failovers (game days) so you know the real RTO, and prefer mechanisms that do not depend on client DNS behavior, such as anycast or proxies that reroute at the edge.
In the interview
Default answer
"Multi-AZ by default for everything, with sync replication for the database. Multi-region only if the requirements justify roughly double the cost and complexity: a regional-disaster RTO, global latency targets, or data residency." Interviewers like hearing you scope the expensive option instead of reaching for it reflexively.
