Design an autoscaling web tier for a flash sale

A retailer runs a 10-minute flash sale every Friday at 12:00. Normal load on the web/API tier is 5k requests per second; during the sale it reaches 250k RPS, and almost all of that arrives within the first 60 seconds. Today the site falls over every week. Design the web tier, its autoscaling and its protections so the site stays up and costs stay reasonable the rest of the week.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • Is the spike timing known in advance, and how accurate are traffic forecasts from past sales?
  • Which requests hit our servers after the CDN: page views, stock checks, reserve and checkout?
  • How long does a new instance take to launch, boot and pass readiness today?
  • What is one instance's capacity from load tests, and at what latency?
  • Is it acceptable to make some users wait in a queue rather than serve everyone instantly?
  • Which downstream systems are shared: database, cache, payment provider limits?

2Your answer

3Hints 0/4

Stuck? Each hint gives a little more away than the last.

H1Work out how long reactive autoscaling takes to add capacity and compare it with a 60-second ramp.
H2The start time is known. Which scaling policy uses that fact, and how do you cover a forecast that is too low?

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: serve the sale page and stock level, let users reserve an item and check out, show a waiting-room position when demand exceeds capacity.
  • Non-functional: survive 250k RPS reached within 60 s; p99 under 300 ms for admitted users; no crash or error storm when demand exceeds capacity (degrade by queueing); pay for peak capacity only around the sale window.

Estimates

text
Load test: one c6i.2xlarge (8 vCPU) serves 500 RPS at ~60% CPU, p99 120 ms
Peak:      250k RPS / 500   = 500 instances, +20% headroom = 600
Baseline:  5k RPS / 500     = 10 instances -> min 12 (4 per AZ x 3 AZs)

Reactive scale-out timeline for a spike at 12:00:00
  detect (1-min metrics, 2 datapoints)     ~2-3 min
  launch + boot + warm-up + readiness      ~3 min
  first new capacity arrives               ~12:05, halfway through the sale

Cost (on-demand ~$0.34/h per instance)
  600 instances x 1.5 h window   = ~$306 per sale
  600 instances x 24 h           = ~$4,900 per day if left running

Database: 600 instances x 10-connection pool = 6,000 connections
vCPU quota: 600 x 8 = 4,800 vCPUs -> request a quota increase in advance

API

http
GET  /api/sale/{saleId}              -> sale info and stock level, cached 1 s
GET  /api/queue/{saleId}/status       -> waiting-room position, admission token when admitted
POST /api/sale/{saleId}/reserve       -> hold one unit for 10 min, needs admission token
POST /api/checkout                    -> pay for a held unit, Idempotency-Key header
GET  /healthz/ready                   -> instance readiness for the ALB

Data model

The interesting data here is the scaling configuration; sale data is small. Stock lives in Redis as an atomic counter (DECR stock:{saleId}), and reservations and orders live in PostgreSQL. Seat-hold and inventory details are covered in Chapter 17.

High-level design

Before the sale: at 11:30 a scheduled action raises the group to 600 instances; they boot, warm up and pass readiness checks by 11:40. The load balancer's capacity is reserved or pre-warmed, because managed LBs scale over minutes too. During the sale: the CDN serves the sale page and assets; API calls go through the waiting room, which issues signed admission tokens at the rate the tier can serve. Admitted users reserve against the Redis counter and check out through PostgreSQL behind PgBouncer. After the sale: at 12:45 the minimum drops and the group scales in gradually with draining.

Deep dives

1. Why reactive scaling alone fails. The ramp takes 60 seconds; detection plus launch takes about 5 minutes. For those 5 minutes the existing 12 instances (about 6k RPS of capacity) face about 40 times their capacity. Requests queue, latency climbs past client timeouts, clients retry, and the retries add even more load, so the fleet can fail health checks and get replaced, making things worse. A known start time is the strongest signal you have, so use scheduled scaling, and use predictive scaling for the general weekly pattern. Reactive target tracking stays on for fine adjustments.

2. Admission control and load shedding. Capacity planning can be wrong, so the system must refuse gracefully instead of falling over. The waiting room holds users in a queue (served from the CDN or a lightweight service) and admits, say, 2,000 new users per second, adjusted using the tier's live latency. Each instance also enforces a concurrency limit and returns 503 with Retry-After once it is reached, and clients retry with jittered backoff. Checkout requests get priority over page refreshes, because a completed sale is worth more than a stock-level poll.

3. The bottlenecks that move. Scaling the web tier 50x stresses everything behind it. 6,000 database connections would overwhelm PostgreSQL, so PgBouncer in transaction mode multiplexes them onto about 200 server connections, and reads are served from Redis. A single Redis key for stock is handled by one shard (roughly 100k ops/s); split stock into 10 sub-counters on different shards if needed. Ask the payment provider for a higher rate limit, and raise the EC2 vCPU quota weeks in advance, since 4,800 vCPUs is above most default quotas.

Trade-offs and bottlenecks

  • Scheduled vs always-on capacity: scheduling costs about $300 per sale against about $4,900 per day for permanent peak capacity, but relies on the schedule being right; the warm pool and step scaling cover forecast misses.
  • Warm pool size: stopped instances cost only their disks, but a bigger pool means more launches that can fail at the worst time; 25% of peak is a reasonable buffer.
  • Waiting room vs serving everyone: queueing adds friction, but a controlled queue beats a site returning errors to everyone.
  • Instance size: fewer large instances mean fewer launches and connections; more small ones mean finer scaling steps and smaller blast radius per failure.
  • Remaining risk: a hot code path that only shows at peak (for example a slow query). Rehearse with a load test at full scale a week before.

5Follow-up questions

  • The marketing team moves the sale time with one hour's notice. What breaks, and how do you make the system robust to that?
  • How would you run this on Kubernetes instead of EC2 Auto Scaling groups?
  • Bots send 70% of the traffic. How do you keep them from taking the stock?
  • How do you prove before Friday that the system can take 250k RPS?
  • The sale goes global, starting at noon local time in five time zones. How does the scaling plan change?
