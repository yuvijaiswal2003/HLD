Vertical vs horizontal scaling, and where state lives

A system scales when it can take on more load (requests per second, users, data) without latency or error rates getting worse. There are only two basic moves: make the machine bigger, or add more machines. Almost every design in this course depends on picking the right one for each tier.

Vertical scaling (scale up)

Vertical scaling means moving to a bigger box: more CPU cores, more RAM, faster NVMe disks. It needs no code changes and no new moving parts, which is why it is the right first move for a young product and often the right long-term move for a primary database. Its limits are hard ones: there is a largest machine you can buy (top-end cloud VMs have a few hundred vCPUs and terabytes of RAM), price climbs steeply near the top of the range, resizing usually means a restart, and one machine is still a single point of failure (SPOF): if it dies, the service is down.

Horizontal scaling (scale out)

Horizontal scaling means running many copies of a service on ordinary machines and putting a load balancer in front to spread requests across them. Capacity grows roughly linearly with machine count, a single failure only removes a fraction of capacity, and you can add or remove machines while serving traffic. The price is complexity: you need a load balancer, health checks, deployment tooling, and, above all, a service that does not care which copy handles a request.

Vertical (scale up)

Strengths
  • No code or architecture change
  • No network hops between parts, simple to reason about
  • Great for databases that are hard to split
Weaknesses
  • Hard ceiling on machine size
  • Cost rises steeply at the top end
  • Still a single point of failure
  • Resizing often needs downtime
Use whenEarly-stage products, primary databases, and anything where splitting is harder than buying a bigger box.

Horizontal (scale out)

Strengths
  • Near-linear capacity growth
  • Fault tolerance: losing one node loses 1/N of capacity
  • Elastic: add and remove nodes with demand
  • Commodity hardware
Weaknesses
  • Needs a load balancer and orchestration
  • Service must be stateless or state must be partitioned
  • More things to monitor and debug
Use whenWeb and API tiers, workers, caches, and any tier that has outgrown one machine or needs high availability.

Stateless vs stateful services

A stateless service keeps nothing about a client in its own memory or disk between requests. Every request carries (or points to) everything needed to handle it, so any instance can serve any request, and instances can be killed or added freely. A stateful service holds data that later requests depend on: databases, cache nodes, a WebSocket gateway holding open connections, a multiplayer game server holding a match in memory.

The standard architecture move is to push state down: keep the application tier stateless and move state into purpose-built stores (PostgreSQL, Redis, S3) that know how to replicate and partition it. Then the app tier scales by just adding boxes, and the hard problem of scaling state is concentrated in a few systems you can reason about carefully (Chapter 7 covers replication and sharding).

Where session state goes

Login sessions, shopping carts and multi-step form progress are the classic state that sneaks into app servers. You have four places to put it:

OptionHow it worksProsCons
Local memory + sticky sessionsSession lives in the server's RAM; the LB pins each user to that serverFastest, zero infrastructureServer dies = users logged out; uneven load; blocks clean scale-in
Shared session storeSession ID in a cookie; data in Redis or Memcached with a TTLAny server can serve any user; ~0.5–1 ms lookup in the same AZOne more system to run and make highly available
DatabaseSessions table in PostgreSQL/MySQL or DynamoDBDurable, uses existing infrastructureAdds a write per login and a read per request to the DB
Client-side tokenSigned cookie or JWT holds the claims; server only verifies the signatureNo server-side lookup at allHard to revoke before expiry; size limits (~4 KB cookies); see Chapter 13
Pitfall
Hidden state breaks scale-out
Sessions are the obvious case, but watch for the quiet ones: files uploaded to local disk, an in-process cache that must be invalidated on writes, a cron job that now runs on all 20 instances at once, rate-limit counters kept in memory, and open WebSocket connections. Each one works on one server and fails subtly on ten.
In the interview
How to say it
When you draw the app tier, say it out loud: I'll keep the API servers stateless so they can scale horizontally behind the load balancer and autoscale. Sessions go in Redis with a 30-minute TTL, uploads go straight to object storage. That one sentence answers three follow-up questions before they are asked.
