Load balancing algorithms

Once a request arrives, the LB must pick a backend. Static algorithms ignore what the backends are doing (round robin, weights, hashing). Dynamic algorithms use live signals such as open connections or recent latency. Dynamic ones adapt better but need accurate state, which is harder when you run many LB instances.

AlgorithmHow it picksBest forWatch out for
Round robinNext backend in orderIdentical servers, short uniform requestsIgnores load; a slow server still gets its share
Weighted round robinRound robin, proportional to weightsMixed instance sizes, canaries (weight 1 of 100)Weights are static guesses

Least response timeLowest recent latency, often combined with fewest active requestsBackends with uneven performanceCan pile onto a server that is fast because it is failing quickly

Round robin and weighted round robin

Round robin is the default in Nginx, HAProxy and most cloud LBs, and it is fine when servers are identical and requests are similar. Weights let a 16-core server take twice the traffic of an 8-core one, or let you send 1% of traffic to a canary. Nginx uses a smooth weighted round robin that interleaves picks instead of sending bursts to the heaviest server:

python
class SmoothWeightedRR:
    """Nginx-style smooth weighted round robin."""
    def __init__(self, weights):            # e.g. {"a": 5, "b": 1, "c": 1}
        self.weights = weights
        self.current = {s: 0 for s in weights}
        self.total = sum(weights.values())

    def pick(self):
        for s, w in self.weights.items():
            self.current[s] += w            # everyone earns credit
        best = max(self.current, key=self.current.get)
        self.current[best] -= self.total    # winner pays the total back
        return best

lb = SmoothWeightedRR({"a": 5, "b": 1, "c": 1})
print([lb.pick() for _ in range(7)])        # a a b a c a a

Least connections and least response time

When some requests take 5 ms and others take 30 seconds (report exports, uploads, WebSockets), round robin keeps handing new work to a server that is already stuck on slow requests. Least connections sends each new request to the backend with the fewest open connections, which naturally routes around busy servers. With HTTP/2 and gRPC, where one connection carries many requests, the equivalent is least requests (count in-flight requests, not connections). Nginx Plus offers least_time, which also weighs recent response time.

Power of two random choices

A fleet of 50 Envoy instances each sees only its own in-flight counts. If each one always picks the globally least-loaded server it knows of, they tend to all pick the same lightly loaded server at the same moment and overload it (herding). The fix is surprisingly simple: pick two backends at random and send the request to the less loaded one. This gets most of the benefit of least-loaded selection, avoids herding, and needs no coordination. It is the default behaviour of Envoy's least-request balancer.

python
import random

class PowerOfTwoChoices:
    def __init__(self, backends):
        self.inflight = {b: 0 for b in backends}

    def pick(self):
        a, b = random.sample(list(self.inflight), 2)
        choice = a if self.inflight[a] <= self.inflight[b] else b
        self.inflight[choice] += 1
        return choice

    def done(self, backend):            # call when the response completes
        self.inflight[backend] -= 1

Hashing for affinity

Sometimes you want the same key to land on the same server every time: a user's requests on the server that has their data cached, or a chat room on the server that holds its connections. Plain hash(key) mod N works until N changes: going from 10 to 11 servers remaps about 10 out of 11 keys and empties every warm cache at once. Consistent hashing moves only about 1/N of keys when a server joins or leaves. Nginx exposes it as hash $request_uri consistent, HAProxy as hash-type consistent, and Envoy as ring hash or Maglev. The algorithm, with code and virtual nodes, is covered in Chapter 7.

text
# Nginx: weighted least-connections pool with passive health checks
upstream api {
    least_conn;
    server 10.0.1.10:8080 weight=2 max_fails=3 fail_timeout=10s;
    server 10.0.1.11:8080 weight=1 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 backup;    # used only if the others are down
}
server {
    listen 443 ssl;
    ssl_certificate     /etc/nginx/tls/site.crt;
    ssl_certificate_key /etc/nginx/tls/site.key;
    location /api/ {
        proxy_pass http://api;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;
    }
}
Tip
A sensible default
For stateless HTTP services, start with round robin or least requests (power of two choices). Switch to least connections when request durations vary widely or connections are long-lived. Reach for consistent hashing only when affinity actually buys you something, such as cache hit rate.
In the interview
Justify the algorithm
Interviewers rarely care which algorithm you pick; they care that you can say why. Uploads take up to a minute and most API calls take 20 ms, so I'll use least connections rather than round robin. Bonus point: mention that with many LB nodes you want power of two choices to avoid herding.
