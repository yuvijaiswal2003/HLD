Making the load balancer itself highly available

Putting one load balancer in front of ten servers moves the single point of failure; it does not remove it. Redundancy for the front door happens at two scales: inside one site (a pair or fleet of LBs sharing an address) and across sites (deciding which data center or region a user reaches at all).

Active-passive pair with a floating virtual IP

The classic on-premises setup runs two LB machines (HAProxy or Nginx) with keepalived, which implements VRRP. Clients connect to a virtual IP (VIP) that is not tied to either machine. The active node owns the VIP and sends a heartbeat advertisement every second; the passive node listens. If the passive node misses about three advertisements, it claims the VIP and broadcasts a gratuitous ARP so switches start sending the VIP's traffic to its MAC address. Failover takes roughly 3–4 seconds with a 1-second interval, and less with sub-second intervals. Open TCP connections on the failed node are lost unless connection state is synced (for example with conntrackd).

  1. Heartbeats stop
    LB 1 crashes or loses its network link. LB 2 stops receiving VRRP advertisements.
  2. Standby promotes itself
    After about 3 missed intervals, LB 2 transitions to master and adds the VIP to its interface.
  3. Network learns the new location
    LB 2 sends gratuitous ARP replies; switches update their tables and route VIP traffic to LB 2.
  4. Clients reconnect
    New connections succeed immediately. Connections that were open on LB 1 reset and clients retry.
Tip
In the cloud, you usually buy this instead
Public clouds generally do not let you float IPs with VRRP multicast. Managed balancers such as ALB, NLB and Google Cloud Load Balancing are already a redundant fleet spread across availability zones behind a DNS name or static IPs. Your job is to enable multiple AZs and register targets in each, not to build a keepalived pair.

DNS round robin

The simplest way to spread users across several LBs or sites is to publish several A records for one name; clients pick one. It costs nothing, but it is crude. Resolvers and clients cache answers for the TTL (and some keep them longer), plain DNS has no idea whether an IP is healthy, and load ends up uneven because big resolvers hand the same answer to many users.

Anycast

With anycast, many locations announce the same IP prefix over BGP, and internet routing delivers each packet to the topologically nearest one. If a site fails, it withdraws its announcement and traffic shifts to the next-nearest site as BGP converges, typically within seconds to a minute and with no DNS caching in the way. Cloudflare serves its entire network over anycast, Google Cloud's global external load balancer gives you a single anycast IP, and AWS Global Accelerator provides two static anycast IPs in front of regional endpoints. Many DNS root servers also use anycast.

Global server load balancing (GSLB)

GSLB is health-aware, policy-driven DNS: the authoritative DNS server answers each query with the address of the region that is best for that user right now. Policies include latency-based (lowest measured RTT), geolocation (EU users to the EU, often for data residency), weighted (shift 10% to a new region) and failover (primary unless its health check fails). Route 53, Cloudflare Load Balancing, Akamai Global Traffic Management and NS1 all do this. TTLs of 30–60 seconds keep failover reasonably fast, but you should still expect a tail of clients on the old answer for several minutes.

In the interview
Give a layered answer
When asked how the LB avoids being a SPOF, answer by layer: Within a region, the managed LB runs across three AZs. Across regions, Route 53 latency routing with health checks sends users to the nearest healthy region, TTL 60 s. If we need faster global failover, put an anycast front door such as Global Accelerator or Cloudflare in front.
