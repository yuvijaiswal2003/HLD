Load balancers: L4 vs L7 and TLS termination

A load balancer (LB) is a reverse proxy (Chapter 2) whose main job is to spread traffic across a pool of backends. It gives clients one stable address, hides failed or draining servers, and lets you add capacity or deploy new code without clients noticing. The most important question about any LB is how much of the traffic it can understand, and that is what the layer numbers describe.

Layer 4: transport-level balancing

An L4 load balancer looks only at the IP and TCP/UDP headers: source and destination IP and port. It never parses HTTP, so it cannot see the URL, headers or cookies. It picks a backend once per connection (or per UDP flow) and then shovels bytes or packets to it. Because the work per packet is tiny, L4 balancers are extremely fast: they handle millions of packets per second and millions of concurrent connections, and some use direct server return so responses bypass the LB entirely. Examples: AWS Network Load Balancer (NLB), HAProxy in mode tcp, Linux IPVS, Google Maglev, Facebook Katran.

Layer 7: application-level balancing

An L7 load balancer terminates the client's connection and parses the application protocol, usually HTTP. It sees the method, host, path, headers, cookies and even the body, and decides per request. That unlocks routing /api/* and /images/* to different services, header-based canaries, retries on another backend, compression, response caching, rate limiting, authentication and WAF rules, and correct balancing of HTTP/2 and gRPC streams. Examples: AWS Application Load Balancer (ALB), Nginx, HAProxy in mode http, Envoy, Traefik.

Pitfall
gRPC behind an L4 balancer
gRPC multiplexes thousands of requests over one long-lived HTTP/2 connection. An L4 balancer only balances connections, so each client stays pinned to whichever backend it connected to first, and newly added backends sit idle. Use an L7 proxy that balances individual streams (Envoy, ALB with gRPC target groups) or client-side load balancing.

TLS termination

To route on HTTP, an L7 LB must decrypt the traffic, which means it holds the certificate and private key. Where you decrypt is a design choice with three common answers:

Terminate at the LB

Strengths
  • Backends skip TLS work
  • Certificates managed in one place (ACM, cert-manager)
  • Enables all L7 features
Weaknesses
  • Plaintext inside your network
  • LB becomes a high-value target
Use whenDefault for most web apps when the internal network is trusted.

Passthrough (L4)

Strengths
  • True end-to-end encryption
  • LB never sees keys or content
Weaknesses
  • No path or header routing (SNI only)
  • Every backend manages certs
  • No L7 retries or WAF
Use whenStrict compliance needs, or non-HTTP protocols over TLS.

Terminate and re-encrypt

Strengths
  • L7 routing plus encryption on every hop
  • Can use mTLS to prove service identity
Weaknesses
  • Two handshakes and more CPU
  • Internal certificate management
Use whenZero-trust networks and service meshes (Istio, Linkerd).

Once the LB terminates the connection, backends see the LB's IP, not the client's. L7 proxies add X-Forwarded-For and X-Forwarded-Proto headers; L4 proxies that open new connections use the PROXY protocol (invented by HAProxy) to pass the original address, while NLB can preserve the source IP directly.

In production
Real L4 + L7 stacks
Google published Maglev, its software L4 balancer that sits in front of its HTTP front ends. Facebook open-sourced Katran, an eBPF/XDP-based L4 balancer that spreads traffic across its Proxygen L7 proxies. Both use the two-tier shape above.
In the interview
What interviewers listen for
Say which layer you need and why: an ALB is enough here because I need path routing and TLS termination, or this is raw TCP from IoT devices, so an NLB. Mention where TLS terminates and how backends learn the client IP. Never just draw a box labelled LB.
