Design the traffic layer for a global e-commerce site

An online retailer with 100 million daily active users in North America, Europe and Asia wants a new traffic layer: everything between the user's device and the backend services. It must route requests to the right service, survive the loss of a server, an availability zone or a whole region, keep carts intact during failover, and allow safe deployments. Static assets are already on a CDN. Design the DNS, load balancing and failover layers.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • Where are users, and what share of traffic comes from each region?
  • What are average and peak dynamic request rates, and how big is the Black Friday spike?
  • What availability target do we need: 99.9% or 99.99%? Is a few minutes of failover acceptable?
  • Are there data residency rules, for example EU customer data must stay in the EU?
  • Which state must survive a regional failover: sessions, carts, in-progress checkouts?
  • Which cloud provider or on-prem constraints apply, and do we prefer managed balancers?

Stuck? Each hint gives a little more away than the last.

H1Split routing into two decisions: which region serves this user, and which server inside that region.
H2For the regional front door, think about what an L4 balancer gives you (static IPs, raw throughput) versus an L7 proxy (TLS, path routing, retries, canaries).
H3Size each region so the surviving regions can absorb a failed one. Then compare DNS failover timing with anycast.
H4Carts must outlive a region: put them in a multi-region replicated store, keep app servers stateless, and make checkout idempotent so retries during failover are safe.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: route each request by host and path to the right service (catalog, search, cart, checkout); terminate TLS; send users to a nearby region; support canary and blue/green deploys.
  • Non-functional: 99.99% availability for browsing and checkout; survive loss of an instance, an AZ or a region; added latency from the traffic layer under 10 ms p99; failover of a region within a few minutes; no lost carts.

High-level design

Request path: the browser resolves shop.example.com; Route 53 returns the NLB address of the lowest-latency healthy region. The NLB spreads TCP connections across Envoy nodes in all three AZs and preserves the client IP. Envoy terminates TLS, applies per-route timeouts and retries, and forwards each request by path to a service, re-encrypting with mTLS. Services are stateless: sessions come from Redis, carts from DynamoDB. A cart write lands in the local DynamoDB replica and replicates to the other regions within about a second.

Deep dives

1. Regional failover. Route 53 health checks probe each region's front door every 10 seconds from several locations; when a region fails, it drops out of latency answers. With a 60-second TTL, most clients move within a couple of minutes, but some resolvers and apps cache longer. If that tail is unacceptable, put AWS Global Accelerator (anycast static IPs) in front of the NLBs: failover then follows edge routing and health checks, not DNS caches. Either way, each region holds 150k RPS of proxy capacity and its app tiers autoscale with a raised minimum during peak season, because you cannot count on scaling a region from cold during a failover.

2. Why NLB plus Envoy, and when not to. The NLB gives static IPs per AZ, absorbs connection floods and costs little per request. Envoy adds what the NLB cannot: TLS termination with central certificate management, path routing, retries on another host, outlier detection that ejects a server returning 5xx, and weighted canaries. For a smaller company an ALB alone is the right answer; the two-tier setup pays off when you need custom L7 logic, more control over load balancing (power of two choices, consistent hashing for a cache tier) or very high connection counts.

3. State and safe retries during failover. Because carts live in DynamoDB global tables, a user rerouted to eu-west sees the cart they built in us-east, give or take the last second of writes. Global tables resolve concurrent writes with last-writer-wins, which is acceptable for carts. Checkout is different: the client sends an Idempotency-Key, and the checkout service records it before charging, so a request retried in another region cannot charge twice (Chapter 11). Inventory and payments keep a single home region per order to avoid conflicting writes.

4. Deployments. Envoy shifts traffic to a new version by weight (1%, 10%, 50%, 100%) while dashboards compare error rates; rollback is a config push. Instances leaving the pool drain for 30 seconds, and Kubernetes pods use a short preStop sleep so proxies stop routing before shutdown starts.

  • Bottleneck to watch: a gray failure where one AZ is slow but passes health checks. Envoy outlier detection and latency-aware balancing help; so does zone-aware routing.
  • The control plane that pushes Envoy config must itself be redundant, and a bad config push is a global outage risk: roll config out region by region.

5Follow-up questions

  • How would you protect this layer from a 1 Tbps DDoS attack?
  • The payment provider only has an endpoint in the US. How does checkout work for EU users when us-east is down?
  • One AZ starts returning slow responses but still passes health checks. How do you detect it and shift traffic away?
  • How would you upgrade the Envoy fleet itself without dropping connections?
  • EU regulators require EU customer data to stay in the EU. What changes in routing and failover?
