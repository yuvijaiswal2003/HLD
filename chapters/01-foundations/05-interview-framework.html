A 45-minute interview framework

Most system design interviews last 45 to 60 minutes. Without a plan, candidates either spend 20 minutes on requirements or draw boxes for 40 minutes and never show depth. The budget below fits a 45-minute slot; stretch each phase proportionally for 60.

PhaseTimeGoalOn the board when done
1. Clarify requirements~5 minAgree on scope and quality barFunctional list, NFR list, out-of-scope list
2. Estimate~5 minFind the scale that drives the designAverage and peak QPS, storage, bandwidth if relevant
3. API and data model5–10 minDefine the contract and core entities2 to 5 endpoints; main tables with keys
4. High-level design10–15 minA working end-to-end designBoxes and arrows covering the main read and write paths
5. Deep dives~10 minShow depth on the 2 or 3 hardest partsDetailed sub-designs with alternatives and numbers
6. Wrap-up~5 minShow you know the weaknessesBottlenecks, failure modes, what changes at 10x

Phase 1: clarify

  • Restate the problem: “So we're building X for Y kind of user. The core features I hear are A, B and C. Anything else critical?”
  • Scale: “Roughly how many daily active users, and is traffic global or regional?”
  • Quality: “Is it worse to show stale data or to be unavailable for a moment?”
  • Scope: “I'll leave out D and E unless you want them.”

Phase 2: estimate

Only compute numbers that can change a decision: read and write QPS, storage growth, and sometimes bandwidth or cache memory. Round hard. Then say what the numbers mean: “3,000 writes per second fits on one well-tuned PostgreSQL primary, but 300 TB over five years does not fit on one machine, so storage must be partitioned.”

Phase 3: API and data model

The API pins down exactly what the system does; the data model reveals the access patterns that pick the database. Keep both short.

http
POST /v1/articles/{article_id}/comments
  body: { "text": "...", "parent_id": null }
  -> 201 Created  { "comment_id": "c_8f2", "created_at": "..." }

GET /v1/articles/{article_id}/comments?cursor=c_8f2&limit=20
  -> 200 OK  { "comments": [ ... ], "next_cursor": "c_7a1" }

Phase 4: high-level design

Draw the simplest design that satisfies every functional requirement end to end: client, load balancer, services, storage. Walk through one write and one read out loud, naming each hop. Only after that works should you start optimizing.

Phase 5: deep dives

Pick the parts where the non-functional requirements bite: a hot key, a large fan-out, a strict consistency need, a dataset too big for one machine. If the interviewer doesn't choose, propose: “The two hardest parts are X and Y. I'd like to start with X.” For each, present two options, compare them against the requirements, and choose.

Phase 6: wrap-up

Name the bottlenecks and remaining single points of failure, the metrics you would alert on, and what you would change at 10x traffic. Pointing out your own design's weaknesses is a strong senior signal.

In the interview
Drive, but check in
Announce transitions (“I have a working design. Now let me look at the bottlenecks.”) and check in about once per phase (“Is this the right level of detail, or should I go deeper on storage?”). Interviewers explicitly grade whether you lead the conversation.
Tip
Keep a parking lot
Write a short list in a corner of the board for topics you'll return to, such as “hot celebrity accounts” or “rate limiting”. It shows awareness without derailing the current phase, and it gives you a ready list of deep-dive candidates.
