Design a personal blog that grows to 1M readers

A writer wants a personal blog. It starts with a few hundred readers a month. Over two years it grows to 1 million monthly readers, and some posts go viral and get shared on Hacker News or Reddit, bringing huge sudden spikes. Readers read posts and leave comments; the author publishes a few posts a week. Design the system, and show how it should evolve from launch to 1M readers without wasting money.

45:00Mock interview timer. Start it when you begin talking.
Clarify requirements5 min
Estimate scale5 min
API and data model8 min
High-level design12 min
Deep dives10 min
Wrap up and bottlenecks5 min

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • Is 1M the number of monthly unique readers or page views? How many pages does a reader view per visit?
  • How big is a viral spike: how many visitors, over how long?
  • Are comments required, and must a new comment appear instantly for other readers?
  • Do posts include images or video, and roughly how large?
  • What is the budget? Should this cost tens of dollars a month or is more acceptable?
  • Is a few minutes of downtime a month acceptable?
  • Are search, newsletters or analytics in scope?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1Compare reads and writes: the author writes a few times a week while readers read all day. What does that suggest?
H2Most of a post page is identical for every reader. Could the HTML itself be cached, not only the images?
H3Calculate page views per second during a spike. Is that a lot for a CDN? For one small server running PHP and SQL on every request?
H4Separate the static part (posts) from the dynamic part (comments); they need very different scaling.
H5A static site generator plus object storage plus a CDN serves posts with no servers at all. Comments can be a tiny API that the page loads separately.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: author publishes and edits posts (Markdown with images); readers view posts, an index page and an RSS feed; readers post and read comments.
  • Non-functional: 1M monthly readers with viral spikes; posts load fast worldwide (first byte p95 under 200 ms); 99.9% availability for reading; new comments visible to others within about 30 s; low cost; acknowledged comments are not lost.

Estimates

text
Monthly page views:  1M readers x 3 pages = 3M page views/month
Seconds per month:   30 x 86,400 = ~2.6M s
Average load:        3M / 2.6M s = ~1.2 page views/s   (tiny)

Viral spike:         200k visitors in 2 hours on one post
                     200,000 / 7,200 s = ~28 page views/s
                     busiest minutes ~5x that = ~150 page views/s
Bytes per new visitor: ~50 KB HTML + ~1.5 MB images, CSS, JS
Spike bandwidth:     150 x 1.5 MB = ~225 MB/s = ~1.8 Gbit/s

Comments:            1% of readers comment = 10k/month = ~0.004 writes/s
Storage after 2 yrs: posts 500 x 50 KB = 25 MB
                     images 500 x 5 x 300 KB = ~750 MB
                     comments 240k x 1 KB = ~240 MB

The numbers make the design obvious. Storage is under a few gigabytes and the average load is about one request per second. The only hard number is the spike: around 150 page views per second and close to 2 Gbit/s of bandwidth. That would knock over a small server that runs code and database queries per request, but it is routine for a CDN. This is a caching and CDN problem, not a database problem.

API

http
GET  /posts/{slug}/                 -> static HTML, served by the CDN
GET  /api/posts/{slug}/comments?cursor=c_91&limit=50
     -> 200 { "comments": [ ... ], "next_cursor": "c_42" }
POST /api/posts/{slug}/comments
     body: { "name": "Ana", "text": "...", "captcha_token": "..." }
     -> 201 { "id": "c_92", "status": "published" }
POST /admin/publish                  (author only, triggers a rebuild)

Data model

StoreContentsNotes
Git repositoryPosts as Markdown files plus imagesSource of truth for content; full history for free
Object storage (S3 or similar)Generated HTML, images, CSS, JSCDN origin; cheap and highly durable
PostgreSQL (small managed instance)comments(id PK, post_slug, parent_id, author_name, text, status, created_at)Index on (post_slug, created_at); relational and tiny, with daily backups

High-level design

Read path: the reader's browser requests the post from the CDN. HTML, CSS and images come from the edge cache; on a miss the CDN fetches the file from object storage once and caches it. JavaScript on the page then fetches comments from /api/..., also through the CDN, which caches the response for 30 seconds. Write path for posts: the author pushes Markdown; a build job (Hugo, Jekyll, Astro or similar) renders HTML, uploads changed files and purges those URLs from the CDN. Write path for comments: the browser posts to the API, which checks the CAPTCHA and a per-IP rate limit, then inserts into PostgreSQL.

Deep dives

Evolving with traffic. Each step is driven by a number, not by fashion:

Readers per monthDesignWhy
Under 10kOne small VM running WordPress or Ghost with its databaseCheapest and simplest; load is negligible
10k to 100kSame VM plus a CDN in front for images and cached pagesOffloads bandwidth and absorbs small spikes
100k to 1MStatic site on object storage plus CDN; separate comments APIPosts need no servers; only comments are dynamic
Beyond 1M with busy commentsMore API instances behind a load balancer, Redis for comment lists, a read replicaOnly when comment traffic itself justifies it

Surviving the spike. The classic failure is the “hug of death”: every page view runs application code and several SQL queries, and a small server collapses at about 100 requests per second. With static HTML on a CDN, origin load hardly changes with traffic. Set cache headers deliberately: HTML gets a long CDN TTL and is purged on publish; CSS, JS and images use content-hashed file names (app.3f9a1c.css) with a one-year TTL, so a change simply produces a new URL. For comments, a 30-second edge TTL means even 150 page views per second produce roughly one origin request per post per CDN location every 30 seconds.

Seeing your own comment. A commenter expects to see their comment immediately, but the cached list may be 30 seconds old. Solve it in the browser: after a successful POST, insert the returned comment into the visible list. Other readers see it within the TTL, which the requirements allow.

Trade-offs and bottlenecks

  • Static generation means a publish takes seconds to minutes to appear. Fine for a blog, wrong for breaking news.
  • The 30-second edge cache on comments trades freshness for protecting a tiny backend.
  • The single PostgreSQL instance is a SPOF for comments only; posts stay readable if it dies. Daily backups plus point-in-time recovery are enough for this SLA.
  • A hosted comment service removes the API entirely, at the cost of privacy, ads and control.
  • The real operational risk is spam: CAPTCHA, per-IP rate limits and a moderation queue matter more than scaling.

5Follow-up questions

  • The author fixes a factual error in a viral post. How long until every reader sees the fix, and how would you shorten it?
  • The author wants a live view counter on each post. How do you add it without hurting the CDN hit ratio?
  • How would you add full-text search over all posts?
  • Spam bots start posting 1,000 comments a minute from thousands of IPs. What do you do?
  • The author adds paid, subscriber-only posts. What changes in your caching?
