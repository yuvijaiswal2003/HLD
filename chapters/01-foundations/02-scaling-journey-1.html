The scaling journey, part 1: from one server to many

Most large systems were not designed at their final size. They evolved: traffic grew, something broke, and the team added the component that fixed that specific bottleneck. Walking through this evolution is the fastest way to learn why each building block exists. We'll follow an imaginary recipe-sharing site from launch to tens of millions of users. At each stage, look for the bottleneck that forces the next change.

Stage 1: everything on one server

At launch, one virtual machine runs the web server (say Nginx), the application code and the database. DNS maps recipes.example.com to that machine's IP address. This is cheap and easy to deploy and debug. It has two problems. First, the machine is a single point of failure (SPOF): a component whose failure takes the whole system down. Second, the app and the database fight over the same CPU, memory and disk.

Stage 2: move the database to its own machine

Separating the database lets each tier be sized for its job: app servers want CPU, databases want RAM and fast disks. It also prepares the app tier to be copied later. At this stage most teams also scale vertically: they move to a bigger machine with more cores and memory. Vertical scaling is simple and buys real time (a single modern server can have 64+ cores and over 1 TB of RAM), but it has a hard ceiling, the price climbs steeply near the top, and the machine is still a SPOF.

Stage 3: a load balancer and many app servers

Horizontal scaling means adding more machines instead of bigger ones. A load balancer sits in front of several identical app servers, spreads requests across them, checks their health, and stops sending traffic to any that fail. Losing one app server now only reduces capacity a little.

This only works if app servers are stateless: they keep nothing in local memory that a later request needs. If user sessions live in one server's memory, a user whose next request lands on another server appears logged out. Shared state moves to a shared store such as Redis, or into a signed token the client carries. Chapter 4 covers load balancing in depth.

Stage 4: add a cache

Most applications are read-heavy: a recipe is viewed hundreds of times for every edit, and a small set of popular recipes gets most of the views. A cache such as Redis or Memcached keeps hot data in memory. A cache read takes well under a millisecond, versus a few milliseconds for an indexed database query, and every cache hit is a query the database never sees. The common pattern is cache-aside: check the cache, and on a miss read the database and store the result with an expiry time. The cost is that cached data can be stale, and keeping it fresh is genuinely hard. Chapter 5 is devoted to caching.

Stage 5: serve static content from a CDN

Images, CSS, JavaScript and video are the same for every user. A content delivery network (CDN) is a provider-run fleet of cache servers in hundreds of locations worldwide. A user in Mumbai downloads a photo from a nearby edge server in tens of milliseconds instead of fetching it from your servers in Virginia, roughly 200 ms of round trip away, and your servers no longer spend bandwidth on it. Files usually live in object storage such as Amazon S3, which acts as the CDN's origin.

Pitfall
Don't start at the last stage
A design for 1,000 users that already has sharding, Kafka and three regions is a red flag, just like a single server for 100 million users. Interviewers want the design to match the numbers. Say which stage the estimated scale requires, and mention what you would add later.
