The scaling journey, part 2: data, async work and regions

After stage 5, the app tier scales by adding servers and static traffic is off our hands. The remaining pressure lands on the database, on slow work done inside requests, and on geography.

Stage 6: read replicas

Even with a cache, cache misses and uncacheable queries eventually saturate the database. Because reads outnumber writes, we add read replicas: copies of the database that receive every change from the primary and serve read queries. All writes still go to the primary. Replicas also give us a standby to promote if the primary dies.

The catch is replication lag. Replication is usually asynchronous, so a replica can be milliseconds to seconds behind. A user who updates their profile and immediately reloads may read from a replica that hasn't applied the change yet and see the old value. Chapter 7 covers fixes such as routing a user's reads to the primary for a short time after they write.

Stage 7: sharding

Replicas multiply read capacity, but every replica still holds the full dataset and every write still goes through one primary. When the data no longer fits on one machine, or writes exceed what one primary can absorb, we shard (also called horizontal partitioning): different rows live on different database servers, chosen by a shard key. For example, hash(user_id) mod 16 picks one of 16 shards, and each shard has its own replicas.

Sharding is powerful and expensive. Queries that span shards (“top recipes across all users”) need scatter-gather or a separate index. Transactions across shards are hard. Adding shards means moving data. A bad shard key creates a hot shard. The shard key should match the main access pattern so most requests touch one shard. Chapter 7 goes deep on this.

Stage 8: queues for asynchronous work

Some work doesn't need to finish while the user waits: resizing an uploaded photo, sending a welcome email, updating the search index, notifying followers. The app puts a message on a message queue (RabbitMQ, Amazon SQS, Kafka) and returns immediately. Workers consume messages at their own pace. Responses get faster, traffic spikes are absorbed by the queue instead of overloading downstream systems (load leveling), and a failing email provider no longer breaks sign-up. The cost: work completes later (eventual consistency), and workers need retries and must tolerate processing a message twice. Chapter 9 covers messaging.

Stage 9: multiple regions

A single data center or cloud region is still one failure domain, and users on other continents pay 100 to 200 ms of network round trip per request. Running full copies of the stack in several regions puts servers near users and lets the system survive a regional outage. GeoDNS or anycast sends each user to a nearby healthy region. The hard part is data: either each user's data has one home region that takes its writes (simpler), or every region accepts writes and they replicate to each other, which requires resolving conflicting updates. Chapters 7 and 12 cover these designs.

In production
Instagram's early path
Instagram's early backend, described on its engineering blog, was Django on AWS with PostgreSQL, Redis and Memcached. As data grew, the team sharded PostgreSQL by user into several thousand logical shards mapped onto far fewer physical servers, so shards could later be moved to new machines without re-splitting the data.
In the interview
Use the journey as a checklist
You rarely walk every stage in an interview. Instead ask: “At the scale we estimated, where is the bottleneck?” Then add only the components that the numbers justify, and say which stage you would reach next if traffic grew 10x.
