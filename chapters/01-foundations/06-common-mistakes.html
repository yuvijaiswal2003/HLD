Common mistakes and how to avoid them

Most failed system design interviews fail for a handful of repeated reasons, and almost none of them are about not knowing a technology. They are about process. Each mistake below has a simple counter-habit.

MistakeWhat it looks likeDo this instead
Jumping to solutions“We'll use Kafka and Cassandra” in minute oneClarify requirements first; let the numbers pick the technology
Buzzword soupEvery box is a product name with no reason attachedFor each component, say what problem it solves and why this one
Ignoring numbersEstimates computed, then never used againTie decisions to numbers: shard count, cache size, server count
Not drivingWaiting for the interviewer to ask the next questionAnnounce the plan and propose deep-dive topics yourself
Over-engineeringMulti-region active-active for a 500-person internal toolMatch the stated scale and SLA; describe how it would evolve
One option onlyPicks a database without considering any otherCompare two options briefly, then choose with a reason
Ignoring failureNo answer to “what if this node dies?”Look for SPOFs; add replicas, failover, retries, health checks
Going silentLong pauses while thinking privatelyThink out loud, even when unsure
Rabbit-holingFifteen minutes on the exact JSON field namesTimebox details; offer to come back later

Buzzword soup versus a reasoned choice

Weak: “We'll put Kafka in the middle, Cassandra for storage, Redis for caching, and run it all on Kubernetes.” Nothing here says why.

Strong: “Writes are about 30,000 per second, append-only, always looked up by user and time, with no multi-row transactions. That suits a wide-column store like Cassandra, which absorbs high write rates by appending to a log-structured storage engine. The trade-off is that we can only query efficiently by partition key, so I'll make user_id the partition key and time the clustering key.” Same technology, but now the interviewer sees the reasoning and the cost.

A self-check before you say you're done

  1. Does the diagram cover every functional requirement, for both the read and the write path?
  2. Does every non-functional requirement have a mechanism? (Availability: replicas and failover. Latency: cache and CDN. Durability: replication and backups.)
  3. Did I use my estimates to size something?
  4. Where are the single points of failure?
  5. What breaks first at 10x traffic, and what would I change?
Pitfall
Don't recite a memorized answer
Interviewers often change a constraint halfway (“now users are in five countries with data-residency laws”) precisely to see whether you reason or recite. Learn why designs look the way they do, so you can adapt when the constraint changes.
In the interview
Criticize your own design
Ending with “The weakest part of this design is the single Redis node for counters; if it fails we lose up to a second of increments. With more time I'd add a replica and periodic reconciliation from the database” scores better than claiming the design has no weaknesses.
