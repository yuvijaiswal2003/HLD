Design a simple poll and voting app

Design a poll service like the polls embedded in social posts or chat apps. A user creates a poll with a question, 2 to 4 options and a closing time. Any logged-in user with the link can vote once. Everyone sees results as vote counts and percentages. Most polls are small, but a celebrity's poll or one shown on live TV can get a million votes in a few minutes.

45:00Mock interview timer. Start it when you begin talking.
Clarify requirements5 min

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • Must voters be logged in? How strictly must we enforce one vote per person?
  • Can a voter change their vote before the poll closes?
  • How fresh must displayed results be: exact and instant, or within a few seconds?
  • How many polls are created per day, and how fast does the hottest poll receive votes?
  • Can people see results before voting, or only after?
  • Must we keep who voted for what after the poll closes?

2Your answer

3Hints 0/4

Stuck? Each hint gives a little more away than the last.

H1Start with the simplest correct design: a votes table with a unique constraint on (poll_id, user_id). What happens to it when one poll receives 10,000 votes per second?
H2Separate two jobs: remembering who has voted (deduplication) and counting votes (aggregation). They don't need the same storage.
H3A single counter row updated by every vote becomes a lock hotspot. How could one counter become many?
H4Results may be a couple of seconds stale. How does that let you serve 100,000 result reads per second cheaply?

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: create a poll (question, 2 to 4 options, closing time); vote once per logged-in user; view per-option counts and percentages; polls close automatically. Changing a vote is out of scope for v1.
  • Non-functional: 10M DAU; the hottest poll gets 1M votes in 5 minutes; vote acknowledgment p99 under 200 ms; displayed results may lag up to about 2 s; every accepted vote is counted exactly once in the final result; 99.9% availability.

Estimates

text
Poll creation:  1M polls/day / ~100,000 s/day = ~10 creates/s
Votes overall:  10M DAU x 3 votes = 30M votes/day
                30M / 100,000 s = ~300 votes/s average, ~1k/s at peak

Hottest poll:   1M votes in 5 min = 1,000,000 / 300 s = ~3,300 votes/s
                bursts up to ~10k votes/s, all on ONE poll
Result reads:   ~10 result views per vote -> up to ~100k reads/s on that poll

Storage:        vote row = poll_id 8 B + user_id 8 B + option 1 B
                + timestamp 8 B = ~25 B, ~100 B with row and index overhead
                30M votes/day x 100 B = 3 GB/day = ~1.1 TB/year
                polls: 1M/day x 1 KB = 1 GB/day

Average load is small: one PostgreSQL primary handles 1,000 inserts per second easily, and a terabyte a year is manageable. The crux is the hot poll: thousands of increments per second to the same few counters, and up to 100,000 reads per second of the same result.

API

http
POST /v1/polls
     body: { "question": "...", "options": ["A", "B", "C"], "closes_at": "..." }
     -> 201 { "poll_id": "p_7Hk2" }

POST /v1/polls/{poll_id}/votes        (Authorization: Bearer token)
     body: { "option_id": 2 }
     -> 201 Created  |  409 Conflict (already voted)  |  410 Gone (closed)

GET  /v1/polls/{poll_id}/results
     -> 200 { "options": [ { "id": 1, "votes": 51234 }, ... ], "total": 98110 }

Data model

TableColumnsPurpose
pollspoll_id PK, creator_id, question, options, closes_at, statusPoll definitions
votespoll_id, user_id, option_id, created_at, primary key (poll_id, user_id)Source of truth; the key enforces one vote per user
Redis counterskey poll:p_7Hk2:counts, a hash of option to countFast running totals for display

PostgreSQL fits because the unique key gives one-vote-per-user for free and the data is relational. When the votes table grows into terabytes, partition it by poll_id (Chapter 7); every query is per poll, so each touches one partition.

High-level design

Vote path: the API inserts into votes. A duplicate violates the primary key and returns 409. On success it increments the option's counter in Redis with HINCRBY and returns 201. Results path: the browser fetches results through the CDN, cached for 2 seconds, so the hottest poll produces about one origin read per CDN location every 2 seconds instead of 100,000 per second. Percentages are computed in the client. Reconciliation: a job periodically recomputes counts with SELECT option_id, COUNT(*) ... GROUP BY option_id and corrects Redis, and it computes the final result when the poll closes.

Deep dives

The hot counter. If totals lived in a single PostgreSQL row per option, every vote would lock that row for the length of its transaction. With about 1 ms per transaction, one row tops out near 1,000 updates per second, below our 3,300 average. Two fixes: (1) sharded counters: keep, say, 32 rows per option, add each vote to a random one, and sum the 32 on read; (2) keep running totals in Redis, where a single key handles on the order of 100,000 increments per second. We use Redis for display and the votes table as the truth.

Exactly-once counting. The insert and the Redis increment are two separate systems, so a crash between them can leave Redis one vote short, and a retried request could double count. We accept that the live number can be very slightly off, because the reconciler rebuilds totals from the deduplicated votes table, which is exact. The final, published result always comes from the database.

If inserts become the bottleneck. At tens of thousands of votes per second on one poll, the API can deduplicate in Redis instead (SADD poll:p_7Hk2:voters user_id returns 1 only for a new voter), increment the counter, and publish the vote to a queue such as Kafka. A consumer then batch-inserts into PostgreSQL with ON CONFLICT DO NOTHING. Votes are acknowledged faster, at the cost of a short window where a vote is accepted but not yet in the database.

5Follow-up questions

  • Voters may now change their vote until the poll closes. What changes in deduplication and counting?
  • How do you stop someone from voting thousands of times with throwaway accounts?
  • Redis crashes in the middle of the hottest poll. What do users see, and how do you restore correct totals?
  • Results must update live on screen without refreshing. How would you push updates to millions of viewers?
  • Some polls must be anonymous: you may not store who voted for which option. How do you still enforce one vote per user?
