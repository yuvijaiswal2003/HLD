Design the API gateway for a mobile and web product

A consumer product (think a food or travel marketplace) has iOS, Android and web clients and about 40 backend microservices. Today each client calls services directly through a load balancer. Design the API gateway layer: routing, authentication, rate limiting, response aggregation for mobile, versioning, and how it stays fast and highly available.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • What is peak request rate and the latency budget the gateway may add?
  • How do clients authenticate today: sessions, JWTs from an identity service, API keys for partners?
  • Do mobile screens need aggregated responses, and how old are the oldest app versions still in use?
  • Are there public partner APIs in scope, or only first-party clients?
  • What is the deployment footprint: one region or several, Kubernetes or VMs?
  • Which concerns must be centralized for compliance: audit logging, PII redaction, WAF?

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: single public entry point per environment; route by host, path and version to services; authenticate users (JWT) and partners (API keys); per-user and per-key rate limits; mobile and web BFFs that aggregate several services per screen; request ids and access logs; canary releases by percentage or header.
  • Non-functional: gateway adds under 5 ms p99 (excluding BFF fan-out); 99.99% availability, multi-AZ; horizontally scalable stateless instances; config changes without restarts; old app versions supported for at least 12 months.

Estimates

  • 20M DAU, about 60 API calls per user per day: 1.2B calls/day / 10^5 s = about 12k requests/s average; peak 5x at dinner time = 60k requests/s.
  • An Envoy or NGINX-based gateway instance handles roughly 10k to 20k proxied requests/s with TLS on a few cores, so peak needs about 6 instances; run 12 across 3 AZs to survive an AZ loss with headroom.
  • Average response 5 KB: 60k x 5 KB = 300 MB/s egress at peak, about 2.4 Gbps, before compression.
  • BFF: the mobile home screen fans out to 6 services in parallel; latency is the slowest call plus overhead, so each service needs a p99 well under 100 ms for a 150 ms screen budget.

High-level design

A request arrives at the CDN, which handles DDoS protection and WAF rules and caches public assets. The L4 load balancer spreads TCP connections across gateway instances in three AZs. The gateway terminates TLS, assigns a request id, validates the JWT signature and expiry locally using cached public keys, checks rate limits in Redis, matches the route, and forwards to the upstream with the user id and scopes in trusted internal headers. Screen-shaped mobile and web calls go to BFFs, which call services in parallel with tight per-call timeouts; plain resource calls such as POST /api/v1/orders route directly to the owning service.

Deep dives

Authentication at the edge. Validating a JWT locally costs microseconds of CPU and no network call, which is why the gateway uses short-lived access tokens (about 15 minutes) signed with asymmetric keys. Revocation is the catch: a stolen token stays valid until it expires, so keep tokens short and, for high-risk actions, have the service check a revocation list or session store. The gateway strips any incoming internal identity headers from clients and sets them itself, so a client cannot forge X-User-Id. Services trust those headers only from the gateway, enforced with mTLS or network policy. Token formats and OAuth flows are covered in Chapter 13.

BFF aggregation and partial failure. The mobile home screen calls catalog, promotions, orders, recommendations, user and banners in parallel. Each call gets its own timeout (for example 80 ms) and a fallback: if recommendations time out, the BFF returns the screen without that carousel and a flag, instead of failing the whole screen. Required data (the store list) fails the request; optional data degrades. Responses are shaped for the client, often 60 to 80% smaller than the combined service payloads, which matters on slow mobile networks.

Versioning for old app versions. Mobile users run versions that are months old, so the mobile BFF keeps /mobile/v2 and /mobile/v3 side by side, translating between the client contract and the current service APIs. Services can evolve freely as long as the BFF adapts. The gateway reads the app version header to apply a minimum supported version: below it, it returns a specific error code that makes the app show an upgrade prompt. Per-version traffic metrics decide when an old BFF version can be removed.

Trade-offs and bottlenecks

  • Gateway as a single point of failure: mitigated by stateless instances across AZs behind an L4 load balancer, gradual config rollout with automatic rollback, and keeping business logic out of it.
  • Extra hop latency: about 1 ms per proxy hop in the same AZ; the BFF hop pays for itself by replacing several client round trips over a 50 to 200 ms mobile network.
  • Managed vs self-hosted: AWS API Gateway or Apigee save operations work but cost per request at high volume and limit customization; Envoy or Kong on Kubernetes cost engineering time but are cheaper at 60k requests/s.
  • BFF sprawl: one BFF per client team is good; one BFF per screen is not. Share libraries for service clients between BFFs.
  • GraphQL instead of REST BFFs: lets clients pick fields and reduces versioning pressure, but needs query cost limits, persisted queries and careful caching.

5Follow-up questions

  • How do you roll out a gateway config change to 12 instances without a bad route taking down the whole API?
  • How would you add response caching at the gateway for the store page without leaking personalized data between users?
  • How do you propagate trace context from the gateway through BFFs to services?
  • A partner integration needs webhooks for order status. Where does webhook delivery live, and how is it secured?
  • How would the design change for two regions with users routed by latency?
