Rate limiting algorithms

A rate limiter caps how many requests a client may make in a period and rejects the rest. It protects services from abuse and accidental floods (a buggy client retrying in a tight loop), stops one tenant from starving others (the noisy neighbor problem), controls cost when each call costs money (SMS, third-party APIs, GPU inference), and enforces paid tiers. Every limiter needs two decisions: the key (user id, API key, IP, tenant, endpoint, or a combination) and the algorithm.

Token bucket

A bucket holds up to capacity tokens and refills at rate tokens per second. Each request takes one token (or cost tokens for expensive calls); with no tokens left, the request is rejected. The two parameters map directly to product language: capacity is the allowed burst, rate is the sustained limit. With capacity 10 and rate 1/s, an idle client can fire 10 requests at once, then 1 per second. You do not need a timer to add tokens: store tokens and the last timestamp, and refill lazily on each request from the elapsed time. That is 2 numbers per key.

python
import time

class TokenBucket:
    def __init__(self, capacity, refill_per_sec):
        self.capacity = capacity          # max burst
        self.rate = refill_per_sec        # sustained requests per second
        self.tokens = float(capacity)     # start full
        self.last = time.monotonic()

    def allow(self, cost=1):
        now = time.monotonic()
        elapsed = now - self.last
        # Lazy refill: add what accrued since the last call, cap at capacity
        self.tokens = min(self.capacity, self.tokens + elapsed * self.rate)
        self.last = now
        if self.tokens >= cost:
            self.tokens -= cost
            return True
        return False

    def retry_after(self, cost=1):
        # Seconds until enough tokens exist, for the Retry-After header
        return max(0.0, (cost - self.tokens) / self.rate)

Leaky bucket, fixed window and sliding window log

  • Leaky bucket: requests enter a FIFO queue of fixed size and are drained at a constant rate; if the queue is full, new requests are dropped. Output is perfectly smooth, which suits a downstream that needs a steady rate, but bursts wait in the queue and add latency. Nginx's limit_req uses the leaky bucket method, and Shopify documents a leaky bucket for its REST Admin API. Implemented as a meter rather than a queue (the GCRA algorithm), it behaves like a token bucket.
  • Fixed window counter: one counter per key per window, e.g. INCR rl:user42:10:01 with a 60 s expiry; reject when it exceeds the limit. Cheapest possible, but bursty at window edges: with a 100/min limit, a client can send 100 requests at 10:00:59 and 100 more at 10:01:00, so 200 in about one second, double the intended rate.
  • Sliding window log: store a timestamp per accepted request (a Redis sorted set), drop entries older than now - window, and allow if fewer than limit remain. Exact, with no edge burst, but memory grows with the limit: a 10,000 per hour limit can hold 10,000 entries for each key.

Sliding window counter

This hybrid keeps only two fixed-window counters, the current and the previous, and estimates the count over the true sliding window by weighting the previous window by how much of it still overlaps. Example: limit 100 per minute, previous minute had 80 requests, current minute has 30 so far, and we are 15 seconds (25%) into the current minute. The sliding window covers the last 75% of the previous minute, so the estimate is 80 x 0.75 + 30 = 90: allow, 10 left. It assumes the previous window's requests were spread evenly, so it is an approximation, but it removes the 2x edge burst at the memory cost of two integers.

python
import time

class SlidingWindowCounter:
    def __init__(self, limit, window_sec):
        self.limit = limit
        self.window = window_sec
        self.counts = {}                  # window_start -> count, keep 2

    def allow(self):
        now = time.time()
        cur_start = int(now // self.window) * self.window
        prev_start = cur_start - self.window
        cur = self.counts.get(cur_start, 0)
        prev = self.counts.get(prev_start, 0)
        # Fraction of the previous window still inside the sliding window
        overlap = 1 - (now - cur_start) / self.window
        estimated = prev * overlap + cur
        if estimated >= self.limit:
            return False
        self.counts = {prev_start: prev, cur_start: cur + 1}
        return True

In production
What real systems use
Amazon API Gateway documents token bucket throttling with a steady-state rate and a burst size. Stripe has described using token buckets backed by Redis for its API limits. Cloudflare has written about using the sliding window counter approximation for rate limiting at its edge, finding it accurate enough while keeping only two counters per key.

Where to enforce

  • Client side: polite SDKs throttle themselves and honor Retry-After, but clients can be modified, so this is never enforcement.
  • Edge (CDN, WAF): cheap, coarse limits by IP or fingerprint that stop floods before they reach your origin. Beware that many users can share one IP behind corporate NAT or mobile carrier-grade NAT.
  • API gateway or middleware: the main place, because it knows the authenticated identity, the plan tier and the route. Limit by API key or user id, not IP.
  • Inside services: limits that need business context, such as 3 password resets per hour per account or a per-tenant cap on expensive report queries, plus concurrency limits to protect a shared database.

Telling clients they are limited

http
HTTP/1.1 429 Too Many Requests
Content-Type: application/problem+json
Retry-After: 12
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1761127260

{ "type": "https://api.example.com/errors/rate-limited", "status": 429,
  "title": "Rate limit exceeded", "detail": "100 requests per minute for this API key." }
Tip
Headers on every response, not just the 429
Return X-RateLimit-Limit, -Remaining and -Reset (epoch seconds, as GitHub does) on successful responses too, so well-behaved clients slow down before hitting the wall. Retry-After (seconds or an HTTP date) is the standard header on 429. An IETF draft standardizes RateLimit and RateLimit-Policy headers. Use 429 for a client exceeding its quota and 503 when the server is shedding load for everyone.
In the interview
The opening interviewers want
Before choosing an algorithm, ask: limit by what key, what limits per tier, is a small overshoot acceptable, and what happens when the limiter itself is down. Then pick token bucket for burst plus sustained limits, or sliding window counter when you want smooth per-minute limits, and say the state lives in Redis and is updated atomically with a Lua script.
