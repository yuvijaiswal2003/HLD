Service discovery, API gateways and service mesh

With dozens of services running on hundreds of autoscaled, frequently replaced instances, IP addresses change all the time. Service discovery is how a caller finds a healthy instance of payment-service right now. It needs a service registry: a database of live instances, kept current by registration plus health checks.

Client-side discovery

Strengths
  • No extra network hop
  • Client can use smart balancing, such as least outstanding requests or zone-aware routing
Weaknesses
  • Discovery and balancing logic in every client, in every language
  • Clients must be upgraded to change behavior
Use whenNetflix Eureka with a client library; gRPC clients with built-in load balancing; anything with a sidecar proxy doing it for the app.

Server-side discovery

Strengths
  • Clients stay simple: call one stable name
  • Language agnostic, centrally managed
Weaknesses
  • Extra hop through the load balancer
  • The load balancer tier must itself scale and be highly available
Use whenAWS ALB or NLB in front of a target group; Kubernetes Services, where kube-proxy routes a stable virtual IP to pods.
  • Registries: Consul (health checks, DNS and HTTP interface, key-value store), Netflix Eureka (AP-leaning, favors availability over strict consistency), and etcd or ZooKeeper (strongly consistent, used underneath Kubernetes and older systems).
  • Registration: either the instance registers itself and heartbeats (self-registration), or the platform registers it (Kubernetes adds a pod to the Service's endpoints once its readiness probe passes).
  • DNS-based discovery is the simplest interface (payments.prod.svc.cluster.local), but clients and resolvers cache answers according to TTL and some runtimes cache longer than asked, so dead instances can receive traffic for a while. Use short TTLs and client retries on connection failure.

API gateway

An API gateway is the single entry point between external clients and internal services. It is a specialized reverse proxy (Chapter 2) that handles cross-cutting concerns once instead of in every service: TLS termination, authentication (validating JWTs or API keys), rate limiting, request routing by path or header, request and response transformation, caching, request IDs for tracing, and canary traffic splits. Common choices are Kong, AWS API Gateway, Apigee, and Envoy-based gateways.

A backend for frontend (BFF) is a gateway layer built for one client type. The iOS app's home screen needs a compact payload aggregated from 6 services; the web app wants richer data; a partner API needs stable, versioned resources. Instead of one gateway full of client-specific branches, each client team owns its BFF, which fans out to services in parallel and shapes the response for its client. GraphQL servers are often used as a BFF.

Pitfall
Keep business logic out of the gateway
A gateway that starts computing discounts or validating orders becomes a new monolith that every team must change and deploy. Gateways route and enforce policy; BFFs aggregate and shape; services own business rules.

Service mesh and sidecars

A gateway handles north-south traffic (clients into the system). A service mesh handles east-west traffic (service to service). Each service instance gets a sidecar proxy, usually Envoy, that intercepts all its inbound and outbound connections. The data plane (all the sidecars) does discovery, load balancing, retries, timeouts, circuit breaking, mutual TLS and telemetry. The control plane (Istio's istiod, Linkerd's control plane) pushes routing rules, certificates and policies to every sidecar.

Libraries in each service

Strengths
  • No extra hop or proxy process
  • Full control in application code
Weaknesses
  • Reimplemented per language, upgraded per service
  • Inconsistent behavior across teams
Use whenFew services in one or two languages.

Service mesh

Strengths
  • Uniform mTLS, retries, timeouts and telemetry with no app code changes
  • Traffic shifting for canaries and fault injection centrally
Weaknesses
  • Each hop adds a little latency, typically around a millisecond or less
  • Memory and CPU for a proxy per pod; a complex control plane to operate
Use whenMany services, many languages, and a zero-trust requirement for encrypted, authenticated service-to-service calls.
In the interview
Say where each concern lives
Interviewers like a crisp split: "Auth, rate limiting and routing at the edge gateway; aggregation per client in a BFF; retries, timeouts, mTLS and discovery between services in the mesh or a shared client library." It shows you know these are layers, not competing products.
