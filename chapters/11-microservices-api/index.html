Remember for the interview

  1. 01Start as a modular monolith; extract microservices only for a concrete reason such as independent scaling, team autonomy or a distinct reliability need.
  2. 02Split services by business capability and bounded context, not by technical layer, and give each service its own database reachable only through its API or events.
  3. 03Service discovery needs a registry kept current by health checks; client-side discovery saves a hop, server-side keeps clients simple.
  4. 04The API gateway handles north-south cross-cutting concerns (TLS, auth, rate limits, routing); BFFs shape responses per client; a service mesh handles east-west retries, timeouts and mTLS through sidecars.
  5. 05Make every non-idempotent create safe to retry with a client-generated Idempotency-Key stored atomically with the result.
  6. 06Use cursor (keyset) pagination for large or changing collections: it seeks via an index instead of scanning and discarding offset rows.
  7. 07Version with /v1 in the path, make only additive changes within a version, and return one consistent error format with a machine-readable code and request id.
  8. 08Token bucket allows bursts up to capacity with a sustained refill rate in two numbers per key; fixed windows allow 2x bursts at edges; sliding window counter approximates a true sliding window with two counters.
  9. 09Distributed rate limiting needs atomic check-and-update, typically a Redis Lua script, and an explicit fail-open or fail-closed decision.
  10. 10Reject with 429 plus Retry-After, and send limit, remaining and reset headers on every response.
