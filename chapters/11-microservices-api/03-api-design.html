API design best practices

An API is a contract that outlives the code behind it. Mobile apps stay installed for years, partners integrate once and never touch it again. Good API design is mostly about making the common case obvious, retries safe, large results cheap, and change possible without breaking anyone. REST over HTTP is the default for public APIs, so the conventions below use it; Chapter 2 covers REST vs GraphQL vs gRPC.

Resource naming

DoAvoidWhy
GET /users/42/ordersGET /getOrdersForUser?id=42Nouns for resources, HTTP methods for verbs
POST /orders to createPOST /orders/createThe method already says create
GET /orders?status=shippedGET /orders/shippedFilters are query parameters, not path segments
POST /orders/42/cancel for a real actionPATCH /orders/42 {status: cancelled} when cancel has side effectsState transitions with business rules deserve an explicit action resource
Plural collections, kebab or snake case, consistent everywhereMixing /user, /Orders, /line_itemsPredictability is the main usability feature

Idempotency keys

GET, PUT and DELETE are idempotent by definition; POST is not. If a client sends POST /payments, the connection drops, and it retries, did the customer pay once or twice? The fix: the client generates a unique Idempotency-Key (a UUID) per logical operation and sends it on every retry. The server stores the key with the result and, on a repeat, returns the stored response instead of executing again.

  1. Atomically claim the key
    INSERT INTO idempotency (key, user_id, request_hash, status) VALUES (..., 'in_progress') with a unique constraint on (user_id, key). If the insert conflicts, go to step 4.
  2. Do the work
    Charge the card, create the order. Ideally write the business row and the idempotency result in the same database transaction.
  3. Store the response
    Save the status code and body against the key and mark it complete. Keep keys for 24 hours or longer, longer than any client's retry window.
  4. Handle a repeat
    Complete: return the stored response. Still in progress: return 409 Conflict so the client retries later. Same key with a different request body: return 422, because the client reused a key by mistake.
In production
Stripe popularized the header
Stripe's API accepts an Idempotency-Key header on POST requests and returns the saved result for repeated keys, so clients can retry payment calls safely after timeouts. Many payment and fintech APIs copy this design.

Pagination: offset vs cursor

Offset pagination (?limit=20&offset=10000) is easy and allows jumping to page 500, but the database still reads and discards the first 10,000 rows, so deep pages get slow. It also skips or repeats items when rows are inserted or deleted between page requests. Cursor (keyset) pagination remembers where the last page ended and asks for rows after that position, which an index can seek to directly.

sql
-- Offset: scans and throws away 10,000 rows
SELECT id, created_at, title FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 10000;

-- Keyset: seeks straight to the position using an index on (created_at, id)
SELECT id, created_at, title FROM posts
WHERE (created_at, id) < ('2026-10-21 09:14:00', 98231)
ORDER BY created_at DESC, id DESC
LIMIT 20;
-- Return the last row's (created_at, id) base64-encoded as an opaque next_cursor

Offset

Strengths
  • Trivial to implement
  • Jump to any page; show total pages
Weaknesses
  • Cost grows linearly with the offset
  • Duplicates or gaps when data changes between requests
Use whenSmall, stable admin tables and search results limited to the first few pages.

Cursor / keyset

Strengths
  • Constant cost per page with the right index
  • Stable under concurrent inserts
  • Natural fit for infinite scroll and feeds
Weaknesses
  • No random page jumps
  • Needs a unique, sortable tie-breaker such as id
  • Cursor must be opaque so you can change it later
Use whenFeeds, timelines, message history, any large or fast-changing collection, and public APIs.

Versioning and evolution

  • Additive changes are free: a new optional field or a new endpoint breaks nobody, provided clients ignore unknown fields. Removing or renaming a field, changing a type, or tightening validation is breaking.
  • URL versioning (/v1/orders) is explicit, cache-friendly and easy to route at the gateway; it is the most common choice. Header versioning (Accept: application/vnd.acme.v2+json) or a date header (Stripe pins each account to an API version by date) keeps URLs stable but is less visible.
  • Bump the major version only for breaking changes, run versions side by side, announce deprecation with a Sunset header and a date, and watch per-version traffic before turning the old one off.

Errors, batching and webhooks

json
{
  "type": "https://api.example.com/errors/insufficient-funds",
  "title": "Insufficient funds",
  "status": 402,
  "detail": "Balance is 30.00 USD, payment requires 45.00 USD.",
  "code": "insufficient_funds",
  "request_id": "req_7Hc2kQ",
  "errors": [ { "field": "amount", "message": "exceeds available balance" } ]
}
  • Errors: use correct status codes (400 validation, 401 unauthenticated, 403 forbidden, 404, 409 conflict, 422, 429 rate limited, 5xx server), plus one consistent JSON body. RFC 9457 (Problem Details) defines the shape above. Include a machine-readable code clients can branch on and a request_id for support. Never leak stack traces.
  • Batching: POST /orders:batchGet with 100 ids, or a bulk create endpoint, saves round trips for mobile clients on high-latency networks. Define partial failure explicitly: return a result per item rather than failing the whole batch for one bad item, and cap batch size.
  • Webhooks: instead of partners polling, you POST events to their URL. Sign each payload with HMAC-SHA256 over the body and a timestamp so receivers can verify it and reject replays. Deliver at least once with exponential backoff for up to a day or more, include an event id so receivers can deduplicate, and offer a list-events endpoint to backfill missed deliveries. Receivers should respond 2xx quickly and process asynchronously.
In the interview
Small details that score points
When you write the API section in any design, add: an Idempotency-Key on every create that moves money or sends messages, cursor pagination on every list, and /v1 in the path. Saying "the next page is an opaque cursor encoding (created_at, id)" takes five seconds and signals real API experience.
