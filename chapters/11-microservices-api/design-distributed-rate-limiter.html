Design a distributed rate limiter

Design a rate limiting service for a public API platform served from three regions (us-east, eu-west, ap-south) by hundreds of gateway instances. Customers have per-API-key limits by plan (e.g. 100 requests per second sustained with bursts to 200 for Pro), plus per-endpoint limits and per-IP limits for unauthenticated traffic. The limiter must add very little latency and stay correct under concurrency.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • Which keys do we limit on: API key, user, IP, endpoint, tenant, or combinations, and how many distinct keys are active?
  • Are limits per region or global across all regions, and how much overshoot is acceptable for a global limit?
  • What latency budget can the limiter add per request (p99 under 1 to 2 ms?)
  • What is the total request rate at peak, and per region?
  • Do limits need burst allowance (token bucket) or smooth per-minute windows?
  • If the limiter's storage is down, should requests be allowed or rejected?
  • How quickly must a limit change (plan upgrade) take effect?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1Where does the counter live so that hundreds of gateway instances see the same value? Local memory alone is not enough.
H2Read the counter, compare, then write it back: what goes wrong when two gateways do that at the same moment?
H3Redis executes a Lua script atomically. Put the whole token bucket refill, check and update in one script, with one key per limited identity.
H4A global limit across regions cannot afford a 100 ms cross-region round trip per request. Consider splitting the limit per region, or syncing counts asynchronously and accepting small overshoot.
H5Decide explicitly what happens when Redis is unreachable, and add a small local in-memory limiter as a fallback and as a first filter for abusive keys.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: limit requests per API key, per key and endpoint, and per IP; configurable rules per plan with burst and sustained rates; return 429 with Retry-After and rate limit headers; rule changes take effect within seconds; support request cost weights (an export call costs 10 tokens).
  • Non-functional: added latency p99 under ~2 ms; no meaningful overshoot within a region under concurrency; global limits accurate within ~10%; highly available (the limiter must never be the reason the API is down); scales to 1M+ decisions per second.

Estimates

  • Peak traffic 1.5M requests/s across 3 regions, about 500k/s per region. Each request checks about 2 rules (key plus key and endpoint), so about 1M limiter operations/s per region.
  • A Redis primary handles on the order of 100k to 200k simple ops/s; a Lua script with a few commands is heavier, so plan about 50k to 80k script calls/s per shard. 1M/s per region needs about 15 to 20 shards; plan 24 with headroom, each with a replica.
  • Active keys: 5M API keys, about 1M active in any hour, times 2 to 3 rules = 3M buckets. Each token bucket is a small hash (tokens, last refill): about 100 bytes with Redis overhead, so 3M x 100 B = 300 MB per region. Memory is trivial; throughput sets the shard count.
  • Latency: same-AZ Redis round trip about 0.2 to 0.5 ms, so one pipelined call per request fits the 2 ms budget. A cross-region round trip (60 to 150 ms) does not, which shapes the multi-region design.

Redis fits because the state is tiny, hot, short-lived and can be lost occasionally without harm, and because Lua scripts give atomic read-modify-write in sub-millisecond time. Durability is deliberately weak: if a shard fails over and loses a second of counts, clients get a slightly more generous limit for a moment, which is acceptable.

High-level design

Request path: the gateway authenticates the API key, resolves its plan, and finds the matching rules from its in-memory rule cache. It sends one pipelined EVALSHA per rule (or one script covering all rules when the keys share a hash slot) to the regional Redis Cluster. If every rule allows, the request goes to the backend with the rate limit headers attached; if any rule denies, the gateway returns 429 immediately with Retry-After computed by the script. Config path: rules live in PostgreSQL, and changes are pushed to all gateways through a pub/sub channel, with a periodic full refresh as a backstop, so a plan upgrade applies within seconds.

Deep dive 1: atomicity and race conditions

The naive version is GET, compare in the gateway, then SET. Two gateways serving the same key at the same moment both read tokens = 1, both allow, and both write 0: two requests passed on one token. Across hundreds of gateways under a burst, overshoot can be many times the limit. Options: WATCH/MULTI/EXEC optimistic transactions (retries under contention, which is exactly when you are busy), or a Lua script, which Redis runs atomically on the shard owning the key: no other command interleaves. The script reads state, refills, decides, writes and sets the TTL in one round trip.

text
-- token_bucket.lua   KEYS[1] = bucket key
-- ARGV: capacity, refill_per_sec, cost
local cap  = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local cost = tonumber(ARGV[3])
local t    = redis.call('TIME')                       -- server clock, not gateway clock
local now  = tonumber(t[1]) + tonumber(t[2]) / 1000000
local s    = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(s[1]) or cap
local ts     = tonumber(s[2]) or now
tokens = math.min(cap, tokens + math.max(0, now - ts) * rate)
local allowed = 0
if tokens >= cost then tokens = tokens - cost  allowed = 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', KEYS[1], math.ceil(cap / rate * 2))
local retry = 0
if allowed == 0 then retry = (cost - tokens) / rate end
return { allowed, tostring(tokens), tostring(retry) }
  • Use the Redis server clock (TIME) so gateways with skewed clocks cannot over-refill a bucket. Since Redis 5, scripts replicate their effects rather than the script itself, so calling TIME inside a script that writes is safe.
  • One key, one shard: a script may only touch keys in one hash slot in Redis Cluster. Wrap the identity in a hash tag, rl:{apikey:ak_9f2}:rule, so all of a key's buckets live together and can be checked in one script call.
  • Load scripts once with SCRIPT LOAD and call EVALSHA, falling back to EVAL on a NOSCRIPT error after a failover.
  • Multiple rules: if the key rule allows but the endpoint rule denies, the first rule has already consumed a token. Either check all rules in one script and commit only if all pass, or accept that a denied request still costs a token, which is usually fine and simpler.

Deep dive 2: hot keys and the local pre-check

One abusive client sending 200k requests/s with one API key sends all of them to one Redis shard, which can saturate it and hurt every other key on that shard. Two defenses: first, once Redis says a key is over its limit, the gateway caches "denied until T" locally (T from retry_after), so further requests from that key in the next second never touch Redis. Second, for very high-limit keys (an enterprise key allowed 50k/s), give each gateway a local token lease: it takes a batch of, say, 100 tokens from Redis in one call and spends them in memory, returning to Redis only when the batch runs out. This cuts Redis traffic by about 100x at the cost of small overshoot (up to one batch per gateway) and slightly uneven fairness between gateways.

Deep dive 3: multiple regions

Per-region limits

Strengths
  • Every decision is local: sub-millisecond
  • Regions fully independent; a regional failure affects only that region
Weaknesses
  • A client spreading traffic across 3 regions gets up to 3x its limit
  • Static splits mismatch real traffic if a client is mostly in one region
Use whenDefault for protection limits, where the goal is protecting each region's capacity rather than enforcing a precise global quota.

Single global Redis

Strengths
  • Exact global counts
Weaknesses
  • 60 to 150 ms cross-region round trip added to every request in remote regions
  • Global outage if that region goes down
Use whenAlmost never on the request path.

Local enforcement plus async global sync

Strengths
  • Local latency with approximately global limits
  • Survives partitions: each region keeps enforcing on its last known view
Weaknesses
  • Overshoot during the sync interval, roughly the limit times interval times regions
  • More moving parts
Use whenPaid global quotas, such as 1M requests per day per customer, where about 1 to 5% overshoot is acceptable.

For the sync approach, each region counts usage per key locally and every second publishes per-key deltas to the other regions (through a replicated stream or a small sync service). Each region enforces against local_usage + last_known_remote_usage. A refinement is dynamic allocation: split a global budget into per-region shares proportional to recent traffic, and rebalance shares every few seconds. Avoid active-active Redis replication of counters with last-writer-wins, which loses increments; CRDT-based counters, such as a grow-only counter per region merged by summing, handle concurrent increments correctly.

Deep dive 4: failure handling

  • Fail open (allow when Redis is unreachable or times out after about 5 ms) for normal API limits: a limiter outage should not become an API outage. Behind it, keep a coarse per-instance in-memory token bucket set to (global limit / number of gateways) times a safety factor, so traffic is still roughly bounded.
  • Fail closed for limits that protect money or security: login attempts, OTP and SMS sends, gift card redemption. A brief outage there is cheaper than a brute-force or toll-fraud window.
  • Timeouts and circuit breaker on the Redis client: tight timeouts so a slow shard cannot stall the gateway, and a breaker that switches to the local fallback after repeated failures instead of paying the timeout on every request.
  • Replica failover loses at most the last moment of increments (Redis replication is asynchronous), which briefly loosens limits; acceptable for this data.

5Follow-up questions

  • How would you implement a concurrency limit (max 10 in-flight requests per key) rather than a rate limit, and how do you avoid leaked slots when a gateway crashes mid-request?
  • A customer upgrades from 100/s to 1,000/s. How do you make it take effect within 5 seconds across all regions?
  • How would you test that the limiter does not overshoot under 500 concurrent gateways?
  • How would you rate limit by cost, such as GPU seconds, when the cost is only known after the request finishes?
  • How would you prevent a limited client's retries from amplifying load, and what should the SDK do with Retry-After?
