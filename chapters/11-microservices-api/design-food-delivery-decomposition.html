Break a food-delivery monolith into microservices

A food-delivery company runs a 6-year-old Rails monolith with one large MySQL database. It handles customers, restaurants, menus, carts, orders, payments, courier dispatch and notifications. Deploys take 2 hours, a slow menu query took down checkout last month, and 150 engineers in 15 teams are blocked on each other. Propose the target service boundaries and a safe migration plan that keeps the business running.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • Which pain hurts most: deploy speed, reliability of checkout, scaling of a specific part, or team autonomy?
  • What is the order volume at peak, and which flows are latency sensitive (checkout, courier location)?
  • Which tables are shared by the most modules, and are there cross-module transactions today?
  • Is there a deadline or freeze period (e.g. no risky changes during festival season)?
  • Is there an existing platform: Kubernetes, CI/CD per service, tracing, Kafka?
  • Can we tolerate eventual consistency between, say, order status and restaurant dashboards?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1Map business capabilities first and see which modules change together. Which ones have very different scaling or reliability needs?
H2Do not extract everything at once. Which first extraction gives the biggest relief with the lowest coupling?
H3Use a routing layer in front of the monolith and move one capability at a time behind it.
H4Data is the hard part. How does a new service get its own copy of data that still lives in the monolith's MySQL?
H5Placing an order touches cart, payment, restaurant and dispatch. What replaces the single transaction?

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: no change in product behavior during migration; checkout, payment and dispatch keep working; each team can deploy its capability independently.
  • Non-functional: checkout isolated from failures of menu, search and notifications; independent deploys several times a day; zero data loss and no double charges during cutovers; each extraction reversible by flipping routing back.

Estimates

  • 2M orders/day, peak 4x average in the dinner hour: 2 x 10^6 / 10^5 = about 20 orders/s average, 80 orders/s peak.
  • Menu and restaurant browsing is about 100 reads per order: 2M x 100 = 200M reads/day, about 2k/s average and 8k/s peak. This read-heavy path is the one that took down checkout by sharing the database.
  • Courier location updates: 100k active couriers every 5 s at peak = 20k writes/s, a completely different workload from orders.
  • Each order produces about 10 status events (placed, accepted, picked up, delivered...): 20M events/day, about 230/s average, trivial for Kafka.

High-level design

Start by making the monolith a modular monolith internally: draw module boundaries along capabilities, and add a check in CI that fails when one module queries another module's tables. Then put the API gateway in front as a strangler layer, routing by path. Extract capabilities one at a time, in order of value and low coupling: Notifications first (consumes events, no one depends on it synchronously), then Menu (read heavy, the cause of the checkout outage), then Location and Dispatch (unique write workload), and only later Payments and Orders, the most coupled and the most sensitive.

Deep dives

Moving data out without a big bang. For the Menu extraction: create the new Menu DB, backfill it from MySQL, then keep it in sync with CDC (Debezium reading the MySQL binlog into Kafka). Switch reads to the new service behind a feature flag, compare responses in shadow mode, and ramp traffic 1%, 10%, 100%. Then move writes: the restaurant dashboard writes to the Menu service, which becomes the source of truth, and the monolith, which still needs menu data for order pricing, now consumes Menu events or calls the Menu API. Finally drop the menu tables from the monolith. At every step, rollback is a routing change.

Replacing the checkout transaction with a saga. Today one MySQL transaction creates the order, reserves the payment and marks the restaurant order. After extraction, an orchestrated saga in the Order service runs: create order (PENDING), then authorize payment, then send to restaurant, then on acceptance mark CONFIRMED, then request a courier. If the restaurant rejects or times out after 3 minutes, the saga issues compensations: void the payment authorization and mark the order CANCELLED. Each step is idempotent, keyed by order id, and the Order service publishes its events through a transactional outbox so the state change and the event are never out of sync. Sagas and outbox are covered in Chapters 8 and 9; here the point is that the business accepts short eventual consistency (the restaurant dashboard may show a new order a second later) in exchange for isolation.

Avoiding a distributed monolith. Order placement must not synchronously call 6 services in a chain. The Order service keeps a local, event-fed copy of what it needs (item prices, restaurant open or closed) via event-carried state transfer, calls Payment synchronously only because the user waits for authorization, and does everything else asynchronously. Every synchronous call gets a timeout, retry with backoff and a circuit breaker, so a Menu outage degrades browsing but checkout still works for users with items in their carts.

Trade-offs and bottlenecks

  • Pace: extract 3 to 5 services in the first year, not 40. Each extraction needs a platform (CI/CD, tracing, on-call) that must exist first.
  • Consistency: sagas bring intermediate states (order placed but payment pending) that the UI and support tooling must understand.
  • Duplicate data: event-fed copies of menu prices can be briefly stale; the Order service re-validates price at checkout and the Menu service versions prices.
  • Operational cost: more databases, more alerts, more network failure modes; offset by checkout isolation and independent deploys.
  • Leaving parts in the monolith is a valid end state: low-churn admin features may never justify extraction.

5Follow-up questions

  • How do you find the right boundary when two capabilities share a very hot table, like orders being read by 8 modules?
  • During the Menu cutover, how do you detect that the new service returns different results from the monolith?
  • How would you handle a payment authorized but the saga crashing before the restaurant is notified?
  • Which team owns the API gateway routes, and how do you stop it from becoming a bottleneck for all teams?
  • How do you run end-to-end tests when 15 teams deploy independently?
