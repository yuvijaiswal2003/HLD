MVCC, pessimistic and optimistic locking

Multi-version concurrency control

With MVCC, an update does not overwrite a row in place from the reader's point of view. The database keeps multiple versions tagged with transaction IDs, and each transaction reads the version visible to its snapshot. The headline benefit is that readers never block writers and writers never block readers. Two writers on the same row still serialize on a row lock. PostgreSQL, MySQL InnoDB, Oracle, CockroachDB and MongoDB's WiredTiger all use MVCC.

  • PostgreSQL writes each new version as a new tuple in the table heap, stamped with xmin and xmax transaction IDs. Old versions become dead tuples that VACUUM (usually autovacuum) reclaims. An UPDATE is effectively an insert plus marking the old tuple dead, which is why update-heavy tables bloat.
  • InnoDB updates the row in the clustered index and writes the previous version to the undo log. A reader with an older snapshot rebuilds the version it needs by walking undo records, and a purge thread discards undo once no snapshot needs it.
Pitfall
Long transactions are an MVCC tax on everyone
A session left idle in transaction, or a six-hour report on the primary, pins the oldest snapshot. PostgreSQL then cannot vacuum any row version that snapshot might need, so tables and indexes bloat. InnoDB's undo history grows and reads slow down. Set idle_in_transaction_session_timeout, and move long analytics to a replica or a warehouse.

Pessimistic locking: lock first, then change

SELECT ... FOR UPDATE locks the selected rows until the transaction ends, and other writers (and other FOR UPDATE readers) wait. Two modifiers are worth knowing. NOWAIT fails immediately instead of waiting, which is useful for 'someone else is booking this seat'. SKIP LOCKED skips rows that are already locked, which is the standard way to build a job queue on PostgreSQL or MySQL 8. Lock rows in a consistent order (for example ORDER BY id) to avoid deadlocks.

Optimistic locking: change, then check nobody else did

Take no lock. Read the row with a version number, and make the write conditional on the version being unchanged. If the update matches zero rows, someone else got there first: reload and retry, or tell the user. Over HTTP the same idea appears as an ETag plus If-Match header, answered with 412 Precondition Failed on conflict.

sql
-- 1. Atomic single statement: best for counters and stock
UPDATE items SET stock = stock - 1
 WHERE id = 7 AND stock >= 1;          -- 0 rows updated means sold out

-- 2. Pessimistic: lock the row, decide, write
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- application checks the balance
UPDATE accounts SET balance = balance - 30 WHERE id = 1;
COMMIT;

-- 3. Optimistic: conditional write on a version column
UPDATE products
   SET price = 1999, version = version + 1
 WHERE id = 42 AND version = 17;       -- 0 rows means a conflict: reload, retry

Pessimistic (FOR UPDATE)

Strengths
  • Conflicts wait instead of failing, so no wasted work
  • Simple to reason about for short critical sections
Weaknesses
  • Blocked writers add latency under contention
  • Deadlocks possible; never hold locks across user think time
Use whenShort transactions on hot rows where conflicts are likely: seat holds, balance checks.

Optimistic (version check)

Strengths
  • No locks held, so high concurrency when conflicts are rare
  • Works across HTTP requests and long edits
Weaknesses
  • Every conflict costs a retry or an error shown to the user
  • Under heavy contention retries pile up
Use whenLow-contention updates, forms and documents that humans edit, REST APIs with ETags.

Atomic statement

Strengths
  • One round trip, no explicit locks to manage
  • The condition and the write are checked together
Weaknesses
  • Only works when the logic fits in one SQL statement
  • Complex rules still need a transaction
Use whenCounters, inventory decrements, compare-and-set on a single row.

Matching the fix to the anomaly

ProblemCheapest reliable fix
Counter increments get lostUPDATE ... SET n = n + 1, or Redis INCR for very hot counters
Inventory goes negativeConditional atomic update with stock >= 1, then check the row count
Two people edit the same recordOptimistic version column, or ETag with If-Match
Write skew on rows that already exist (on-call rule)SELECT ... FOR UPDATE on the rows you read, or Serializable
Write skew through inserts (overlapping bookings)A unique constraint, a PostgreSQL exclusion constraint on time ranges, pre-created rows to lock, or Serializable
A report needs one consistent view of many tablesA read-only transaction at Repeatable Read (snapshot)
In the interview
Say why you picked the locking style
'Contention is low and the edit spans minutes of user time, so I use optimistic concurrency with a version column. Holding a row lock across an HTTP round-trip is not an option.' Or: 'Seat holds are short and highly contended, so I lock the exact seat rows with FOR UPDATE NOWAIT and fail fast.'
