Storage engines: B-trees versus LSM-trees

Under every database sits a storage engine that decides how bytes are laid out on disk. Two families dominate. B-tree engines update pages in place. Log-structured merge-tree (LSM) engines never modify files; they append and merge. That one choice largely decides a database's write throughput, read latency and disk usage.

B-tree engines

PostgreSQL, MySQL InnoDB, SQL Server, Oracle and MongoDB's WiredTiger (B-tree by default) belong here. A write appends to the WAL, modifies the page in the buffer pool, and later flushes the whole page to its fixed location: random I/O. A full page splits in two. Torn-page protection adds more writes (InnoDB's doublewrite buffer, PostgreSQL's full-page images after each checkpoint). So changing a 100-byte row can eventually cost a 16 KB page write plus log records. Reads are predictable: each key lives in exactly one place, one root-to-leaf path away.

LSM-tree engines

  1. Append to the commit log
    Each write is appended to a write-ahead log (Cassandra calls it the commit log) so it survives a crash. This is sequential I/O.
  2. Insert into the memtable
    The write goes into an in-memory sorted structure, often a skip list. Nothing is read first, and an update is just a newer entry.
  3. Flush to an SSTable
    When the memtable fills (RocksDB's default write buffer is 64 MB), it is frozen and written out sequentially as an immutable SSTable (sorted string table) with a sparse index and a Bloom filter.
  4. Compact in the background
    Compaction merge-sorts SSTables, keeps only the newest version of each key, and drops deleted data and expired tombstones. This is where the engine pays for its cheap writes.

Reads are the weak spot. A point lookup may have to check the memtable and several SSTables. Bloom filters make this cheap for keys a file does not contain: about 10 bits per key gives roughly a 1% false-positive rate, so most files are skipped without a disk read. Range scans cannot use Bloom filters and must merge iterators from every level, so they cost more than on a B-tree.

Deletes write a tombstone, a marker that hides older values until compaction removes both. Cassandra keeps tombstones for gc_grace_seconds (10 days by default) so that replicas which missed the delete do not bring the data back. A query that scans many tombstones is slow; Cassandra warns at 1,000 tombstones per query and aborts at 100,000 by default. Queue-like tables, where you insert and then delete, are a classic Cassandra anti-pattern for this reason.

Compaction strategies

The three amplifications

  • Write amplification: bytes written to disk divided by bytes the application wrote. It burns disk bandwidth and SSD endurance.
  • Read amplification: disk reads per query. It drives tail latency.
  • Space amplification: bytes on disk divided by live data size, inflated by stale versions, tombstones and half-empty pages.
  • You cannot minimize all three at once. Each engine and compaction strategy picks a point in that triangle, and that is the trade-off to state in an interview.

B-tree engine

Strengths
  • Fast, predictable point reads and range scans
  • Each key in one place, which makes range locks and transactions straightforward
  • Mature tooling: PostgreSQL, MySQL
Weaknesses
  • Random writes and page splits
  • A small row change rewrites a whole page
  • Fragmentation leaves pages partly empty
Use whenRead-heavy or mixed OLTP with transactions and secondary indexes: the default for most product databases.

LSM-tree engine

Strengths
  • Very high write throughput from sequential I/O
  • Compresses well because files are immutable and densely packed
  • No read before write
Weaknesses
  • Read amplification, mitigated by Bloom filters and compaction
  • Compaction uses CPU and I/O and can cause latency spikes
  • Tombstones and more tuning knobs
Use whenWrite-heavy workloads such as messages, events, metrics and IoT: Cassandra, ScyllaDB, HBase, RocksDB, CockroachDB's Pebble, TiKV.
In production
Facebook's MyRocks
Facebook built MyRocks, a RocksDB storage engine for MySQL, and moved its main user database to it. It reported roughly halving storage compared with compressed InnoDB and greatly reducing write amplification on flash. The SQL layer stayed the same; only the engine underneath changed.
In the interview
Why are Cassandra writes so fast?
Give the mechanism, then the bill: 'A write is a commit-log append plus a memtable insert. No page is read or rewritten in place. The cost shows up later as compaction I/O, read amplification across SSTables and tombstones, so I pick the compaction strategy to match the workload.'
