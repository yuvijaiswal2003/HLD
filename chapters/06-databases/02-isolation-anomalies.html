Isolation levels and the anomalies they prevent

Running transactions one at a time would be perfectly correct and far too slow. Databases let transactions overlap and offer isolation levels that trade correctness for concurrency. The SQL-92 standard defined four levels by three phenomena (dirty read, non-repeatable read, phantom). Real systems add two more anomalies that cause most production bugs: lost update and write skew.

The five anomalies

  • Dirty read: transaction B reads a row that A wrote but has not committed. If A rolls back, B acted on data that never existed.
  • Non-repeatable read (also called read skew): A reads a row, B commits an update to it, A reads it again and gets a different value. A report that sums balances during a transfer can see money missing.
  • Phantom: A runs a query with a condition (WHERE room = 5 AND day = 'Mon'), B inserts or deletes a matching row and commits, and A's rerun returns a different set of rows.
  • Lost update: two transactions read the same row, modify the value in application code, and write it back. The second write silently overwrites the first.
  • Write skew: two transactions read the same data, each makes a decision based on it, and each writes a different row. Each write is fine alone, but together they break an invariant. Double-booking a meeting room by inserting two overlapping reservations is write skew.

PostgreSQL. It accepts READ UNCOMMITTED but treats it as Read Committed, so dirty reads never happen. At Read Committed every statement sees a fresh snapshot. Its Repeatable Read is snapshot isolation: the whole transaction sees the snapshot taken at its first statement. If it tries to update a row that a concurrent transaction changed and committed, it fails with could not serialize access due to concurrent update (first updater wins), and the application must retry.

MySQL InnoDB. At Repeatable Read, plain SELECTs read from a snapshot fixed at the first read. But UPDATE, DELETE and SELECT ... FOR UPDATE do a current read of the latest committed row and lock it. Range scans take next-key locks (a record lock plus a lock on the gap before it), which block inserts into the scanned range. The consequence is that a plain SELECT followed by an UPDATE based on it can lose updates without any error. PostgreSQL would have raised one.

Serializable. PostgreSQL implements it as Serializable Snapshot Isolation (SSI, since version 9.1). Transactions run on snapshots as before, the engine tracks read-write dependencies, and it aborts one transaction with SQLSTATE 40001 when a dangerous pattern appears. That is optimistic: little extra blocking, but you must retry. InnoDB's Serializable turns plain SELECTs into shared-locking reads when autocommit is off, which is classic two-phase locking with more waiting and more deadlocks. CockroachDB defaults to Serializable. Oracle's level named SERIALIZABLE is really snapshot isolation and still allows write skew.

Pitfall
Repeatable Read is not one thing
The name means different guarantees in the ANSI standard, in PostgreSQL and in MySQL. Code that is safe on PostgreSQL Repeatable Read (lost updates abort) can silently lose updates on MySQL Repeatable Read. When isolation matters, name the database and the level together.
Tip
Always wrap transactions in a retry loop
At Serializable, and at PostgreSQL Repeatable Read, aborts are normal behavior, not errors. Retry on serialization failure (SQLSTATE 40001) and on deadlock (40P01 in PostgreSQL, error 1213 in MySQL) with a small backoff. Keep transactions short so retries are cheap, and never call an external API while holding a transaction open.
In the interview
How to talk about isolation
Name the anomaly, then the cheapest fix: 'Two users can both see seat F8 free and both insert a booking. That is write skew through a phantom, and Read Committed will not stop it. I would either lock the seat row with SELECT ... FOR UPDATE, rely on a unique constraint on (show_id, seat_id), or run this one transaction at Serializable with retries.'
