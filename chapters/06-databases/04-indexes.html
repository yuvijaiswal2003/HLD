Indexes: B-tree, hash, composite and covering

Without an index, finding rows means a full table scan. A 100-million-row table at 200 bytes per row is 20 GB; scanning it at about 1 GB/s takes about 20 seconds. An index is a separate data structure, kept sorted or hashed by some columns, that points to the matching rows. With one, the same lookup takes well under a millisecond when the index pages are in memory.

B-tree indexes

Almost every database index is a B+tree: a balanced tree of fixed-size pages (8 KB in PostgreSQL, 16 KB in InnoDB). Internal pages hold separator keys and child pointers. Leaf pages hold the keys in sorted order with a pointer to each row, and every leaf links to its neighbor. Equality lookups walk root to leaf. Range scans, ORDER BY and prefix matches find the first leaf and then follow sibling links.

~500Keys per 8 KB page (fan-out) for a small key
3 levelsEnough for ~125 million keys (500 cubed)
4 levelsEnough for ~60 billion keys
1 to 2Disk reads per lookup, since upper levels stay cached

Clustered versus heap tables. InnoDB stores each row inside the primary-key B-tree (a clustered index). Its secondary indexes store the primary key rather than a row address, so a secondary lookup walks two trees. That makes primary-key choice matter. Increasing keys (AUTO_INCREMENT, UUIDv7, Snowflake IDs, see Chapter 14) append at the right edge of the tree. Random UUIDv4 keys scatter inserts across the tree, causing page splits and cache misses, and they make every secondary index entry bigger. PostgreSQL stores rows in an unordered heap, and every index, including the primary key, points at a physical tuple location.

Hash indexes. A hash index maps hash(key) to a bucket, so equality lookups are O(1) on average. It cannot answer range queries, ORDER BY or prefix matches, because hashing destroys order. PostgreSQL has hash indexes (crash-safe since version 10), but B-trees are usually close enough that few people use them. Hashing shines in in-memory stores such as Redis and Memcached. InnoDB can also build an internal adaptive hash index over hot B-tree pages on its own (off by default since MySQL 8.4).

Composite indexes and the leftmost-prefix rule

An index on (a, b, c) is sorted by a, then by b within equal a, then by c. Think of a phone book sorted by last name, then first name: you can find every Smith, or John Smith, but not every John. The index can seek on any leftmost prefix of its columns. Once a column is used for a range, the columns after it can only filter rows, not narrow the seek.

Query on an index over (tenant_id, status, created_at)Index used?Why
WHERE tenant_id = 7YesLeftmost column
WHERE tenant_id = 7 AND status = 'open'YesTwo-column prefix
WHERE tenant_id = 7 AND status = 'open' ORDER BY created_at DESC LIMIT 20Yes, with no sort stepRows are already in created_at order within the prefix, so it reads 20 entries and stops
WHERE tenant_id = 7 AND created_at > now() - interval '1 day'PartlySeeks on tenant_id; status is skipped, so created_at can only filter inside that tenant's range
WHERE status = 'open'Usually noNot a prefix. MySQL 8 skip scan helps only when tenant_id has few distinct values
Tip
Ordering columns in a composite index
Put equality columns first, then the column you sort by, then range columns (MongoDB documents this as the ESR rule, and it applies to B-trees generally). Among equality columns, lead with the one most queries filter on, so the index serves as many queries as possible.

Covering indexes

If an index contains every column a query needs, the database answers from the index alone and never visits the table. PostgreSQL shows this as an Index Only Scan (it works best on recently vacuumed tables, because it checks a visibility map). MySQL shows Using index in EXPLAIN. PostgreSQL 11+ and SQL Server can INCLUDE extra payload columns in the leaf entries without making them part of the sort key.

sql
-- Hot query: a customer's 10 most recent orders
SELECT status, total FROM orders
 WHERE customer_id = 42
 ORDER BY created_at DESC
 LIMIT 10;

-- Seek by customer, rows already in date order, payload in the index:
CREATE INDEX orders_customer_recent
    ON orders (customer_id, created_at DESC)
    INCLUDE (status, total);
-- EXPLAIN: Index Only Scan using orders_customer_recent ... rows=10

Indexes are not free

  • Write cost. Every INSERT touches every index, so a table with 5 secondary indexes does about 6 B-tree writes per insert. InnoDB updates a secondary index only when its columns change. PostgreSQL is harsher: unless an update qualifies as a cheap HOT (heap-only tuple) update, which requires that no indexed column changed and the page has room, it adds a new entry to every index on the table.
  • Space and memory. Indexes can rival the table in size, and they compete for the buffer pool. The hot part of every index should fit in RAM.
  • Low selectivity. An index on a boolean or a three-value status rarely helps on its own. Use a partial index, for example CREATE INDEX ON jobs (run_at) WHERE status = 'pending'.
  • Find dead weight. PostgreSQL pg_stat_user_indexes.idx_scan and MySQL sys.schema_unused_indexes show indexes nobody reads.

Other index types worth naming: GIN for JSONB, arrays and full-text search in PostgreSQL; GiST for geometry and range types (and exclusion constraints); BRIN, a tiny per-block min/max summary, for huge append-only tables ordered by time; and expression indexes such as lower(email).

In the interview
Every table you draw should come with its indexes
When you write a schema in an interview, list each index next to the query it serves: '(user_id, created_at DESC) for the profile timeline; unique (email) for login.' It shows you think about access patterns, and it heads off the 'how is this query fast?' follow-up.
