Design storage for an IoT time-series platform

Design the storage layer for an industrial IoT platform. One million devices each report 10 metrics (temperature, vibration, power and so on) every 10 seconds. Customers view live dashboards, chart any device over any time range, and run fleet-wide aggregates per site. Raw data must be kept for 30 days and summaries for 5 years.

45:00Mock interview timer. Start it when you begin talking.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • Exactly how many devices, metrics per device and seconds between readings? Do these grow?
  • Which queries matter most: one device's recent data, fleet aggregates, or exports?
  • What resolution is needed for old data: is a 1-hour average enough after 90 days?
  • Can devices buffer offline and send data hours late or out of order?
  • Are readings ever corrected or deleted, for example for GDPR or bad sensors?
  • Is real-time alerting part of this system, or does it consume from the same stream?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1Compute points per second and bytes per day before choosing anything; the numbers decide the design.
H2The workload is append-only and time-ordered. Which storage engine family loves that, and which one fights it?
H3Sort the data by (device, metric, time), use time-series compression codecs, and partition by day so retention becomes a cheap partition drop instead of millions of deletes.
H4Build rollups at ingest time, not at query time. Store sum and count, not average, so rollups can be rolled up again correctly.
H5Put a durable log such as Kafka in front, so reconnect storms are absorbed and writes can be batched and replayed.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: ingest readings; chart one device's metric over any range; fleet aggregates by site and metric; latest value per device for live dashboards; raw data for 30 days, 5-minute rollups for 90 days, hourly rollups for 5 years.
  • Non-functional: sustain 1M points/s with 3x burst headroom; no loss of acknowledged data; chart queries p99 under 500 ms; storage cost dominated by compression ratio; tolerate late data up to 24 hours.

Estimates

text
Ingest
  1M devices x 10 metrics / 10 s     = 1M points/s (100k messages/s of 10 metrics)
  per day: 1M x 86,400               = 86.4B points/day
  network: 100k msg/s x ~200 B       = ~20 MB/s

Raw storage, 30 days
  naive 16 B/point (8 B time + 8 B float) = ~1.4 TB/day before tags and overhead
  with delta-of-delta time + XOR floats, budget ~2 B/point
                                     = ~170 GB/day x 30 = ~5.2 TB, x2 replicas = ~10 TB

Rollups (10M series; 4 values each: min, max, sum, count)
  5-minute: 30 raw points -> 4 values = ~13% of raw = ~23 GB/day x 90 days = ~2 TB
  hourly: 360 raw points -> 4 values  = ~1.1% of raw = ~1.9 GB/day x 5 years = ~3.5 TB

Total ~11 TB logical, ~22 TB with 2 replicas: a modest cluster, if compression holds.

Data model

The data is append-only, time-ordered and read by series and time range: a textbook case for an LSM-style, time-partitioned, compressed store, not for B-tree page updates. At 1M points/s we need horizontal write scaling, so we use ClickHouse. Its MergeTree engine writes immutable sorted parts and merges them in the background, LSM-style. It supports per-column compression codecs, day partitions for retention, and materialized views for rollups. Device metadata (owner, site, model) lives in PostgreSQL, and the latest value per device lives in Redis.

sql
CREATE TABLE readings (
  device_id UInt64,
  metric    LowCardinality(String),
  ts        DateTime CODEC(DoubleDelta, ZSTD),   -- regular intervals compress to almost nothing
  value     Float64  CODEC(Gorilla, ZSTD)        -- XOR float encoding from the Gorilla paper
) ENGINE = MergeTree                             -- ReplicatedMergeTree in production
PARTITION BY toDate(ts)                          -- one partition per day
ORDER BY (device_id, metric, ts)                 -- a series is contiguous on disk
TTL ts + INTERVAL 30 DAY                         -- expired days are dropped as whole parts
SETTINGS ttl_only_drop_parts = 1;

CREATE TABLE readings_5m (
  device_id UInt64, metric LowCardinality(String), bucket DateTime,
  min_v SimpleAggregateFunction(min, Float64),
  max_v SimpleAggregateFunction(max, Float64),
  sum_v SimpleAggregateFunction(sum, Float64),
  cnt   SimpleAggregateFunction(sum, UInt64)
) ENGINE = AggregatingMergeTree
PARTITION BY toYYYYMM(bucket) ORDER BY (device_id, metric, bucket)
TTL bucket + INTERVAL 90 DAY;

CREATE MATERIALIZED VIEW readings_5m_mv TO readings_5m AS
SELECT device_id, metric, toStartOfFiveMinutes(ts) AS bucket,
       min(value) AS min_v, max(value) AS max_v, sum(value) AS sum_v, count() AS cnt
FROM readings GROUP BY device_id, metric, bucket;

High-level design

Write path: gateways authenticate devices and publish to Kafka keyed by device_id, and return 202 once Kafka acknowledges, which makes the write durable. Batch writers consume about one second of data at a time and insert it in large blocks (ClickHouse prefers tens of thousands of rows per insert over many tiny ones). Materialized views update the 5-minute rollups as each block lands, and a second view from the 5-minute table feeds the hourly table. A separate consumer keeps the latest reading per device in a Redis hash for live tiles. Read path: the query service picks a resolution from the requested range (raw under 6 hours, 5-minute under 7 days, hourly beyond that), so every chart scans at most a few thousand points per series.

Deep dive 1: why this engine and layout

ClickHouse (chosen)

Strengths
  • Columnar codecs reach about 1 to 2 bytes per point
  • Built-in rollups through materialized views, plus partition-drop retention
  • Fleet-wide GROUP BY queries are fast
Weaknesses
  • Prefers large batches, so a buffer such as Kafka is required
  • Updates and deletes are heavy, asynchronous operations
Use whenOur scale: 1M points/s with both per-device and fleet-wide queries.

TimescaleDB

Strengths
  • Plain PostgreSQL: SQL joins with the device registry
  • Compression and continuous aggregates built in
Weaknesses
  • Write scaling is bounded by a single primary node
Use whenAround 10x smaller scale, where one strong node is enough and simplicity wins.

Cassandra or ScyllaDB

Strengths
  • Linear write scaling
  • Time-window compaction with TTL drops whole SSTables
Weaknesses
  • Generic block compression (LZ4 or Zstd), so several times more bytes per point
  • No built-in downsampling, so you need a separate stream job
Use whenWhen you already run it and need only per-device reads.

Sorting by (device_id, metric, ts) makes each series contiguous, so a 24-hour chart for one device reads a few compressed blocks. The repeated device_id and metric values compress to almost nothing, timestamps 10 seconds apart compress with DoubleDelta to a fraction of a byte, and slowly changing floats compress well with Gorilla XOR encoding. Validate the 2-bytes-per-point budget on real data early, because noisy sensors compress worse, and the whole storage estimate rests on that number.

Deep dive 2: retention, rollups and late data

  • Retention without tombstones: with day partitions and TTLs, expiry drops whole parts. Deleting 86 billion rows a day one by one would be ruinous in any engine; in Cassandra it would also mean tombstones.
  • Composable rollups: store min, max, sum and count. Average is sum / count at query time, which stays correct when 5-minute buckets are rolled into hours or across devices. Averaging averages is wrong when counts differ.
  • Merges are eventual: the rollup table may briefly hold several partial rows per bucket, so queries re-aggregate with min(min_v), sum(sum_v) / sum(cnt) and so on.
  • Late data: a device that was offline for 3 hours sends old timestamps. The rows land in the correct day partition and the materialized view adds a partial row for the old bucket, so rollups self-correct. Reject data older than the 24-hour window, or route it to a backfill job.
  • Fleet aggregates: a third materialized view keyed by (site_id, metric, bucket) pre-aggregates per site, so a site dashboard does not scan thousands of device series.

Deep dive 3: ingest durability and bursts

When a factory's network recovers, thousands of devices flush buffered data at once. Kafka absorbs the spike, and the batch writers drain it at the store's pace; at 20 MB/s, 24 hours of retention is about 1.7 TB per replica. Writers commit Kafka offsets only after the insert succeeds (at-least-once). A retry re-sends the identical block, and ClickHouse's replicated tables discard an identical re-inserted block, so retries do not double count. Keep tags low-cardinality: a free-form tag such as a request ID multiplies the number of series, which is the classic way time-series systems fall over.

5Follow-up questions

  • A customer wants alerts within 5 seconds when vibration crosses a threshold. Where does that run, and why not query the store?
  • Tag cardinality explodes because firmware starts sending a per-boot UUID as a tag. How do you detect and contain it?
  • A bug corrupted 5-minute rollups for the last two weeks. How do you rebuild them without stopping ingest?
  • How do you isolate tenants so one customer's backlog flush does not slow everyone else's dashboards?
  • Regulators require deleting one device's data on request. How do you do that in an append-only, partitioned store?
