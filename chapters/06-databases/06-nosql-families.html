NoSQL families and what each is for

NoSQL is an umbrella term for non-relational stores. Many grew out of Google's Bigtable paper (2006) and Amazon's Dynamo paper (2007), built to scale horizontally across commodity machines and to hold data that did not fit rigid schemas. Each family is optimized for a particular access pattern and gives up something to get there, usually joins, ad-hoc queries or multi-row transactions.

Key-value: DynamoDB

DynamoDB is a managed key-value and document store. Every item has a partition key, which picks the internal partition, and an optional sort key. Items sharing a partition key are stored sorted by sort key, so Query can fetch ranges such as 'all orders for user 42 in March' in a single request. It offers single-digit-millisecond latency, items up to 400 KB, global secondary indexes (always eventually consistent) and local secondary indexes, and reads that are eventually consistent by default with an opt-in strongly consistent mode. Multi-item ACID writes are available through TransactWriteItems. You model around access patterns up front, often with several entity types in one table.

Document: MongoDB

MongoDB stores BSON documents (up to 16 MB each) in collections, with rich secondary indexes and an aggregation pipeline. It has supported multi-document ACID transactions since 4.0 on replica sets and 4.2 on sharded clusters. Model data that is read together as one document. Do not embed unbounded arrays, such as every comment on a viral post; those belong in their own collection.

json
{
  "_id": "order_8812",
  "user_id": 42,
  "status": "shipped",
  "placed_at": "2026-03-14T10:22:00Z",
  "shipping_address": { "city": "Pune", "zip": "411001" },
  "items": [
    { "sku": "KB-104", "qty": 1, "price_cents": 4999 },
    { "sku": "MS-220", "qty": 2, "price_cents": 1999 }
  ],
  "total_cents": 8997
}

Wide-column: Cassandra and friends

In Cassandra, ScyllaDB, HBase and Bigtable, the partition key decides which nodes own the data, and clustering columns keep rows sorted inside a partition. You design one table per query (query-first modeling) and accept duplicated data across tables. Writes are cheap because the engine is an LSM-tree. Keep partitions bounded, with a common rule of thumb of under about 100 MB, by adding a time bucket to the partition key.

sql
-- CQL: one partition per channel per time bucket, newest messages first
CREATE TABLE messages (
  channel_id  bigint,
  bucket      int,        -- e.g. 10-day window number, bounds partition size
  message_id  bigint,     -- time-sortable Snowflake ID
  author_id   bigint,
  body        text,
  PRIMARY KEY ((channel_id, bucket), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
In production
Discord's message store
Discord stored messages in Cassandra, partitioned by channel and a time bucket and clustered by Snowflake message ID, which is essentially the table above. As the cluster grew to trillions of messages, garbage-collection pauses and hot partitions hurt latency, and in 2022 it migrated to ScyllaDB, a Cassandra-compatible engine written in C++.

Graph, time-series and search

Graph databases such as Neo4j make a traversal cost proportional to the neighborhood visited, not to the total graph size. They fit fraud rings, recommendations and knowledge graphs, queried with languages like Cypher. Note that most social products do not use a graph database for the social graph. Facebook's TAO is a graph-shaped cache over sharded MySQL, because nearly all queries are one hop.

Time-series databases exploit append-only, time-ordered writes. TimescaleDB, a PostgreSQL extension, splits a hypertable into time chunks, compresses old chunks and maintains continuous aggregates. InfluxDB and Prometheus are purpose-built engines. Typical tricks are delta-of-delta timestamps and XOR-encoded floats (Facebook's Gorilla paper reported about 1.37 bytes per point), retention by dropping whole chunks, and downsampling old data. The limit is usually cardinality, the number of distinct series.

Search engines such as Elasticsearch and OpenSearch (built on Lucene) maintain an inverted index for full-text relevance and facets. New documents become searchable after a refresh, one second by default, so they are near-real-time. They are usually fed from the primary database through change data capture rather than being the system of record. Chapter 10 covers their internals.

Pitfall
Two myths to avoid
'NoSQL is schemaless': the schema moved into your code, and migrations become application logic. 'SQL does not scale': YouTube and Slack run sharded MySQL through Vitess, and distributed SQL databases (Spanner, CockroachDB, TiDB, YugabyteDB) shard automatically with serializable transactions. Choose by access pattern and consistency needs, not by slogan.
