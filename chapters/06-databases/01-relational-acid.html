The relational model, transactions and ACID

A relational database stores data in tables (relations). Each table has a fixed set of typed columns, each row is identified by a primary key, and rows in different tables point at each other with foreign keys. You query with SQL, which is declarative: you say which rows you want, and the query planner decides how to get them (which index, which join order, scan or seek).

Relational databases have been the default for decades for three reasons. Joins let you store each fact once and combine facts at read time. Constraints (NOT NULL, UNIQUE, FOREIGN KEY, CHECK) enforce invariants in one place instead of in every service. And transactions let several changes succeed or fail together. PostgreSQL and MySQL (with its InnoDB engine) are the two you will name most often in interviews.

Transactions

A transaction groups statements into one unit of work between BEGIN and COMMIT. If anything fails before the commit, ROLLBACK (explicit or automatic) undoes every change in the unit. A money transfer is the classic case: the debit, the credit and the ledger entry must all happen, or none of them.

sql
CREATE TABLE accounts (
  id       bigint PRIMARY KEY,
  owner_id bigint NOT NULL REFERENCES users(id),
  balance  numeric(12,2) NOT NULL CHECK (balance >= 0)
);

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- CHECK rejects overdraft
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
INSERT INTO ledger (from_id, to_id, amount) VALUES (1, 2, 100);
COMMIT;  -- all three changes become visible together, or none do

ACID, one letter at a time

PropertyWhat it promisesHow the database delivers itWhat it does not mean
AtomicityAll of a transaction's writes happen, or none do, even across a crashWrite-ahead log plus undo information; incomplete transactions are rolled back on recoveryNothing about concurrency; that is isolation
ConsistencyA transaction takes the data from one valid state to anotherConstraints and foreign keys; everything else is your application logicNot the C in CAP, which means linearizability (Chapter 8)
IsolationConcurrent transactions do not see each other's half-done workLocks, MVCC snapshots and conflict detection, to the degree the isolation level promisesNot full serializability by default in most databases
DurabilityOnce COMMIT returns, the change survives a crash or power lossThe commit record is fsynced to the log before the client gets OKNot protection against losing the disk; that needs replicas and backups

How durability works: the write-ahead log

Writing every changed 8 KB page to its home on disk at commit time would be slow and full of random I/O. Instead the engine changes pages in memory (the buffer pool) and appends a compact description of the change to a write-ahead log (PostgreSQL calls it the WAL, InnoDB the redo log). At commit it fsyncs the log, which is a sequential append. Dirty pages are written to the data files later, at checkpoints. After a crash, the engine replays the log from the last checkpoint. Group commit lets many concurrent transactions share one fsync, which is how a single primary sustains thousands of commits per second.

Pitfall
Durability knobs that quietly trade safety for speed
PostgreSQL synchronous_commit = off acknowledges before the WAL fsync, so a crash can lose the last fraction of a second of commits (up to three times wal_writer_delay, about 600 ms by default), with no corruption. MySQL innodb_flush_log_at_trx_commit = 2 or 0 flushes about once per second, so an OS crash or power loss can lose about a second. These are fine for clickstream data and wrong for payments. Also remember that single-node durability does not survive losing the machine; that takes synchronous replication (Chapter 7).
In the interview
Name the invariant, not just the database
Saying 'use PostgreSQL for payments' earns little. Saying 'the debit, credit and ledger insert run in one transaction, and CHECK (balance >= 0) stops overdrafts even if two withdrawals race' shows you know what the transaction actually buys you.
