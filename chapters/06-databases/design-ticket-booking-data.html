Design the data layer for a movie ticket booking system

Design the data layer for a movie ticket booking service like BookMyShow or Fandango. Users browse shows, pick specific seats on a seat map, hold them for a few minutes while they pay, and receive a confirmed booking. The hard requirement: a seat must never be sold twice, even when thousands of people rush a blockbuster's opening show.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • Do users pick specific seats, or is it general admission with a count?
  • How long should a seat hold last before it is released, and can it be extended?
  • What is the peak: how many people hit the most popular show in the first minute of sales?
  • Are seats also sold through other channels, such as the cinema box office or partner apps?
  • How does payment work: authorize then capture, and who handles refunds?
  • Must the seat map be exactly up to date, or is a second or two of staleness acceptable?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1Find the exact moment two users can collide, and name the anomaly. Why does 'check the seat is free, then insert a booking' fail at Read Committed?
H2Give the conflict a row to lock: pre-create one row per seat per show when the show is scheduled.
H3Claim seats with a statement that checks and writes in one step, such as SELECT ... FOR UPDATE NOWAIT in seat order, or a conditional UPDATE whose row count you check.
H4Model the hold as a held_until column. Confirmation succeeds only if the hold is still yours and unexpired, and the booking call carries an idempotency key.
H5Seat-map reads vastly outnumber holds. Cache them and accept slight staleness, because the write path re-checks everything.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: list shows; view a seat map with live-ish availability; hold 1 to 10 seats for 10 minutes; confirm with payment; cancel.
  • Non-functional: zero double bookings (strong consistency on seat inventory); hold or confirm p99 under 300 ms; seat map p99 under 200 ms; booking path available at 99.95%; survive opening-day spikes of 50x average.

Estimates

text
Inventory
  3,000 screens x 5 shows/day x 250 seats = 3.75M show-seat rows per day
  scheduled 7 days ahead                  = ~26M live rows x ~100 B = ~2.6 GB (fits in RAM)

Bookings
  2M bookings/day, 2.5 seats each
  average  = 2M / 86,400        = ~23 bookings/s
  peak 50x                      = ~1,200 hold attempts/s system-wide
  storage  = 2M x ~300 B        = ~600 MB/day = ~220 GB/year

Seat-map reads
  ~10 seat-map views per booking = 20M/day = ~230/s average, ~12k/s at peak

Conclusion: one PostgreSQL primary handles the write volume. The hard parts are
correctness under contention on a single show, and read scale for seat maps.

API

http
GET  /v1/shows/{show_id}/seats
     -> 200 { seats: [ { id: "F7", status: "available", price_cents: 25000 }, ... ] }

POST /v1/shows/{show_id}/holds          { "seat_ids": ["F7", "F8"] }
     -> 201 { hold_id, expires_at }   |   409 { unavailable: ["F8"] }

POST /v1/bookings                        Idempotency-Key: 6f1c...
     { "hold_id": "...", "payment_token": "..." }
     -> 201 { booking_id, status: "confirmed" }   |   410 hold expired

DELETE /v1/holds/{hold_id}              -> 204 (user backed out)

Data model

PostgreSQL, because the core operation is a multi-row invariant (all requested seats or none, never two owners) that needs transactions, row locks and constraints. Static catalog data (movies, cinemas, screens, seat layouts) lives in ordinary normalized tables. The key table is show_seats: one pre-created row per seat per show, which gives every potential conflict a row to lock.

sql
CREATE TABLE show_seats (
  show_id     bigint NOT NULL REFERENCES shows,
  seat_id     text   NOT NULL,                      -- 'F7'
  price_cents int    NOT NULL,
  status      text   NOT NULL DEFAULT 'available'
              CHECK (status IN ('available', 'held', 'booked')),
  hold_id     uuid,
  held_until  timestamptz,
  booking_id  bigint,
  PRIMARY KEY (show_id, seat_id)                    -- also serves the seat-map query
);
CREATE INDEX show_seats_expiring ON show_seats (held_until)
  WHERE status = 'held';                            -- small partial index for the sweeper

CREATE TABLE bookings (
  booking_id      bigint PRIMARY KEY,
  user_id         bigint NOT NULL,
  show_id         bigint NOT NULL,
  status          text   NOT NULL,                  -- confirmed, cancelled, refunded
  amount_cents    int    NOT NULL,
  idempotency_key text   UNIQUE,                    -- retried POST returns the same booking
  created_at      timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON bookings (user_id, created_at DESC); -- 'my bookings' page

High-level design

Read path: the seat map is read from Redis, which is populated from a replica with a 2-second TTL. Availability shown to users can be slightly stale, which is acceptable because the hold transaction re-checks every seat. Hold path: one short transaction on the primary locks the requested seat rows, verifies they are all available (or holding an expired hold), and marks them held for 10 minutes. Confirm path: authorize the payment, then in one transaction flip the held seats to booked and insert the booking, then capture the payment. Booking events flow out through CDC to ticketing and email.

Deep dive 1: making double booking impossible

ApproachVerdict
Check with SELECT, then INSERT a booking, at Read CommittedBroken. Two transactions both see F8 free and both insert. This is write skew through a phantom.
Unique constraint on (show_id, seat_id) in a booked-seats tableCorrect, and a good safety net, but it cannot model temporary holds by itself
SELECT ... FOR UPDATE NOWAIT on pre-created seat rowsChosen. Locks the exact rows, fails fast under contention, works at Read Committed
Conditional UPDATE ... WHERE status = 'available', then check the row countAlso correct in one statement; PostgreSQL re-checks the WHERE clause after waiting on a row lock
Run the transaction at SerializableCorrect, but on a hot show many transactions abort and retry, which wastes work
Seat locks in Redis with SET NXFast, but creates a second source of truth; useful only as a front-line filter
sql
BEGIN;  -- Read Committed is enough: we lock exactly the rows we check
SELECT seat_id FROM show_seats
 WHERE show_id = 991 AND seat_id IN ('F7', 'F8')
   AND (status = 'available' OR (status = 'held' AND held_until < now()))
 ORDER BY seat_id          -- same lock order everywhere: no deadlocks
 FOR UPDATE NOWAIT;        -- another user mid-hold: error now, not a wait
-- app: if fewer rows than requested, ROLLBACK and return 409
UPDATE show_seats
   SET status = 'held', hold_id = 'a1b2...', held_until = now() + interval '10 minutes'
 WHERE show_id = 991 AND seat_id IN ('F7', 'F8');
COMMIT;

Deep dive 2: holds, expiry and payment

  • The hold is just columns, so no extra system is needed. Expired holds are treated as available by the hold query itself (lazy expiry), and a sweeper uses the partial index to reset them every few seconds so the seat map stays accurate.
  • Confirmation is conditional: UPDATE show_seats SET status = 'booked', booking_id = ? WHERE hold_id = ? AND status = 'held' AND held_until > now(). If the row count is less than the seat count, the hold expired and someone may have taken a seat, so void the payment authorization and return 410.
  • Always use the database's now() for hold timing, never application server clocks, so every decision uses one clock.
  • The Idempotency-Key is stored with a unique constraint, so a client that retries after a timeout gets the same booking back instead of paying twice. Capture the payment only after the confirm transaction commits.

Deep dive 3: hot shows and growth

Contention is per seat, not per show, so a 250-seat show can only have 250 concurrent winners, and losers fail fast with NOWAIT instead of queueing. The real flood is seat-map reads, which Redis and replicas absorb. If the business grows past what one primary can handle, shard by cinema_id (Chapter 7). Every row of a show then lives on one shard, so hold and confirm stay single-shard transactions with no distributed commit. For extreme on-sale events, put a virtual waiting room in front (Chapter 17).

Trade-offs and bottlenecks

  • Pre-creating show_seats rows costs about 2.6 GB of live rows but turns write skew into simple row locking. That is cheap insurance.
  • NOWAIT gives a fast 409 and a better experience than lock queues, but a user can lose a seat to a hold that later expires. The seat map refreshes within seconds.
  • A stale seat map (up to 2 s) causes some 409s on hold. That is acceptable because the write path is authoritative.
  • A single primary is a write single point of failure: use synchronous replication to a standby in another zone, with automatic failover (Chapters 7 and 12).
  • Serializable everywhere would also be correct, but it costs retries under contention; targeted row locks keep the hot path predictable.

5Follow-up questions

  • How would you implement 'best available' to find 4 adjacent seats while hundreds of users race for the same rows?
  • The cinema's box office sells from its own legacy system. How do you keep both channels from selling the same seat?
  • Payment was captured but the confirm transaction failed because of a timeout. How do you detect and reconcile that?
  • Would you ever run the booking transaction at Serializable? What would you monitor if you did?
  • How does the design change for general-admission events with 50,000 identical tickets?
