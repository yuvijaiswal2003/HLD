ACID vs BASE, normalization, and choosing a database

ACID versus BASE

BASE stands for Basically Available, Soft state, Eventually consistent. It describes the stance of many early NoSQL stores: keep accepting reads and writes during failures, let replicas disagree for a while, and converge later. Conflict handling moves to the application. ACID describes the opposite stance: strong per-transaction guarantees, even if that sometimes means waiting or refusing a request.

ACID

Strengths
  • Invariants enforced by the database
  • Simple mental model for developers
  • Multi-row transactions
Weaknesses
  • Coordination costs latency, especially across regions
  • Harder to scale writes beyond one primary without distributed SQL
Use whenMoney, inventory, bookings, identity: anything where a wrong answer is worse than a slow one.

BASE

Strengths
  • Stays writable through node and network failures
  • Low latency and linear horizontal scale
Weaknesses
  • Readers may see stale or conflicting data
  • The application must handle conflicts and retries
Use whenFeeds, likes, carts, sensor data, logs: anything where stale for a second is acceptable.

The line has blurred. DynamoDB and MongoDB now offer multi-item transactions. Cassandra offers lightweight transactions (INSERT ... IF NOT EXISTS, UPDATE ... IF col = x), implemented with Paxos and costing several round trips. Spanner and CockroachDB give serializable ACID across shards and regions. So decide per operation, not per company: the payment path can be ACID while the activity feed is eventually consistent. Replication and consistency models get their own treatment in Chapters 7 and 8.

Normalization versus denormalization

Normalization stores each fact exactly once. Third normal form, informally, means every non-key column depends on the key, the whole key, and nothing but the key. Writes touch one row, nothing can drift out of sync, and storage is compact. The price is that reads need joins.

Denormalization copies data to where it is read: author_name on every post, a like_count column instead of COUNT(*), a precomputed feed. Reads become a single lookup, but every change now fans out to many rows, and you need a way to keep the copies in sync: the same transaction, a trigger, or change data capture events (Chapter 9). Some copies are actually correct modeling. An order should keep a snapshot of the shipping address and price at purchase time, because those are historical facts.

Tip
Where each approach belongs
In a relational database, normalize by default and denormalize a specific hot read path once measurements show the join is the bottleneck. In DynamoDB or Cassandra there are no joins, so you denormalize by design: list the access patterns first, then build one table or index per pattern.

How to choose

  1. Access patterns: by key, by key plus range, ad-hoc filters, full text, multi-hop relationships, time-range aggregates?
  2. Load: read/write ratio, peak QPS, and how bursty it is.
  3. Size and growth: does it fit on one primary for the next 2 to 3 years?
  4. Consistency: which operations need transactions or invariants, and which tolerate staleness?
  5. Latency: p99 targets, and whether users are in one region or many.
  6. Operations: managed service available, team expertise, cost per GB and per request.

In the interview
Default to boring, justify the exception
A strong answer: 'Orders and payments go in PostgreSQL because I need transactions across the order, its line items and the inventory. Product search goes in Elasticsearch fed by CDC, because users need relevance-ranked text search. I would only move orders off PostgreSQL if writes outgrew a single primary, and at our estimate of 2k writes per second they do not.' Name the requirement that forces each store.
