Design an ad-click aggregation system

Design a system that ingests ad click events and produces click counts per ad per minute, available to advertiser dashboards within about a minute and accurate enough to bill advertisers. It should also answer "top 100 most-clicked ads in the last N minutes" and support filtering by country and device.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • What is the click volume per day and at peak, and how many active ads are there?
  • How fresh must dashboards be, and how accurate: is approximate fine for dashboards if billing is exact?
  • How late can events arrive (mobile clients offline, retries), and how long do we keep correcting a minute?
  • Do we need to filter bot or duplicate clicks, and what defines a duplicate?
  • Which dimensions do queries filter on: country, device, campaign, advertiser?
  • How long do we keep minute-level data, and can older data be rolled up to hours or days?
  • Do billing numbers need an audit trail back to raw events?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1Separate the raw click log (the source of truth) from the aggregated counts (a derived view). Where does each live?
H2Count by event time, not arrival time. What decides when a minute is closed, and what happens to a click that arrives 3 minutes late?
H3Retries and replays will deliver the same click twice. How do you make counting idempotent?
H4Think about a stream job keyed by ad id with 1-minute tumbling windows, a watermark, and an upsert sink keyed by ad and minute.
H5For billing, add a daily batch reconciliation over the raw events in the lake that recomputes and corrects the minute totals.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: record every click; clicks per ad per minute; filter by country and device; top 100 ads over the last 1, 5 or 60 minutes; deduplicate repeated clicks; queryable history for billing.
  • Non-functional: dashboard latency under ~1 minute from click; billing totals exact (no loss, no double count); tolerate events up to several minutes late; survive node failures without wrong numbers; horizontally scalable to 10x growth.

Estimates

  • 1B clicks/day: 10^9 / 10^5 s = about 10,000 clicks/s average; peak 5x = 50,000/s.
  • Raw event about 200 bytes (click id, ad id, user id, timestamp, IP, country, device): 10^9 x 200 B = 200 GB/day raw, about 73 TB/year before compression.
  • 2M active ads; at most 2M x 1,440 minutes = 2.9B minute rows/day if every ad got clicks every minute, but realistically ~10% are active per minute: about 290M rows/day of roughly 50 bytes = about 15 GB/day of aggregates, more with country/device breakdowns.
  • Kafka: 50,000/s x 200 B = 10 MB/s at peak, which is modest; 32 to 64 partitions give room for parallel consumers and growth.

High-level design

Write path: the redirect server assigns a unique click_id, produces the event to Kafka with acks=all and an idempotent producer, and immediately redirects the user. A sink connector writes raw events to the lake every few minutes. Aggregation: a Flink job keyed by ad_id deduplicates by click_id, assigns each click to a 1-minute event-time tumbling window, and emits (ad_id, minute, country, device, count) when the watermark passes the window end. Results go to an aggregates topic that the OLAP store ingests with upsert semantics. Read path: the query service sends time-range and dimension queries to the OLAP store and reads the top-K lists from Redis.

Deep dives

Late events and watermarks. Clicks carry the device or server timestamp, and mobile clients may send them minutes late. Use a bounded out-of-orderness watermark of about 15 seconds, so each minute's count is emitted roughly 15 seconds after that minute ends. Set an allowed lateness of 5 minutes: a late click updates the window state and Flink re-emits the corrected count, which the upsert sink overwrites. Clicks later than that go to a side output topic and are folded in by the daily reconciliation. This gives a clear story: dashboards are fast and nearly complete, billing is exact.

Exactly-once counts. Duplicates come from three places: the user double-clicking, client retries, and replays after a failure. A per-key dedupe state of seen click_ids with a TTL of about 10 minutes (Flink keyed state, or a Bloom filter per window for memory efficiency) removes client duplicates. Flink checkpoints window state together with Kafka offsets, so a crash rewinds both consistently. Because each output row is keyed by (ad_id, minute, country, device) and written as an upsert, replaying a window rewrites the same value instead of adding to it. Avoid sinks that do count = count + n, which double-count on replay.

Hot ads and top-K. A viral ad can take 5% of all clicks, overloading the single Flink subtask that owns its key. Pre-aggregate in two stages: first key by (ad_id, random 0..9) and count locally for the minute, then re-key by ad_id and sum the 10 partial counts. For top 100 over the last N minutes, each window's per-ad counts feed a top-K operator that keeps a min-heap of size 100 and writes the result to a Redis sorted set per window; 5- and 60-minute views use sliding windows or merge the minute lists. Approximate structures such as Count-Min Sketch (Chapter 14) work if exactness is not required for top-K.

5Follow-up questions

  • How would you detect and exclude click fraud from bots before it reaches billing counts?
  • An advertiser disputes a bill. How do you prove the count from raw data?
  • How would you change the design to support arbitrary group-by dimensions chosen by the advertiser?
  • What happens if the Flink job is down for 2 hours, and how does it catch up without breaking the dashboards?
  • How would you run this in two regions so a regional outage does not lose clicks or double-count them?
