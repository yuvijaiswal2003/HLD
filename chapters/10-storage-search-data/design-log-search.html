Design a log search system (like ELK)

Design a centralized logging platform for a company running about 5,000 services across 20,000 hosts. Engineers must be able to search logs by free text and by fields (service, level, trace id, host) within seconds of the log being written, and keep logs searchable for 14 days and archived for 1 year.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • What is the ingest volume: log lines per second at peak and average line size?
  • How fresh must search be: seconds, or is a minute of lag acceptable?
  • What retention is needed for hot search versus cheap archive, and is there a compliance requirement?
  • Are logs structured (JSON) or free text, and which fields are commonly filtered on?
  • What query patterns dominate: needle-in-haystack by trace id, free-text error search, or aggregations for dashboards?
  • Is it acceptable to drop or sample debug logs under extreme load, or must every line be kept?
  • Do we need per-team access control or PII redaction?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1Never let the log pipeline put backpressure on the applications that produce logs. What sits between the agents and the indexer?
H2Indexing is the expensive step. Think about how you partition indices so that writing, searching and deleting by age are all cheap.
H3Recent logs are searched far more than old ones. How would you place data on hardware by age?
H4Consider time-based indices (one per day), a hot-warm-cold tier layout, and deleting whole indices instead of documents.
H5For one-year retention, archive compressed raw logs to object storage and only rehydrate them when someone needs them.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: ingest logs from all hosts; full-text and field search; filter by time range; aggregations (errors per service per minute); tail live logs; 14-day hot search, 1-year archive.
  • Non-functional: searchable within ~10 s of emission; ingest must never block applications; tolerate node loss without losing acknowledged logs; queries over the last hour return in under 2 s; cost-efficient at many TB per day.

Estimates

  • 20,000 hosts x 50 lines/s average = 1M lines/s average; peak 3x = 3M lines/s.
  • Average line 500 bytes, so 1M x 500 B = 500 MB/s, about 43 TB/day raw (500 MB/s x 86,400 s).
  • Indexed in Elasticsearch with one replica, roughly 1.2x raw per copy after indexing overhead: 43 x 1.2 x 2 = about 100 TB/day; 14 days = about 1.4 PB of hot and warm index storage.
  • Archive: compressed about 8x with zstd to object storage: 43 / 8 = about 5.4 TB/day, 365 days = about 2 PB, cheap in infrequent-access or archive storage classes.
  • Kafka buffer: 500 MB/s with 3 replicas, 24 h retention = 500 MB x 86,400 x 3 = about 130 TB across the Kafka cluster.
  • If one indexing node sustains about 20 MB/s of raw log ingest, peak 1.5 GB/s needs about 75 nodes for primaries, about 150 hot nodes once the replica copy is indexed too, plus headroom.

Data model

FieldMappingWhy
@timestampdateEvery query has a time range; also drives index selection

messagetext, standard analyzerFull-text search

Indices are per day and per tenant group, e.g. logs-checkout-2026.10.22, behind an alias or data stream. Elasticsearch (or OpenSearch) is the search tier because it provides the inverted index, field aggregations and shard distribution out of the box. Raw logs are also archived as compressed newline-delimited JSON or Parquet in S3, partitioned by date/service/hour.

High-level design

Write path: a lightweight agent on each host tails log files, adds host metadata, batches and compresses, and ships to Kafka. If Kafka is slow the agent buffers to local disk and eventually drops debug lines, never blocking the app. Indexer workers consume, parse and enrich (service, level, trace id), redact secrets and PII, and send _bulk requests of a few MB each. The archiver independently writes hourly compressed files to S3. Read path: the query service checks the user's permissions, rewrites the time range into the set of daily indices to hit, enforces a timeout and result limit, and runs the search. Old data is queried by restoring archive files into a temporary index or querying Parquet with Trino or Athena.

Deep dives

Index lifecycle and tiering. Daily indices make retention free: deleting a 14-day-old index drops whole files instead of marking billions of documents as deleted, which would cost huge merge I/O. Index lifecycle management rolls an index over at a size or age limit, moves it from hot NVMe nodes to warm HDD nodes after 2 days, force-merges it to a single segment once it is read-only (faster searches, less heap), and deletes it at day 14. Most queries are about the last hour, so the hot tier carries most of the read load with a small fraction of the data.

Shard sizing and noisy services. One index per service per day gives thousands of tiny shards, wasting heap. One giant index makes a chatty service's volume dominate. Group small services into shared indices and give the top few heavy services their own, targeting 20 to 50 GB per shard. Enforce per-service ingest quotas at the indexer; a service that suddenly logs 10x (a debug flag left on) gets sampled or dropped with a metric, rather than degrading search for everyone.

Backpressure and durability. Kafka with acks=all and replication factor 3 is the durability point: once Kafka acknowledges, the line will be indexed eventually. If Elasticsearch is slow (merges, a node down), consumer lag grows but nothing is lost, and indexers catch up later. Indexers commit Kafka offsets only after the bulk request succeeds, so delivery is at least once; to avoid duplicates, set the document id to a hash of host, file, offset, so a replayed line overwrites itself. Alert on consumer lag in seconds, because lag is the freshness SLO.

Trade-offs and bottlenecks

  • Full-text index vs cost: indexing every field of every line is the dominant cost. Alternatives like Grafana Loki index only labels (service, host, level) and brute-force scan compressed chunks, trading query speed for much lower ingest cost. A hybrid indexes errors fully and keeps debug logs label-only.
  • Freshness vs throughput: raising refresh_interval from 1 s to 30 s substantially increases indexing throughput but delays searchability; 5 to 10 s is a reasonable compromise for logs.
  • Replicas: one replica doubles storage; the warm tier could rely on the S3 archive for recovery instead, accepting slower restore on node loss.
  • Expensive queries: leading wildcards and month-long regex searches can overload the cluster; the query service needs timeouts, max time range for free-text queries and per-user concurrency limits.
  • Schema chaos: thousands of teams emitting different JSON keys cause mapping explosion; use a flattened field type or an allowlist of mapped attributes.

5Follow-up questions

  • How would you support live tail across 20,000 hosts without polling Elasticsearch every second?
  • A team accidentally logs credit card numbers. How do you detect, redact and purge them from hot indices and the archive?
  • How would you cut indexing cost by 70% if most logs are never searched?
  • How do you correlate a log search with distributed traces and metrics for the same request?
  • How would the design change for multiple regions with data-residency rules?
