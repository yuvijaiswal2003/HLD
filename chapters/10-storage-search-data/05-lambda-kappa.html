Lambda vs Kappa architecture

Early stream processors were fast but approximate and lost state on failure; batch was slow but exact. The Lambda architecture (named by Nathan Marz) runs both: a batch layer periodically recomputes accurate views from the immutable master dataset, a speed layer computes recent results from the stream, and a serving layer merges them: batch results for everything up to the last batch run, speed results for the rest.

The Kappa architecture (named by Jay Kreps) argues that with a replayable log and a stream engine with exactly-once state, the batch layer is redundant. Keep everything in one streaming pipeline. To fix a bug or change logic, start version 2 of the job reading the log from the beginning (long Kafka retention, or tiered storage, or a lake-backed source), let it catch up into a new output table, then switch readers over and delete version 1.

Lambda

Strengths
  • Batch layer gives exact, auditable numbers
  • Easy to reprocess years of history on cheap batch compute
  • Tolerates a lossy or approximate speed layer
Weaknesses
  • The same logic is written twice, in two frameworks, and the two drift
  • Two systems to operate and a merge layer to maintain
Use whenBilling or financial reporting where the nightly number must be reconciled exactly, or when streaming logic is approximate (sketches, sampled data).

Kappa

Strengths
  • One codebase and one set of semantics
  • Lower operational burden
  • Modern engines provide exactly-once state
Weaknesses
  • Reprocessing a large history through the stream engine can be slow and costly
  • Requires long log retention or a replayable lake source
Use whenMost new real-time analytics pipelines, especially when the logic is the same for fresh and historical data.

Choosing between them

  • Is the stream logic exact? With event-time windows, checkpointed state and idempotent sinks, yes, and Kappa is enough. If the speed layer uses sampling or sketches, keep a batch layer for exact numbers.
  • How much history must you reprocess? Replaying a week of Kafka is routine; replaying five years through Flink is slow and expensive, and a Spark job over Parquet in the lake is better at that.
  • Does the same code serve both? Flink and Spark both run batch and streaming jobs from one API, which reduces the code duplication that made Lambda painful.
In the interview
A good hybrid to propose
A common real answer: stream processing with Flink produces the real-time numbers, and a daily batch reconciliation job over raw events in the lake checks or corrects them. Call that what it is (a Lambda-flavored reconciliation) and justify it with the money involved: advertisers are billed on these counts.
