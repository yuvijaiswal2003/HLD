Stream processing, windows and watermarks

Stream processing handles unbounded data continuously: events flow in from Kafka, the job updates state and emits results within seconds. Fraud detection, live dashboards, ad-click counting and alerting are stream problems. The main engines are Apache Flink (a dedicated cluster, rich windowing and event-time support, large keyed state), Kafka Streams (a library inside your own service that reads and writes Kafka, with state in local RocksDB backed by changelog topics) and Spark Structured Streaming (micro-batches, a good fit if you already run Spark).

Event time vs processing time

Event time is when the event actually happened, stamped by the device or producer. Processing time is when your job sees it. They differ because of network delays, retries, consumer lag and phones that buffer events offline for hours. If you count clicks per minute by processing time, a 5-minute consumer outage shifts all those clicks into the minute the consumer recovers: the chart shows a dip then a fake spike. Counting by event time gives the right answer, but it raises a hard question: when do you know a minute is complete?

Watermarks and late data

A watermark is the engine's assertion "I believe no more events with event time earlier than W will arrive". A common strategy is bounded out-of-orderness: W = highest event time seen minus an allowed delay, say 10 seconds. When the watermark passes the end of a window, the window fires and emits its result. Events that arrive after that are late: you can drop them, send them to a side output for later correction, or keep the window open for an allowed lateness period and emit an updated result. A longer delay means more complete results but higher latency; that trade-off is yours to state.

State, checkpoints and exactly-once

A windowed count is state: a counter per key per open window. Flink keeps it in local RocksDB on each worker and periodically takes a consistent checkpoint of all operator state plus the Kafka offsets that produced it, using the Chandy-Lamport style barrier algorithm. After a crash the job restores the last checkpoint and rewinds Kafka to the saved offsets, so internal state is exactly-once. End-to-end exactly-once also needs the sink to cooperate: either transactional writes committed with the checkpoint (Kafka transactions, two-phase commit sinks) or idempotent upserts keyed by (key, window), so a replayed result overwrites rather than double-counts. Delivery semantics themselves are covered in Chapter 9.

sql
-- Flink SQL: clicks per ad per 1-minute event-time window
CREATE TABLE clicks (
  ad_id STRING, user_id STRING, ts TIMESTAMP(3),
  WATERMARK FOR ts AS ts - INTERVAL '10' SECOND
) WITH ('connector' = 'kafka', 'topic' = 'ad-clicks', 'format' = 'json');

SELECT ad_id, window_start, COUNT(*) AS clicks
FROM TABLE(TUMBLE(TABLE clicks, DESCRIPTOR(ts), INTERVAL '1' MINUTE))
GROUP BY ad_id, window_start, window_end;
Pitfall
Watermarks stall on idle partitions
A Flink source's watermark is the minimum across the Kafka partitions it reads. If one partition stops receiving events, its watermark stops advancing and every window waits forever. Configure idleness detection (withIdleness) so idle partitions are ignored, and monitor watermark lag as a first-class metric.
