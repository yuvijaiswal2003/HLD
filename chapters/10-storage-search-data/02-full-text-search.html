Full-text search and Elasticsearch

A query like WHERE body LIKE '%timeout%' forces a full table scan: a B-tree index sorts whole values, so it cannot help with a word in the middle of a string. It also cannot rank results by relevance, handle plurals, or tolerate typos. Search engines solve this with a different data structure, built for one question: which documents contain this term?

The inverted index, worked example

Take three documents. D1: "Kafka stores events in partitions". D2: "Redis stores keys in memory". D3: "Kafka partitions are replicated". The analyzer lowercases, drops stop words like in and are, and stems words to a root form. The result maps each term to a postings list: the documents containing it, with the word positions.

TermPostings: doc at positionDocument frequency

The query kafka AND partitions is analyzed the same way into kafka, partition, then the engine intersects two sorted postings lists: {D1, D3} and {D1, D3} gives {D1, D3}. Intersecting sorted lists is a linear merge, and real engines add skip pointers so they can jump ahead. The phrase query "kafka partitions" also checks positions: in D3 the terms sit at 1 and 2 (adjacent, match), in D1 at 1 and 5 (not adjacent, no match). Term lookup itself uses a sorted term dictionary (Lucene uses a compact finite-state transducer), so finding a term's postings is fast even with hundreds of millions of distinct terms.

Analyzers: how text becomes terms

  • Character filters clean raw text: strip HTML, map special characters.
  • Tokenizer splits text into tokens: on whitespace and punctuation, or by language rules (Chinese and Japanese need dictionary-based tokenizers because words are not separated by spaces).
  • Token filters transform tokens: lowercase, remove stop words, stem (running to run), add synonyms (tv and television), or emit edge n-grams (ka, kaf, kafk) to support search-as-you-type.
  • The same analyzer, or a compatible one, must run at index time and at query time. Otherwise the query asks for terms that were never written to the index.
Pitfall
text vs keyword fields
In Elasticsearch a text field is analyzed for full-text search, while a keyword field is stored as one exact term for filtering, sorting and aggregations. Mapping a status code or user id as text breaks exact matches and aggregations; mapping a message body as keyword makes word search impossible. Many fields are mapped both ways.

Ranking: TF-IDF and BM25

Matching documents must be ordered. TF-IDF scores a term higher when it appears often in the document (term frequency) and rarely across the corpus (inverse document frequency): "kafka" in a doc about Kafka matters more than "the". BM25, the default in Lucene, Elasticsearch and OpenSearch, improves on it in two ways: term frequency saturates (the 20th mention adds little over the 5th, controlled by k1, about 1.2), and scores are normalized by document length so long documents do not win just by containing more words (controlled by b, about 0.75). Production ranking then layers business signals on top: recency, popularity, personalization, or a learned re-ranking model over the top few hundred hits.

python
import math

def bm25(query_terms, doc_tf, doc_len, avg_len, df, n_docs, k1=1.2, b=0.75):
    """doc_tf: term -> count in this doc. df: term -> docs containing term."""
    score = 0.0
    for t in query_terms:
        if t not in doc_tf:
            continue
        idf = math.log(1 + (n_docs - df[t] + 0.5) / (df[t] + 0.5))
        tf = doc_tf[t]
        length_norm = 1 - b + b * doc_len / avg_len
        score += idf * tf * (k1 + 1) / (tf + k1 * length_norm)
    return score

Elasticsearch: shards, replicas, near-real-time

  • An index is split into primary shards; each shard is a self-contained Lucene index. A document goes to shard hash(routing) % number_of_primary_shards, where routing defaults to the document id. Because of that modulo, the primary shard count is fixed at index creation; changing it means a reindex or a split/shrink operation.
  • Each primary has replicas on other nodes. Writes go to the primary, which forwards them to replicas; searches can be served by any copy, so replicas add both fault tolerance and read throughput.
  • A Lucene shard is a set of immutable segments. New documents sit in an in-memory buffer and are written to the translog for durability. Every refresh_interval (default 1 second) the buffer becomes a new searchable segment. That is why Elasticsearch is near-real-time: a document is durable when the write returns but searchable about 1 second later.
  • Background merging combines small segments into large ones and purges deleted documents. Updates are delete plus re-insert, so update-heavy workloads cost merge I/O.
  • Rule of thumb: keep shards around 10 to 50 GB. Too many tiny shards waste heap and cluster-state overhead; giant shards make recovery and rebalancing slow.
  • Deep pagination with from + size forces every shard to return from + size hits to the coordinator, so it is capped (10,000 by default). Use search_after with a sort key for deep or infinite scroll.

Keeping search in sync with the database

Dual writes from the app

Strengths
  • Simple to start
  • Low latency to searchable
Weaknesses
  • Two writes without a transaction: one can fail and they drift apart
  • Concurrent updates can land in different orders in the two stores
Use whenPrototypes only, or with a periodic repair job.

Change data capture into an indexer

Strengths
  • DB commit log is the single source of truth
  • Kafka buffers indexing spikes and lets you replay
  • Ordering per key is preserved by partitioning on the row id
Weaknesses
  • More moving parts: Debezium, Kafka, indexer workers
  • Seconds of lag between commit and searchable
Use whenThe default production answer for keeping Elasticsearch in sync with PostgreSQL or MySQL.

Periodic full reindex with alias swap

Strengths
  • Fixes any drift, allows mapping changes
  • Zero-downtime cutover by flipping an alias
Weaknesses
  • Expensive for large corpora
  • Stale between runs if used alone
Use whenSchema changes, analyzer changes, and as a backstop to CDC.
In the interview
Search is a derived view
State clearly that the database is the source of truth and the search index is a derived, rebuildable view fed by CDC. Mention that the indexer writes with the row's version number using external versioning, so a late, out-of-order event can never overwrite a newer document. Interviewers listen for whether you treat Elasticsearch as a primary store; it should not be one for data you cannot regenerate.
