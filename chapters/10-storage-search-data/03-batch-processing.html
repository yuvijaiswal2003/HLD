Batch processing: MapReduce and Spark

Batch processing runs a job over a large, bounded dataset (yesterday's logs, the full orders table) and produces output some time later: minutes to hours. Nobody waits on it interactively. It answers questions like "daily revenue per country" or "rebuild the recommendation model", and its great property is that it is repeatable: if the code had a bug, fix it and rerun over the same immutable input.

The MapReduce model

MapReduce, published by Google in 2004 and popularized by Hadoop, splits any job into two functions you write and one step the framework does for you. Map reads input records and emits key-value pairs. Shuffle moves all pairs with the same key to the same machine and sorts them. Reduce processes all values for one key at a time. The framework handles splitting input, scheduling tasks near the data, and rerunning failed tasks.

python
# Word count, the hello world of MapReduce
def map_fn(_, line):
    for word in line.lower().split():
        yield word, 1

def reduce_fn(word, counts):
    yield word, sum(counts)

# A combiner runs reduce_fn locally on each mapper's output before the
# shuffle, so a mapper sends (the, 5000) once instead of (the, 1) 5000 times.
  • Move compute to data. Shipping a 10 GB input split across the network is slow; shipping a few KB of code to the node already holding it is cheap.
  • Fault tolerance by recomputation. Map and reduce are deterministic over immutable input, so a failed task is simply rerun on another node.
  • Skew is the real enemy. If one key (a celebrity user, the null key) has 30% of the values, one reducer does 30% of the work and the job waits on it. Fixes: salting the hot key into key#0..key#9 and merging afterwards, or broadcasting the small side of a join.

Spark: the successor

Classic MapReduce writes intermediate results to disk between every stage, so a 10-stage pipeline means 10 rounds of disk I/O. Apache Spark represents a job as a DAG of transformations over partitioned datasets, keeps intermediate data in memory where it fits, and pipelines narrow operations (map, filter) without materializing them. Lost partitions are recomputed from their lineage rather than restored from replicas. Spark SQL and DataFrames add a query optimizer, so most jobs are written as SQL-like code. It is typically several times to an order of magnitude faster than Hadoop MapReduce for multi-stage jobs, which is why new batch work is built on Spark, or on warehouse engines like BigQuery, Snowflake and Trino.

In the interview
When batch is the right answer
If the requirement says "daily report", "nightly", "reconcile" or "retrain", propose a batch job on Spark reading from the data lake, and say why: simpler than streaming, cheap on spot instances, and trivially re-runnable. Do not reach for Flink when hourly freshness is fine.
