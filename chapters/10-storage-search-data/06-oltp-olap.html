OLTP vs OLAP, warehouses and lakes

OLTP (online transaction processing) is your application database: many small reads and writes touching a few rows by key, with low latency and strong transactional guarantees. OLAP (online analytical processing) answers questions like "revenue by region by month for 3 years": few queries, each scanning billions of rows but only a handful of columns. Running analytics on the OLTP primary steals its I/O and buffer cache from user requests, so analytics data is copied into a separate system built for scans.

OLTPOLAP
Query shapePoint lookups and small range scans by keyAggregations over millions to billions of rows
UsersEnd users through the applicationAnalysts, dashboards, ML pipelines
Latency targetMillisecondsSeconds to minutes
DataCurrent state, normalizedHistory, often denormalized into star schemas
Storage layoutRow-orientedColumn-oriented
ExamplesPostgreSQL, MySQL, DynamoDBSnowflake, BigQuery, Redshift, ClickHouse, Druid

Why columnar storage wins for analytics

A row store keeps all columns of a row together, which is ideal for "fetch order 42". A column store keeps each column in its own file or block. For SELECT region, SUM(amount) FROM orders WHERE year = 2025 GROUP BY region on a 100-column table, a column store reads only 3 columns: roughly 3% of the bytes. Values within a column are similar, so they compress very well (run-length, dictionary and bit-packing encodings often give 5 to 10x), and engines process them with vectorized SIMD loops. Per-block min and max statistics let the engine skip blocks whose year range cannot match. The cost: writing one row touches every column file, so column stores ingest in large batches and are bad at single-row updates.

~3%Bytes read when a query uses 3 of 100 columns
5 to 10xTypical compression of columnar data
Parquet, ORCOpen columnar file formats for data lakes

Warehouse vs lake vs lakehouse

Data warehouse

Strengths
  • Fast SQL, managed, strong governance
  • Schema-on-write keeps data clean
Weaknesses
  • Proprietary storage, costly at petabyte scale
  • Awkward for raw, semi-structured and ML data
Use whenBusiness intelligence on curated data: Snowflake, BigQuery, Redshift.

Data lake

Strengths
  • Cheapest storage: open files on S3 or GCS
  • Holds anything: raw logs, images, Parquet
  • Many engines can read it: Spark, Trino, Presto
Weaknesses
  • Schema-on-read: easily becomes a data swamp
  • No transactions or updates on plain files
Use whenRaw event archive, ML training data, the replay source for reprocessing.

Lakehouse

Strengths
  • ACID transactions, schema enforcement and time travel on lake files
  • Upserts and deletes, important for GDPR erasure
  • One copy serves BI and ML
Weaknesses
  • Table formats and compaction add operational work
  • Interactive latency can trail a tuned warehouse
Use whenUnifying lake and warehouse: Delta Lake, Apache Iceberg, Apache Hudi on object storage.

ETL vs ELT

ETL (extract, transform, load) transforms data in a separate engine before loading it into the warehouse; it made sense when warehouse compute was scarce and expensive. ELT loads raw data first and transforms it inside the warehouse with SQL, typically managed with dbt. Elastic cloud warehouses made ELT the default: raw data is preserved, so a transformation bug is fixed by rerunning SQL rather than re-extracting from source systems. ETL still fits when data must be cleaned or masked before it lands, for example stripping PII for compliance.

In production
Real-time OLAP at LinkedIn and Uber
Real-time OLAP stores such as Apache Druid, Apache Pinot and ClickHouse sit between streams and dashboards: they ingest from Kafka continuously and answer aggregation queries in sub-second time. Apache Pinot was created at LinkedIn to power user-facing analytics such as "who viewed your profile", and Uber also runs Pinot for real-time analytics.
Tip
The pipeline shape to draw
OLTP database to CDC (Debezium) to Kafka, then two consumers: a stream job feeding a real-time OLAP store for dashboards, and a sink writing Parquet to the lake for batch and ML. That one diagram covers most "add analytics to this system" follow-ups.
