Block, file and object storage

Every system eventually has to store bytes that are not rows: profile photos, videos, log archives, ML datasets, database backups. There are three storage abstractions, and interviewers expect you to pick the right one without hesitation. The short version: block storage is a raw disk, file storage is a shared folder tree, and object storage is a giant key to blob map spoken over HTTP.

How an object store works inside

An object store splits into two very different subsystems. The metadata service maps bucket + key to an object id, size, checksum, version and the list of data nodes holding its pieces. It is small per object but must be strongly consistent and handle huge request rates, so it lives in a partitioned, replicated database. The data service stores the actual bytes on many storage nodes and is optimized for throughput and cheap capacity. Stateless API servers sit in front, authenticate the request, consult metadata and stream bytes to or from data nodes.

Replication vs erasure coding

The simple way to survive disk loss is replication: keep 3 full copies in 3 zones. It is fast to read and trivial to repair, but you pay 3x the raw capacity. Erasure coding (usually Reed-Solomon) splits an object into k data fragments and computes m parity fragments; any k of the k + m fragments rebuild the original. With RS(6,3) you store 9 fragments of 1/6 size each, so 1.5x raw capacity, and you survive any 3 fragment losses, which is more fault tolerance than 3x replication at half the cost.

Tip
Replicate hot data, erasure-code cold data
Erasure coding costs CPU on writes, makes repairs read many fragments across the network, and turns a normal read into a multi-node read when a fragment is missing. Small objects waste space when cut into fragments, so stores pack many small objects into large append-only volumes before coding them. A common design: write new data replicated, then a background job converts it to erasure-coded form once it cools down. HDFS ships an RS(6,3) policy for exactly this reason.

Where 11 nines of durability comes from

Durability is the probability you never lose the data; availability is the probability you can read it right now. S3 is designed for 99.999999999% (11 nines) durability but only about 99.99% availability. Eleven nines means an annual loss probability of 10^-11 per object: store 10 million objects and you expect 10^7 x 10^-11 = 10^-4 losses per year, about one object every 10,000 years. It comes from four things working together: fragments spread across at least 3 zones, continuous checksum scrubbing to catch silent bit rot, fast automatic repair so the window of reduced redundancy is minutes not days, and versioning plus object lock to protect against the most common cause of loss, which is humans deleting things.

Presigned URLs and multipart upload

  1. Client asks your API for an upload slot
    POST /uploads with file name, size and type. Your API checks auth, quota and content type.
  2. API signs a URL
    Using its own cloud credentials, the API creates a presigned PUT URL for one exact key, valid for e.g. 15 minutes. No network call to S3 is needed; it is a local HMAC signature.
  3. Client uploads straight to the object store
    The bytes never touch your app servers, so a 2 GB video does not tie up an app thread or your bandwidth bill.
  4. Object store notifies you
    An event notification (S3 to SQS or Lambda) or a client POST /uploads/id/complete call tells your backend to write the metadata row and kick off processing.

For large files use multipart upload: initiate, upload parts in parallel (in S3 each part is 5 MiB to 5 GiB, up to 10,000 parts), then send a complete call listing the part ETags. A failed part is retried alone, uploads can resume after a network drop, and parallel parts saturate the client's bandwidth. Add a lifecycle rule that aborts incomplete multipart uploads after a few days, or orphaned parts silently accumulate storage cost.

In the interview
Say this in any media-heavy design
"Uploads go directly from the client to S3 using presigned URLs, with multipart for anything over ~100 MB. Our servers only handle metadata. Downloads are served through a CDN in front of the bucket." That one sentence removes your app tier from the bandwidth path and shows you know the standard pattern.
In production
S3 became strongly consistent
Since December 2020, Amazon S3 provides strong read-after-write consistency for PUTs and DELETEs, including overwrites and LIST operations. Older designs had to work around eventual consistency on overwrites; you no longer do.
