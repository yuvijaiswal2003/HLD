Design a live sports score update service

Design the backend for a sports app that shows live scores for football, cricket and basketball matches. Scores come from an official data provider. When a goal or wicket happens, fans watching that match in the app or on the website should see it within about 2 seconds. A normal day has 2 million concurrent viewers; a big final can reach 10 million concurrent viewers, most of them watching that one match.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • Is data only server-to-client, or do fans also send things such as reactions or predictions?
  • How fresh must updates be: under 2 seconds end to end, or is 10 seconds acceptable?
  • Which clients: browsers, native mobile apps, or both? Do backgrounded apps need notifications?
  • How often does the provider send updates per match, and in what format?
  • Do we show only the current score, or also a play-by-play commentary feed?
  • What is the peak concurrency for a single match versus all matches?

3Hints 0/5

H1Compare the inbound rate (updates from the provider) with the outbound rate (messages to fans). Where is the real scale?

H5Think about what happens at the moment of a goal: who reconnects, and who suddenly opens the app?

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: list live matches with current scores; open a match and see score, clock and key events update live; receive push notifications for followed teams' key events (goal, wicket, final result) when the app is in the background.
  • Non-functional: provider-to-screen latency under 2 s at p95; 10M concurrent viewers at peak, up to 8M on one match; 99.95% availability during matches; updates never shown out of order (a score must not go backwards); low cost per viewer.

Estimates

text
Inbound
  live matches at once:      up to ~500
  state changes:             ~1 per 10 s per match on average
  inbound rate:              500 / 10 = ~50 updates/s       (tiny)

Outbound
  big final: 8M viewers, 1 update per 10 s = 800k messages/s
  all viewers: 10M / 10 s = ~1M messages/s
  message size with SSE framing: ~300 B
  bandwidth: 1M x 300 B = 300 MB/s = ~2.4 Gbit/s

Connections
  plan 100k per fan-out server (100k x 30 KB = ~3 GB RAM)
  10M / 100k = 100 servers, +50% headroom = ~150 servers
  per server: 100k / 10 s = 10k writes/s

Polling alternative
  10M clients every 2 s = 5M requests/s at the CDN
  3-hour match: 5M x 10,800 s = 54 billion requests
  at ~$0.01 per 10k requests = ~$54,000 in request fees alone

Inbound is about 50 updates per second; outbound is about a million. The design is a fan-out problem: take a tiny stream of updates and copy each to millions of open connections quickly.

API

http
GET  /v1/matches/live
     -> 200 [ { "match_id": "m77", "version": 1042, "home": 2, "away": 1 }, ... ]

GET  /v1/matches/{match_id}/stream        (Accept: text/event-stream)
     Last-Event-ID: 1041
     -> 200, then events: id: 1042  event: state  data: {full scoreboard}

GET  /v1/matches/{match_id}/snapshot      (fallback, Cache-Control: max-age=2)

PUT  /v1/users/me/follows/{team_id}       (push notifications for key events)

POST /internal/v1/provider/events         (provider webhook or feed adapter)

High-level design

Write path: the ingest service receives a provider event, checks it, assigns the next per-match version number, writes the event and new snapshot, and publishes the full scoreboard to Kafka keyed by match_id, which keeps each match's updates in order. Read path: a fan opening a match connects through the load balancer to any fan-out server and opens an SSE stream. The server registers the connection under that match_id in a local in-memory map, sends the current snapshot immediately, then forwards each new update. Each fan-out server consumes the whole topic with its own consumer group (only about 50 messages per second) and drops updates for matches none of its clients watch. Notification workers send pushes for key events to followers' devices.

Deep dives

SSE vs WebSockets vs polling. Data flows one way, so SSE is the simplest fit: plain HTTP, automatic reconnect with Last-Event-ID, and good behavior through proxies and over HTTP/2. WebSockets would also work and make sense if we later add reactions or chat. Polling a CDN-cached snapshot is the easiest to build and is our fallback for clients where streaming fails, but at 10M viewers polling every 2 s it means 5M requests per second and tens of thousands of dollars in request fees per match, versus about 150 fan-out servers for a few hours.

Ordering and reconnects. Every message carries the full scoreboard (under 1 KB) and a per-match version. Clients ignore any message whose version is not newer than what they show, so a score never goes backwards even if messages are duplicated or reordered around a reconnect. On reconnect, the server compares the client's Last-Event-ID with the snapshot's version and sends the snapshot if the client is behind. No replay log is needed. A play-by-play commentary feed would need one, such as the last 200 events per match in a Redis list.

The goal moment. Two surges arrive together. Push notifications bring millions of fans into the app within a minute: 2M new connections in 60 s is about 33,000 new TLS connections per second, which the load balancer tier must be sized for, and each needs a snapshot served from memory or Redis, never PostgreSQL. And if a fan-out server crashes, its 100,000 clients reconnect at once. The server sends an SSE retry: value with a random component, clients back off with jitter, and the load balancer spreads new connections across the remaining servers. Deploys drain one server at a time.

5Follow-up questions

  • The provider occasionally sends a correction (a goal is disallowed). How do clients handle a score that legitimately goes down?
  • Fans can now send emoji reactions that everyone watching sees. What changes?
  • Inbound grows to 100,000 updates/s across many minor leagues. Is broadcasting to every fan-out server still OK?
  • How do you measure the provider-to-screen latency in production?
  • One region of your cloud provider fails during the final. What happens to the fans connected there?
