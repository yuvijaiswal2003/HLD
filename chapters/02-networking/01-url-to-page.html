What happens when you type a URL

“What happens when you type https://www.example.com into a browser and press Enter?” is a classic warm-up question, and it is also the best map of this chapter. Every step is a piece of infrastructure you will place in later designs: DNS, TCP, TLS, load balancers, reverse proxies, app servers, caches and databases.

  1. Parse the URL
    The browser splits it into a scheme (https), a host (www.example.com), an optional port (443 is the default for HTTPS, 80 for HTTP), a path (/) and an optional query string. If the site is on the browser's HSTS list, it upgrades http to https before sending anything.
  2. Check local caches
    If the browser holds a fresh cached copy of the page, it may skip the network entirely. Otherwise it needs the server's IP address.
  3. Resolve the name with DNS
    The browser checks its own DNS cache, then the operating system's cache (and hosts file), then asks a recursive resolver, usually run by the ISP or a public service like 8.8.8.8 or 1.1.1.1. On a full miss the resolver walks root, TLD and authoritative servers, as the next lesson shows. Result: an IP address such as 203.0.113.10.
  4. Open a TCP connection
    The browser performs the TCP three-way handshake with that IP on port 443. This costs one network round trip before any data flows.
  5. Negotiate TLS
    The browser and server agree on encryption keys, and the browser verifies the server's certificate for www.example.com against trusted certificate authorities. TLS 1.3 takes one more round trip.
  6. Send the HTTP request
    GET / HTTP/2 with headers such as Host, Cookie, Accept-Encoding. Usually the IP belongs not to an app server but to a CDN edge or a load balancer.
  7. Serve it on the backend
    A load balancer or reverse proxy terminates TLS and forwards the request to one of many app servers. The app authenticates the user via the cookie, reads from a cache or database, and renders HTML or JSON.
  8. Return and render
    The response travels back along the same path. The browser parses the HTML, discovers CSS, JavaScript and images, and fetches them (many from a CDN, over the already-open connection where possible), then lays out and paints the page.

Where the time goes

On a first visit, most of the delay is round trips, not computation. A round-trip time (RTT) is how long a tiny packet takes to reach the other side and come back. From London to a data center in Virginia the RTT is around 75 to 80 ms. DNS (up to one or more RTTs on a miss), TCP (1 RTT), TLS 1.3 (1 RTT) and the request itself (1 RTT) add up to roughly 250 to 300 ms before the first byte of HTML arrives, even if the server answers instantly. That is why designers care so much about connection reuse, CDNs and terminating TLS close to the user.

In the interview
Breadth first, then depth
When asked this question, list the steps briefly end to end first, then offer depth: “I can go deeper on DNS resolution, the TLS handshake, or what the load balancer does.” The interviewer wants to see that you know the whole path and can zoom into any part.
Tip
Map each step to a design lever
DNS → GeoDNS sends users to a nearby region. TCP/TLS → keep-alive, HTTP/2 and HTTP/3 reduce setup cost. Edge → a CDN caches content near users. Backend → load balancers, caches and replicas. When a design has a latency problem, ask which step of this path it lives in.
