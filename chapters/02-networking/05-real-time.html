Real-time communication: polling, SSE, WebSockets, WebRTC

Plain HTTP is request-response: the client asks, the server answers. Chat, live scores, notifications, collaborative editing and dashboards need the server to send data the moment something happens. There are five common techniques, from simplest to most capable.

Short polling

The client asks “anything new?” on a fixed interval, say every 5 seconds. It is trivial to build and works everywhere, and responses can even be cached by a CDN. But most requests return nothing, latency averages half the interval, and the load scales with clients times frequency: 1 million clients polling every 5 seconds is 200,000 requests per second, mostly wasted.

Long polling

The client sends a request and the server holds it open until there is new data or a timeout (often 20 to 30 seconds) passes. As soon as a response arrives, the client sends the next request. Updates arrive almost immediately, and it is still plain HTTP. Each message still costs a full request, and the server must hold many open requests cheaply, which suits event-driven servers (Node.js, Go, Nginx) better than thread-per-request ones.

Server-Sent Events (SSE)

With SSE, the client makes one HTTP request and the server keeps the response open, writing events as lines of text (Content-Type: text/event-stream). It is one-way: server to client. The browser's EventSource API reconnects automatically and sends a Last-Event-ID header so the server can resume where it left off. Because it is ordinary HTTP, it passes through most proxies and works well over HTTP/2. Over HTTP/1.1, browsers limit open connections to about 6 per host, which caps how many SSE streams a user can have open across tabs.

http
GET /v1/matches/m77/stream HTTP/1.1
Accept: text/event-stream
Last-Event-ID: 1041

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

id: 1042
event: score
data: {"home": 2, "away": 1, "minute": 67}

WebSockets

A WebSocket starts as an HTTP request with an Upgrade: websocket header; the server answers 101 Switching Protocols, and from then on the TCP connection carries small bidirectional frames with only 2 to 14 bytes of overhead each. This is the standard choice for chat, multiplayer games, collaborative editors and anything where the client also sends frequent messages. The price is that connections are long-lived and stateful: load balancers must support them, a message for user X must be routed to whichever server holds X's socket, and deploys must drain connections gracefully.

WebRTC

WebRTC lets browsers and apps send audio, video and data directly to each other, usually over UDP, with very low latency. Peers first exchange connection details through a signaling server (often over a WebSocket), use STUN servers to discover their public addresses through NAT, and fall back to relaying through a TURN server when a direct path is impossible. Use it for calls and screen sharing, not for server-to-client notifications. Chapter 16 covers video conferencing at scale.

What persistent connections cost at scale. An idle connection costs memory (kernel socket buffers plus your application's per-connection state, from a few KB to tens of KB), one file descriptor, and periodic heartbeats to detect dead peers and keep NAT and load balancer mappings alive. A tuned server can hold hundreds of thousands of mostly idle connections. Worked example: 10 million concurrent users at 100,000 connections per server needs 100 servers before headroom; a heartbeat every 30 s means 10M ÷ 30 ≈ 333,000 pings per second across the fleet, which is tiny per server but not free.

In production
WhatsApp's connection density
In 2012 WhatsApp's engineering blog reported more than 2 million concurrent TCP connections on a single server, using Erlang on tuned FreeBSD. It shows that holding connections is not the hard part; routing messages between millions of them and surviving failures is.
Pitfall
Reconnect storms
If a gateway with 100,000 connections restarts, all 100,000 clients reconnect at once, each doing a TCP and TLS handshake and refetching state. Restart gateways one at a time with connection draining, and make clients reconnect with exponential backoff plus random jitter so the herd spreads out over seconds.
