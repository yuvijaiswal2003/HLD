Design a real-time “who's online” and typing indicator

A web-based team chat app wants two features: a green dot next to people who are online (and “last seen 5 min ago” for those who aren't), and a “Priya is typing…” indicator in a conversation. The app has 20 million daily active users and up to 5 million online at once. Users often have the app open in several tabs and on their phone.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • How quickly must status change: when someone comes online, and when they leave?
  • What does “online” mean with multiple tabs and devices, or an idle tab?
  • How large can conversations and contact lists get: 2 people, 50, 10,000?
  • Can users hide their status (invisible mode)?
  • Is it acceptable to occasionally miss a typing indicator?
  • Is there already a WebSocket connection for chat messages we can reuse?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1The client both sends (typing) and receives (presence, typing). Which connection type fits?
H2If every client sends a heartbeat to a central store every 30 s, how many writes per second is that? Can the connection itself be the heartbeat?
H3What if a whole gateway server dies? Do you need to write 100,000 “offline” records?
H4Typing events are worthless after a few seconds. Do they need storage at all?
H5A user with 2,000 contacts comes online. Who actually needs to know right now?

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: show online, away or offline for users visible on screen; show “last seen” for offline users; show who is typing in the open conversation; support multiple tabs and devices per user; invisible mode.
  • Non-functional: 5M concurrent users; coming online visible to others within ~2 s; going offline visible within ~30 s (a short delay avoids flicker); typing indicator latency p99 under 500 ms; best effort: a lost typing event is acceptable; presence must not overload the chat system.

Estimates

text
Connections
  5M concurrent, ~1.5 connections each (tabs + phone) = ~7.5M sockets
  100k per gateway -> 75 gateways, ~110 with headroom

  7.5M sockets / 30 s = 250k writes/s           (avoidable)

Connect / disconnect events instead
  20M DAU x ~10 sessions/day x 2 = 400M events/day
  400M / 86,400 s = ~4.6k/s average, ~15k/s peak

Typing
  ~10% of online users typing at any moment = 500k
  one typing event every 3 s while typing = ~170k events/s in
  ~3 recipients with the conversation open = ~500k deliveries/s

Presence state in Redis
  5M users x ~100 B = ~500 MB

Data model

Key or tableContentsNotes
Redis presence:{user_id}Hash of connection_id → gateway_id, plus away flagOnline if any connection's gateway is alive
Redis gw:{gateway_id}Liveness lease, TTL 30 s, refreshed every 10 sOne key covers all users on that gateway
PostgreSQL users.last_seen_atTimestamp written when the last connection closesDurable “last seen”; low write rate
Redis pub/sub channelsconv:{id} for typing, pres:{user_id} for status changesEphemeral; nothing is stored

High-level design

Coming online: a client opens a WebSocket to any gateway. The gateway adds the connection to presence:{user_id}; if it is the user's first connection, it publishes “online” on pres:{user_id}. Watching: when a screen shows a member list, the client sends presence.watch with the visible user IDs; the gateway reads their current state in one batched Redis call and subscribes to those users' channels. Typing: the client sends a typing event; the gateway publishes it on conv:{id}; gateways with a member viewing that conversation receive it and forward it to those sockets.

Deep dives

Detecting offline without a heartbeat flood. Gateways send WebSocket pings every 25 s and close sockets that miss two in a row; that local heartbeat never touches Redis. Each gateway refreshes one lease key, gw:{id}, every 10 s with a 30 s TTL. A user is online if any of their connections points at a gateway with a live lease. If a gateway crashes, its lease expires within 30 s and all its users read as offline, with zero per-user writes. A background sweeper later removes their stale connection entries. Central writes drop from about 250,000 per second to about 15,000 connect and disconnect events per second.

Multiple devices and flicker. A user is online while any connection exists, and “away” only when every connection reports idle. When the last connection closes, wait a grace period of about 10 to 15 s before announcing “offline”, because page reloads and Wi-Fi to cellular handoffs reconnect quickly; if the user reconnects within the grace period, nothing is published. Write last_seen_at to PostgreSQL only when the user actually goes offline.

Typing is ephemeral and throttled. The client sends at most one typing event every 3 s while keys are pressed, and a stop event when the message is sent or the input is cleared. Receivers show the indicator and hide it automatically 5 s after the last event, so a lost stop event fixes itself. Nothing is stored. Deliver typing only to members who currently have that conversation open, and in large channels collapse it to “several people are typing” after three names.

Presence fan-out. Pushing every status change to every contact is the expensive part: 15,000 changes per second times hundreds of contacts each would be millions of messages per second. Pushing only to watchers of users visible on screen (a sidebar shows perhaps 30 to 50 people) cuts it by orders of magnitude. For a 10,000-member channel, show an online count and load individual statuses on demand. Invisible mode is enforced at the gateway: changes for an invisible user are published as “offline” to everyone else.

Trade-offs and bottlenecks

  • Gateway leases mean a crashed gateway's users show online for up to 30 s. That is the price of avoiding per-user heartbeat writes.
  • The offline grace period trades accuracy (up to 15 s of false “online”) for no flicker during reconnects.
  • Redis pub/sub is fire-and-forget: a gateway that is briefly disconnected misses events. Acceptable for typing; presence recovers on the next watch or reconnect.
  • Watch-what-you-see keeps fan-out bounded but adds a batched presence read whenever the user scrolls to new people.
  • Single Redis is a bottleneck at this scale; use Redis Cluster sharded by user_id, and shard pub/sub channels across nodes.

5Follow-up questions

  • How would you show a user's own status consistently across their phone and two browser tabs?
  • Users in a 50,000-member community channel complain the member list is slow. What do you change?
  • How do you ensure a user who blocked someone doesn't leak presence to them?
  • The product wants “last active 3 minutes ago” for online-but-idle users. How do you track activity without a write per keystroke?
  • Redis loses all presence data in a failover. How does the system recover, and what do users see?
