TCP, UDP, HTTP versions and TLS

TCP vs UDP

IP delivers individual packets with no guarantees: packets can be lost, duplicated or arrive out of order. Two transport protocols sit on top. TCP (Transmission Control Protocol) provides a reliable, ordered byte stream: it numbers bytes, acknowledges them, retransmits losses, controls the sending rate so a slow receiver isn't overwhelmed (flow control), and backs off when the network is congested (congestion control). UDP (User Datagram Protocol) sends independent datagrams with almost no extras: no connection setup, no retransmission, no ordering.

TCP

Strengths
  • Reliable, ordered delivery
  • Built-in flow and congestion control
  • Universally supported by proxies, firewalls and load balancers
Weaknesses
  • 1 RTT handshake before data
  • Head-of-line blocking: one lost packet stalls all later bytes
  • Connection state on both ends
Use whenAlmost everything: HTTP/1.1 and HTTP/2, databases, Kafka, SSH, email.

UDP

Strengths
  • No handshake; send immediately
  • No head-of-line blocking; late data can be skipped
  • Small header (8 bytes vs 20+ for TCP)
Weaknesses
  • Loss, duplication and reordering are the application's problem
  • Some networks block or throttle it
  • No built-in congestion control
Use whenDNS queries, voice and video calls, online games, and as the base for QUIC and HTTP/3.

Head-of-line (HOL) blocking means one stalled item holds up everything queued behind it. In TCP, if packet 5 is lost, packets 6 to 20 may have arrived, but the application can't read them until packet 5 is retransmitted, because TCP promises in-order bytes. For a file download that is fine. For a live voice call, a sample that arrives 300 ms late is useless, so real-time media uses UDP and conceals losses instead.

The TCP and TLS handshakes

TCP opens a connection with a three-way handshake: SYN, SYN-ACK, ACK. TLS (Transport Layer Security, the S in HTTPS) then sets up encryption: the client says which cipher suites it supports and which host it wants (SNI, server name indication, so one IP can serve many certificates); the server sends its certificate, which the client verifies against trusted certificate authorities; and both derive shared session keys using an ephemeral Diffie-Hellman exchange. TLS 1.3 needs 1 RTT for this; the older TLS 1.2 needs 2.

Worked example: a user in London, a server in Virginia, RTT 80 ms. A fresh connection costs TCP (80) + TLS 1.3 (80) + request (80) = 240 ms before the first response byte, plus DNS. With TLS 1.2 it is 320 ms. Now put a CDN edge 10 ms away from the user that terminates TLS and keeps a warm, already-open connection to the origin: 10 + 10 + (10 + 80) = 110 ms. Same server, same code, less than half the latency.

Keep-alive and connection pooling

Because setup is expensive, connections should be reused. HTTP/1.1 connections are persistent (keep-alive) by default, so a browser sends many requests over the same connection. Between services, the same idea is a connection pool: an app server keeps, say, 20 open connections to PostgreSQL or to a downstream service and hands them out per request. Pools avoid handshake latency, avoid ephemeral port exhaustion, and keep the database from drowning in connection churn. PostgreSQL in particular uses one process per connection, which is why poolers like PgBouncer are common.

QUIC implements reliability, congestion control and encryption itself on top of UDP, and delivers each stream independently, so a lost packet only delays the streams whose data it carried. It identifies connections by a connection ID rather than the IP and port 5-tuple, so a phone moving from Wi-Fi to cellular keeps its connection. HTTP/3 helps most on lossy, high-latency networks such as mobile. Inside a data center, where loss is rare, HTTP/2 or HTTP/1.1 with pooling is usually fine.

In the interview
When the protocol matters in a design
You rarely need to pick an HTTP version in an interview. It matters when you discuss mobile clients on poor networks (HTTP/3 helps), internal RPC (gRPC requires HTTP/2), or global latency (terminate TLS at an edge near the user and reuse connections to the origin).
