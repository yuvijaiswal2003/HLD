API styles, HTTP methods and status codes

An API is the contract between a client and a service. Three styles dominate system design discussions: REST, GraphQL and gRPC. They are not rivals for every job; each wins in a different place.

REST

REST models the system as resources with URLs (/users/42/orders) and uses HTTP methods as the verbs. Responses are usually JSON. REST's strengths come from HTTP itself: it is understood by every language, tool and proxy, and GET responses can be cached by browsers and CDNs using Cache-Control and ETag headers. Its weakness is fixed response shapes: a mobile screen may need three calls (under-fetching), or receive fields it doesn't need (over-fetching).

http
GET /v1/users/42/orders?limit=20 HTTP/1.1
Host: api.shop.example
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: private, max-age=30

{"orders": [{"id": "o_981", "total_cents": 4599, "status": "shipped"}],
 "next_cursor": "o_955"}

GraphQL

GraphQL, created at Facebook, exposes one endpoint and a typed schema. The client sends a query naming exactly the fields it wants, possibly across related objects, and gets them in one round trip. That suits mobile apps and many-screen frontends. The costs move to the server: each field has a resolver, and naive resolvers cause the N+1 query problem (one query for the list, then one per item), usually fixed by batching with a DataLoader. Arbitrary queries can be very expensive, so servers limit query depth and cost. Queries are typically POSTed to one URL, so ordinary HTTP caching doesn't work unless you use persisted queries over GET.

text
query {
  user(id: 42) {
    name
    orders(last: 3) { id total status }
    recommendations(limit: 5) { title price }
  }
}

gRPC

gRPC, open-sourced by Google, is a remote procedure call framework. You define services and messages in a .proto file; tools generate client and server code in many languages; messages are encoded as compact binary Protocol Buffers and sent over HTTP/2. It supports unary calls and client, server and bidirectional streaming, and has deadlines built in. It shines for internal service-to-service traffic. Browsers can't speak native gRPC, so web clients need gRPC-Web through a proxy such as Envoy, and binary payloads are harder to inspect by hand.

text
service OrderService {
  rpc GetOrder (GetOrderRequest) returns (Order);
  rpc WatchOrder (GetOrderRequest) returns (stream OrderEvent);
}
message GetOrderRequest { string order_id = 1; }

REST

Strengths
  • Universal tooling; easy to debug with curl
  • HTTP caching for GET at browsers and CDNs
  • Simple mental model
Weaknesses
  • Over- and under-fetching
  • Many round trips for nested data
  • Versioning and conventions vary by team
Use whenPublic APIs, CRUD services, anything that benefits from HTTP caching.

GraphQL

Strengths
  • Client picks exactly the fields it needs
  • One round trip for nested data
  • Strongly typed schema and introspection
Weaknesses
  • HTTP caching is harder
  • N+1 resolvers and expensive queries need guarding
  • More server complexity
Use whenRich client apps with many screens and varied data needs; a backend-for-frontend layer.

gRPC

Strengths
  • Compact binary encoding, fast to parse
  • Generated, typed clients in many languages
  • Streaming and deadlines built in
Weaknesses
  • No native browser support
  • Not human-readable
  • Requires HTTP/2 end to end, which some proxies handle poorly
Use whenInternal microservice calls with high QPS and tight latency budgets.

HTTP methods: safe and idempotent

A method is safe if it doesn't change server state. It is idempotent if sending the same request once or many times leaves the server in the same state. Idempotency is what makes retries safe: networks time out, and a client often can't tell whether the server processed the request.

MethodTypical useSafeIdempotent
GETRead a resourceYesYes
HEADRead headers only, e.g. check existence or sizeYesYes
POSTCreate a resource or trigger an actionNoNo
PUTCreate or replace a resource at a known URLNoYes
PATCHPartially update a resourceNoNot guaranteed
DELETERemove a resourceNoYes

PATCH is not guaranteed idempotent because “add 10 to the balance” changes state on every retry, while “set the email to x” would not. To make a POST safe to retry, clients send an idempotency key (a unique ID per logical operation, often in an Idempotency-Key header); the server stores the result under that key and returns the stored result on a repeat instead of acting twice. Chapter 11 covers this pattern in detail.

In the interview
Default to REST, justify the exceptions
A good default: REST for the public and mobile API, gRPC between internal services, and GraphQL only when many different clients need flexible shapes. Whatever you choose, mark which endpoints are idempotent and how retries are made safe; interviewers often probe that.
