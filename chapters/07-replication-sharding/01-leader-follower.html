Why replicate: leader-follower and sync vs async

Replication means keeping copies of the same data on several machines. You do it for four reasons: availability (keep serving when a machine dies), read scaling (spread reads over many copies), latency (put a copy near users in another region) and durability (an acknowledged write exists in more than one place). Copying data once is easy. The hard part is handling changes, and there are three ways to do it.

ApproachWho accepts writesExamplesMain risk
Single-leader (leader-follower)One leader per dataset or partitionPostgreSQL, MySQL, MongoDB replica sets, Redis, Kafka partitionsReplica lag and failover
Multi-leaderSeveral leaders, usually one per region or deviceDynamoDB global tables, CouchDB, PostgreSQL BDRWrite conflicts
Leaderless (Dynamo-style)Any replica; clients write to several at onceCassandra, ScyllaDB, RiakStale reads, conflicts, repair work

Leader-follower replication

One replica is the leader (also called primary or master). Every write goes to it. The leader records each change in its replication log and streams the log to the followers (replicas, secondaries, standbys), which apply the changes in the same order. Reads can go to the leader or to any follower. Because there is a single place where writes are ordered, there are no write conflicts. This is the default in PostgreSQL streaming replication, MySQL binlog replication and MongoDB replica sets.

Synchronous, asynchronous and semi-synchronous

ModeLeader waits forIf the leader diesCostWhere you see it
AsynchronousOnly its own local commitAcknowledged writes not yet shipped are lostFastest; a slow follower never blocks writesDefault in PostgreSQL and MySQL replication
Synchronous (all followers)Every follower to confirmNo acknowledged write is lostAny one slow or dead follower stalls every writeRarely used for all followers
Semi-synchronous (one or a quorum)At least one follower, or a majority, to confirmNo loss, provided you promote a follower that confirmedOne extra round trip per commitPostgreSQL synchronous_standby_names = 'ANY 1 (s1, s2)'; MySQL semi-sync; MongoDB w: "majority"
~0.5 to 2 msExtra commit latency for a sync follower in another availability zone
60 to 150 msExtra commit latency for a sync follower in another region
under 1 sTypical lag of a healthy async follower in the same region

Two details matter in interviews. MySQL's semi-sync replica acknowledges once the change is in its relay log, meaning received, not yet applied. If no acknowledgment arrives within rpl_semi_sync_source_timeout (10 seconds by default), the source silently falls back to asynchronous replication, so monitor that state. In PostgreSQL, synchronous_commit = remote_apply waits until the standby has applied the change, so a read on that standby immediately afterwards sees it.

What travels in the replication log

Log formatWhat it shipsStrengthWeakness
Statement-basedThe SQL text, such as UPDATE ... SET n = n + 1CompactNondeterministic functions such as NOW() and RAND() diverge; MySQL moved to row-based as the default in 5.7
Physical (WAL shipping)Byte-level page changes from the storage engineExact copy, low overhead; PostgreSQL streaming replicationLeader and followers must run the same major version, and you cannot filter tables
Logical (row-based)Row images: inserted values, plus keys and new values of changed rowsWorks across versions and engines; feeds change data capture (Debezium, Chapter 9)More bytes for bulk updates; DDL handling varies

To add a follower without downtime: take a consistent snapshot that records its exact log position (PostgreSQL pg_basebackup, MySQL's clone plugin or XtraBackup with a GTID position), copy it to the new machine, then stream the log from that position until it catches up.

Pitfall
A replica is not a backup
An accidental DROP TABLE or a buggy UPDATE without a WHERE clause replicates to every follower within milliseconds. Keep point-in-time backups (Chapter 12). A delayed replica (PostgreSQL recovery_min_apply_delay, MySQL SOURCE_DELAY) set an hour behind is a cheap extra safety net.
In the interview
State the durability you are buying
'Writes go to the primary and replicate to two read replicas. One replica in another AZ is semi-synchronous, so every acknowledged write exists on two machines and failover loses nothing. The cross-region replica is async because a 100 ms commit penalty is not worth it for this data.'
