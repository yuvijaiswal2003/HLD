Design sharding for a multi-tenant SaaS database

You run a B2B project-management SaaS (think Asana or Jira) on a single large PostgreSQL primary that is running out of headroom. There are 100,000 customer companies (tenants) of wildly different sizes, a few EU customers require their data to stay in the EU, and one huge tenant regularly slows everyone else down. Design how to shard the database so it can grow 10x, keep tenants isolated, and move tenants between shards without downtime.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • How skewed are tenant sizes: what share of the data and traffic do the largest 1% of tenants have?
  • Do any queries span tenants, such as admin reporting, global search or login by email?
  • Which data-residency rules apply, and do they cover backups and logs too?
  • What downtime is acceptable when moving a tenant: none, seconds of read-only, or minutes?
  • Is it acceptable to change application code, or must sharding be transparent to it?
  • Must we support per-tenant restore, for example when a customer deletes a project by mistake?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1Almost every query already filters by tenant. What happens to joins and transactions if all of one tenant's rows live together?
H2Compare hashing tenant_id with a tenant-to-shard directory. Which one lets you put a whale on its own shard, or an EU tenant on an EU shard?
H3Lead every primary key and index with tenant_id, and use globally unique row IDs so a tenant's rows can move without colliding.
H4Moving a tenant online is snapshot, then catch up on changes, then a brief freeze, then flip the directory. How do routers with a stale cache get stopped from writing to the old shard?
H5Some lookups happen before the tenant is known, such as login by email. Give them a small global table.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: route every request to its tenant's shard; place tenants by policy (region, size, plan); move a tenant between shards online; support global lookups needed before the tenant is known (login by email).
  • Non-functional: scale to 10x data and traffic; p99 query latency under 50 ms; one tenant's load must not degrade others; at most a few seconds of read-only time per tenant move; EU tenants' data stays in the EU; no cross-tenant data leaks.

Estimates

text
Tenants and data
  100,000 tenants; 95% have under 50 users; the top 100 hold ~40% of the data
  data today 20 TB, growing ~60%/year        -> ~51 TB in 2 years
  largest tenant ~3% of data                  = ~600 GB today, ~1.5 TB in 2 years

Traffic
  1M DAU x 300 API calls/day                  = 300M/day = ~3.5k req/s average
  peak 4x                                     = ~14k req/s
  ~3 queries per request                      = ~42k queries/s at peak, 85% reads

Shard sizing
  target at most ~1 TB per primary (restore in about an hour, room to grow)
  2-year plan: 51 TB / 1 TB                   = ~50 shards; start with 24 at ~0.83 TB
  per shard at peak: 42k / 24                 = ~1.75k queries/s, easy for a primary + 2 replicas
  the largest tenant will need a dedicated shard within a year

API

http

     -> 200 { tasks: [...], next_cursor }     (tenant comes from the token, never the URL)

Data model

Each shard is an ordinary PostgreSQL cluster (a primary plus two replicas) holding the full schema for the tenants placed on it. tenant_id leads every primary key and index, so a tenant's rows cluster together, and joins and transactions never leave one shard. A small tenant directory lives in its own highly available PostgreSQL cluster and is cached on every API server. Off-the-shelf options exist: Citus distributes and co-locates PostgreSQL tables by tenant_id, and Vitess does the same for MySQL.

sql
-- Control plane: tiny, strongly consistent, cached on every API server
CREATE TABLE tenant_directory (
  tenant_id bigint PRIMARY KEY,
  shard_id  text NOT NULL,           -- 'pg-17'
  region    text NOT NULL,           -- 'us' or 'eu' (data residency)
  state     text NOT NULL,           -- active, read_only, moving
  epoch     int  NOT NULL            -- bumped on every move
);

-- On every shard: tenant_id leads every key and index
CREATE TABLE tasks (
  tenant_id  bigint NOT NULL,
  task_id    bigint NOT NULL,        -- globally unique Snowflake ID, safe to move
  project_id bigint NOT NULL,
  title      text   NOT NULL,
  status     text   NOT NULL,
  updated_at timestamptz NOT NULL,
  PRIMARY KEY (tenant_id, task_id)
);
CREATE INDEX ON tasks (tenant_id, project_id, updated_at DESC);

-- Global lookup used before the tenant is known (login)
CREATE TABLE user_logins (email text PRIMARY KEY, tenant_id bigint, user_id bigint);

High-level design

Request path: the API server authenticates the user, takes tenant_id from the token, looks up the shard in its in-memory directory cache (refreshed by a change feed, with a TTL backstop), and runs the query on that shard's primary or a replica. Every query is generated with a tenant_id = ? predicate, and PostgreSQL row-level security on the same column is a second guard against cross-tenant leaks. Login path: user_logins maps an email to its tenant before any shard is known. Analytics: cross-tenant reports run on a warehouse fed by change data capture, never by scatter-gather across production shards.

Deep dive 1: shard key and placement

OptionProsCons
Consistent hash of tenant_idNo lookup; even spread of tenant countsCannot place whales or EU tenants deliberately; one hot tenant still overloads its shard
Ranges of tenant_idSimple; easy to splitNew tenants all land on the newest range; sizes unrelated to IDs
Directory (chosen)Placement by policy: least-loaded shard in the tenant's region, dedicated shards for whales; one-row movesDirectory must be HA and cached; stale caches must be detected

Tenant count is not the load that matters; data size and QPS are, and they are extremely skewed. A directory lets the placement service put each new tenant on the least-loaded shard in its region and promote a fast-growing tenant to a dedicated shard. If one tenant ever outgrows even a dedicated shard, split it a second time by (tenant_id, project_id) within its own group of shards.

Deep dive 2: moving a tenant online

  1. Snapshot
    Start logical replication of the tenant's rows from the source shard to the target (PostgreSQL 15 publications support row filters such as WHERE (tenant_id = 4711)). At about 100 MB/s, a 50 GB tenant copies in roughly 8 minutes.
  2. Catch up
    Keep streaming changes until the replication lag is under a second. The tenant stays fully live on the source the whole time.
  3. Freeze writes
    Set the tenant to read_only in the directory and in the source shard's local tenant-state table. Writes get a retryable error for a few seconds.
  4. Drain and verify
    Wait for lag to reach zero, then compare row counts and per-table checksums for the tenant.
  5. Flip
    Point the directory at the target shard, bump the epoch and set the state to active. API servers receive the change within a second.
  6. Fence the old copy
    The source shard marks the tenant as moved. Every write transaction there checks that flag with one indexed lookup, so a router with a stale cache gets an error, refreshes its directory and retries on the right shard.
  7. Clean up
    Delete the tenant's rows from the source in small batches a day later, after backups have covered the target.

Deep dive 3: noisy neighbors and cross-shard concerns

  • Noisy neighbors: per-tenant token-bucket limits on requests and on database connections at the router (Chapter 11), plus per-statement timeouts, keep one tenant's import job from starving its shard-mates.
  • IDs: Snowflake-style global IDs (Chapter 14) mean rows never collide when a tenant moves, and IDs can be exposed in URLs safely.
  • Schema migrations: roll each migration out shard by shard with a migration tracker. Application code must tolerate both the old and new schema during the rollout.
  • Per-tenant restore: restore the shard's backup to a scratch cluster at the requested time, then copy just that tenant's rows back.
  • Residency: EU shards, their replicas and their backups live only in EU regions, and the directory refuses to place an EU tenant elsewhere.

Trade-offs and bottlenecks

  • The directory is a dependency on every request. Caching makes reads free, but a directory outage blocks only new placements and moves, not traffic.
  • Co-locating by tenant makes per-tenant joins local, but cross-tenant queries become scatter-gather, which is why they go to the warehouse.
  • Moves cost a few seconds of read-only time per tenant. Truly zero-downtime moves need dual writes, which are much more complex.
  • Dedicated whale shards cost more and run less utilized, which is a price paid for isolation that can also be charged to that customer.
  • Many shards multiply operational work (backups, upgrades, migrations), so automate shard lifecycle operations before passing about 20 shards.

5Follow-up questions

  • The whale tenant alone now needs more write throughput than the largest single machine. How do you split it?
  • An EU tenant is acquired by a US company and wants to move to the US. What has to happen, and what must you check legally and technically?
  • How do you run a schema migration that adds a NOT NULL column across 50 shards without downtime?
  • A router's directory cache is stale during a move and it writes to the old shard. Walk through exactly what prevents data loss.
  • Product wants a global search across all of a user's tenants. How do you build it without scatter-gather on the shards?
