Design a globally replicated user-profile store

Design the user-profile store for a social app with 500 million users spread across North America, Europe and Asia. Profiles (display name, username, bio, avatar URL, settings) are read constantly, since every feed item and comment shows a name and avatar, and edited rarely. Reads must be fast in every region, users must immediately see their own edits even while traveling, usernames must be globally unique, and the store must survive the loss of an entire region.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • What are the read and write volumes, and what latency is required for each?
  • Can other users see a profile edit a few seconds late, or must it appear everywhere immediately?
  • What happens when a user travels: do they keep writing to their home region?
  • After a full region outage, how much recent data may be lost (RPO), and how fast must writes resume (RTO)?
  • Are there data-residency rules, for example EU profiles stored only in the EU?
  • Can two devices edit the same profile at the same moment, and what should happen then?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1Compute the read:write ratio first. It tells you where to spend latency: reads must be local; writes can afford a cross-region trip.
H2Avoid multi-leader conflicts by giving every user a home region whose leader owns all of that user's writes.
H3Every region keeps async replicas of everyone's profile for local reads. How do you give the editing user read-your-writes when their read hits a replica?
H4For RPO zero on a region loss, make each commit wait for one replica in another region. At about 500 writes per second, can you afford that?
H5Username uniqueness is a global constraint. It needs one strongly consistent authority, and it is rare enough to pay a cross-region round trip.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: get a profile by user ID or username; update profile fields; claim or change a globally unique username.
  • Non-functional: reads p99 under 20 ms from cache and under 50 ms from the database, served in-region; writes p99 under 300 ms from anywhere; read-your-writes for the editor, other viewers within a few seconds; survive a region loss with no acknowledged writes lost and writes resuming within a minute; 99.99% read availability.

Estimates

text
Users and size
  500M users, 200M DAU; profile ~1 KB (images live in object storage)
  one full copy = 500M x 1 KB                   = 500 GB
  copies: 3 in the home region + 2 in each of 2 other regions = 7 -> ~3.5 TB total

Reads (names and avatars render everywhere)
  200M DAU x 50 profile reads/day             = 10B/day = ~116k/s average, ~350k/s peak
  90% served by regional Redis                 -> ~35k/s reach the databases, across 3 regions

Writes
  200M DAU x 0.05 edits/day                   = 10M/day = ~116/s average, ~500/s peak
  read:write ratio about 1000:1
  cross-region replication: 500/s x 1 KB x 2 remote regions = ~1 MB/s

API

http
GET   /v1/users/81723/profile            X-Min-Version: 912   (only sent by the editor)
      -> 200 { display_name, username, bio, avatar_url, version: 912 }

PATCH /v1/users/81723/profile            If-Match: 911
      { "bio": "Climber. Coffee." }
      -> 200 { version: 912 }   |   412 someone else edited it first

GET   /v1/usernames/ana_k                -> 200 { user_id: 81723 }

      -> 200   |   409 username taken

Data model

Profiles are partitioned by home region first, then by hash of user_id within the region. Each partition has a single leader in its home region, with two more replicas in other zones of that region, plus replicas in each other region for local reads (deep dive 3 makes one remote replica confirm each commit). That is single-leader per row, so there are no write conflicts. A version number on each row supports optimistic concurrency between a user's own devices. CockroachDB's REGIONAL BY ROW tables implement this layout natively; the same design can be built from per-region PostgreSQL clusters with cross-region replicas and a routing layer.

sql
CREATE TABLE profiles (
  user_id      bigint PRIMARY KEY,
  home_region  text   NOT NULL,       -- 'us', 'eu', 'ap': decides which leader owns the row
  username     text   NOT NULL,
  display_name text   NOT NULL,
  bio          text,
  avatar_url   text,
  settings     jsonb  NOT NULL DEFAULT '{}',
  version      bigint NOT NULL,       -- bumped on every write; used by If-Match and X-Min-Version
  updated_at   timestamptz NOT NULL
);

-- Global uniqueness: one strongly consistent authority, replicated by consensus
CREATE TABLE usernames (
  username   text PRIMARY KEY,        -- the unique constraint does the work
  user_id    bigint NOT NULL,
  claimed_at timestamptz NOT NULL
);

High-level design

Read path: GeoDNS sends users to the nearest region. Any profile is read from the regional Redis cache, then from that region's replica, with no cross-region hop, whoever owns the row. Write path: the API server looks up the user's home region (it is stored on the profile and cached) and forwards the write to that region's leader. A user at home pays no forwarding hop; a traveler pays one extra cross-region round trip, about 80 to 200 ms, which is acceptable for a rare action. The leader commits once one replica in another region has also flushed the change, using PostgreSQL-style quorum commit ANY 1 (eu_replica, ap_replica), which typically means waiting about 80 ms for the nearest region. Each region runs a change-data-capture consumer that deletes the cache key when a replicated change arrives, with a 10-minute TTL as a backstop.

Deep dive 2: read-your-writes and monotonic reads across regions

  1. Write returns a version
    The leader bumps version to 912 in the same transaction and returns it.
  2. Client remembers it
    The app keeps min_version = 912 for the user's own profile, and the server stores it per user for 60 seconds so the user's other devices get it too.
  3. Read checks freshness
    The user's own profile reads send X-Min-Version. The regional API serves from cache or replica only if that copy's version is at least 912.
  4. Fall back if behind
    If the local copy is older, wait up to 100 ms for replication, then read from the home leader. This is rare: one cross-region read right after an edit.
  5. Everyone else reads freely
    Other viewers send no token and may see the old bio for a second or two, which the requirements allow. Clients keep the highest version they have seen, so the profile never moves backwards on refresh.

Deep dive 3: region failure and usernames

Region loss. If the US region goes dark, reads continue everywhere, since every region holds a copy of every profile, and US users are re-routed by GeoDNS to the EU. For US-homed partitions, a controller picks the remote replica with the highest replayed position. Quorum commit guarantees that at least one remote replica has every acknowledged write. The controller takes a lease and a new epoch from the etcd cluster (five members spread 2-2-1 across three regions, so it survives losing any one region) and promotes that replica. RPO is zero and RTO is under a minute. When the US returns, its old leaders see the higher epoch and rejoin as followers after rewinding any unacknowledged tail (PostgreSQL pg_rewind), so there is no split brain and no lost acknowledged write.

Usernames. Uniqueness cannot be checked against a stale replica, so the usernames table lives in a small store replicated by consensus across all three regions, such as Spanner or CockroachDB configured to survive a region failure. A claim inserts the username row, where the primary key does the uniqueness check at the cost of one cross-region quorum round trip, about 100 to 200 ms, and then updates the profile. If the profile update fails, a cleanup job releases the orphaned claim. Username lookups read from local follower replicas, so a name claimed a second ago may briefly not resolve in another region.

Trade-offs and bottlenecks

  • Quorum commit adds about 80 ms to every profile write in exchange for zero RPO. That is a good trade at 500 writes per second, and a bad one for a write-heavy store.
  • Travelers pay cross-region latency on writes. If many users move permanently, re-home them by copying their row and flipping home_region.
  • Seven copies of every profile cost about 3.5 TB, which is cheap next to the read latency it buys.
  • Other users can see a profile a few seconds stale, and cache invalidation through CDC can lag during replication backlogs; the TTL caps the damage.
  • The username authority is the one globally coordinated component, and it is kept small and touched only on claims and renames.

5Follow-up questions

  • EU regulators require EU users' profiles to be stored only in the EU, yet US users must still see their names. How do you reconcile those?
  • Lag to the AP region grows to 30 seconds during a backlog. What do users notice, and what do you alert on?
  • How would you design 'follower count' on the profile, which changes thousands of times per second for celebrities?
  • Two of a user's devices edit the bio at the same moment. Walk through what each one sees.
  • How would you migrate this from a single-region PostgreSQL deployment without downtime?
