Chapter 7: Replication, Partitioning and Consistent Hashing

Copy data for safety and speed, split it for scale, and know what breaks when you do.

Remember for the interview

  1. 01Replicate for availability, read scale, latency and durability. The hard part is propagating changes, done with single-leader, multi-leader or leaderless replication.
  2. 02Async replication is fast but loses acknowledged writes on failover. Semi-sync (wait for one follower or a majority) keeps every acknowledged write on two machines for one extra round trip.
  3. 03Replica lag anomalies have targeted fixes: read-your-writes (read own data from the leader or require a caught-up replica), monotonic reads (stick a user to one replica), consistent prefix (keep causally related writes in one partition).
  4. 04Failover means detect, elect the most up-to-date replica, reroute and fence. Prevent split brain with majority-based leases and epoch fencing, not shorter timeouts.
  5. 05In multi-leader setups, avoid conflicts first with a home leader per record. LWW silently drops concurrent writes, version vectors detect concurrency, and CRDTs merge automatically.
  6. 06Quorums: with R + W > N, reads overlap the latest write. N = 3, W = 2, R = 2 tolerates one node down, but quorums are not linearizable (sloppy quorums, LWW clocks, partial writes).
  7. 07Range partitioning gives cheap scans but hot-spots sequential keys; hash partitioning spreads load but scatters range queries; directory partitioning gives flexible placement at the cost of a lookup service.
  8. 08Hashing never fixes a single hot key: split it into sub-keys, cache it, or handle celebrities and whale tenants specially.
  9. 09Local secondary indexes keep writes cheap but make reads scatter-gather; global indexes give one-partition reads but asynchronous or transactional writes.
  10. 10Never use hash % N over nodes: consistent hashing moves about 1/N of keys when a node joins, and virtual nodes even out load and spread recovery.
