Partitioning: range, hash and directory

Partitioning, usually called sharding, splits a dataset so that each node holds only part of it. You need it once the data, or the write throughput, outgrows what one machine can handle. Replication still applies: each partition has replicas on several nodes, and each node holds replicas of many partitions. Every system uses its own name: shard, partition, region (HBase), tablet (Bigtable), range (CockroachDB), chunk (MongoDB), vnode (Cassandra), vBucket (Couchbase).

Three ways to assign keys to partitions

StrategyHow a key is placedGood atBad atExamples
RangeContiguous key ranges per partition, such as A to F; boundaries move as data growsRange scans and ordered reads; splitting hot rangesSequential keys such as timestamps or auto-increment send all writes to one partitionHBase, Bigtable, CockroachDB, TiKV, MongoDB ranged sharding
Hashhash(key) picks the partition, often through consistent hashingSpreading load evenly, even for sequential keysRange queries across keys must ask every partitionCassandra, DynamoDB, MongoDB hashed sharding, Redis Cluster
Directory (lookup)A lookup table maps each key, or tenant, to a partitionMoving single tenants, isolating big ones, data residencyThe directory sits in the request path and must be fast and highly availableVitess lookup vindexes, many multi-tenant SaaS products

Range partitioning keeps neighboring keys together, so 'all events from 10:00 to 10:05' is a single scan. But a key that always increases, such as a timestamp, sends every new write to the last range. The usual fix is to lead the key with something that spreads writes, such as (sensor_id, timestamp), accepting that a time scan across all sensors must touch every range.

Hash partitioning destroys order on purpose, which is what spreads the load. A compound key gets you both: Cassandra hashes the partition key to pick the nodes, then keeps rows sorted by clustering columns inside the partition, so 'messages in channel 7, newest first' is a cheap range read inside one partition. Never use hash(key) % number_of_nodes; the last lesson of this chapter shows why.

Directory-based partitioning trades a lookup for flexibility. A tenant can move to a new shard by copying its data and updating one row. The directory must be cached on every router, versioned so stale caches are detected, and replicated so it is never a single point of failure. A related trick is to embed the shard in the ID: Instagram's IDs carry a 13-bit logical shard number, so any server can route an ID without a lookup.

Hot spots and the celebrity problem

Hashing spreads different keys across partitions, but every request for the same key still lands on one partition. A celebrity's post, a viral product or a whale tenant can overload a single partition while the rest of the cluster idles. DynamoDB, for example, caps a single partition at about 3,000 read units and 1,000 write units per second.

  • Split the hot key: write to likes:post42:0 through likes:post42:99 at random, and read by summing the sub-keys or from a cached total. Writes spread 100 ways, and reads cost 100 lookups, so apply this only to keys known to be hot.
  • Cache hot reads in Redis or in process memory, with request coalescing (Chapter 5).
  • Treat celebrities differently: for example, fan out a celebrity's posts on read instead of on write (Chapter 16).
  • Isolate whales: give the biggest tenants dedicated shards through the directory.
  • Let the system split by load: DynamoDB splits hot partitions, and CockroachDB does load-based range splitting. Neither can split a single hot key.
python
import random
SHARDS = 100  # only for keys known to be hot

def incr_like(kv, post_id):
    kv.incr(f"likes:{post_id}:{random.randrange(SHARDS)}")   # spread the writes

def get_likes(kv, post_id):
    keys = [f"likes:{post_id}:{i}" for i in range(SHARDS)]
    return sum(int(v or 0) for v in kv.mget(keys))            # gather on read; cache it

Secondary indexes on partitioned data

A partition key answers 'get by ID' with a single partition. A query by any other attribute, such as 'all red products', needs a secondary index, and that index must be partitioned too. There are two ways to do it.

Local index (document-partitioned)

Strengths
  • A write updates only its own partition's index, in the same local transaction
  • Simple and always consistent with the data
Weaknesses
  • Every secondary-key query fans out to all partitions
  • Tail latency follows the slowest partition; capacity does not grow as you add partitions
Use whenWrite-heavy data with occasional secondary queries: MongoDB and Cassandra secondary indexes, Elasticsearch shards.

Global index (term-partitioned)

Strengths
  • A secondary-key query reads one index partition
  • Read capacity scales with the index
Weaknesses
  • One write can touch several partitions
  • Updated either asynchronously (stale reads) or with a distributed transaction (slower writes)
Use whenRead-heavy lookups by another attribute: DynamoDB global secondary indexes (asynchronous), CockroachDB and Spanner indexes (transactional).

Scatter-gather gets worse with scale. If each partition is slow 1% of the time, a query that must wait for 100 partitions is slow 1 - 0.99^100, or about 63%, of the time. That is why high-traffic secondary lookups usually earn a global index or a separate lookup table.

In the interview
Choose the partition key from the dominant query
Pick the key that turns the most frequent queries into single-partition operations, then check every other query out loud: 'Fetch a user's orders hits one partition. Find an order by ID needs a global index or an ID that embeds the user. Admin search across all users is a scatter-gather, which is fine at 1 QPS.'
