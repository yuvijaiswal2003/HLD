Replication lag and its anomalies

Asynchronous followers lag behind the leader. On a healthy system the lag is milliseconds to under a second, but it can grow to seconds or minutes under heavy write load, during a long-running query on the replica, or when the network degrades. While it lasts, reads from a follower can return stale data. Calling the system eventually consistent is true but vague. Interviewers want three specific guarantees, each with a targeted fix.

Read-your-writes

Read-your-writes (also called read-after-write consistency) promises that after a user writes something, that user's own reads reflect it. Other users may still see the old value for a while.

  • Read your own data from the leader. Profile pages read the viewer's own profile from the leader and other people's profiles from followers. This is simple and enough for most products.
  • Pin to the leader for a short window. For a few seconds after a user writes (say twice the p99 lag), route that user's reads to the leader.
  • Carry a position token. The write returns its log position (PostgreSQL LSN, MySQL GTID, a version number). The client sends it back with later reads, and a follower serves the read only if it has replayed that far; otherwise the read goes to the leader or waits briefly. MongoDB's causally consistent sessions do this for you with afterClusterTime.
  • Cross-device reads need the token stored server-side, keyed by user ID, because a cookie on the phone does not help the laptop.

Monotonic reads

Monotonic reads promises that a user never sees time move backwards. Without it, a user sees a new comment, refreshes, hits a replica that is further behind, and the comment vanishes. The fix is to route each user's reads to the same replica, for example by hashing the user ID, and to fail over to another replica only if that one is down. A position token works too: never serve a user from a replica older than the newest position they have already seen.

python
def read_profile(user_id, session):
    min_lsn = session.get("last_write_lsn")    # set when this user last wrote
    replica = replicas[hash(user_id) % len(replicas)]   # sticky: monotonic reads
    if min_lsn is None or replica.replayed_lsn() >= min_lsn:
        return replica.query(PROFILE_SQL, user_id)       # caught up: read-your-writes
    return leader.query(PROFILE_SQL, user_id)            # too far behind: use leader

Consistent prefix reads

Consistent prefix reads promises that if writes happened in a certain order, anyone reading them sees them in that order. It breaks mainly in partitioned databases, where each partition replicates on its own schedule. If a question is stored on partition 1 and its answer on partition 2, and partition 1 is lagging, an observer can see the answer before the question. The fix is to keep causally related writes in the same partition (partition a conversation's messages by conversation_id) or to track causal dependencies explicitly (causal consistency, Chapter 8).

GuaranteeSymptom when brokenTypical fixCost
Read-your-writesMy edit disappears right after I saveRead own data from the leader, or require a replica caught up to my write positionMore load on the leader, or a token to track
Monotonic readsData appears, then disappears on refreshStick each user to one replica, or track the newest position seenUneven replica load; fallback handling
Consistent prefixAn answer is visible before its questionKeep related writes in one partition, or track causal orderConstrains the partition key
Pitfall
Watch lag, and stop sending reads to laggards
Alert on replication lag, and take a replica out of the read pool when it falls too far behind. ProxySQL's max_replication_lag and health checks that compare the replica's replay position with the leader's both do this. Otherwise one slow replica quietly serves minutes-old data to a third of your users.
In the interview
The most common follow-up in this area
'A user updates their profile and still sees the old one.' Name the guarantee (read-your-writes), then give the cheapest targeted fix: 'Reads of your own profile go to the primary, or to a replica whose replay LSN is at least the LSN of your last write. Everyone else's profile can be served from any replica.' Don't propose synchronous replication everywhere.
