Multi-leader replication and conflict resolution

In multi-leader replication, several nodes accept writes, and each one replicates its changes to the others asynchronously. Three situations call for it. In multi-region deployments, each region has a leader, so writes are local and fast and every region keeps working if another goes dark. In offline-capable clients, each device is effectively a leader (a calendar or notes app on a phone). In collaborative editing, every user's local copy accepts edits.

The price is write conflicts. If two leaders change the same record before they hear about each other's change, both writes have already been acknowledged, and the system has to end up with one answer anyway. Examples include DynamoDB global tables, CouchDB and PouchDB, and EDB Postgres Distributed (formerly BDR). Cassandra's multi-datacenter mode is leaderless rather than multi-leader, but it faces the same conflicts.

Ways to resolve conflicts

StrategyHow it worksLoses data?Used by
Conflict avoidanceRoute every write for a given record to one home leader, such as the user's home regionNo, unless the home changes during a failoverThe most common practical choice
Last write wins (LWW)Keep the version with the highest timestamp and discard the restYes, silently. Clock skew can even let the older write winCassandra (per cell), DynamoDB global tables by default
Keep siblingsDetect concurrent versions with version vectors, store all of them, and merge on read or ask the userNo, but the application must write merge logicRiak, CouchDB conflicting revisions, the original Dynamo
CRDTsUse data types whose merge is commutative, associative and idempotent, so all replicas converge automaticallyNo, for the operations the type supportsRiak data types, Redis Enterprise Active-Active, Automerge and Yjs

Version vectors: telling 'newer' from 'concurrent'

A timestamp can say which write came later by the clock, but not whether one writer had seen the other's write. A version vector keeps one counter per replica, such as {us: 3, eu: 1}. Each replica increments its own entry when it accepts a write. When comparing two versions: if every entry of A is greater than or equal to the matching entry of B, A supersedes B and B can be dropped. If each has an entry larger than the other's ({us: 3, eu: 1} versus {us: 2, eu: 2}), the writes were concurrent, and both must be kept as siblings. Vector clocks and causality are covered in depth in Chapter 8.

CRDTs at a high level

A CRDT (conflict-free replicated data type) builds the merge into the data type. The simplest is a grow-only counter: each replica counts only its own increments, the value is the sum, and merging takes the maximum of each replica's entry. Merges can happen in any order and any number of times, and every replica still ends up with the same total. Richer CRDTs exist for counters that go down (PN-Counter), sets (OR-Set), maps, and text sequences for collaborative editors (Chapter 14).

python
class GCounter:
    """Grow-only counter CRDT: one slot per replica, merge takes the max."""
    def __init__(self, replica_id):
        self.id = replica_id
        self.counts = {}                    # replica_id -> increments made there

    def increment(self, n=1):
        self.counts[self.id] = self.counts.get(self.id, 0) + n

    def value(self):
        return sum(self.counts.values())

    def merge(self, other):                 # order and repetition do not matter
        for rid, c in other.counts.items():
            self.counts[rid] = max(self.counts.get(rid, 0), c)

us, eu = GCounter("us"), GCounter("eu")
us.increment(3); eu.increment(2)            # concurrent, while partitioned
us.merge(eu); eu.merge(us); us.merge(eu)    # repeated merges are harmless
assert us.value() == eu.value() == 5        # no increment lost
In production
Amazon's shopping cart
The 2007 Dynamo paper describes Amazon's cart. When replicas held concurrent versions of a cart, the application merged them by taking the union of items. 'Add to cart' was never lost, which mattered most to the business, at the cost that an item the customer had deleted could occasionally reappear.
Pitfall
LWW is data loss by design
Under last write wins, two writes that were both acknowledged can end with one silently discarded. That is fine for a 'last seen at' timestamp or a cache entry, and wrong for a bank balance or a document body. If you choose LWW, say so out loud and say why losing a concurrent write is acceptable for that data.
In the interview
Avoid conflicts before you resolve them
The best answer usually avoids multi-leader conflicts: 'Each user has a home region, and all writes to that user's data go to its leader there. Other regions serve local reads from async replicas. Only if we truly need concurrent writes to the same record, such as a shared counter, do I use a CRDT.'
