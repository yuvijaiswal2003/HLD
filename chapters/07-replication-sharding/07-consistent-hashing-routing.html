Consistent hashing, rebalancing and request routing

The naive way to spread keys is node = hash(key) % N. It balances well, until N changes. A key stays put only if hash % N equals hash % (N + 1), which is true for only about 1 in N + 1 keys. Growing from 10 to 11 nodes moves about 91% of all keys. For a cache, that is a miss storm that can take down the database behind it. For a database, it means migrating nearly everything.

The hash ring

Consistent hashing (Karger et al., 1997, designed for distributed web caches and later the basis of Akamai's CDN) maps both nodes and keys onto the same circular hash space, for example every 64-bit value, with the largest value wrapping back to zero. Each node is placed at the hash of its name, called its token. A key belongs to the first node clockwise from the key's hash. When node E joins, it takes over only the keys between its predecessor and itself, about 1/(N + 1) of the total, and every other key stays where it was. When a node leaves, only its keys move, to its successor.

Virtual nodes

With one token per node, random positions leave some nodes with arcs several times larger than others. When a node dies, its whole arc falls on a single neighbor, which may then overload too. Bigger machines also cannot take a bigger share. Virtual nodes fix all three: each physical node is placed at many points on the ring, typically 100 to 256, so its share is the sum of many small arcs. Load evens out, a failed node's keys scatter across many survivors, and a machine with twice the capacity gets twice the virtual nodes.

These figures come from running the code below with 10 nodes and 50,000 keys over 8 runs. The ideal fraction to move is 1/11, about 9.1%. With few virtual nodes, the share the new node takes is as random as everyone else's, anywhere from 2% to 31%. With 100 or more it stays close to ideal. In every run, every key that moved went to the new node; no keys shuffled between old nodes.

python
import bisect, hashlib

def ring_pos(key):
    # 64-bit position on the ring; md5 is stable across processes, hash() is not
    return int.from_bytes(hashlib.md5(key.encode()).digest()[:8], "big")

class ConsistentHashRing:
    def __init__(self, vnodes=100):
        self.vnodes = vnodes
        self.tokens = []    # sorted ring positions of every virtual node
        self.owner = {}     # ring position -> physical node

    def add_node(self, node):
        for i in range(self.vnodes):
            pos = ring_pos(f"{node}-vn{i}")
            bisect.insort(self.tokens, pos)
            self.owner[pos] = node

    def remove_node(self, node):
        for i in range(self.vnodes):
            pos = ring_pos(f"{node}-vn{i}")
            self.tokens.remove(pos)
            del self.owner[pos]

    def get_node(self, key):
        # first virtual node clockwise from the key, wrapping past the top
        i = bisect.bisect(self.tokens, ring_pos(key)) % len(self.tokens)
        return self.owner[self.tokens[i]]
python
    def replicas(self, key, n=3):
        # keep walking clockwise until n DISTINCT physical nodes are found
        start = bisect.bisect(self.tokens, ring_pos(key))
        found = []
        for j in range(len(self.tokens)):
            node = self.owner[self.tokens[(start + j) % len(self.tokens)]]
            if node not in found:
                found.append(node)
                if len(found) == n:
                    break
        return found        # found[0] owns the key; the rest hold its replicas

ring = ConsistentHashRing(vnodes=256)
for name in ["db1", "db2", "db3", "db4", "db5"]:
    ring.add_node(name)
ring.get_node("user:42")        # 'db1'
ring.replicas("user:42", n=3)   # ['db1', 'db4', 'db2']
ring.remove_node("db3")         # only db3's keys move, spread over the other four

replicas() builds Dynamo's preference list. It skips extra virtual nodes of a machine already chosen, and production systems also skip nodes in the same rack or availability zone. Cassandra cut its default num_tokens from 256 to 16 in version 4.0, pairing it with a smarter token allocator: fewer tokens make repair and streaming cheaper while keeping balance. Related schemes you can name: rendezvous hashing (each key picks the node with the highest hash(key, node)), jump consistent hash (no memory, but buckets can only be added or removed at the end) and Maglev hashing in Google's load balancers.

Rebalancing strategies

StrategyHow it worksExamplesWatch out for
Many fixed partitionsCreate far more partitions than nodes up front and move whole partitions between nodes; keys never change partitionRedis Cluster's 16,384 hash slots, Couchbase's 1,024 vBuckets, Instagram's thousands of logical shards on fewer databases, Elasticsearch shardsThe count is hard to change later: Elasticsearch fixes an index's primary shard count at creation, and changing it means a split, shrink or reindex
Dynamic splittingSplit a range or partition when it grows too big or too hot, and merge small onesMongoDB chunks (128 MB default), CockroachDB ranges (512 MiB), HBase regions, DynamoDB partitions (10 GB)An empty database starts as one partition, so pre-split before a bulk load
Proportional to nodesEach node owns a fixed number of tokens; a joining node takes slices from many othersCassandra and ScyllaDB virtual nodesStreaming and repair cost grows with the token count
Directory movesCopy one tenant or key range, catch up on changes, then flip the directory entryVitess MoveTables and Reshard, Citus shard movesNeeds a short write freeze or dual writes during the cutover
Pitfall
Automatic rebalancing can cascade
Suppose a node slows down, the failure detector declares it dead, and the cluster starts moving its data. The transfer loads the remaining nodes, which slow down too and get declared dead in turn. Throttle data movement, separate 'temporarily down' (rely on hints and replicas) from 'permanently gone' (rebalance), and keep a human approving large moves.
