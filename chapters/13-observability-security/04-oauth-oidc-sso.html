OAuth 2.0, OpenID Connect and single sign-on

OAuth 2.0 solves delegated access: letting an app act on your behalf at another service without giving it your password. A calendar app can read your Google contacts because Google issued it an access token limited to specific scopes, not because you typed your Google password into it. OAuth has four roles: the resource owner (the user), the client (the app requesting access), the authorization server (issues tokens after the user logs in and consents, such as Okta, Auth0, Keycloak or Google) and the resource server (the API that accepts the tokens).

Authorization code flow with PKCE

The browser is sent to the authorization server, the user logs in there, and the browser comes back to the app with a short-lived, single-use authorization code. The app then exchanges the code for tokens in a direct back-channel request. Tokens never pass through the URL bar or browser history. PKCE (Proof Key for Code Exchange, pronounced "pixy") closes the remaining hole: before starting, the client makes a random secret code_verifier and sends only its SHA-256 hash, the code_challenge. At the token step it must present the verifier itself.

python
import base64, hashlib, secrets

def b64url(data: bytes) -> str:
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode()

code_verifier = b64url(secrets.token_bytes(32))          # 43 chars, kept by the client
code_challenge = b64url(hashlib.sha256(code_verifier.encode()).digest())
state = secrets.token_urlsafe(16)                         # CSRF protection for the callback

# step 1: redirect with code_challenge, code_challenge_method=S256, state
# step 2: POST /token with code and code_verifier; server recomputes the hash

Why it matters: on mobile and desktop, another app can register the same custom URL scheme and intercept the redirect carrying the code; in browsers, codes can leak through logs or referrer headers. Without PKCE, whoever holds the code can redeem it. With PKCE, the attacker also needs the verifier, which never left the client, and the hash in the request does not reveal it. PKCE was designed for public clients (single-page apps, mobile and desktop apps, which cannot keep a client secret), and current guidance (the OAuth security best current practice, RFC 9700, and the OAuth 2.1 draft) requires it for public clients and recommends it for confidential server-side clients too, so just use it everywhere. Two more rules: the state parameter ties the callback to the session that started the flow (preventing login CSRF), and the server must match the redirect_uri exactly against a registered value.

OpenID Connect: adding identity

OAuth by itself is about authorization: an access token says "the bearer may read mail", not who the user is. OpenID Connect (OIDC) is a thin identity layer on top. The client adds the openid scope and receives an ID token: a JWT whose audience is the client, with sub (a stable user ID), iss, exp, auth_time and the nonce the client sent (which prevents replaying an old ID token). OIDC also standardizes a /userinfo endpoint, a discovery document at /.well-known/openid-configuration and the JWKS endpoint for signing keys.

Pitfall
ID token and access token are not interchangeable
The ID token tells the client who logged in; it is meant to be read by the client and nothing else. The access token is meant for an API and should carry that API in its aud claim. An API that accepts ID tokens as credentials, or that accepts any token without checking aud, can be fooled with a token that was issued for a different app.

Single sign-on

Single sign-on (SSO) lets a user log in once and then use many apps. It falls out of the flow above. The authorization server, now called the identity provider (IdP), sets its own session cookie on its domain at the first login. When a second app redirects the user to the IdP, the IdP sees that session and immediately issues a code with no password prompt. Enterprises use SAML 2.0 (XML assertions, older and very common in enterprise SaaS) or OIDC (JSON and JWT, the modern default). IdPs can also federate: your IdP trusts a customer's Okta or Microsoft Entra ID, so their employees sign in with their corporate account.

In the interview
Keep the vocabulary straight
Say "OIDC for login and SSO, OAuth access tokens for APIs, authorization code with PKCE for every user-facing client, client credentials or mTLS for service-to-service." Mention the state and nonce parameters and exact redirect URI matching if asked about security. Mixing up OAuth (authorization) with authentication is the most common slip.
