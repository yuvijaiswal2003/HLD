Authorization models: RBAC, ABAC and ReBAC

Once you know who the caller is, every request asks: may this subject perform this action on this resource? Two principles apply regardless of model: default deny (no rule means no access) and least privilege (grant the minimum needed). The models differ in how they express rules.

RBAC: role-based access control

Permissions attach to roles, and users get roles: admin can do everything, editor can write articles, viewer can read. It is simple to understand and to audit ("who has admin?"), and it covers most internal tools and B2B products. Its failure mode is role explosion: when access depends on context ("editor, but only for the EMEA region's documents"), teams create emea-editor, apac-editor and so on until there are thousands of roles nobody understands.

ABAC: attribute-based access control

Policies are rules over attributes of the subject, resource, action and environment: "allow read if user.department == doc.department and doc.classification != secret and the request comes from a managed device." ABAC handles context without role explosion and is how AWS IAM condition keys work. Policy engines such as Open Policy Agent (Rego) and AWS Cedar let you keep policies as code, separate from the application. The cost: it is hard to answer "who can access this document?" because the answer depends on evaluating rules against every user's attributes.

ReBAC: relationship-based access control

In collaborative products, access follows relationships: Alice can edit a document because she is in a team that is an editor of the folder that contains the document. ReBAC stores those relationships as a graph and answers checks by walking it. Google described its system, Zanzibar, in a 2019 paper; it stores relation tuples of the form object#relation@subject and a schema of rewrite rules that derive permissions from relations.

text
# relation tuples  (object#relation@subject)
doc:q4-plan#parent@folder:roadmap
folder:roadmap#editor@team:eng#member
team:eng#member@user:alice
doc:q4-plan#viewer@user:bob

# schema: rules that derive permissions
doc.edit = doc.editor  OR  parent.editor
doc.view = doc.viewer  OR  doc.edit  OR  parent.viewer

check(doc:q4-plan, edit, user:alice) -> ALLOWED  (alice -> team:eng -> folder:roadmap -> doc)
check(doc:q4-plan, edit, user:bob)   -> DENIED   (bob is only a viewer)

The paper reports Zanzibar serving Google Drive, YouTube, Calendar, Cloud and other products, with trillions of tuples, millions of checks per second and p95 latency under 10 ms. One subtle design point is the new enemy problem: if you remove Bob from a folder and then add a secret document to it, a stale replica must not let Bob see the new document. Zanzibar solves this with consistency tokens ("zookies") that tie a check to a snapshot at least as new as the content change. Open-source implementations include SpiceDB and OpenFGA.

RBACUser → role → permissionSimple, auditable, fastRole explosion when context mattersAdmin consoles, internal tools, B2B seat roles
ABACPolicies over attributesContext-aware: time, device, department, data classificationHard to audit and to list who has accessEnterprise and compliance rules, cloud IAM
ReBACRelationship graph plus rewrite rulesNatural for sharing, nesting and inheritance; can answer who has accessNeeds a dedicated, consistent, low-latency serviceDocs and files, chat channels, social and multi-tenant SaaS

Where to enforce

  • Gateway: coarse checks only: the token is valid, unexpired, for this audience and carries the needed scope.
  • Service: fine-grained, per-resource checks, because only the service knows which document or order is involved. Call the authorization service or evaluate a local policy.
  • Lists and search: filter results by permission ("list documents Alice can see") rather than checking after fetching thousands of rows; ReBAC systems offer list or lookup APIs for this.
  • Caching: cache decisions briefly, and accept that a revoked permission may linger for that TTL, or use consistency tokens.
  • Audit: log every denied request and every change to roles or relationships.
In the interview
Pick the model from the product
For a Google Docs-, Slack- or Dropbox-style design, say "ReBAC, Zanzibar-style: tuples for owner, editor and viewer, inheritance from folders, a check API with p99 under 10 ms, and consistency tokens for the new enemy problem." For an admin console, RBAC is enough, and saying so shows judgment. Many real systems combine them: RBAC for org roles plus ReBAC for sharing.
