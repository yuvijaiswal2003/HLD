Common attacks and defenses

System design interviews rarely go deep on exploits, but they expect you to recognize the classic attacks, know the standard defense for each, and place those defenses in the architecture. Most of these attacks share a root cause: the system treats untrusted input as code, or trusts a request because of where it came from.

SQL injection

If user input is concatenated into a SQL string, an attacker can change the query itself. The defense is parameterized queries (prepared statements), where the driver sends the SQL and the values separately so input can never become syntax. ORMs do this by default. Add defense in depth: the app's database user gets only the privileges it needs, so even a successful injection cannot DROP tables or read other schemas.

python
# Vulnerable: input becomes part of the SQL text
cur.execute("SELECT id, name FROM users WHERE email = '" + email + "'")
# email = "x' OR '1'='1"  -> returns every user

# Safe: placeholder; the value is sent separately and never parsed as SQL
cur.execute("SELECT id, name FROM users WHERE email = %s", (email,))

Cross-site scripting (XSS)

XSS injects script into a page other users view: a comment containing a script tag (stored XSS), a malicious link whose query parameter is echoed into the page (reflected XSS), or client code writing untrusted data into the DOM. The script runs with the victim's privileges on your origin and can read tokens, call APIs and change the page. Defenses: context-aware output encoding (modern template engines and React escape by default; avoid raw-HTML escape hatches), sanitize any user HTML you must allow (for example with DOMPurify), a strict Content-Security-Policy that blocks inline and third-party scripts, and HttpOnly cookies so scripts cannot steal the session.

Cross-site request forgery (CSRF)

Browsers automatically attach cookies to requests to your domain, even when the request is triggered by another site. A malicious page can auto-submit a hidden form to bank.example/transfer, and the victim's session cookie goes along. Defenses: SameSite=Lax or Strict cookies (Chromium-based browsers treat cookies without the attribute as Lax, but set it explicitly), an unpredictable CSRF token in each form or header that the server checks, verifying the Origin header, and never changing state on GET. APIs authenticated with a bearer token in the Authorization header are not exposed to CSRF, because browsers do not attach that header automatically.

Server-side request forgery (SSRF)

Any feature where your server fetches a URL the user supplies (link previews, "import from URL", webhooks, image fetching) can be turned against your internal network. The attacker submits an internal address, and your server, which sits inside the trusted network, fetches it for them: an admin endpoint, an internal database's HTTP interface, or the cloud instance metadata service at 169.254.169.254, which can hand out the server's IAM credentials. Defenses: allowlist destinations where possible; resolve the hostname and block private, loopback and link-local ranges, re-checking after every redirect and against DNS rebinding; route fetches through an egress proxy in an isolated network segment; and require IMDSv2 on AWS, whose session tokens and hop limit block most SSRF paths to metadata.

In production
Capital One, 2019
An attacker abused a misconfigured web application firewall to make SSRF requests to the AWS metadata service, obtained the credentials of the role attached to the instance, and used them to copy data from S3 on about 100 million people in the US and Canada. The incident is a common reason teams now enforce IMDSv2 and keep instance roles narrowly scoped.

Distributed denial of service (DDoS)

DDoS attacks overwhelm you with traffic from many sources. Volumetric attacks flood bandwidth, often using amplification: small spoofed requests to open DNS, NTP or memcached servers produce large responses aimed at the victim. In 2018 GitHub absorbed a memcached amplification attack peaking at about 1.35 Tbps. Protocol attacks such as SYN floods exhaust connection tables. Application-layer (L7) attacks send realistic-looking HTTP requests to expensive endpoints like search or login. Defense is layered, and the first layers belong to providers with far more capacity than you have.

In the interview
Where defenses live in your diagram
Draw the edge explicitly: "CDN with DDoS protection and a WAF in front, rate limiting at the gateway (Chapter 11), TLS terminated at the load balancer, mTLS inside." Then mention input handling at the services (parameterized queries, output encoding) and SSRF protection for any URL-fetching feature. Security placed on the diagram beats a list of buzzwords at the end.
