Design single sign-on for a suite of business apps

A company sells a suite of business apps (mail, calendar, chat, video meetings and a file drive) to organizations, as web, mobile and desktop clients on separate subdomains. Design single sign-on so a user logs in once and can use every app, enterprise customers can connect their own identity provider such as Okta or Microsoft Entra ID, and an admin can disable a user everywhere within a minute.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • How many organizations and users, and what are peak login rates, for example 9 a.m. Monday across time zones?
  • Which client types: browser, iOS, Android, desktop? Do the apps call each other's APIs directly?
  • Must we support SAML for enterprise IdPs as well as OIDC, and SCIM for automated user provisioning?
  • What are the session rules: idle timeout, maximum session length, MFA requirements set per organization?
  • How fast must revocation take effect, and does it have to cut off already-open WebSocket connections such as chat and meetings?
  • Are there per-region data residency requirements for identity data?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1Put one identity provider at the center. What protocol do the apps use to talk to it, and what does each app keep after login?
H2SSO comes from the IdP's own session. How does the second app get a user signed in without prompting for a password?
H3Enterprise customers bring their own IdP. Can your IdP act as a client to theirs, so the apps never need to know?
H4Access tokens are verified locally for speed. How do you still revoke a disabled user in under a minute, including long-lived WebSocket connections?
H5Every app now depends on the IdP. How do you make it highly available, and what keeps working if it is briefly down?

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: one login across mail, calendar, chat, meet and drive on web, mobile and desktop; MFA and passkeys; organizations can federate their own IdP (OIDC or SAML); SCIM provisioning; single logout; admin disable takes effect everywhere.
  • Security: authorization code + PKCE for every client, short-lived access tokens with audience per app API, refresh token rotation, full audit log of logins and admin actions.
  • Revocation: a disabled user loses access to all apps, including open WebSocket connections, within 60 seconds.
  • Availability: the IdP is on every login path, so it targets 99.99%, and existing sessions must keep working through short IdP outages.
  • Latency: token verification adds under 1 ms per API request; an SSO hop into a second app takes under 500 ms.

Estimates

  • 50M users, 20M daily active, each using 3 apps on 2 devices.
  • Interactive logins: assume one a day per active user, with a morning peak at 5x the average: 20,000,000 / 86,400 ≈ 230 per second average, about 1,200 per second at peak. Each involves a password or passkey check; Argon2id at ~50 ms of CPU each means roughly 60 CPU cores at peak for hashing alone, which federated and passkey logins reduce.
  • Token refreshes: 20M users × 3 apps × 2 devices with 10-minute access tokens across an 8-hour active day = 120M sessions × 48 ≈ 5.8B refreshes a day ≈ 67k per second, the dominant load. Use 15-minute tokens and refresh only while an app is active to cut this substantially.
  • API verification: tens of millions of requests per minute across the apps, all verified locally with cached public keys, so zero calls to the IdP.
  • Session store: 120M sessions × ~1 KB ≈ 120 GB, which fits a Redis cluster with replicas, backed by a durable database.

Data model

Identity data (users, organizations, credentials, federation settings) lives in PostgreSQL, replicated across AZs with a synchronous standby, because it needs transactions and uniqueness for emails. Sessions and refresh tokens live in Redis for fast lookups, with durable copies in the database so a Redis failure does not log everyone out.

High-level design

First login: the user opens the mail web app, which redirects to auth.suite.com with a PKCE challenge. The IdP looks up the email domain; if the organization federates, the IdP acts as an OIDC or SAML client of the customer's Okta and redirects there. After the customer's IdP authenticates the user, the suite IdP creates its own session (an HttpOnly, Secure cookie on auth.suite.com), issues an authorization code, and the mail backend exchanges it for an ID token, a 15-minute access token with aud=mail-api, and a refresh token. Second app: opening the calendar redirects to the IdP, which finds its session cookie and issues a code without prompting; the user sees a brief redirect. API calls: gateways verify the JWT signature with cached JWKS keys and check iss, aud, exp and scopes, with no network call.

Deep dive: revocation within 60 seconds

  1. Disable
    An admin, or a SCIM update from the customer's IdP, sets the user's status to disabled, deletes their IdP sessions and refresh tokens, and sets min_token_iat to now.
  2. Publish
    The IdP publishes a user_disabled event to a Kafka topic, and pushes OpenID back-channel logout notifications to each app's backend.
  3. Block at gateways
    Every API gateway consumes the topic and keeps a small in-memory denylist of user IDs with min_token_iat, so tokens issued before that time are rejected within seconds. Entries expire after the maximum access-token lifetime, 15 minutes, so the list stays small.
  4. Close live connections
    Chat and Meet WebSocket gateways consume the same event and close the user's connections. Reconnecting requires a fresh token, which the IdP will not issue.
  5. Backstop
    Even if an event is missed, the access token expires within 15 minutes and refresh fails. Gateways also re-sync the denylist on startup from the database.

Deep dive: brokering enterprise IdPs

The apps only ever speak OIDC to the suite's IdP; the IdP translates. For each organization it stores the customer's IdP metadata (OIDC issuer and client credentials, or a SAML certificate and SSO URL). It maps the external identity to an internal user_id by a stable claim (OIDC sub or SAML NameID), never by display name, and verifies that the email domain belongs to that organization so one customer cannot assert users of another. SCIM keeps users and group membership in sync automatically, which also powers the disable path. Organization admins choose MFA policy; when they federate, MFA usually happens at their IdP, and the suite can require an acr or amr claim proving it did.

Deep dive: availability of the IdP

  • The IdP is stateless behind load balancers across 3 AZs; session data is in a replicated Redis cluster with PostgreSQL as the durable copy.
  • Most traffic never touches it: API verification is local, so an IdP outage blocks only new logins and refreshes, not current work. Allowing a short grace period for refresh retries keeps users signed in through a brief blip.
  • Publish signing keys ahead of use: keep the next key in JWKS before signing with it, so gateway caches already have it when rotation happens.
  • Deploy the IdP active-active in at least two regions with replicated session data; it is the one service whose outage stops everything.

5Follow-up questions

  • How would you implement single logout so signing out of mail also signs the user out of every other app and device?
  • A customer's Okta tenant goes down for an hour. What do their users experience, and can you offer a break-glass login?
  • How would you add step-up authentication, requiring fresh MFA before a user downloads a whole drive folder?
  • How do service-to-service calls work, for example calendar asking mail to send invites on a user's behalf?
  • How would you rotate the token signing key safely without logging anyone out?
