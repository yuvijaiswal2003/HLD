Logs, metrics and traces

Monitoring tells you that something you anticipated is wrong: error rate is up, the disk is full. Observability is the ability to answer questions you did not anticipate, such as "why are checkouts from Android users in Brazil slow since 14:05?", from the telemetry the system already emits. That telemetry comes in three forms, often called the three pillars: logs, metrics and traces. Each answers a different question, and a production system needs all three.

Logs: what exactly happened

A log is a timestamped record of a discrete event. Write them as structured logs, one JSON object per line with consistent field names, not free-form text, so a log platform can filter and aggregate on fields without fragile regexes. Use levels deliberately: DEBUG (off in production by default), INFO (normal milestones), WARN (unexpected but handled), ERROR (a request or job failed), and FATAL (the process cannot continue).

json
{
  "ts": "2026-10-22T14:05:31.204Z",
  "level": "ERROR",
  "service": "checkout",
  "version": "2026.10.21-3",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "request_id": "req_7Hc91",
  "user_id": "u_8812",
  "route": "POST /v1/orders",
  "msg": "payment authorization failed",
  "psp": "adyen",
  "error_code": "PSP_TIMEOUT",
  "duration_ms": 2003
}
  • Correlation IDs: generate a request ID (or use the trace ID) at the edge, pass it to every downstream call, and put it in every log line, so one search returns the whole story of a request across 15 services.
  • Never log secrets (passwords, tokens, card numbers) and minimize personal data; logs are copied widely and kept for a long time.
  • Mind the volume: 10,000 requests per second × 5 lines × 500 bytes = 25 MB/s, about 2.2 TB a day. Sample noisy success logs, keep all errors, and set retention by value.
  • Ship logs to a central store such as Elasticsearch/OpenSearch, Loki or Splunk. Chapter 10 designs that pipeline.

Metrics: how much and how fast

A metric is a numeric value sampled over time, identified by a name and a set of labels, for example http_requests_total{service="checkout", code="500"}. Metrics are cheap to store (a few bytes per sample after compression), fast to query and easy to aggregate across thousands of servers, which makes them the basis for dashboards and alerts. Prometheus, Datadog, CloudWatch and InfluxDB are common systems.

Use percentiles, not averages, for latency. If 1,000 requests are sorted by duration, p50 is the 500th, p99 the 990th. An average of 80 ms can hide 1% of users waiting 4 seconds. Two traps: you cannot average percentiles (the mean of ten servers' p99s is not the fleet's p99; merge histogram buckets instead), and tails compound under fan-out. If a page calls 100 backends and each is slow 1% of the time, 1 − 0.99^100 ≈ 63% of page loads hit at least one slow call.

Pitfall
Label cardinality kills metrics systems
Every unique combination of label values is a separate time series. method (5) × status (10) × endpoint (50) × instance (200) is already 500,000 series. Add a user_id label with a million users and you have hundreds of billions, which no TSDB can hold. Put high-cardinality fields like user IDs in logs and traces, not metric labels.

Two checklists tell you which metrics to collect. The RED method (Tom Wilkie) is for request-driven services: Rate (requests per second), Errors (failed requests per second) and Duration (latency distribution). The USE method (Brendan Gregg) is for resources such as CPUs, disks, network links and connection pools: Utilization (percent busy), Saturation (queued work that cannot be served yet) and Errors. Google SRE's four golden signals (latency, traffic, errors, saturation) combine the two.

Traces: where the time went

A distributed trace follows one request through every service it touches. It is a tree of spans; each span is one unit of work (an HTTP handler, a SQL query, a cache call) with a trace ID, its own span ID, its parent's span ID, a start time, a duration and attributes. Context propagation makes this work: each service forwards the trace context to the next, over HTTP in the W3C traceparent header (version, 32-hex-digit trace ID, 16-hex-digit parent span ID, flags) and over Kafka or other queues in message headers. Instrument with OpenTelemetry and send spans to a backend such as Jaeger, Zipkin, Grafana Tempo or Honeycomb.

Tracing every request is expensive, so you sample. Head-based sampling decides at the first hop (keep 1%) and passes the decision downstream in the trace flags: cheap, but it throws away 99% of the rare slow or failed requests you most want. Tail-based sampling buffers all spans of a trace in a collector and decides after the trace completes: keep every error and every request slower than p99, plus 1% of the rest. It costs more memory and infrastructure but keeps the interesting traces.

In the interview
How the pillars work together
"An alert fires on the checkout error-rate metric. The dashboard shows errors started at 14:05 on version 2026.10.21-3. A trace of a failed request shows 2 seconds spent in the payment-service span. Searching logs for that trace ID shows PSP_TIMEOUT from one processor." Metrics tell you that something is wrong, traces where, and logs why. Linking them by trace ID is the key design point.
