Design a metrics monitoring and alerting system

Design a metrics monitoring and alerting platform like Prometheus or Datadog for a company running 10,000 servers and about 500 microservices. Teams must be able to send metrics, build dashboards, query recent and historical data, and define alerts that notify on-call engineers through PagerDuty, Slack or email.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • How many active time series, and at what collection interval: 10 seconds, 15, or 60?
  • Push (agents send metrics) or pull (the system scrapes endpoints), or both?
  • How long must data be kept at full resolution, and is downsampled long-term data acceptable?
  • What query latency do dashboards need, and how many people view them at once during an incident?
  • How quickly must an alert fire after a problem starts, for example under one minute?
  • Is this metrics only, or also logs and traces? Do we need multi-tenancy with per-team quotas?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1Size it first: active series × samples per second gives the ingestion rate. How many bytes does a sample take after compression?
H2Metrics data is append-only, time-ordered and queried by recent time ranges. What storage layout and compression does that suggest instead of a general-purpose database?
H3Ingestion must survive bursts and node failures. Where would you put a durable buffer, and how would you partition the data?
H4Old data is rarely queried at full resolution. How do you keep a year of data affordable?
H5The alerting system must keep working when the infrastructure it monitors is failing. How do you avoid it sharing the same fate, and how do you avoid paging 500 times for one outage?

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: ingest counters, gauges and histograms with labels; query with a PromQL-like language; dashboards; alert rules with routing, grouping, silencing and escalation.
  • Scale: about 10M active time series at a 10-second interval, growing 2x a year.
  • Retention: 15 days at full resolution, 13 months downsampled.
  • Latency: dashboard queries over the last hour in under 1 second; alerts fire within 1 minute of the condition.
  • Reliability: alerting must be more available than the systems it monitors, and must keep working during partial outages.

Estimates

  • Series: 10,000 hosts × ~1,000 series each (system plus application metrics) ≈ 10M active series.
  • Ingestion: 10M series / 10 s = 1M samples per second, peaking at maybe 2M during deploys when series churn.
  • Raw size: a sample is a 64-bit timestamp plus a 64-bit float, 16 bytes. Gorilla-style compression (delta-of-delta timestamps, XOR-encoded values) gets this to about 1.37 bytes per sample, the figure Facebook reported for Gorilla.
  • Storage per day: 1M × 86,400 × ~1.5 B ≈ 130 GB a day; 15 days ≈ 2 TB, ×3 replicas ≈ 6 TB. Without compression it would be about 1.4 TB a day.
  • Downsampled: 5-minute rollups (min, max, sum, count) are 30x fewer points: about 4–5 GB a day before rollup overhead, so 13 months is a few TB in object storage.
  • Network: 1M samples/s × ~100 bytes on the wire with labels, before compression ≈ 100 MB/s into the ingestion tier.

Data model

A series is identified by its metric name plus sorted labels, hashed to a 64-bit series ID. Data is stored in a purpose-built time-series database (Prometheus TSDB format, as used by Thanos, Cortex/Mimir or VictoriaMetrics), not a relational or general key-value store, because the workload is append-only, time-ordered, highly compressible and queried by label matchers over time ranges.

High-level design

Write path: agents on each host scrape local endpoints (pull, so the system knows when a target is down via an up metric) and remote-write batches to stateless distributors. Distributors validate, enforce per-tenant limits on series count and rate, and write to Kafka partitioned by series ID, so all samples of a series land on the same ingester in order. Ingesters append to an in-memory head block and a WAL, replicate (3 copies via Kafka consumers or quorum writes), and every 2 hours flush a compressed, immutable block to object storage. Read path: the query frontend splits a range query by time, serves cached results for older intervals, sends the recent part to ingesters and the older part to store gateways that read blocks from object storage, and merges the results.

Deep dive: compression and cardinality

Compression is what makes the system affordable. Scrape timestamps are nearly regular, so the delta-of-delta is usually zero and fits in one bit. Consecutive values of a series are close, so XOR with the previous value gives mostly zero bits. This turns 16 bytes into about 1.4. The real threat is cardinality: memory per active series in the ingesters is several kilobytes (labels, index entries, the open chunk), so 10M series need tens of GB of RAM across the cluster, and one team adding a user_id label can add millions of series in minutes. Enforce per-tenant series limits at the distributor, reject or drop offending labels, and expose a cardinality explorer so teams can see their top metrics.

Deep dive: alerting that works during outages

  • Evaluate rules close to the data: rule evaluators run every 30–60 seconds on recent data from the ingesters. A for: 2m clause requires the condition to hold across consecutive evaluations, which suppresses one-off blips.
  • Alertmanager receives firing alerts, groups them (500 instances of one service down becomes one notification), deduplicates across evaluator replicas, applies inhibition (do not page for app errors when the whole data center is down) and silences, then routes by labels to the owning team's PagerDuty or Slack.
  • Run Alertmanager as a 3-node cluster that gossips notification state, so a node failure does not drop pages; delivery is at-least-once, so a rare duplicate page is possible during a partition.
  • Independent failure domain: the monitoring stack runs in separate infrastructure or a separate region, and a dead man's switch (an always-firing alert sent to an external service) pages if the alert pipeline itself goes silent.
  • Meta-monitoring: a small, separate Prometheus watches the monitoring system's own ingestion lag, rule evaluation duration and notification failures.

Deep dive: long-range queries

A 30-day dashboard over 1,000 series at 10-second resolution would read 1,000 × 259,200 ≈ 260M points. With 1-hour rollups it reads 720,000. The query frontend picks the coarsest resolution that still gives at least one point per pixel, splits the query into day-sized pieces that run in parallel, and caches results for completed days, since data older than a few hours no longer changes.

5Follow-up questions

  • How would you support SLO tracking and multi-window burn-rate alerts as a built-in feature for every service?
  • An ingester crashes with 90 minutes of unflushed data in memory. Walk through the recovery and what the dashboards show meanwhile.
  • A team wants per-customer latency metrics for 2M customers. How do you serve that without destroying the TSDB?
  • How would you add exemplars so a latency spike on a graph links directly to an example trace?
  • How would you make the system multi-region while still giving a global view of all metrics?
