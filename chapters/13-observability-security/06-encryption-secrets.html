Encryption, secrets and password storage

Data must be protected in two states: in transit across networks and at rest on disks, in databases, in backups and in object storage. On top of that come the secrets that unlock everything (keys, database passwords, API tokens) and the one kind of data you should never be able to read back: user passwords.

In transit: TLS and mTLS

Use TLS 1.3 (Chapter 2 covers the handshake) for all external traffic, typically terminated at the load balancer or CDN. Internal traffic used to be plain text inside a "trusted" network; modern zero-trust designs encrypt it too, because an attacker who gets onto the network should not be able to read or forge service calls. Mutual TLS (mTLS) has both sides present certificates, so the server also authenticates the client service. Doing this by hand is painful; a service mesh such as Istio or Linkerd issues short-lived certificates (hours, rotated automatically) to sidecars and gives each workload an identity, often in SPIFFE format, that authorization policies can reference.

At rest: KMS and envelope encryption

At rest, encryption happens at several layers: full-disk or volume encryption (protects against stolen disks), database or storage-service encryption (S3 server-side encryption, transparent data encryption in databases), and application-level or field-level encryption for the most sensitive fields, which also protects against someone with database access. The hard part is not the cipher (AES-256-GCM is the default) but the keys. A key management service (AWS KMS, Google Cloud KMS, Azure Key Vault, HashiCorp Vault) keeps master keys inside the service, backed by hardware security modules in AWS KMS and in the HSM tiers of the others, never exports them, enforces IAM on every use and logs every operation. The pattern for using it is envelope encryption.

  • Performance and limits: gigabytes are encrypted locally at memory speed; only a 32-byte key goes to KMS. KMS APIs are rate limited and accept only small payloads (AWS KMS encrypts at most 4 KB directly).
  • Rotation: rotating the master key means re-wrapping data keys, not re-encrypting petabytes.
  • Blast radius: one data key per object, tenant or file limits what a single leaked key exposes.
  • Crypto-shredding: delete a tenant's key and all their data, including copies in backups, becomes unreadable. This is a practical way to honor deletion requests.
  • Audit: every unwrap is an authorized, logged KMS call, so you can see who decrypted what.

Secrets management

  • No secrets in source code, git history, container images or plain config files. Scanners such as GitHub secret scanning exist because leaked keys are found and abused within minutes.
  • Store them in a secrets manager (HashiCorp Vault, AWS Secrets Manager, Google Secret Manager) and fetch them at startup or through a sidecar, with access controlled per service.
  • Prefer workload identity over static keys: IAM roles for compute instances or Kubernetes service accounts give short-lived credentials automatically.
  • Use dynamic secrets where possible: Vault can mint a database user that expires in an hour, so a leaked credential dies on its own.
  • Rotate regularly and make rotation boring, so an emergency rotation is not the first time you try it.

Storing passwords

Never store passwords in plain text or with reversible encryption: you only ever need to verify a password, so store a one-way hash. Fast hashes such as MD5 or SHA-256 are the wrong tool, because a single modern GPU computes billions of SHA-256 hashes per second and cracks most leaked human passwords quickly. Use a deliberately slow, salted, tunable password hash. A unique random salt per user, stored next to the hash, means identical passwords produce different hashes and precomputed rainbow tables are useless. Tune the cost so one hash takes tens of milliseconds on your servers: invisible at login, ruinous for an attacker making billions of guesses.

MD5, SHA-1, SHA-256 (even salted)Never for passwordsDesigned to be fast; GPUs try billions of guesses per second

Pitfall
Do not invent crypto
Use TLS libraries, KMS envelope encryption and standard password hashes as designed. Hand-rolled schemes ("we XOR with a secret", "we SHA-256 the password twice", reusing a nonce with AES-GCM) are where real breaches come from. Add rate limiting and MFA on login, and a hash will rarely be your last line of defense.
In the interview
One-sentence security posture
"TLS everywhere with mTLS between services through the mesh, encryption at rest with KMS-managed keys using envelope encryption, per-tenant data keys so we can crypto-shred, secrets in Vault with workload identity, and passwords hashed with Argon2id." Each phrase invites a follow-up you can answer.
