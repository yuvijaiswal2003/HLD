Lesson 6 of 7 · 10 min read

Retries, dead-letter queues, backpressure and lag

Messages fail for two kinds of reasons. Transient failures (a downstream timeout, a deadlock, a 503 from a partner API) usually succeed on retry. Permanent failures (malformed JSON, a schema the consumer does not understand, a bug triggered by one particular input) fail every time; such a message is a poison message. Retrying a poison message forever wastes capacity and, on a log-based broker, blocks every message behind it.

Retries in queues vs logs

In SQS or RabbitMQ, failure is per message: the consumer simply does not acknowledge, and the message is redelivered later while others flow past it. In SQS a received message becomes invisible for the visibility timeout (30 seconds by default, up to 12 hours); if it is not deleted in time it reappears, and the queue's redrive policy moves it to a dead-letter queue (DLQ) after maxReceiveCount receives. RabbitMQ routes rejected or expired messages to a dead-letter exchange, and quorum queues can cap redeliveries with a delivery limit. In Kafka there is no per-message ack: the consumer cannot commit offset 501 while skipping 500, so a stuck message stalls its partition.

The retry topic pattern: on a transient failure, the consumer publishes the message to a retry topic with metadata (attempt count, error, original topic and offset) and commits the original offset, so the main partition keeps moving. A retry consumer reads each retry topic and pauses until each message's due time; because every message in a given retry topic has the same delay, they become due in the order they arrived. After the last tier, the message goes to the DLQ. The trade-off: a message for key K that goes to retry can be overtaken by newer messages for K. If per-key order matters, either retry in place with backoff (accepting the stall) or park every later message for that key until the failed one clears.

In production
Uber's retry topics
Uber's engineering team published this design for Kafka in 2018: a chain of retry topics with increasing delays, each consumed by a delayed retry consumer, ending in a dead-letter topic that engineers inspect and can replay once the underlying problem is fixed.
  • Detect poison early. Classify errors: deserialization and validation failures go straight to the DLQ; timeouts and 5xx responses go to retry.
  • Make the DLQ useful. Store the original payload, headers, error message, stack trace, attempt count and source offset. Alert when it is non-empty.
  • Plan the redrive. After a fix, replay DLQ messages back to the main topic (SQS has a built-in DLQ redrive). Consumers must be idempotent, since some replayed messages may have partially succeeded.
  • Back off with jitter between attempts (Chapter 12) so a recovering dependency is not hit by a synchronized wave of retries.

Backpressure

Backpressure is how a slow stage tells a fast stage to slow down. Pull-based consumers apply it naturally: they fetch only what they can handle, and the broker holds the rest. The pressure then moves to the broker's storage and to latency. Producers need limits too: the Kafka producer blocks send (up to max.block.ms) when its buffer.memory is full, brokers can enforce per-client byte-rate quotas, and RabbitMQ applies flow control to publishers when memory or disk alarms fire. Inside a consumer, use bounded in-memory queues between the poll loop and worker threads; an unbounded buffer turns overload into an out-of-memory crash.

Consumer lag

Consumer lag is how far a consumer group trails the head of the log: per partition, the log-end offset minus the group's committed offset. Track it in records and, more usefully, in time (age of the oldest unprocessed record), because '50,000 messages behind' means nothing without the rate. Steady lag near zero is healthy; lag that grows without recovering means consumers cannot keep up, and if it approaches the retention period, unprocessed data will be deleted.

SymptomLikely causeFix
Lag grows on every partitionConsumers are under-provisioned or a dependency got slowerAdd consumers up to the partition count, batch database writes, scale the dependency
Lag grows on one partition onlyHot key, or a stuck poison messageBetter key choice or key salting; route the poison message to a DLQ
Lag saw-tooths with frequent rebalancesProcessing exceeds max.poll.interval.ms, or pods restartSmaller max.poll.records, cooperative or static membership, faster processing
SQS age of oldest message keeps risingToo few workers, or a visibility timeout shorter than processing time causing repeated redeliveryScale workers on queue depth; raise or extend the visibility timeout
Tip
Autoscale on lag, within limits
Tools such as KEDA scale Kubernetes consumers from Kafka lag or SQS queue depth. For Kafka, the maximum useful replica count equals the partition count, so size partitions for your peak consumer count ahead of time.
