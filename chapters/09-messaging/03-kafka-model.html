Kafka internals: partitions, offsets and consumer groups

A Kafka cluster is a set of brokers (servers). Data is organized into topics, and each topic is split into partitions. A partition is an ordered, append-only log stored on disk as a series of segment files. Every message appended to a partition gets the next sequential offset (0, 1, 2 ...), which identifies it within that partition. Offsets are per partition: offset 42 in partition 0 and offset 42 in partition 1 are unrelated messages.

Producers and partition keys

A producer sends each record to a topic with an optional key. If the record has a key, the default partitioner hashes it (murmur2 in the Java client) and takes the result modulo the partition count, so every record with the same key lands in the same partition, in the order it was sent. Records without a key are spread across partitions; since Kafka 2.4 the producer 'sticks' to one partition until the current batch is full or sent, then switches, which gives bigger batches. Producers batch records per partition (tuned with linger.ms and batch.size) and compress whole batches, which is a large part of Kafka's throughput.

text
topic "orders", 3 partitions, key = order_id

partition 0 | off 0: o-17 CREATED | off 1: o-17 PAID   | off 2: o-41 CREATED | ...
partition 1 | off 0: o-23 CREATED | off 1: o-23 PAID   | off 2: o-23 SHIPPED | ...
partition 2 | off 0: o-09 CREATED | off 1: o-55 CREATED | off 2: o-09 PAID    | ...

partition = murmur2("o-23") mod 3 = 1, always, while the count stays 3
all events for o-23 are in partition 1, in send order
no ordering exists between o-17 in partition 0 and o-23 in partition 1

Consumers and consumer groups

Consumers pull records from brokers and track their position, the offset of the next record to read. Consumers that share a group.id form a consumer group: each partition is assigned to exactly one consumer in the group, so the group divides the work. Different groups are fully independent: each has its own offsets and receives every record. Groups periodically commit their offsets to an internal topic, __consumer_offsets, so a replacement consumer resumes where the previous owner stopped.

  • Parallelism is capped by partitions. A group can have at most one active consumer per partition. With 12 partitions, a 13th consumer sits idle.
  • Rebalancing. When a consumer joins, leaves or misses heartbeats, partitions are reassigned. With the old 'eager' protocol the whole group pauses; cooperative rebalancing (CooperativeStickyAssignor) moves only the affected partitions, static membership (group.instance.id) lets a restarting pod reclaim its partitions without a rebalance, and Kafka 4.0 made a new broker-coordinated group protocol generally available.
  • Slow processing triggers rebalances. If a consumer does not call poll within max.poll.interval.ms (5 minutes by default), it is removed from the group and its partitions are reassigned, so its in-flight records get processed twice.

Ordering guarantees

Kafka guarantees order within a partition only. There is no global order across a topic's partitions. If you need all events about one entity in order (all updates to order o-23, all moves in one chess game), make that entity's ID the key. If you need total order across everything, you need a single partition, which caps throughput at what one partition and one consumer can do.

Retention and compaction

Consuming a record does not delete it. Kafka deletes old data by policy: time-based retention (retention.ms, default 7 days) or size-based retention (retention.bytes per partition, unlimited by default), applied by dropping whole old segments. Because data persists, a new consumer group can read history from the beginning, and a team that ships a bug can reset its offsets and reprocess. The alternative policy, log compaction (cleanup.policy=compact), keeps at least the latest record for every key and discards older ones; a record with a null value (a tombstone) eventually removes the key. A compacted topic is a durable changelog of current state, ideal for rebuilding a cache or a table of user settings.

Choosing the key and the partition count

Key choiceOrdering you getRisk
order_idAll events of one order in orderLittle risk: high cardinality, even spread
customer_idAll events of one customer in orderHot partition if one B2B customer generates 30% of traffic
countryPer-country orderSevere skew: a handful of keys, a few partitions take most load
No keyNoneBest spread; use it only when order truly does not matter

Pick the narrowest key that gives the ordering you need, with high cardinality and no dominant values. For the partition count, divide the target throughput by what one consumer can process: at 50,000 msg/s with consumers that each handle 2,000 msg/s you need at least 25 partitions; choose something like 48 for headroom. Plan the count up front, because adding partitions remaps keys: hash mod 48 differs from hash mod 64, so new records for a key may land in a different partition than its older records, breaking per-key ordering across the change. Kafka never moves existing data, and partitions cannot be removed.

Tip
Why Kafka is fast
Appends and sequential reads are the fastest operations disks have. Kafka leans on the OS page cache instead of its own cache, batches and compresses records end to end, and sends data from page cache to the network socket with zero-copy (sendfile). A consumer that is keeping up usually reads from memory, not disk.
In the interview
The questions you will get
'How do you preserve ordering?' Key by the entity ID, and ordering holds per partition. 'How do you scale consumers?' Add consumers up to the partition count. 'What happens when a consumer dies?' The group rebalances, a surviving consumer takes the partition and resumes from the last committed offset, so some records are processed again.
