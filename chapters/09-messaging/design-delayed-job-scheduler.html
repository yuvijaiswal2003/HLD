Design a distributed delayed-job scheduler

Design a service that lets internal teams schedule a job to run at a specific future time T, from seconds to months ahead: 'send this reminder at 09:00 tomorrow', 'expire this cart in 30 minutes', 'retry this webhook in 5 minutes'. Jobs must fire close to T, survive machine failures, and be cancellable.

45:00Mock interview timer. Start it when you begin talking.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • How many jobs are scheduled per day, how many are pending at once, and how far ahead?
  • How precise must firing be: within 1 second, 10 seconds, a minute?
  • Is at-least-once execution acceptable if job handlers are idempotent?
  • What does 'run' mean: call an HTTP endpoint, or publish a message to the owner's topic?
  • Do we need recurring (cron) schedules, or only one-shot jobs?
  • Are there traffic spikes at round times, such as midnight or the top of the hour?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1Kafka cannot delay individual messages, and SQS delays cap at 15 minutes. You need a store indexed by due time.
H2Storing jobs by due time makes 09:00:00 a hot partition. How do you spread one time bucket across many partitions?
H3Split the work: a durable store holds far-future jobs; scheduler nodes load only jobs due in the next minute or so into memory.
H4Each time-bucket shard must be owned by exactly one scheduler node at a time. Use leases from a coordination service, and fence stale owners.
H5Firing is a state change, SCHEDULED to ENQUEUED, made with a conditional write. Then hand the job to a queue that workers consume with an idempotency key.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: schedule a one-shot job (run_at, target topic, payload, idempotency key); cancel or reschedule before it fires; query status; optional recurring schedules expanded one occurrence at a time.
  • Non-functional: fire within 2 seconds of T at p99; never lose an accepted job; at-least-once execution, with duplicates rare and detectable; 99.95% availability for scheduling; scale to 1B pending jobs and 50k firings/s at peaks.

Estimates

  • 200M new jobs/day ÷ 86,400 s ≈ 2,300 writes/s average, ~10k/s peak.
  • Firings average the same ~2,300/s, but round times spike: if 5% of a day's jobs target 00:00:00, that is 10M jobs due in one second. We cannot dispatch that in one second, so we either smear it (jobs declare a tolerance window) or accept a short drain: at 50k/s, 10M takes 200 s.
  • Pending storage: 1B jobs × ~1 KB ≈ 1 TB; × RF 3 = 3 TB in the job store.
  • Lookahead memory: at 50k firings/s peak with a 60 s lookahead, ~3M jobs in memory across all scheduler nodes × ~200 B (ID, run_at, small payload reference) ≈ 600 MB, spread over a dozen nodes.

API

http
POST /v1/jobs
Idempotency-Key: cart-expire-c77
{"run_at": "2026-10-23T09:00:00Z", "tolerance_s": 30,
 "target_topic": "cart-expirations", "payload": {"cart_id": "c-77"}}
  -> 201 {"job_id": "j-7f3a", "status": "SCHEDULED"}

DELETE /v1/jobs/j-7f3a
  -> 204, or 409 if already fired

GET /v1/jobs/j-7f3a
  -> 200 {"status": "ENQUEUED", "fired_at": "2026-10-23T09:00:00.4Z"}

Data model

Use Cassandra or DynamoDB: very high write rates, simple key access, and range scans within a partition. Two tables, both written when a job is created:

sql
-- Jobs by due time: what scheduler nodes scan
CREATE TABLE jobs_by_time (
  bucket   text,       -- run_at truncated to the minute: '2026-10-23T09:00'
  shard    int,        -- hash(job_id) mod 256, splits hot minutes
  run_at   timestamp,
  job_id   text,
  target   text, payload blob, status text,
  PRIMARY KEY ((bucket, shard), run_at, job_id));

-- Jobs by id: status lookups, cancels, idempotent creates
CREATE TABLE jobs_by_id (
  job_id text PRIMARY KEY, idempotency_key text,
  bucket text, shard int, run_at timestamp,
  status text,        -- SCHEDULED, ENQUEUED, CANCELLED, DONE, FAILED
  attempt int);

High-level design

Schedule path: the API writes both rows (status SCHEDULED) and returns. A job due within the current lookahead window is also pushed straight to the owning scheduler node so it is not missed by a scan that already ran. Fire path: every few seconds each scheduler node reads the next minute's buckets for the shards it owns, ordered by run_at, and loads them into an in-memory hierarchical timing wheel (or a min-heap). When a job comes due, the node changes its status from SCHEDULED to ENQUEUED with a conditional write, publishes the payload to the target Kafka topic with the job ID as key and as idempotency header, and moves on. Owner teams consume their topic like any other.

Deep dives

1. Why not just use a queue's delay? SQS per-message delays max out at 15 minutes, and RabbitMQ has no native arbitrary delay without a plugin. Kafka stores records in append order, not due-time order, so a record due tomorrow would block everything appended after it. Kafka works for fixed delays (a retry-5m topic, where all records become due in append order), but arbitrary T needs a time-indexed store. A Redis sorted set (score = run_at, poll with ZRANGEBYSCORE) is a fine choice at smaller scale and is how Sidekiq stores scheduled jobs, but holding a terabyte of pending jobs in memory is expensive.

2. Hot buckets. Partitioning only by minute would put every 09:00 job in one Cassandra partition and one scheduler node. Adding shard = hash(job_id) mod 256 splits each minute into 256 partitions, spread over many nodes, and the shards are spread across scheduler nodes. For round-time spikes, jobs with a tolerance_s are fired anywhere within their window, smoothing the dispatch rate, and dispatch is rate-limited per target topic to protect owners from a flood.

3. Exactly one firing node, at least once execution. Shard ownership comes from etcd leases with fencing tokens (Chapter 8). A node that loses its lease, for example after a long GC pause, stops firing; if it fires anyway, the conditional status update (UPDATE ... SET status = 'ENQUEUED' IF status = 'SCHEDULED', a Cassandra lightweight transaction or a DynamoDB condition expression) fails because the new owner already moved the job. The remaining gap is a crash between the status update and the Kafka publish: on taking over a shard, a node republishes recent ENQUEUED jobs whose fire acknowledgment is missing. That can produce a duplicate, which is why consumers deduplicate on job_id. The guarantee is at least once, with duplicates rare.

4. Cancellation, retries and recurrence. Cancel sets status CANCELLED with the same conditional write, so it either wins before firing or returns 409. Failed executions are rescheduled as new occurrences with exponential backoff and an attempt count, ending in a DLQ topic after N attempts. A recurring job stores its cron expression; when one occurrence fires, the scheduler writes the next occurrence in the same step, so only one future occurrence exists at a time.

Tip
Timing wheels
A hierarchical timing wheel puts timers into slots of a circular array (one slot per second, say), with coarser wheels for longer delays, giving O(1) insert and cancel. Kafka itself uses hierarchical timing wheels to manage delayed requests in its request purgatory.

5Follow-up questions

  • How would you guarantee firing within 100 ms instead of 2 seconds? What gets more expensive?
  • A team schedules 50M jobs for exactly midnight on New Year's Eve. Walk through what happens.
  • How would you move shard ownership when adding scheduler nodes without double-firing or missing jobs?
  • How do you support 'run at 09:00 in the user's local time zone' across daylight saving changes?
  • How would you build this on DynamoDB alone, using TTL or streams, and what would you give up?
