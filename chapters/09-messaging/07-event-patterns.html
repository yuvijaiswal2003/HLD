Event-driven patterns: from notifications to event sourcing

'Event-driven' covers several quite different patterns. Martin Fowler's well-known breakdown distinguishes event notification, event-carried state transfer, event sourcing and CQRS. Mixing them up leads to confused designs, so name the one you mean.

Event notification vs event-carried state transfer

Event notification (thin events)

Strengths
  • Tiny messages: OrderPlaced with only order_id
  • The producer's schema stays private
  • Consumers always fetch the latest state
Weaknesses
  • Every consumer calls back to the producer, adding load and a runtime dependency
  • The callback may see a newer state than the event described
Use whenFew consumers, or data that changes after the event and must be fresh, such as 'something changed, re-sync'.

Event-carried state transfer (fat events)

Strengths
  • The event contains everything consumers need, so no callbacks
  • Consumers keep a local copy and keep working while the producer is down
Weaknesses
  • Larger messages and duplicated data
  • The event schema becomes a public contract that is hard to change
  • Local copies are eventually consistent
Use whenMany consumers needing the same data, such as a customer profile used by shipping, billing and support.

Event sourcing

In event sourcing, the source of truth is an append-only log of domain events (AccountOpened, MoneyDeposited, MoneyWithdrawn), not a table of current values. Current state is derived by replaying events in order, and services keep periodic snapshots so they do not replay from the beginning. You get a complete audit trail, the ability to answer 'what was the balance on March 3?', and the freedom to build new read models later by replaying history.

python
def apply(state, event):
    if event.type == "AccountOpened":
        return {"balance": 0, "status": "open"}
    if event.type == "MoneyDeposited":
        return {**state, "balance": state["balance"] + event.amount}
    if event.type == "MoneyWithdrawn":
        return {**state, "balance": state["balance"] - event.amount}
    return state

def load_account(account_id):
    snap = snapshots.latest(account_id)            # e.g. state as of version 9,000
    state, version = snap.state, snap.version
    for e in event_store.read(account_id, after=version):
        state, version = apply(state, e), e.version
    return state, version

# appending enforces optimistic concurrency on the stream
event_store.append(account_id, new_events, expected_version=version)

The costs are real. Events are immutable, so their schemas must be versioned and old versions handled forever (often by 'upcasting' old events when read). Queries such as 'all accounts with balance over 1,000' need separate read models. Deleting personal data is hard in an immutable log; a common answer is crypto-shredding, which encrypts each user's data with a per-user key and deletes the key. Use event sourcing where the history itself is valuable (ledgers, order lifecycles, compliance-heavy domains), not as a default.

CQRS

Command Query Responsibility Segregation splits the model that handles writes (commands, validated against invariants) from one or more models that serve reads, each shaped for its queries: a denormalized PostgreSQL table for the order page, an Elasticsearch index for search, a Redis sorted set for leaderboards. Read models are updated asynchronously from events, so they are eventually consistent. CQRS pairs naturally with event sourcing but does not require it; feeding read models from CDC on an ordinary database is very common.

Pitfall
CQRS breaks read-your-writes by default
A user saves an order and the next page, served from the read model, does not show it yet. Fixes: return the new version with the command response and have the query side wait until its projection reaches that version; read from the write model for the user's own recent changes; or update the UI optimistically on the client.

Change data capture and the outbox

Change data capture (CDC) turns a database's replication log into a stream of change events. Debezium, a set of Kafka Connect source connectors, reads the PostgreSQL write-ahead log through logical decoding or the MySQL binlog and publishes one event per inserted, updated or deleted row to Kafka, with before and after images. It captures every change, including ones made by scripts or other services, adds no load to the write path, and preserves commit order per row. Its weakness: raw table changes expose your internal schema to every consumer.

The transactional outbox (Chapter 8) combines naturally with CDC: the service writes business rows and an outbox row describing a public, versioned event in one local transaction, and Debezium's outbox event router publishes only the outbox rows, routed to topics by aggregate type and keyed by aggregate ID. You get atomicity without dual writes, ordering per aggregate, and a deliberate public contract instead of leaked tables.

PatternSource of truthMain benefitMain cost
Event notificationProducer's databaseLoose coupling, tiny eventsCallback load and runtime coupling
Event-carried state transferProducer's database, copied downstreamConsumer autonomy, no callbacksDuplicate data, schema contract
Event sourcingThe event log itselfFull history, replayable projectionsSchema evolution, query complexity
CQRSWrite model; read models derivedEach query gets an optimal storeEventual consistency between models
CDCDatabase, log exportedCaptures every change with no dual writeLeaks internal schema unless combined with an outbox
Transactional outboxDatabase, outbox tableAtomic state change plus eventA relay or CDC process to run, at-least-once publishing
Tip
Treat event schemas as APIs
Use a schema registry (Confluent Schema Registry, AWS Glue Schema Registry) with Avro or Protobuf and enforce compatibility rules: adding an optional field with a default is safe; renaming a field, or removing one that consumers still require, is not. Include an event ID, type, version, occurrence timestamp and aggregate ID in every event envelope.
In the interview
Choosing the pattern out loud
'Order service publishes fat OrderPlaced events through an outbox, so shipping and billing don't call back. We don't event-source orders, since we have no need for full history beyond an audit table. The order-history page reads from a CQRS read model in Elasticsearch, built from the same events, and is a second or two behind.'
