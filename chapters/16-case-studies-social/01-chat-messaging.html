Design a chat app (WhatsApp / Slack)

This walkthrough designs a WhatsApp-style messenger and points out where Slack-style team chat differs. Chat looks simple — send text, show text — but it combines four hard problems: holding hundreds of millions of long-lived connections, giving every participant the same message order, never losing a message the server has acknowledged, and catching up devices that were offline. It builds on WebSockets (Chapter 2), Kafka partition ordering (Chapter 9), leases (Chapter 8) and Snowflake IDs (Chapter 14).

1. Requirements

  • Functional: 1:1 and group conversations (groups capped at ~1,000 members; 100k-member Slack channels are a design-problem variation).
  • Sent, delivered and read receipts; typing indicators; online presence and last seen.
  • Push notifications to offline devices, and offline catch-up when a device reconnects.
  • Multi-device: phone, desktop and web show the same history.
  • Media (images, voice notes, files) sent as references to objects in object storage, not inline bytes.
  • Latency: under ~200 ms end to end (p99 under 500 ms) when both users are online in the same region.
  • Durability: once the sender sees the first tick, the message is never lost.
  • Ordering: every member of a conversation sees the same order.
  • Availability over consistency for presence and typing; those may be briefly wrong.
  • Security: TLS everywhere; end-to-end encryption is a client concern, and the server then stores only ciphertext.
In the interview
Scope it before you draw
Ask: 1:1 only, or groups, and how large? Is history kept on the server forever (Slack) or only until delivered (WhatsApp keeps an undelivered message for up to 30 days, then deletes it)? Multi-device? End-to-end encryption? These answers change storage by orders of magnitude and decide whether the server can search messages. Repeat the scope back in one sentence: '1:1 and groups up to 1,000, server-side history for multi-device sync, receipts, presence and push.'

3. API

The estimates say the expensive parts are ~200M long-lived connections and a write-heavy message log, and the API mirrors that split. One persistent WebSocket per device carries every real-time frame in both directions; plain HTTPS handles request/response work — history pages, sync after reconnect, media upload and group management.

In production
Discord's message store
Discord's engineering blog describes storing messages in Cassandra with partition key (channel_id, bucket), where the bucket is a fixed time window, and the Snowflake message ID as the clustering key — the same shape as the table above, with a time-window bucket. In 2023 they described migrating those trillions of messages to ScyllaDB, a Cassandra-compatible store, to cut tail latency.

5. High-level design

Write path: the client sends a frame over its WebSocket; the gateway forwards it to the chat-service instance that owns the conversation (consistent hashing on conv_id, Chapter 7). The owner dedupes on client_msg_id, assigns the next seq, appends to Cassandra with a quorum write, and only then acks the sender — that ack is the first tick. It publishes the message to Kafka keyed by conv_id so per-conversation order survives the queue. Delivery path: fan-out workers read the member list, look up each member's live devices in the session registry, group them by gateway and send one batched RPC per gateway; devices without a socket get a push. Read path: opening a conversation reads the newest page from one Cassandra partition, already sorted by seq.

6. Deep dives

Message IDs and ordering. Never order by client clocks — phones drift by seconds or minutes. Use two identifiers. The client generates a client_msg_id (a UUID) so a retry after a lost ack is deduplicated instead of stored twice. The server assigns a per-conversation seq that is dense and strictly increasing, and that order is the truth every device renders. Because one owner (the chat-service instance holding the conversation's lease) assigns seq, two members typing at the same instant still get one agreed order, and dense numbers give gap detection: a client holding 1042 that receives 1044 fetches 1043. A global Snowflake msg_id remains useful as a stable handle for replies, edits and deletes. On owner failover, the new owner reads the max seq from the store before accepting writes, and a fencing token or a conditional insert on the (conv_id, seq) key stops a stale owner from reusing a number.

Delivery guarantees and receipts. Delivery is at-least-once end to end: the server redelivers until a device acks, and devices dedupe by seq. Receipts are cursors: 'read up to 1044' implies every earlier message is read, so one small write per member per read action covers any number of messages. In a group, 'read by 7 of 12' for a message is computed by comparing members' last_read_seq with its seq. Clients coalesce receipts (reading 30 messages sends one), otherwise receipts would outnumber messages.

  • Group fan-out. Store each group message once, in the conversation's partition, and fan out delivery, not storage. A worker loads the cached member list, finds members with live devices, and sends one batched frame per gateway: a 1,000-member group spread over 300 gateways costs ~300 RPCs, not 1,000. Members without a socket get a push unless they muted the group. This is the push-versus-pull choice of the next lesson: chat can push to every member only because groups are capped, and 100k-member channels deliver only to online members while everyone else pulls on reconnect. With end-to-end encryption the client encrypts for each recipient device, or with a shared group sender key as WhatsApp does with the Signal protocol, and the server relays ciphertext.
  • Presence. Each device heartbeats every ~30 s; the presence service keeps presence:u42 in Redis with a ~90 s TTL (gateways batch these refreshes). Missing two to three heartbeats, or a clean close followed by a short debounce, marks the user offline, so a phone in a tunnel does not flap. Do not broadcast to every contact: clients subscribe to presence only for users on screen (the open chat, the visible rows of the chat list). 'Last seen' is just the last heartbeat time.
  • Offline sync and multi-device. Each device stores locally the last seq it has per conversation. On reconnect it calls /v1/sync; the server reads the user's conversation list and each conversation's last_seq from Redis, returns the conversations where the device is behind, and the client pages in the missing ranges, newest first. Because every device syncs from the same server log, phone and laptop converge on identical history.
  • Push is a hint, not delivery. APNs and FCM cap payloads at 4 KB, may delay or coalesce notifications, and APNs stores only the latest notification for an offline device. Use push to wake the app or show a preview; the message itself always arrives through the socket or sync.
  • Gateway failures and reconnect storms. When a gateway holding 250k sockets dies, those clients all reconnect at once. Clients back off with jitter (Chapter 12), registry entries expire by TTL, and nothing is lost because undelivered messages are still in the store. For deploys, drain gateways gradually by telling clients to reconnect elsewhere.

7. Trade-offs and bottlenecks

DecisionWe choseCost / what to watch
TransportWebSocket per device behind an L4 load balancerStateful connections: deploys, reconnect storms, ~1,000 gateways to operate
OrderingPer-conversation seq from a single ownerOne conversation's throughput is bounded by one owner (thousands of msgs/s, far above human rates); failover needs leases and fencing
StorageWide-column store, partition (conv_id, bucket)No cross-conversation queries or full-text search without a separate index
DeliveryAt-least-once plus client dedupe by seqDuplicates on the wire are normal; every client path must be idempotent
ReceiptsPer-member cursorsExact per-message read times are lost; only 'read up to' survives
PresenceHeartbeats, TTL, subscribe-on-viewSeconds of staleness; heartbeat volume must stay at the gateway tier
Pitfall
Classic chat mistakes
Ordering by client timestamps; acking the sender before the message is durable; treating a push notification as the delivery; broadcasting every presence change to every contact; and storing a copy of each group message per recipient, which multiplies storage by group size for no benefit (end-to-end encryption with per-device ciphertext is the one case where per-recipient copies are unavoidable).
