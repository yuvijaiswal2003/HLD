Design caching for a product page serving 100k RPS

An e-commerce site has 50 million products. At peak the product detail page gets 100,000 page views per second, with heavily skewed popularity and occasional flash deals where one product gets a large share of all traffic. Each page shows details (title, images, description, specs), price and stock, and a review summary. Prices and stock change about 2,000 times per second across the catalog. Design the caching so pages are fast, the database survives, and users never pay a stale price.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • How fresh must each part be: description, price, stock level, reviews?
  • Is the page personalized, or is most of it identical for every user in a region?
  • Do prices vary by region, currency or customer segment?
  • What does the database handle today, and what is the read/write mix?
  • How hot can one product get during a flash deal?
  • Are there bots or scrapers hitting product URLs?

3Hints 0/4

Stuck? Each hint gives a little more away than the last.

H1Split the page by freshness: data that changes hourly and data that changes every second should not share a cache entry or a TTL.
H2Count the layers: what fraction can the CDN absorb, what reaches the app tier, what reaches Redis, and what reaches the database?
H3Think about how an update in the database reaches Redis and every CDN PoP, including updates made outside the app.
H4Plan for the flash-deal product: one key, tens of thousands of reads per second, and an expiry at the worst moment. And plan for bots requesting IDs that do not exist.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: serve product details, price and stock, and review summary for any of 50M products; reflect admin and price updates.
  • Non-functional: 100k page views/s at peak; API p99 under 100 ms at origin; details may be up to 60 s stale, price and stock up to 5 s, reviews minutes; the price charged at checkout is always current; survive a flash deal and a cache node failure.

Estimates

  x 1.3 overhead = 65 GB -> 4 shards x ~16 GB, 1 replica each
  (throughput is easy: 25k ops/s vs ~100k per node)

Writes: 2k price/stock changes/s -> 2k Redis DELs/s + CDN tag purges
App servers: 50k RPS / ~2k RPS per instance (mostly hits) = 25 -> 40

High-level design

Read path: the browser loads a cached HTML shell and assets from the CDN, then calls the details and offer APIs. Most details calls are CDN hits; misses go through the origin shield to the product API, which checks the Bloom filter, its in-process cache, then Redis, then a PostgreSQL replica, populating each layer on the way back. Write path: the pricing service updates offers in PostgreSQL. Debezium streams the change to Kafka; the invalidator deletes offer:42:us in Redis and purges surrogate key product-42 at the CDN. App instances' 2-second local TTL bounds their staleness without any broadcast.

Deep dives

1. Split by freshness, and keep checkout honest. Bundling price into the details object would force the whole object to a 5-second TTL and a purge 2,000 times per second. Splitting gives details a 60-second edge TTL with stale-while-revalidate (users almost never wait on a miss) and gives the small offer object a 5-second TTL. The displayed price can be up to about 5 seconds stale, so cart and checkout read the price from the database (or the pricing service) and show a notice if it changed. Cached data is for display; decisions use the source of truth.

2. Invalidation that cannot be skipped. Deleting keys from application code would miss bulk price imports and scripts, and would leave stale data if a process crashed between commit and delete. CDC from the WAL produces an invalidation for every committed change, in order. The cache-aside race (a slow reader setting an old value after the delete) is handled by storing the row version with the value and using a Lua script that refuses to overwrite a newer version, with the TTL as a final safety net. CDN objects are tagged with surrogate keys, so one purge removes the product's details from every PoP in well under a second on providers such as Fastly.

3. Flash deals: stampede and hot key. If one product takes 30% of traffic, that is 30k details and offer requests per second. At the edge, the CDN and shield collapse concurrent misses into one origin fetch, and stale-while-revalidate means expiry never causes a wait. At origin, the in-process cache serves the product from memory on all 40 instances, so Redis sees at most about 20 reads per second for it (one per instance per 2-second TTL); single-flight loading ensures each instance makes only one Redis call per expiry. If needed, the deal service writes copies offer:42:us:r0 to r7 across shards.

4. Bots and missing IDs. Scrapers iterating IDs would turn every request into a database query. The Bloom filter rejects IDs that are definitely invalid with a 404 before any cache lookup; the roughly 1% that slip through hit a 60-second negative cache entry after the first miss. Rate limiting per client at the edge handles the rest.

  • Remaining risk: losing a Redis shard drops about 25% of hot data at once; replicas with automatic failover and a rate-limited fallback to read replicas keep the database safe.
  • Watch the CDN purge rate limits: 2,000 purges per second may exceed a provider's API limits, so batch purges per second or rely on the 5-second TTL for offers and purge only details.

5Follow-up questions

  • Prices become personalized per customer segment. How does that change what can be cached at the CDN?
  • The Kafka consumer for invalidations falls 10 minutes behind. What do users see, and how do you detect and limit it?
  • How would you warm the cache for a new region launch?
  • Redis Cluster loses a primary during peak. Walk through what happens to latency and database load.
  • How would you measure that the cache is actually helping, and what dashboards would you build?
