Invalidation and consistency

Once data lives in two places, the copies can disagree. The cache does not know the database changed unless something tells it or a timer runs out. Designing a cache is therefore really designing how stale data is allowed to get, for how long, and for whom.

Invalidation strategies

StrategyHow it worksStaleness boundCost and risk
TTL onlyEntries expire after a fixed timeUp to the TTLZero coordination; short TTLs lower the hit ratio
Delete on writeWriter deletes the key after the DB commit (cache-aside)Usually millisecondsMissed if the writer crashes between commit and delete; race below
Update on writeWriter sets the new value (write-through)MillisecondsConcurrent writers can set out of order
Event-driven (CDC)A consumer tails the DB log and deletes affected keysTypically under a secondMore infrastructure; catches every write, even from scripts
Versioned keysKey includes a version: product:42:v7; a write bumps the versionNone for readers who look up the new versionNeeds the current version from somewhere; old versions expire via TTL

In practice you combine them: explicit invalidation for freshness, and a TTL on every entry as a safety net so that any bug, missed event or race heals itself within a bounded time.

The cache-aside race

Even delete-on-write has a window. A reader misses, reads the old row, and is delayed (a GC pause, a slow network). Meanwhile a writer commits a new value and deletes the key. Then the delayed reader writes its old value into the cache, where it stays until the TTL expires.

  • Keep a TTL on every key to cap how long the stale value can live.
  • Leases: on a miss the cache hands the reader a token, and a delete invalidates outstanding tokens, so the late SET is rejected. Facebook's memcache uses leases for exactly this race and for thundering herds.
  • Versioned writes: store a version with the value and use a small Lua script so a SET only succeeds if its version is newer than the cached one.
  • Delayed double delete: delete again a few hundred milliseconds after the write. Cheap, but it only narrows the window.

Dual writes and change data capture

Updating the database and then deleting the key is a dual write: two systems, no shared transaction. If the process crashes between the two, or the delete times out, the cache stays stale until TTL. Writes from migrations, admin scripts or other services skip the delete entirely. The robust fix is to drive invalidation from the database's own commit log with change data capture (CDC): Debezium reads the PostgreSQL WAL or MySQL binlog and publishes row changes to Kafka, and an invalidator service deletes the affected cache keys and purges CDN objects. Every committed change produces an invalidation, in commit order, no matter who wrote it.

In production
Invalidation from the database log
Facebook's memcache paper describes mcsqueal, a daemon on each database that tails the MySQL commit log and broadcasts deletes to memcache clusters. This removed the need for every web server to issue invalidations correctly.

Many layers, many copies

In-process caches multiply the problem: 200 app instances means 200 copies. Options are a very short TTL (1–5 seconds, often good enough for hot keys), broadcasting invalidations over Redis pub/sub or Kafka to every instance, or Redis 6 client-side caching, where the server tracks which keys each client holds and pushes invalidation messages.

Pitfall
Never decide on cached data that must be exact
Show a cached price on the product page, but compute the charged price from the database at checkout. Show a cached stock level, but decrement inventory transactionally. For read-your-writes (a user edits their profile and immediately reloads it), read that user's own data from the primary for a few seconds after a write, or write-through for their own record.
In the interview
Say how stale is acceptable
Interviewers want to hear a staleness budget per data type: descriptions can be a minute stale, prices five seconds, and the checkout total never. Then pair TTL as a safety net with explicit or CDC-based invalidation for freshness.
