CDNs and HTTP caching

A content delivery network (CDN) is a fleet of caching reverse proxies in hundreds of points of presence (PoPs) around the world, close to users. A user in Sydney fetching an image from an origin in Virginia pays about 200 ms of round trip per request; from a Sydney PoP, about 10 ms. The CDN also absorbs most of the bandwidth (often 90–99% of bytes for static content), shields the origin from traffic spikes and DDoS attacks, and terminates TLS near the user. Major providers include Akamai, Cloudflare, Fastly, Amazon CloudFront and Google Cloud CDN.

Pull CDN

Strengths
  • Zero upload step: the edge fetches from origin on the first miss
  • Only requested content is stored
  • Works with any origin, including dynamic APIs
Weaknesses
  • First request per PoP is slow
  • Origin must handle miss traffic and stay available
Use whenThe default for websites, APIs and user-generated content with long-tail popularity.

Push CDN

Strengths
  • Content is on the edge before the first request
  • Origin traffic is predictable
Weaknesses
  • You manage uploads, updates and deletes
  • Storage cost for content nobody requests
Use whenLarge, known files released on a schedule: game patches, software downloads, video catalogs.

Cache keys

The cache key decides which requests share a cached response. By default it is roughly scheme, host, path and full query string. Every variation you let into the key splits the cache: ?utm_source=mail, reordered parameters, or a session cookie can turn one cached object into thousands of near-duplicates and push the hit ratio toward zero. Normalize at the edge: sort query parameters, strip tracking parameters, ignore cookies for public content, and include only the headers that truly change the response. The Vary header tells caches to key on a request header; Vary: Accept-Encoding is fine, but Vary: User-Agent or Vary: Cookie effectively disables shared caching.

TTLs and Cache-Control

DirectiveMeaning
max-age=NAny cache may reuse the response for N seconds
s-maxage=NOverrides max-age for shared caches (CDNs, proxies) only; browsers ignore it
public / privateShared caches may store it / only the user's own browser may store it
no-cacheMay be stored, but must be revalidated with the origin before every use
no-storeMust not be stored anywhere: use for sensitive responses
immutableThe content at this URL will never change; skip revalidation
stale-while-revalidate=NServe a stale copy for up to N seconds while fetching a fresh one in the background
stale-if-error=NServe a stale copy for up to N seconds if the origin errors or is down

When a cached copy expires, a cache can revalidate instead of downloading again: it sends If-None-Match with the stored ETag (or If-Modified-Since), and the origin answers 304 Not Modified with no body if nothing changed.

http
# Fingerprinted static asset: cache for a year, never revalidate
GET /static/app.3f9a1c.js
HTTP/1.1 200 OK
Cache-Control: public, max-age=31536000, immutable

# Product API: browsers 30 s, CDN 5 min, serve stale during refresh or outage
GET /api/products/42
HTTP/1.1 200 OK
Cache-Control: public, max-age=30, s-maxage=300, stale-while-revalidate=60, stale-if-error=86400
ETag: "p42-v17"
Surrogate-Key: product-42 category-shoes

# Personalized page: never in a shared cache
GET /account
HTTP/1.1 200 OK
Cache-Control: private, no-store

Purging and versioned URLs

There are two ways to change content that a CDN has cached. Purging (invalidation) tells every PoP to drop an object: Fastly's purges complete globally in around 150 ms, CloudFront invalidations take longer and are billed per path beyond a free monthly allowance. Purging by tag (Fastly surrogate keys, Akamai cache tags, Cloudflare cache tags) drops every object labelled, say, product-42 in one call. Versioned URLs avoid purging entirely: put a content hash or version in the file name (app.3f9a1c.js), cache it forever with immutable, and reference the new name from HTML when it changes. This is the standard for static assets because browser caches cannot be purged at all; only the short-lived HTML that points to them needs to be fresh.

Origin shield

With 300 PoPs each missing independently, a new popular object can cause 300 origin fetches, and a purge causes another 300. An origin shield (CloudFront Origin Shield, Fastly shielding, Cloudflare Tiered Cache, Akamai tiered distribution) adds a mid-tier cache in one region: edge PoPs fetch from the shield, and only the shield fetches from origin. Combined with request collapsing at the shield, the origin sees about one request per object per TTL, and the overall hit ratio rises.

Edge compute

Modern CDNs run your code at the PoP: Cloudflare Workers, Fastly Compute, CloudFront Functions and Lambda@Edge, Akamai EdgeWorkers. Typical uses are cache-key normalization, redirects and A/B bucketing, authentication of signed URLs or JWTs, geo-based routing, header rewrites, image format negotiation and assembling pages from cached fragments. Keep edge logic small and fast; heavy work and anything needing the primary database still belongs at the origin.

In production
Netflix runs its own CDN
Netflix built Open Connect, its own CDN, and places Open Connect appliances (storage-heavy cache servers) inside ISP networks and at internet exchange points. It pre-positions popular titles during off-peak hours, so nearly all video bytes are served from inside or next to the viewer's ISP.
In the interview
What to say about the CDN
Do not stop at put a CDN in front. Say what is cached at the edge and for how long, how the cache key is normalized, how updates propagate (versioned URLs for assets, tag purges for content), whether there is an origin shield, and what the origin load is at the expected hit ratio.
