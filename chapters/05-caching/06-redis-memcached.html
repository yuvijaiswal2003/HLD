Redis vs Memcached

Redis and Memcached are the two standard distributed caches. Both keep data in RAM, answer simple reads in well under a millisecond, and speak a simple protocol over TCP. They differ in what they store and what they do beyond caching.

Memcached

Strengths
  • Multithreaded: scales across all cores of one large node
  • Very simple, predictable memory use with a slab allocator
  • Mature, tiny feature surface
Weaknesses
  • Values are opaque strings, default max item size 1 MB
  • No persistence and no built-in replication
  • Sharding is done by clients (consistent hashing such as ketama)
Use whenPure, simple key-value caching of serialized objects where you want maximum throughput per node.

Redis

Strengths
  • Rich data structures with atomic server-side operations
  • Replication, automatic failover (Sentinel) and sharding (Redis Cluster)
  • Optional persistence (RDB snapshots, AOF log)
  • Pub/sub, streams, Lua scripting, TTL per key
Weaknesses
  • Commands execute on a single main thread per node, so one slow command blocks all
  • More operational surface: persistence, failover, cluster topology
  • Licensing changed in 2024; the open-source fork Valkey is now offered by major clouds
Use whenThe default choice: caching plus counters, leaderboards, rate limiters, sessions, queues and locks.

Persistence

Redis offers two persistence mechanisms, usable together. RDB snapshots fork the process and write a compact point-in-time file every few minutes: fast restarts and good backups, but you lose everything since the last snapshot. AOF (append-only file) logs every write; with the common appendfsync everysec setting you lose at most about one second of writes, at the cost of larger files and periodic rewrites. For a pure cache you may turn persistence off entirely and rebuild from the database, but persistence shortens the cold start after a restart, which helps prevent avalanches.

Replication and Redis Cluster

A Redis primary replicates to replicas asynchronously, so a failover can lose the last few writes that had not reached the replica yet (WAIT narrows but does not eliminate this). Redis Sentinel watches a primary and its replicas and promotes a replica when the primary fails. Redis Cluster shards data across several primaries: the key space is split into 16,384 hash slots, a key's slot is CRC16(key) mod 16384, and each primary owns a range of slots, with replicas for failover. Clients cache the slot map and are redirected with MOVED (slot has moved for good) or ASK (slot is mid-migration) when it is out of date.

Multi-key commands (MGET, transactions, Lua scripts) work only when all keys are in the same slot; otherwise Redis returns a CROSSSLOT error. Hash tags solve this: only the part inside braces is hashed, so {user:42}:cart and {user:42}:profile land in the same slot. Use them deliberately, because putting too many keys under one tag recreates a hot shard.

Pitfall
One slow command stalls everyone
Because commands run one at a time, KEYS * on a 50-million-key node, HGETALL on a hash with a million fields, or deleting a huge set blocks every other client for the duration. Use SCAN to iterate, UNLINK to delete large keys in the background, and keep values small (under about 100 KB is a good rule).
In the interview
Choosing between them
If the interviewer asks, pick Redis unless you have a reason not to, and say why: I need sorted sets for the leaderboard and atomic INCR for rate limiting, plus replication for failover. Mention Memcached when the need is only a large, simple, multithreaded object cache. Either way, do not treat Redis as a durable system of record without discussing persistence and async replication loss.
