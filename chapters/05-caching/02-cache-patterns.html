Caching patterns: who reads, who writes

Every caching pattern answers two questions: on a read miss, who loads the data into the cache, and on a write, what happens to the cache. The answers decide how stale data can get, what happens when the cache fails, and how much code you write.

Cache-aside (lazy loading)

In cache-aside, the application talks to both the cache and the database. On a read it checks the cache; on a miss it reads the database and writes the result into the cache with a TTL. On a write it updates the database and then deletes the cache entry, so the next reader loads a fresh copy. It is the most common pattern by far (it is what most teams mean by putting Redis in front of PostgreSQL), because the cache holds only data that is actually requested, and a cache outage degrades into slower reads rather than errors.

python
import json, random

TTL = 3600

def get_product(pid):
    key = f"product:{pid}"
    cached = redis.get(key)
    if cached is not None:
        return json.loads(cached)                    # hit
    row = db.query_one("SELECT * FROM products WHERE id = %s", pid)
    if row is not None:
        ttl = TTL + random.randint(0, 300)           # jitter, see failure modes
        redis.set(key, json.dumps(row), ex=ttl)
    return row

def update_product(pid, fields):
    db.execute("UPDATE products SET ... WHERE id = %s", pid)
    redis.delete(f"product:{pid}")                   # invalidate, do not set

Why delete instead of writing the new value? If two writers update the same row, their cache writes can arrive in the opposite order to their database commits and leave the older value cached indefinitely. A delete is idempotent and order-independent: whatever happens, the next read loads whatever the database holds. Deleting also avoids paying to cache values that may never be read.

Read-through

In read-through, the application asks only the cache, and the cache itself loads missing entries from the database through a loader you configure. Caffeine's LoadingCache in Java and Amazon DynamoDB Accelerator (DAX) work this way. The logic is identical to cache-aside, but it lives in one library instead of being repeated at every call site, and the library can coalesce concurrent misses for the same key.

Write-through

In write-through, every write goes to the cache and the database synchronously, and the write succeeds only when both do. The cache is always warm for recently written data, though two racing writers can still update it in a different order than the database. Writes become slower (two writes on the critical path), the cache fills with data that may never be read, and you still need a TTL or invalidation for writes that bypass the cache. DAX is write-through for DynamoDB.

Write-behind (write-back)

In write-behind, the application writes only to the cache and gets an immediate acknowledgement; the cache flushes changes to the database asynchronously, often batched. Writes are very fast and the database sees a fraction of the write load (100 increments of a counter can become one UPDATE). The danger is durability: if the cache node dies before flushing, acknowledged writes are gone. Use it for data you can afford to lose or rebuild, such as view counters, likes and analytics events.

Write-around and refresh-ahead

In write-around, writes go straight to the database and do not touch the cache; data enters the cache only when someone reads it (usually via cache-aside). This keeps write-once, rarely-read data such as logs, audit records and bulk imports from flushing useful entries out of the cache. The first read after a write is always a miss.

In refresh-ahead, the cache reloads an entry before it expires if it has been accessed recently, for example when 80% of its TTL has passed. Popular keys then never expire under load, so users never wait on a miss for them. The cost is extra backend calls for entries that may not be read again, and it only helps when you can predict which keys will be needed. Caffeine's refreshAfterWrite and CDN stale-while-revalidate are both forms of it.

In production
Facebook's look-aside memcache
Facebook's 2013 paper Scaling Memcache at Facebook describes memcache as a demand-filled look-aside cache: web servers read from memcache, fall back to MySQL on a miss, and populate the cache. On writes they update the database and delete the key rather than updating it, precisely because deletes are idempotent.
In the interview
Pick per data type
A strong answer uses different patterns for different data in the same design: cache-aside with delete-on-write for product details, write-behind for view counts because losing a few seconds of counts is fine, and no cache at all for inventory decrements at checkout.
