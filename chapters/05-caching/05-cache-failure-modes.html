Stampedes, penetration, avalanches and hot keys

A cache does not just speed things up; it reshapes load. A database tuned for 5% of traffic will collapse if it suddenly sees 100%. Four failure modes cause most cache-related outages, and interviewers ask about all of them.

ProblemWhat happensMain fixes
Stampede (thundering herd, dogpile)A hot key expires and thousands of concurrent misses hit the DB to rebuild the same valueLock or lease per key, request coalescing, serve stale while revalidating, probabilistic early expiry
PenetrationRequests for keys that do not exist always miss, so every one reaches the DBNegative caching, Bloom filter of valid keys, input validation
AvalancheMany keys expire together, or the cache cluster fails, and the DB takes the full loadTTL jitter, replicated cache, circuit breakers, warm-up before traffic
Hot keyOne key gets so many reads that its single cache shard saturatesLocal in-process cache, key replication across shards, read replicas

Stampede

Suppose the homepage feed key is read 20,000 times per second and takes 200 ms to rebuild. When it expires, roughly 4,000 requests miss during those 200 ms, and each runs the same expensive query. The database slows down, the rebuild takes longer, more requests pile up, and the system can tip over. The fixes all make sure only one caller rebuilds a key while the others wait or get the old value:

  • Per-key lock: the first miss runs SET lock:key token NX PX 5000; the winner rebuilds, the others briefly wait and re-read, or return the stale value.
  • Request coalescing: within one process, concurrent misses for the same key share a single in-flight load (Go's singleflight, Nginx proxy_cache_lock, Varnish and CDNs do this for origin fetches).
  • Serve stale while revalidating: keep the value past its soft expiry, return it immediately, and refresh in the background.
  • Probabilistic early expiry: each reader may decide to refresh slightly before expiry, with probability rising as expiry approaches, so one request usually refreshes early and the herd never forms.
python
import asyncio

inflight = {}                                   # key -> Future for the load in progress

async def get_coalesced(key, load):
    val = await cache.get(key)
    if val is not None:
        return val
    if key in inflight:                         # someone is already loading it
        return await inflight[key]
    fut = asyncio.get_running_loop().create_future()
    inflight[key] = fut
    try:
        val = await load(key)                   # exactly one DB call per key
        await cache.set(key, val, ex=300)
        fut.set_result(val)
        return val
    except Exception as e:
        fut.set_exception(e)                    # waiters see the same error
        raise
    finally:
        del inflight[key]

Probabilistic early expiration (the XFetch algorithm) needs no locks at all. Store the value with the time it took to compute (delta); on every read, refresh early if the expression below is true. -log(random()) is a positive random number, usually small and occasionally large, so the chance of an early refresh grows smoothly as expiry approaches, and slow-to-compute values start refreshing earlier.

python
import math, random, time

def should_refresh(expiry, delta, beta=1.0):
    # delta: seconds the last recompute took; beta above 1 refreshes earlier
    return time.time() - delta * beta * math.log(random.random()) >= expiry

Penetration

If a key does not exist in the database, cache-aside never caches anything for it, so every request for it is a miss that reaches the database. A buggy client or an attacker iterating random product IDs can push thousands of such queries per second. Negative caching stores a short-lived marker for not found (for example a 60-second TTL), so repeated misses become hits. Against random IDs that never repeat, put a Bloom filter of all valid IDs in front: it answers definitely not present with certainty, so invalid requests are rejected without touching the cache or the database. At a 1% false-positive rate it needs about 10 bits per key, around 60 MB for 50 million IDs (the math is in Chapter 14).

Avalanche

An avalanche is a stampede across many keys at once. The classic cause is a bulk load or deploy that writes a million keys with the same one-hour TTL; an hour later they all expire within seconds. The fix is TTL jitter: use TTL + random(0, 10% of TTL) so expiries spread out. The other cause is losing the cache itself: a Redis primary fails, or every app instance restarts with an empty local cache. Defend with replicas and automatic failover, a circuit breaker or rate limit on the database fallback path so it degrades instead of collapsing, and pre-warming the most popular keys before sending traffic to a new cluster.

Hot keys

In Redis Cluster each key lives in exactly one hash slot on one shard, so adding shards does nothing for a single key that receives 500,000 reads per second when one node handles roughly 100,000 to 200,000. Three fixes, usually combined: cache the hot key in process on every app server with a 1–5 second TTL so the cache cluster barely sees it; replicate the key under several names (product:42:r0 to product:42:r9) that hash to different shards, read a random copy and write or delete all copies; or serve reads from shard replicas. Detect hot keys with per-key sampling on the client side or redis-cli --hotkeys (which requires an LFU policy).

Tip
Plan for the cache being empty
Ask what the database sees with a 0% hit ratio. If the answer is an outage, you need a cold-start plan: warm the top keys before switching traffic, ramp traffic gradually, and rate limit fallback queries. A cache whose failure takes down the database has become a critical dependency, not an optimization.
In the interview
Match the fix to the failure
Use the precise names: stampede means one hot key expiring (coalescing, locks, early refresh); penetration means keys that do not exist (negative caching, Bloom filter); avalanche means many keys or the whole cache at once (jitter, replicas, breakers); hot key means one key overloading a shard (local cache, replication). Mixing them up is a common way to lose points.
