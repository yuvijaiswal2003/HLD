Eviction policies and building an LRU cache

A cache has finite memory, so when it is full and a new item arrives, something must go. The eviction policy picks the victim, and a good one keeps the items most likely to be read again. Eviction is different from expiry: a TTL removes an item because it might be stale, while eviction removes a perfectly valid item because of space.

PolicyEvictsStrengthWeaknessWhere you see it
LRULeast recently used itemSimple; great for recency-driven trafficOne big scan flushes hot itemsMemcached (segmented LRU), Redis allkeys-lru

W-TinyLFUAdmits new items only if likely more popular than the victimNear-optimal hit ratios on real workloadsMore complexCaffeine (Java); Ristretto (Go) uses a TinyLFU variant

LRU in O(1): hash map plus doubly linked list

An LRU cache needs two operations in constant time: find an item by key, and move an item to the front of a recency order (or drop the item at the back). A hash map gives the first; a doubly linked list gives the second. The map stores key -> node, and the list orders nodes from most recently used (next to the head) to least recently used (next to the tail). Two sentinel nodes at the ends remove the edge cases for empty lists.

python
class Node:
    def __init__(self, key=None, val=None):
        self.key, self.val, self.prev, self.next = key, val, None, None
class LRUCache:
    def __init__(self, capacity):
        self.cap, self.map = capacity, {}
        self.head, self.tail = Node(), Node()        # sentinels
        self.head.next, self.tail.prev = self.tail, self.head
    def _unlink(self, n):
        n.prev.next, n.next.prev = n.next, n.prev
    def _push_front(self, n):                         # after head = most recent
        n.prev, n.next = self.head, self.head.next
        self.head.next.prev = n
        self.head.next = n
    def get(self, key):
        n = self.map.get(key)
        if n is None:
            return None
        self._unlink(n)
        self._push_front(n)                           # touch: now most recent
        return n.val
    def put(self, key, val):
        if key in self.map:
            self._unlink(self.map[key])
        n = self.map[key] = Node(key, val)
        self._push_front(n)
        if len(self.map) > self.cap:                  # evict least recent
            lru = self.tail.prev
            self._unlink(lru)
            del self.map[lru.key]

Both get and put are O(1): a map lookup plus a few pointer swaps. The list must be doubly linked because unlinking a node from the middle needs its predecessor, and a singly linked list would need an O(n) walk to find it. The node stores its own key so that eviction can delete the map entry. In production Python you would use collections.OrderedDict (move_to_end, popitem(last=False)), and in Java a LinkedHashMap with access order; both are this same structure inside.

LFU and scan resistance

LRU's weakness is a scan: a nightly job that reads every product once makes millions of one-off items most recent and evicts the genuinely hot ones. LFU counts accesses instead, so one read does not outrank a thousand. An O(1) LFU keeps a map from frequency to a list of keys plus a pointer to the minimum frequency. Pure LFU never forgets, so last month's viral item stays forever; practical versions decay counts over time. Caffeine's W-TinyLFU combines a small LRU window for new items with a compact frequency sketch that decides whether a newcomer deserves to evict an existing item.

How Redis evicts

Redis evicts only when maxmemory is set, according to maxmemory-policy. It does not keep an exact LRU list (that would cost memory per key); instead it samples a few keys (maxmemory-samples, default 5) and evicts the best candidate among them, which approximates LRU closely. Its LFU mode, added in Redis 4.0, uses an 8-bit logarithmic counter per key that decays over time. The volatile-* policies only consider keys that have a TTL; the allkeys-* policies consider everything.

text
# redis.conf for a pure cache node
maxmemory 24gb                 # leave headroom below physical RAM
maxmemory-policy allkeys-lfu   # or allkeys-lru
maxmemory-samples 10           # better accuracy, slightly more CPU
Pitfall
The default policy is not a cache policy
Redis defaults to noeviction: once memory is full, writes fail with an OOM error instead of evicting anything. The volatile-lru family has a similar trap: if your keys have no TTL, there is nothing it is allowed to evict, and it behaves like noeviction. For a cache, set an allkeys-* policy explicitly.
In the interview
LRU is a classic coding question
Implementing an LRU cache shows up in both coding and design rounds. Explain the two structures and why each is needed before writing code, mention the sentinel trick, and then discuss what changes at scale: per-key memory overhead, approximate LRU in Redis, and when LFU beats LRU.
