Design an image CDN and resizing service

A marketplace stores 300 million user-uploaded photos and adds 1 million per day. Web and mobile clients need each image in many sizes and formats (thumbnails, product gallery, full screen; JPEG, WebP, AVIF). Design a service that serves resized images on demand from a URL, globally and quickly, without precomputing every variant, while keeping costs and abuse under control.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • How many image views per second at peak, and from which regions?
  • Which sizes and formats do clients really need: a fixed set of presets or arbitrary dimensions?
  • Can images be edited or replaced, and must deletions (for example legal takedowns) disappear quickly?
  • Are some images private, requiring signed or authenticated access?
  • What are the size limits on uploads (bytes and pixels)?
  • Is there a latency target for the first view of a brand-new variant?

2Your answer

3Hints 0/4

Stuck? Each hint gives a little more away than the last.

H1Think in cache tiers: browser, edge, shield, a durable store of generated variants, and only then the resizer.
H2If anyone can request any width, how many cache keys can an attacker create? Restrict and sign the transformation parameters.
H3Format negotiation via the Accept header can explode the cache. How can the edge turn it into a small, fixed part of the cache key?
H4Make URLs immutable by putting a version in them. Then decide what a deletion still requires.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: upload originals; serve /i/{id}/v{version}/{preset}.{format} resized, cropped and encoded on demand; replace an image (new version); delete an image everywhere.
  • Non-functional: p95 under 50 ms for cached variants worldwide; first render of a new variant under 1 s; 99.9% availability; deleted images gone from CDN within minutes; resistant to cache-busting and decompression-bomb abuse.

Estimates

text
Storage: 300M originals x 2 MB = 600 TB, +1M/day x 2 MB = +2 TB/day
Views:   3B/day / 86,400 = ~35k RPS average, ~100k RPS peak
Egress:  100k RPS x 60 KB average variant = 6 GB/s = ~48 Gbps at the edge

Tiered hit ratios at peak
  edge 95%           -> 5k RPS to the shield
  shield 80%         -> 1k RPS to origin
  variant store 70%  -> 300 RPS need a real resize

Resize cost (libvips: decode 2 MB JPEG, resize, encode WebP) ~150 ms CPU
  300 x 0.15 s = 45 cores busy -> 12 x 8-vCPU instances at ~50% utilization
  AVIF encoding is several times slower -> separate, autoscaled pool

Variant store: 60M images with variants x 4 variants x 50 KB = ~12 TB

API

http
POST   /v1/images
       -> 201 { imageId, version: 1, uploadUrl: presigned S3 PUT URL }
GET    /i/{imageId}/v{version}/{preset}.{format}?sig={hmac}
       e.g. /i/8f3k2a/v3/w400-cover.webp?sig=9c1e...
       -> 200 image bytes, Cache-Control: public, max-age=86400, s-maxage=31536000
          Surrogate-Key: img-8f3k2a
PUT    /v1/images/{imageId}      -> new original, version + 1
DELETE /v1/images/{imageId}      -> delete originals and variants, purge CDN tag

High-level design

Upload: the client asks the upload API for an image ID and a presigned URL, then PUTs the original directly to S3; a validation job checks the format and pixel count and marks the image active. Read: the edge function verifies the HMAC signature, maps the Accept header to one of avif, webp or jpeg and rewrites the URL so the format is part of the cache key. On a miss the shield forwards one collapsed request to the resizer, which checks the variant store, and otherwise reads the original, resizes it, returns it and saves it.

Deep dives

1. A bounded, normalized cache key. If clients could request any width, quality and crop, an attacker could generate billions of distinct URLs, each a guaranteed miss and a CPU-heavy resize. Instead, allow only named presets (say 12) and sign URLs with an HMAC over the path, issued by the app servers that render pages. For format negotiation, Vary: Accept would split the cache by every distinct Accept string browsers send; normalizing Accept at the edge to three values and baking the format into the key keeps at most 3 variants per preset. The resulting key space is 12 presets x 3 formats per image version.

2. Four cache tiers and request coalescing. Browser cache (one day), edge (one year, immutable URLs), shield, and the S3 variant store, which matters because CDNs evict long-tail objects; regenerating from S3 costs a GET, while regenerating by resizing costs 150 ms of CPU. When a seller shares a new listing and thousands of people open it at once, every PoP misses together: shield request collapsing turns those into one origin request per variant, and the resizer's single-flight map (keyed by variant path) ensures one resize even if two shields ask at once.

3. Updates and deletions. Because the version is in the URL, replacing an image creates new URLs; old variants are never served for the new version and simply age out, so no purge is needed. Deletion is different: the delete API marks the metadata deleted, removes the S3 originals and variants, and purges surrogate key img-8f3k2a, removing every variant from every PoP in one call. Browser caches cannot be purged, which is why the browser max-age is one day rather than one year; for takedown-sensitive content you can lower it further.

4. Protecting the resizer. A 2 MB PNG can decode to 20,000 x 20,000 pixels (1.6 GB of RAM): reject originals above about 50 megapixels at upload, set per-request memory and time limits, and isolate the slow AVIF pool so it cannot starve JPEG and WebP work. If the resizer is overloaded, the edge can fall back to the nearest larger existing variant rather than failing.

Trade-offs and bottlenecks

  • On-demand vs precomputed variants: on-demand stores only what is requested (12 TB instead of potentially 300M x 36 variants) but makes the first view slower; precompute the two or three presets used on every listing page at upload time.
  • Presets vs arbitrary sizes: presets bound the cache and the attack surface; arbitrary sizes give designers freedom. Signed URLs let you allow a few custom sizes safely.
  • Variant store cost vs CPU: storing 12 TB costs a few hundred dollars per month; regenerating evicted variants would cost far more CPU and add latency.
  • AVIF vs WebP: AVIF is smaller (often 20–30% fewer bytes) but much slower to encode; serve WebP while AVIF is generated asynchronously for popular images.
  • Bottleneck: egress is the dominant cost at 48 Gbps, so hit ratio and format choice drive the bill more than compute does.

5Follow-up questions

  • Some images are private (only the buyer and seller may see them). How do you serve them through the CDN?
  • A viral image gets 50k requests per second within a minute of upload. Walk through every tier.
  • How would you add smart cropping that keeps faces or products in frame?
  • How would you migrate 300M originals to a new storage class to save cost without breaking URLs?
  • How do you measure and improve the edge hit ratio for the long tail of rarely viewed images?
