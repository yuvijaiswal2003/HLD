Why cache, where caches live, and hit ratio math

A cache is a smaller, faster store that holds copies of data whose source of truth lives somewhere slower: a database, another service, or an origin server across an ocean. Caches work because real access patterns are skewed. A small fraction of items (the popular products, the celebrity profiles, today's news) receive most of the reads, and an item read once is likely to be read again soon. Keep that hot fraction close and fast, and most requests never touch the slow system.

Caching buys three things. Latency: a memory lookup is orders of magnitude faster than a query that joins tables or a round trip to another continent. Throughput and cost: every hit is a request the database never sees, so one cache node can stand in for many database replicas. Availability: a cache that can serve slightly stale data keeps the product working while the origin is slow or down. The price is always the same: a cache is a copy, and copies go stale.

~100 nsLookup in an in-process hash map
~0.2–1 msRedis GET over the network in the same AZ
~5–50 msDatabase query with joins, or one that touches disk
~100–300 msFetching from an origin on another continent

Where caches live

A single request can pass through half a dozen caches. Each layer trades freshness and control for speed: the closer a cache is to the user, the faster and cheaper it is, but the harder it is to invalidate.

Hit ratio math

The hit ratio h is the fraction of lookups served from the cache. If a cache lookup costs t_cache and a miss costs the lookup plus the backend call t_db, the average latency is h x t_cache + (1 - h) x (t_cache + t_db). The backend's load is proportional to the miss ratio, 1 - h, which is the number that really matters for capacity.

text
Cache GET = 1 ms, DB query = 20 ms, traffic = 50,000 reads/s

hit ratio   avg latency                       DB load
  80%       0.8 x 1 + 0.2 x 21  = 5.0 ms      10,000 QPS
  90%       0.9 x 1 + 0.1 x 21  = 3.0 ms       5,000 QPS
  99%       0.99 x 1 + 0.01 x 21 = 1.2 ms        500 QPS

Going from 90% to 99% looks like +9 points.
It is really a 10x cut in database load.

Hit ratio depends on how much of the working set (the items read in a typical window) fits in memory. With skewed traffic, a cache holding 20% of the items often serves 80% or more of the reads, which is how you size cache memory (Chapter 3). TTLs that are too short, cache keys that include needless variation (a timestamp, a tracking parameter) and constant invalidation all push the hit ratio down.

Tip
What to cache, and what not to
Good candidates are read often, change rarely, and are expensive to compute: product details, user profiles, rendered fragments, configuration, results of heavy aggregations. Poor candidates are written more often than read, unique per request, or must be exactly current, such as an account balance used to approve a payment. A read-to-write ratio of 10:1 or higher is a good sign that caching will pay off.
In the interview
Name the five parameters
Whenever you add a cache in an interview, state: what is cached, the key, the TTL, the expected hit ratio and what that does to database load, and how it is invalidated. Cache product JSON in Redis under product:id, TTL one hour plus jitter, deleted on update; at 95% hits the DB sees 5k of 100k reads per second.
