Design a distributed lock service

Design a lock service, in the spirit of Chubby or etcd's lock API, that thousands of internal services use to elect leaders and guard shared resources. Two clients must never both act as the holder in a way that corrupts data, and the service must survive machine failures.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • Are the locks for efficiency (avoid duplicate work) or correctness (prevent corruption)? Correctness requires fencing.
  • How many clients, locks and acquisitions per second? How long are locks usually held?
  • Do waiters need FIFO fairness, or is try-lock with retry enough?
  • Do clients need blocking waits and change notifications, or is polling acceptable?
  • What must we survive: one node, one availability zone, a whole region?
  • Can the protected resources check a token on each write?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1A single node is a single point of failure, and asynchronous replication can grant a lock twice after failover. What gives you a replicated, linearizable state machine?
H2A crashed client must not hold a lock forever. Tie locks to a session with a TTL that the client keeps alive.
H3A client that pauses past its lease still believes it holds the lock. What can the storage system check that the client cannot fake?
H4The Raft log index of the grant is a ready-made, strictly increasing fencing token.
H5When a popular lock is released, avoid waking every waiter. Keep an ordered queue and hand the lock to the next waiter only.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: create a session with a TTL and keep it alive; acquire a named lock (try or blocking with timeout); release; return a fencing token with each grant; watch a lock's holder; leader-election helpers (campaign, observe).
  • Non-functional: safety first (at most one valid holder per lock at any token); tolerate two node failures; acquire p99 under 10 ms within a region; linearizable operations; tiny data volume.

Estimates

  • 20,000 client processes, one session each, keepalive every 3 s with a 10 s TTL: 20,000 / 3 ≈ 6,700 keepalives/s. The leader tracks lease expiry in memory, so keepalives do not go through the log.
  • Peak 2,000 acquisitions/s; acquire plus release = 2 log writes, so ~4,000 replicated writes/s. A 5-node Raft group on SSDs with batching handles 10k–30k small writes/s, so one group fits with headroom.
  • State: 200,000 locks and waiters × ~300 B ≈ 60 MB. Fits in memory; snapshots are small and fast.
  • Latency: in-region quorum round trip ~1 ms plus an fsync ~1 ms, so acquire p50 is ~2–3 ms.

API

  -> 201 {"session_id": "s-81f", "ttl_ms": 10000}

Data model

KeyValueNotes
session/{id}ttl_ms, created_indexExpiry tracked by the leader with its monotonic clock
lock/{name}holder_session, token, acquired_indextoken = Raft log index of the grant entry
lock/{name}/waiters/{seq}session_idFIFO queue; seq = Raft index of the wait request

This is not a general-purpose database. Each node runs the same in-memory state machine, fed by a Raft log on local SSD with periodic snapshots (the way etcd uses bbolt). Linearizable compare-and-set is the core operation, so the state must be tightly coupled to the consensus log.

High-level design

Acquire path: the client library sends acquire to any node, which forwards to the leader. The leader appends 'grant lock X to session S' (or 'enqueue S') to the Raft log; once a majority stores it, the entry is applied, and its log index is returned as the token. Release and expiry: release, or the leader noticing a session's TTL has elapsed, appends an entry that frees the lock and grants it to the head of the waiter queue in the same entry. Reads such as 'who holds X' use ReadIndex, so a deposed leader can never answer from stale state.

Deep dives

1. Session expiry without trusting clocks. The leader measures each TTL with its monotonic clock from when it received the last keepalive. The client measures from when it sent the keepalive and considers itself expired early, at TTL minus a margin (for example 8 s of a 10 s TTL), stopping protected work before the server could expire it. After a leader change, the new leader does not know when each session last renewed, so it gives every session a fresh full TTL. That errs toward keeping locks longer, which is safe, rather than freeing them early, which is not. Chubby uses a similar grace period on master failover.

2. Fencing tokens. Using the grant's Raft log index as the token makes tokens strictly increasing across all locks and across leader changes with no extra state. Protected stores apply writes conditionally (WHERE fence_token <= :token) and record the new maximum. For resources that cannot check tokens, such as third-party APIs, the lock is only advisory, so those operations must be idempotent (idempotency keys) or conditional.

3. Waiters without a thundering herd. Waiters are queued in log order. On release the leader grants the lock directly to the next waiter and notifies only that client, instead of waking everyone to race (the ZooKeeper recipe achieves the same effect by having each waiter watch only its predecessor's znode). Waiters whose sessions expire are removed from the queue in the same way.

4. Why not Redis? A single Redis SET NX PX is fast but replicates asynchronously, so a failover can lose a granted lock and grant it again. Redlock adds timing assumptions but no fencing. Both are acceptable for efficiency locks; correctness locks need this consensus-backed design.

5Follow-up questions

  • How would you add shared (read) locks alongside exclusive ones?
  • The protected system is a third-party API that cannot check tokens. What can you still guarantee?
  • How would you make acquisition fast for clients in three different regions?
  • A client's keepalives are delayed 9 seconds by a network blip. Walk through what each side believes.
  • How would a 50-instance service use this API to elect exactly one active leader?
