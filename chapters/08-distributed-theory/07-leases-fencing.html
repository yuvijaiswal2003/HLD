Leases, locks and fencing tokens

Distributed locks are used for two different reasons, and the difference decides how careful you must be. An efficiency lock prevents duplicate work, such as two workers generating the same nightly report; if it occasionally fails, you waste some compute. A correctness lock prevents corruption, such as two writers modifying the same file or two leaders accepting writes; if it fails, you lose data.

Distributed locks are almost always leases: locks with an expiry time. The holder renews the lease periodically with keepalives. If the holder crashes or is partitioned away, the lease expires and someone else can take over, so a dead client cannot hold a lock forever. Expiry introduces a new danger, though: the holder may still be alive and unaware that its lease has run out.

The pause problem

Client 1 cannot notice the pause from the inside. Checking 'is my lease still valid?' right before writing does not help: the pause can happen between the check and the write, or the write can sit in a network buffer for seconds. A longer TTL only shrinks the window. A lock based purely on time is not safe for correctness on its own.

Fencing tokens

The fix is to make the resource enforce the lock. Each time the lock service grants the lock, it returns a fencing token, a number that strictly increases with every grant. The client sends the token with every write; the storage system remembers the highest token it has accepted and rejects anything lower. A paused or delayed ex-holder always carries an older token, so its writes bounce. Consensus-backed services provide such numbers for free: ZooKeeper's zxid or znode version, etcd's revision of the lock key, or the Raft log index of the grant.

sql
-- Storage-side fencing: accept a write only if its token is not older
-- than the newest token already applied to this resource.
UPDATE documents
SET    body = :body,
       fence_token = :token
WHERE  id = :doc_id
  AND  fence_token <= :token;
-- 0 rows updated: a newer lock holder has written. Abort and re-acquire.

Redis locks, Redlock and consensus-backed locks

Single Redis SET NX PX

Strengths
  • One round trip: SET lock:job owner NX PX 30000
  • Simple and very fast
Weaknesses
  • Replication is asynchronous, so a failover can lose the key and grant the lock twice
  • No fencing token
Use whenEfficiency locks where an occasional double run is acceptable.

Redlock across 5 Redis nodes

Strengths
  • Survives a minority of Redis nodes failing
  • No consensus system to operate
Weaknesses
  • Safety depends on bounded clock drift, network delay and pauses
  • Still no fencing token, the core of Martin Kleppmann's well-known critique
Use whenDebated. If you need correctness, prefer a consensus-backed lock with fencing.

etcd or ZooKeeper lock

Strengths
  • Grants go through consensus, so node failures never cause double grants
  • Revision or zxid doubles as a fencing token
Weaknesses
  • A few milliseconds per acquire, slower than Redis
  • The protected resource must check tokens
Use whenCorrectness locks: leader election, exclusive writers, schema migrations.
Pitfall
A lock without fencing is only a hint
If the protected resource cannot check a token (an external API, a legacy file share), the lock alone cannot guarantee mutual exclusion. Make the operation itself idempotent or conditional instead: an API call with an idempotency key, or a compare-and-set on a version number.
Tip
Leader leases follow the same rules
A leader that serves reads from local state under a lease must stop before the lease could have expired on any node. It measures with its monotonic clock, starts the timer when it sent the renewal (not when the reply arrived), and subtracts a safety margin for drift. A new leader waits out the old leader's maximum lease before acting.
In the interview
Locks in a design round
When your design says 'take a lock', expect 'what if the holder pauses?'. A strong answer: 'The lock is an etcd lease with a 10-second TTL and keepalives; each grant returns the key's revision as a fencing token, and the storage layer rejects writes with a lower token. For mere deduplication of work, a Redis SET NX with a TTL is enough.'
