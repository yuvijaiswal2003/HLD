Lesson 2 of 7 · 10 min read

CAP and PACELC, stated precisely

The CAP theorem is the most quoted and most misquoted result in system design. Eric Brewer stated it as a conjecture in 2000; Seth Gilbert and Nancy Lynch proved a precise version in 2002. The proof uses narrow definitions, and nearly every misconception comes from swapping them for everyday meanings:

  • Consistency (C) means linearizability: the system behaves as if there were a single copy of the data, and every read returns the latest completed write (lesson 3 defines this carefully).
  • Availability (A) means every request received by a non-failing node eventually gets a non-error response. Not 'most requests' and not 'the majority side': every node that is up must answer.
  • Partition tolerance (P) means the system keeps working while the network drops arbitrary messages between nodes, for example when a switch failure splits the cluster into two groups that cannot talk.

The theorem: while a partition is in progress, a system cannot provide both C and A. The proof is almost obvious. Node A and node B are cut off from each other, and a client writes x = 2 to A. Another client reads x from B. B cannot know about the write, so it can either refuse or wait (staying consistent, giving up availability) or return its old value x = 1 (staying available, giving up consistency).

Misconceptions to correct

MisconceptionWhat is actually true
'Pick any two of C, A and P'Partitions are not optional for anything that uses a network, so P is a given. The real statement is: if a partition happens, choose C or A. When there is no partition you can have both.
'Our database is CA'Only a single-node system, or one that assumes partitions never happen, is CA. A multi-node 'CA' system still meets partitions and then loses consistency or availability in an unplanned way.
'CP means the system goes down'CAP availability is very strict. A Raft cluster whose majority side keeps serving while only minority-side clients get errors is 'not available' in CAP terms, yet can deliver 99.99% uptime.
'AP means anything goes'AP systems can still offer eventual, session or causal guarantees. They only give up linearizability during a partition.
'C in CAP is the C in ACID'ACID consistency means application invariants hold (a balance never goes negative). CAP consistency is linearizability of reads and writes. Different ideas that share a letter.
'Every system is either CP or AP'Many systems are tunable per request: Cassandra consistency levels, DynamoDB's ConsistentRead flag, MongoDB read and write concerns. And CAP says nothing about latency or about behavior when the network is healthy.
Pitfall
Never say 'I'll choose CA'
It signals that you think partitions can be designed away. Say instead: 'Partitions will happen. For this data I would rather reject writes on the minority side than accept conflicting ones' (CP), or 'for this data I would rather keep accepting writes and reconcile later' (AP).

PACELC: the trade-off you pay every day

Partitions are rare; latency is constant. Daniel Abadi's PACELC extends CAP: if there is a Partition, choose Availability or Consistency; Else, choose Latency or Consistency. The 'else' half matters more day to day because strong consistency needs coordination (waiting for a leader or a quorum to acknowledge), and coordination costs round trips: a millisecond or two inside a region, 60–150 ms across regions.

DynamoDB (default reads), Cassandra at ONEALReplicas answer locally. Strongly consistent reads or QUORUM trade latency for freshness.

Interview phrasing that lands well: 'Account balances are PC/EC: a transfer waits for a majority acknowledgment and the minority side rejects writes. The like counter on a post is PA/EL: increments go to the nearest replica and converge within seconds.'

In the interview
Use CAP per piece of data
Don't classify the whole system. Classify each kind of data by the cost of being wrong versus the cost of being unavailable: inventory reservations, payments, usernames and locks lean CP; feeds, counters, presence and recommendations lean AP. Then name the mechanism that delivers the choice: quorum writes, leader-only reads, or LWW with async replication.
