Time, clocks and ordering events

Distributed systems order events constantly: which of two writes to a key wins, whether a lease has expired, which snapshot a transaction reads, which log line came first during an incident. The obvious tool, each machine's clock, is less reliable than it looks.

Physical clocks drift and jump

Every server's clock is driven by a quartz oscillator that runs slightly fast or slow, and the error changes with temperature. Google's Spanner paper assumed up to 200 parts per million of drift, about 17 seconds per day if never corrected. NTP corrects drift by polling time servers, typically keeping machines within a few milliseconds of each other on a good network and tens of milliseconds over the internet, but congestion can throw it off, and when a clock is far off NTP may step it, so it jumps forward or backward. Operating systems therefore expose two clocks: the time-of-day clock (wall-clock time; can jump; only roughly comparable across machines) and the monotonic clock (only moves forward; meaningless across machines; the right tool for measuring timeouts and durations).

~200 ppmWorst-case quartz drift assumed by Spanner, ~17 s per day
1–10 msTypical NTP skew between servers on a good network
1–7 msTrueTime uncertainty reported in the Spanner paper
Pitfall
Last-write-wins on wall clocks silently loses data
If node A's clock runs 50 ms ahead of node B's, a write that reaches B 20 ms after A's write still gets the earlier timestamp and is discarded by last-write-wins (LWW). No error is raised; the newer data simply vanishes. Cassandra and DynamoDB global tables (in their default mode) resolve conflicts with timestamp-based LWW, which is fine for blind overwrites of independent values and dangerous for read-modify-write updates such as counters.

Lamport timestamps

Leslie Lamport's 1978 insight was that many problems need only an order consistent with causality, not real time. Each node keeps a counter, increments it on every local event, attaches it to every message it sends, and on receiving a message sets its counter to max(local, received) + 1. Ties are broken by node ID, so the pair (counter, node_id) gives a total order. Vector clocks, below, extend the idea.

python
class LamportClock:
    def __init__(self, node_id):
        self.t, self.node_id = 0, node_id
    def tick(self):                       # local event or message send
        self.t += 1
        return (self.t, self.node_id)
    def receive(self, remote_t):          # message arrival
        self.t = max(self.t, remote_t) + 1
        return (self.t, self.node_id)

class VectorClock:
    def __init__(self, node_id, nodes):
        self.node_id, self.v = node_id, {n: 0 for n in nodes}
    def tick(self):
        self.v[self.node_id] += 1
        return dict(self.v)
    def receive(self, remote):            # element-wise max, then tick
        for n, c in remote.items():
            self.v[n] = max(self.v.get(n, 0), c)
        return self.tick()

def compare(a, b):                        # a, b: dict of node -> counter
    keys = set(a) | set(b)
    le = all(a.get(k, 0) <= b.get(k, 0) for k in keys)
    ge = all(a.get(k, 0) >= b.get(k, 0) for k in keys)
    if le and ge: return "equal"
    if le: return "a happened before b"
    if ge: return "b happened before a"
    return "concurrent"

Lamport timestamps guarantee one direction: if A happened before B, then L(A) < L(B). The converse fails: L(A) < L(B) does not mean A influenced B; they may be concurrent. So Lamport clocks can order events but cannot detect concurrency. A subtler limit: you only know a timestamp's final position once you are sure no node will later produce a smaller one, which means hearing from every node. That is why Lamport clocks alone cannot implement 'the first user to claim a username wins'; that needs consensus (next lesson).

Vector clocks

A vector clock keeps one counter per node. A node increments its own entry on each event and, on receiving a message, takes the element-wise maximum before incrementing. Compare two vectors entry by entry: if every entry of A is less than or equal to the matching entry of B, A happened before B; if neither dominates, the events are concurrent. This is exactly what a leaderless store needs to decide whether a write supersedes another or both must be kept as siblings for the application to merge (the version vectors of Chapter 7). The cost is size: one entry per participant, so real systems bound or prune the vector.

Hybrid logical clocks

A hybrid logical clock (HLC) packs both ideas into one compact timestamp: a physical part that tracks the largest wall-clock time the node has seen, plus a logical counter that breaks ties and preserves causality like a Lamport clock. HLC values stay within the NTP skew of real time, so they are meaningful to humans and usable for snapshot reads ('as of 10:00:00'), and they never go backwards. CockroachDB and YugabyteDB use HLCs for transaction timestamps, and MongoDB's cluster time is an HLC. CockroachDB, lacking atomic clocks, also assumes a configured maximum clock offset (a few hundred milliseconds by default) and restarts reads whose values fall inside that uncertainty window.

Spanner's TrueTime and commit wait

Google's Spanner makes clock error explicit instead of pretending it is zero. Each data center has GPS receivers and atomic clocks, and the TrueTime API returns an interval (earliest, latest) guaranteed to contain the true time, usually a few milliseconds wide. Spanner uses it to provide external consistency: if transaction T1 commits before T2 starts, T1 gets the smaller timestamp, on every server.

  1. Acquire locks
    The transaction's leader takes write locks (with two-phase commit across Paxos groups when several shards are involved).
  2. Pick the timestamp
    Choose commit timestamp s = TT.now().latest, a time that cannot yet have passed anywhere.
  3. Replicate
    Send the commit record through Paxos to a majority of replicas; this overlaps with the wait.
  4. Commit wait
    Wait until TT.now().earliest is greater than s, roughly twice the uncertainty. Now every clock in the system agrees s is in the past.
  5. Release and acknowledge
    Apply the writes, release locks and reply. Any transaction that starts afterwards sees a TrueTime interval entirely after s, so it is assigned a larger timestamp.
In the interview
Answering 'how do you order events across machines?'
Walk the ladder: wall clocks are skewed, so LWW can drop writes; Lamport clocks give a causality-respecting total order but cannot detect concurrency; vector clocks detect concurrency at the cost of size; HLCs add human-meaningful time to causality; TrueTime bounds clock error and waits it out to get external consistency. Then pick the rung your design needs.
