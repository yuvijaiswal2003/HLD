Part 3 / Ch 8 · Distributed Systems: CAP, Consistency and Consensus
Lesson 1 of 7 · 9 min read

Why distributed systems are hard

On one machine, failures are mostly all-or-nothing: if the kernel panics or the power goes, everything stops, and a program run twice on the same input does the same thing. Spread that program across a network and you get partial failure: some nodes and links work while others are broken, slow or flaky, and the failures are nondeterministic. A request can succeed on Tuesday and hang on Wednesday for reasons no single node can see. Almost every hard idea in this chapter exists to cope with that.

You cannot tell slow from dead

Data center networks are asynchronous packet networks: a message can be lost, delayed for an unbounded time, duplicated or reordered, and the sender is told about none of it. When a client sends a request and hears nothing back, three very different situations look exactly the same:

The only tool the client has is a timeout, and a timeout means only 'no answer yet'. It does not say whether the operation happened, which is why retries must be paired with idempotency (applying a request twice has the same effect as applying it once). Picking the timeout is itself a trade-off: too short and you declare healthy-but-slow nodes dead, triggering failovers that add load exactly when the system is struggling; too long and users wait while a dead node is still treated as alive. Chapter 12 covers retry strategy in depth; Chapter 14 covers adaptive failure detectors.

The fallacies of distributed computing

In the 1990s, engineers at Sun Microsystems (largely credited to L. Peter Deutsch, with James Gosling adding the eighth) listed the assumptions newcomers make that eventually break every system built on them:

FallacyRealityDesign consequence
The network is reliableSwitches fail, cables get cut, NICs drop packets, config pushes go wrongTimeouts, idempotent retries, replicas in separate failure domains
Latency is zero~0.5 ms round trip inside a data center, 60–150 ms across regionsAvoid chatty APIs, batch calls, keep synchronous quorums inside a region
Bandwidth is infiniteLinks saturate; cross-region bandwidth is expensiveCompress, paginate, send deltas, move compute to the data
The network is secureTraffic can be sniffed or spoofed, even inside a VPCTLS or mTLS everywhere, authenticate service-to-service calls
Topology doesn't changeNodes autoscale, pods reschedule, IPs changeService discovery and health checks, no hardcoded addresses
There is one administratorMany teams and vendors change things independentlyBackward-compatible APIs, versioning, clear ownership
Transport cost is zeroSerialization CPU and egress fees are real moneyCompact encodings such as Protobuf; watch cross-AZ and egress traffic
The network is homogeneousMixed hardware, OSes, MTUs and protocol versionsStandard protocols, test across environments

Processes pause and clocks lie

Even a node that is up can stop executing without knowing it. A stop-the-world garbage collection on a large JVM heap can take seconds; a hypervisor can suspend a VM for live migration; the OS can swap memory to disk; a write can stall on a slow disk. When the process resumes, its next line of code runs as if no time passed, while the rest of the cluster may have declared it dead and moved on. Clocks are no better: each machine's clock drifts and can jump when NTP corrects it (lesson 4). The conclusion: a node cannot trust its own view of the world. Decisions such as 'who is the leader' or 'is this lock still mine' must be made by a quorum of nodes, never by one node's opinion.

~0.5 msRound trip inside one data center
60–150 msRound trip between regions
SecondsWorst-case stop-the-world GC pause on a large heap
2f + 1Nodes needed to survive f crashed nodes with majority quorums

Algorithms are proven correct under a system model, so name the one you assume. For node faults: crash-stop (a node dies and never returns), crash-recovery (it can come back with whatever it had written to disk, the usual assumption for databases) and Byzantine (nodes may lie; tolerating f traitors needs 3f + 1 nodes, which matters for blockchains and avionics, not typical backends). For timing: synchronous (bounded delays, unrealistic), asynchronous (no bounds at all, where some problems become impossible) and partially synchronous (well-behaved most of the time, with occasional unbounded hiccups). Raft, Paxos and nearly every production system assume crash-recovery with partial synchrony: they stay safe no matter what and make progress whenever the network behaves.

In production
GitHub, October 2018
A 43-second loss of connectivity between GitHub's US East Coast network hub and its primary East Coast data center caused its MySQL failover tooling (Orchestrator) to promote databases on the West Coast. When connectivity returned, some writes existed only in the East and others only in the West, and GitHub ran degraded for about 24 hours while reconciling them. A short partition plus automatic failover produced a long incident.
In the interview
What interviewers listen for
Whenever one component calls another, say what happens when the call is slow, fails, or its response is lost: 'the call has a 500 ms timeout, retries twice with jittered backoff, and carries an idempotency key so a duplicate is harmless.' Naming partial failure explicitly is one of the clearest seniority signals in a design round.
