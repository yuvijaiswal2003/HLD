Consensus: Raft, Paxos and coordination services

Consensus means getting several nodes to agree on a value and keep agreeing even when some crash. In practice we agree on a log, an ordered sequence of commands. If every node applies the same commands in the same order to the same deterministic state machine, every node ends up in the same state. This replicated state machine underpins etcd, ZooKeeper, Consul, CockroachDB, TiKV and Kafka's KRaft controller. Many problems that look different are equivalent to consensus: leader election, distributed locks, atomic compare-and-set, uniqueness constraints and total-order broadcast.

Consensus uses majority quorums. With 2f + 1 nodes any two majorities share at least one node, so every new decision 'sees' every previous one, and the cluster survives f failures: three nodes tolerate one, five tolerate two. Four nodes still tolerate only one (a majority of four is three), so even sizes add cost without fault tolerance. The FLP impossibility result (Fischer, Lynch and Paterson, 1985) shows that in a fully asynchronous network no deterministic algorithm can guarantee consensus terminates if even one node may crash. Real algorithms sidestep it with timeouts: they are always safe (never decide two different values) and are live (make progress) whenever the network is reasonably timely.

Raft: roles, terms and elections

Raft (Ongaro and Ousterhout, 2014) was designed to be understandable. Each server is a follower, candidate or leader. Time is divided into numbered terms; each term starts with an election and has at most one leader. Terms act as a logical clock: every message carries the sender's term, and a server that sees a higher term immediately adopts it and becomes a follower. An old leader that was partitioned away is therefore demoted the moment it talks to anyone in the new term.

  • Election timeout. A follower that hears nothing from a leader for a randomized timeout (the paper suggests 150–300 ms; etcd defaults to 1 s with 100 ms heartbeats) becomes a candidate, increments its term, votes for itself and sends RequestVote to every server.
  • One vote per term. Each server votes for at most one candidate per term, first come first served, and persists that vote to disk before replying so a restart cannot make it vote twice.
  • Up-to-date check. A server refuses to vote for a candidate whose log is less up to date than its own: compare the term of the last entry first (higher wins), then log length. This guarantees the winner already holds every committed entry.
  • Randomized timeouts make split votes rare; if nobody wins, candidates time out at different moments and the next term usually elects someone.
  • Heartbeats. The leader sends empty AppendEntries messages regularly so followers do not start elections.

Log replication and commit

  1. Append locally
    The leader appends the command to its log with the current term and the next index.
  2. Replicate with a consistency check
    AppendEntries carries the index and term of the entry just before the new ones. A follower accepts only if its log has a matching entry there; otherwise it rejects, the leader backs up and retries until the logs match, and then overwrites the follower's conflicting, uncommitted suffix.
  3. Commit on a majority
    Once a majority of servers have stored the entry, the leader advances its commit index. A committed entry is guaranteed to be in the log of every future leader.
  4. Apply and respond
    The leader applies committed entries in order to its state machine and replies to the client.
  5. Propagate the commit index
    Followers learn the new commit index from later AppendEntries calls and apply the same entries in the same order.
Pitfall
Two subtleties interviewers like
First, a new leader never commits an entry from an earlier term just by counting replicas; it commits an entry from its own term, which implicitly commits everything before it. Counting old-term entries can let a 'committed' entry be overwritten (Figure 8 of the Raft paper). Second, a leader must not serve reads from local state blindly: a partitioned old leader may not know it was replaced. It first confirms leadership with a quorum round (etcd's ReadIndex) or relies on a time-based leader lease, which assumes bounded clock drift.

Paxos in one paragraph

Lamport's Paxos predates Raft and solves the same problem with proposers, acceptors and learners. In phase 1 a proposer picks a unique, increasing proposal number n and asks acceptors to promise to ignore lower numbers; acceptors reply with any value they have already accepted. In phase 2 the proposer asks acceptors to accept (n, v), where v must be the value of the highest-numbered proposal reported in phase 1, if any. A value is chosen once a majority accepts it. Multi-Paxos keeps a stable leader so phase 1 is skipped for later log slots, which makes it look much like Raft. Google's Chubby lock service and Spanner use Paxos; ZooKeeper uses a similar protocol called ZAB.

ZooKeeper and etcd: consensus as a service

Few teams implement consensus themselves. They run a coordination service and build on its primitives: small linearizable key-value data, watches (push notification on change), sessions or leases that expire when a client dies, and monotonically increasing sequence or revision numbers.

In production
Real deployments
Kubernetes stores all cluster state (pods, services, config) in etcd. Kafka originally kept its metadata and controller election in ZooKeeper, replaced it with its own Raft-based KRaft quorum, and removed ZooKeeper support entirely in Kafka 4.0.
Tip
Keep consensus small and off the hot path
A consensus group's write throughput is bounded by its leader and fsync latency, typically thousands to tens of thousands of small writes per second. Store metadata (etcd's default storage quota is 2 GB), not user data. When you need consensus over large data, shard it into many independent groups, as CockroachDB and TiKV do with one Raft group per key range.
In the interview
Using consensus in a design
Say where you need agreement and keep it narrow: 'Shard ownership and the current leader live in etcd; the data path uses ordinary replication.' Interviewers reward reaching for consensus for coordination and avoiding it for bulk data.
