Design a cross-service money transfer (wallet to bank) with sagas

A fintech app holds user balances in its own Wallet service. Design 'cash out': a user moves money from their wallet to their external bank account through a third-party payout provider. Money must never be created or lost, the user must never be paid twice, and the provider's API is slow and sometimes times out.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • How many transfers per day, and what does the peak look like (paydays)?
  • Does the payout provider support idempotency keys, a status lookup endpoint and webhooks?
  • How fast must money arrive, and what does the user see while a transfer is pending?
  • Are fraud and risk checks or daily limits part of the flow?
  • What audit and reconciliation obligations exist (double-entry ledger, settlement reports)?
  • Can a payout bounce back days later (bank returns), and how should that be reflected?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1The wallet database and the provider cannot share a transaction, and the provider will never join 2PC. What sequence of local transactions with compensations would work?
H2Reserve money with a hold instead of debiting it outright, so the compensation is simply releasing the hold.
H3The payout call is the pivot. Once the provider might have accepted it, you cannot compensate blindly. How do you resolve a timeout?
H4Use an orchestrator with a durable state machine, the transfer ID as the idempotency key at every hop, and an outbox for every state change that emits a message.
H5Add a daily reconciliation job that compares your ledger with the provider's settlement report and alerts on any mismatch.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: start a cash-out with amount and destination; show status; allow cancel before payout; notify the user; handle provider rejections and later bank returns.
  • Non-functional: no money lost or duplicated (correctness over latency); idempotent API; 99.95% availability for initiating transfers; completion within minutes; full audit trail; keep accepting requests during provider outages by queueing.

Estimates

  • 20M users, 2% cash out per day: 400,000 transfers/day ÷ 86,400 s ≈ 5/s average; payday peak 20x ≈ 100/s.
  • About 6 state transitions per transfer, each a local transaction plus an outbox event: ~600 writes/s and ~600 messages/s at peak. Trivial for PostgreSQL and Kafka; the challenge is correctness, not scale.
  • Storage: transfer row 1 KB + 4 ledger entries × 200 B + 6 events × 500 B ≈ 4.8 KB per transfer; 400,000 × 4.8 KB ≈ 1.9 GB/day ≈ 700 GB/year. Audit rules require years of retention, so partition by month and archive old partitions.
  • Provider calls average ~1 s, so at 100/s about 100 are in flight at once (Little's Law), an easy concurrency level for a worker pool.

Data model

Each service owns a PostgreSQL database: money needs transactions, constraints and an append-only double-entry ledger, which relational databases do well at this volume.

sql
-- Wallet service
CREATE TABLE accounts (
  id TEXT PRIMARY KEY,
  available NUMERIC(18,2) NOT NULL CHECK (available >= 0),
  held      NUMERIC(18,2) NOT NULL DEFAULT 0 CHECK (held >= 0));
CREATE TABLE ledger_entries (             -- append-only, double entry
  id BIGSERIAL PRIMARY KEY, transfer_id TEXT NOT NULL, step TEXT NOT NULL,
  account TEXT NOT NULL, direction TEXT NOT NULL, amount NUMERIC(18,2) NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (transfer_id, step, account));    -- a replayed step cannot post twice
CREATE TABLE processed_commands (command_id TEXT PRIMARY KEY);
CREATE TABLE outbox (id BIGSERIAL PRIMARY KEY, topic TEXT, key TEXT, payload JSONB);

-- Transfer orchestrator
CREATE TABLE transfers (
  id TEXT PRIMARY KEY, idempotency_key TEXT UNIQUE NOT NULL,
  wallet_id TEXT NOT NULL, amount NUMERIC(18,2) NOT NULL,
  state TEXT NOT NULL, attempts INT NOT NULL DEFAULT 0,
  next_action_at TIMESTAMPTZ, version BIGINT NOT NULL DEFAULT 0);

Every transition is one local transaction in the Transfers DB that updates state and version and inserts an outbox row for any command it sends. The Wallet service handles each command in one local transaction too: check processed_commands, move money between available and held, insert ledger entries, and add a reply to its outbox.

Deep dives

1. Orchestration, not choreography or 2PC. The flow has ordered steps, timeouts, an external pivot and money at stake, so an explicit, queryable state machine (built in-house or on Temporal) beats events scattered across services. 2PC is impossible because the provider will not participate, and it would block on coordinator failure anyway.

2. The payout timeout is not a failure. A timed-out payout may have succeeded, so releasing the hold would let the user spend money that was also sent to their bank. The orchestrator moves to PAYOUT_UNKNOWN, retries with the same idempotency key (the provider returns the original result rather than paying twice) and polls the status endpoint. Only a definitive 'not found after the provider's documented window' or an explicit rejection triggers compensation. Webhooks and polls can arrive out of order, so transitions only move forward: a late PENDING status after PAID is ignored.

3. Holds as semantic locks. PlaceHold runs UPDATE accounts SET available = available - :amt, held = held + :amt WHERE id = :id AND available >= :amt; zero rows updated means insufficient funds. Because the hold is taken first, a concurrent purchase cannot spend the same money, which covers the isolation that sagas otherwise lack. Compensation (ReleaseHold) and completion (CaptureHold) are both idempotent and keyed by transfer_id.

4. Exactly-once effects over at-least-once messaging. Commands and replies travel through outboxes and may be delivered twice. Wallet deduplicates on command_id, the ledger's unique constraint stops double posting, and the orchestrator ignores replies for states it has already left (checked against version). A daily job reconciles the ledger's clearing account against the provider's settlement file; any mismatch pages finance operations.

5. Bank returns. A payout can bounce days after PAID. That is not a rollback of the saga but a new business flow: a 'payout returned' saga credits the wallet with new ledger entries and notifies the user.

Trade-offs and bottlenecks

  • Asynchronous 202 response: users see PENDING for seconds to minutes, in exchange for surviving provider outages without failing requests.
  • Holds reduce the spendable balance immediately; users may be confused, so show 'available' and 'pending' separately.
  • PAYOUT_UNKNOWN can last hours during provider incidents; the funds stay held, which is correct but needs clear user messaging and an operations dashboard.
  • The orchestrator is a critical component; run it stateless over its database, with several instances claiming due transfers via next_action_at and optimistic locking on version.
  • Reconciliation is the safety net for bugs in everything else; without it, a silent mismatch can persist for months.

5Follow-up questions

  • The provider's webhook says PAID, but a status poll a second earlier said PENDING and is processed afterwards. How do you keep state correct?
  • How would you add a currency-conversion step whose quote expires after 30 seconds?
  • A new step must be added to the state machine while 50,000 transfers are in flight. How do you migrate?
  • The Wallet service is down for 20 minutes at payday peak. What do users and the orchestrator experience?
  • Up to which state can a user cancel, and what does cancel do in each state?
