Consistency models from linearizable to eventual

A consistency model is a contract between a data store and its clients: given concurrent reads and writes, which results may a read return? Stronger models make applications easier to reason about but need more coordination, which costs latency and availability. Weaker models are cheap and fast but push complexity into the application.

Linearizability: behave like a single copy

A system is linearizable if every operation appears to take effect atomically at some instant between its request and its response, and all clients agree on that order. The consequence is a recency guarantee: once any read has returned a new value, every later read, by any client, returns that value or a newer one. Reading from asynchronously replicated followers breaks it:

You need linearizability whenever correctness depends on everyone agreeing on the current state right now: electing a single leader, holding a lock, enforcing uniqueness (one account per username), or checking a balance before a withdrawal. It also matters across channels: if a web server stores an uploaded image and then tells a resizer through a queue, the resizer's read must see the upload. The cost is coordination: in a single-leader system reads go to the leader, and the leader must confirm it is still the leader.

Pitfall
Linearizable is not serializable
Serializability is a transaction isolation property: concurrent multi-object transactions produce the same result as some serial order, and that order need not match real time, so a read-only transaction may legally see a snapshot from a few seconds ago. Linearizability is a real-time recency guarantee on single objects. A system with both is strictly serializable; Spanner calls this external consistency. Interviewers like to probe this distinction.

The spectrum, strongest to weakest

ModelGuaranteeExample systemsGood fit

CausalCausally related operations are seen in the same order by everyone; concurrent ones in any orderMongoDB causally consistent sessionsComments and replies, chat, collaboration

EventualIf writes stop, replicas converge; no ordering promise meanwhileDNS, Cassandra at ONE, DynamoDB default readsCounters, feeds, caches, analytics

Causal consistency deserves special attention. Event A happens before event B if B could have been influenced by A: they ran in that order in one process, or B read a value A wrote, or a chain of such links connects them. Events with no such link are concurrent. A causally consistent store guarantees that if you can see a reply, you can see the comment it answers. Crucially, causal consistency can be provided while staying available during a partition; it is roughly the strongest model that can. That makes it the sweet spot for user-facing features that cannot afford CP behavior.

Session guarantees are weaker still but fix the anomalies users actually notice: posting a comment and not seeing it, or refreshing and watching data go backwards. Chapter 7 shows how to implement them with replicas. Eventual consistency promises only convergence; it says nothing about what you read before then, and the definition puts no upper bound on 'eventually', though replication lag is usually milliseconds to seconds in practice.

In production
Amazon S3 became strongly consistent
For years S3 offered only eventual consistency for overwrites and deletes, so a read right after an update could return the old object. In December 2020 AWS made S3 GET, PUT and LIST operations strongly consistent (read-after-write) at no extra cost, removing a whole class of workarounds that data pipelines had needed.

Choosing a model in an interview

  • Ask what goes wrong if a read is one second stale. If the answer is 'money is lost' or 'two people get the same seat', that data needs linearizable or serializable operations.
  • If the answer is 'a user is briefly confused', session guarantees such as read-your-writes are usually enough.
  • If the answer is 'a number is briefly off', eventual consistency is fine and much cheaper.
  • Mix models in one design: seat inventory is strongly consistent, the seat map shown to browsers is cached and eventually consistent, and the final booking re-checks the strong store.
In the interview
Name the model and the mechanism
Avoid the vague phrase 'strong consistency'. Say 'linearizable writes through a Raft-replicated leader', 'causal consistency using session tokens', or 'eventual, with LWW and async replication, lag under a second'. Precise vocabulary shows you know what each guarantee costs.
