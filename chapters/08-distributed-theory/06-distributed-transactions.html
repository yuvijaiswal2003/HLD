Distributed transactions: 2PC, sagas and the outbox

Inside one database, a transaction makes several writes atomic. Many business operations span several databases or services: create the order (Orders DB), reserve stock (Inventory DB), charge the card (Payments service). We want all of it or none of it. There are two broad approaches: make the participants commit atomically with two-phase commit, or give up atomic commit and run a saga of local transactions with compensations.

Two-phase commit (2PC)

2PC has a coordinator (a transaction manager, often inside the application or database) and several participants. The key move is prepare: a participant that votes YES makes a binding promise. It has durably logged everything needed to commit and will commit if told to, even after crashing and restarting.

  1. Phase 1: prepare
    The coordinator sends PREPARE to all participants. Each executes the work, writes a prepared record to its log, keeps its row locks, and votes YES, or votes NO and aborts.
  2. Decision
    If every vote is YES, the coordinator durably logs COMMIT; that write is the commit point. Any NO or timeout means ABORT.
  3. Phase 2: commit or abort
    The coordinator sends the decision to every participant and retries until each acknowledges. Participants apply it and release their locks.

Why 2PC blocks

The weak spot is the window after a participant votes YES. It can no longer abort unilaterally, because others may already have committed; it cannot commit unilaterally, because the decision may have been ABORT. If the coordinator crashes in that window, the participant is in doubt and must hold its locks until the coordinator returns, blocking every other transaction that touches those rows. Participants can ask each other, but if none received the decision, all are stuck. Operators sometimes resolve in-doubt transactions by hand ('heuristic' decisions), which can break atomicity. 2PC also costs latency (two round trips plus forced log writes on every participant) and lowers availability to that of the least available participant. Three-phase commit tries to remove the blocking but is only correct if network delays are bounded, so it is not used in practice.

2PC / XA across databases

Strengths
  • Real atomicity and isolation across participants
  • Application code looks like one normal transaction
Weaknesses
  • Blocks if the coordinator fails after prepare
  • Locks held across network round trips cut throughput
  • Every participant must support prepare; third-party APIs never do
Use whenRarely across services; occasionally between a database and a broker from the same vendor.

2PC over consensus groups

Strengths
  • Coordinator and participants are Raft or Paxos groups, so one machine failure does not block
  • Strictly serializable cross-shard transactions
Weaknesses
  • Higher write latency, especially across regions
  • Only works inside one distributed database
Use whenWhat Spanner, CockroachDB and YugabyteDB do internally. Pick such a database when you need cross-shard ACID.

Saga

Strengths
  • Each step is a short local transaction with no distributed locks
  • Works across services and external APIs
Weaknesses
  • No isolation: others see intermediate states
  • Every step needs a compensation and idempotency
Use whenBusiness workflows across microservices and third parties: orders, bookings, payouts.

Sagas

A saga (Garcia-Molina and Salem, 1987) splits a long transaction into local transactions T1, T2 ... Tn, each committed in its own service. Each step that may need undoing has a compensating transaction Ci that semantically reverses it: release the reservation, refund the charge, send a cancellation email. If step Tk fails, the saga runs Ck-1 ... C1 in reverse order. Compensations are new business operations, not rollbacks: a refund is a new ledger entry, not a deleted row, and a sent email cannot be unsent. Put steps that cannot be compensated last. The step after which the saga is committed to finishing is the pivot; steps after it must be retried until they succeed.

Choreography

Strengths
  • No central component; services react to each other's events
  • Very loose coupling, simple for 2–4 steps
Weaknesses
  • The workflow exists only implicitly across services, hard to see and debug
  • Risk of cyclic event dependencies
  • Adding a step or a timeout touches several services
Use whenShort, stable flows where each step naturally reacts to an event that already exists.

Orchestration

Strengths
  • One state machine defines steps, timeouts and compensations explicitly
  • Saga state is stored durably, so 'where is order 123?' is one query
  • Easier to test and evolve
Weaknesses
  • The orchestrator is another service to run and scale
  • Temptation to move business logic out of the services into it
Use whenMany steps, branching, timeouts or money involved. Temporal, AWS Step Functions and Camunda are common engines.
Pitfall
Sagas give up isolation
Between steps, others see partial results: stock reserved for an order that will fail, a balance reduced by a charge that will be refunded. Standard countermeasures: semantic locks (mark records PENDING so other flows treat them carefully), ordering steps so likely failures and irreversible actions come last, commutative updates (increment and decrement rather than overwrite), and re-checking state before acting. Every step and compensation must also be idempotent, because messages arrive at least once.

The transactional outbox

Sagas and event-driven systems need a service to change its database and publish a message. Doing both directly is the dual-write problem: crash after the database commit but before the publish and the event is lost; publish first and crash before the commit and you announced something that never happened. A Kafka transaction cannot include a PostgreSQL write. The transactional outbox fixes it with one local transaction that writes the business row and an outbox row describing the event. A separate relay publishes outbox rows to the broker, either by polling the table or by tailing the database's write-ahead log with change data capture (Debezium, Chapter 9).

In the interview
What to say about distributed transactions
Default to avoiding them: keep data that must change atomically in one database or one shard. When a workflow must span services, say 'orchestrated saga with compensations, each step idempotent, state changes published through an outbox.' Mention 2PC to show you know why it is avoided across services: it blocks on coordinator failure and third parties cannot take part.
