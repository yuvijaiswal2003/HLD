Design a proximity service (find nearby restaurants)

Design the backend for a Yelp-style app. Given the user's location and a radius such as 500 m, 2 km or 10 km, return nearby restaurants and other businesses, optionally filtered by category, sorted by distance or rating, with pagination. Business owners can add and edit listings. Assume 200M businesses worldwide and 100M daily active users.

45:00Mock interview timer. Start it when you begin talking.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • Which radii must we support, and is there a maximum such as 10 km?
  • Is the default sort by distance or by a relevance score that combines distance, rating and popularity?
  • How quickly must a new or edited business appear in search results: seconds, minutes, or by the next day?
  • Do businesses ever move, or only users? Do we need live-moving objects such as delivery drivers?
  • Which filters are required in the first version: category, open now, price, rating?
  • Is the traffic global, and how uneven is density between dense cities and rural areas?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1Explain why an ordinary index on latitude and longitude does a poor job of answering a 2D radius query.
H2Turn locations into grid cells with sortable IDs, such as geohash prefixes, so a cell lookup becomes a range scan in an ordinary store.
H3A user near a cell edge needs results from the next cell, so search the user's cell and its 8 neighbours, then filter by true distance.
H4Businesses change rarely compared with how often they are searched. Estimate the geo index size; it may fit in memory, which means read replicas, not sharding.
H5Dense downtowns and empty deserts need different cell sizes. Consider expanding the search to coarser precision until enough results are found, or a quadtree.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: search nearby businesses by location, radius (0.5, 1, 2, 5 or 10 km) and optional category; sort by distance or rating; paginate; view a business; owners create, update and delete listings.
  • Non-functional: search p99 under 200 ms; 99.99% availability for search; listing edits visible within minutes, not instantly; read-heavy; scale to 200M businesses and peak tens of thousands of searches per second.
  • Out of scope: moving objects such as drivers (Chapter 17), reviews and photo storage, personalised ranking.

Estimates

  • Search QPS: 100M DAU × 5 searches per day = 5 × 10^8 per day; ÷ ~10^5 s ≈ 5,000 QPS on average (5,800 exactly); peak at 3x ≈ 17,000 QPS.
  • Writes: about 100k business creates and edits per day ≈ 1 write per second. The read-to-write ratio is about 5,000:1.
  • Business data: 200M × ~1 KB (name, address, hours, category, rating) ≈ 200 GB. That fits on one PostgreSQL primary with replicas.
  • Geo index: 200M × (12-byte geohash + 8-byte ID + 16 bytes of lat/lng + ~24 bytes of row and index overhead ≈ 60 bytes) ≈ 12 GB. It fits in RAM on a single machine.
  • Replicas: if one in-memory index replica serves ~3,000 searches per second (9 range lookups plus distance math each), 17k peak ÷ 3k ≈ 6, so run about 8 per region for headroom and failover.
  • Hydration: 20 results per page × 5,800 searches/s ≈ 116k business lookups/s, served by Redis multi-gets.

Data model

sql
-- Source of truth: PostgreSQL primary + replicas
CREATE TABLE business (
  business_id BIGINT PRIMARY KEY,          -- Snowflake ID
  name        TEXT NOT NULL,
  category    TEXT NOT NULL,
  lat         DOUBLE PRECISION NOT NULL,
  lng         DOUBLE PRECISION NOT NULL,
  rating      NUMERIC(2,1),
  hours       JSONB,
  updated_at  TIMESTAMPTZ NOT NULL
);

-- Geo index: one row per business, full-precision geohash.
-- Any coarser cell is a prefix, so one column serves every radius.
CREATE TABLE geo_index (
  geohash     TEXT COLLATE "C" NOT NULL,   -- 9 chars, about 4.8 m cells
  category    TEXT NOT NULL,
  business_id BIGINT NOT NULL,
  lat         DOUBLE PRECISION NOT NULL,   -- copied so distance needs no join
  lng         DOUBLE PRECISION NOT NULL,
  PRIMARY KEY (geohash, business_id)
);
CREATE INDEX geo_by_category ON geo_index (category, geohash);

-- One cell of the 3x3 block:
-- SELECT business_id, lat, lng FROM geo_index
--  WHERE geohash >= '9q8yyk' AND geohash < '9q8yym';

PostgreSQL is fine here because the dataset is small and the write rate is tiny; the geo index is a plain B-tree on a C-collated string, so prefix ranges are index range scans. The (category, geohash) index lets a category filter run inside the index instead of fetching every place in the cell. The same layout works in DynamoDB or Cassandra with the cell prefix as the partition key, if you prefer a managed key-value store.

High-level design

  1. Pick the precision
    The location search service maps the radius to a geohash precision whose cell's short side is at least the radius: 0.5 km uses 6 characters; 1 and 2 km use 5; 5 and 10 km use 4. Above about 65° latitude cells get narrow, so drop one more level.
  2. Compute the 3 × 3 block
    Encode the user's position, compute the 8 neighbouring cells (a pure function, no I/O) and issue 9 prefix range scans in parallel, or one query with 9 OR-ed ranges, against a geo index replica.
  3. Filter and rank
    Compute the haversine distance for every candidate, drop those outside the radius, apply filters and sort by distance or by a score such as rating weighted by distance. Keep the top limit after the cursor.
  4. Hydrate
    Fetch names, ratings and hours for the 20 IDs with one Redis MGET; fill misses from a PostgreSQL replica and cache them with a TTL of about 10 minutes.
  5. Write path
    An owner edit commits to the business table. A CDC stream (Debezium reading the write-ahead log) feeds the index updater, which upserts the geo_index row (deleting the old row first if the business moved) and invalidates the cached details. End-to-end lag is seconds to minutes, inside the requirement.

Deep dives

1. Uneven density. A 10 km search uses precision 4, and the 3 × 3 block around Manhattan covers roughly 90 × 58 km, which can hold hundreds of thousands of businesses, far too many to distance-sort per request, while the same block in rural Nevada holds a handful. Three tactics: (a) push the category filter into the index so "sushi" scans only sushi rows; (b) for distance-sorted queries, search outward: start with the precision-6 block and expand to precision 5 and 4 only while fewer than limit results lie within the distance the current block fully covers (its cell's short side, about 600 m at precision 6), so dense areas stop early and sparse ones widen automatically; (c) cap candidates per cell, for example by keeping cells pre-sorted by rating when the sort is by rating. If density skew still hurts, replace the flat geohash table with an in-memory quadtree (leaf capacity about 100) on each search server, rebuilt from the geo index at startup; with 200M places that is about 5 GB per server and takes a few minutes to build.

2. Why replicas rather than shards. The whole index is about 12 GB, so every replica can hold all of it in memory, and any server can answer any query without a scatter-gather. Sharding by geohash would create hot shards (a city at lunchtime) and cross-shard queries along cell edges, all to solve a size problem that does not exist. Scale reads by adding replicas, and replicate the full index to every region so each user is served locally. Shard only if the index grows past one machine's memory, and then by region: a covering of cell prefixes per shard, so a query touches one shard except near shard borders.

3. Caching cell lookups. Businesses barely change, so the result of "cell 9q8yyk, category sushi" can be cached in Redis as a list of (ID, lat, lng) with a TTL of a few minutes plus an explicit invalidation when the index updater touches that cell. Popular cells (downtown, airports) get very high hit rates. Never cache the final response keyed by the user's raw coordinates: two users a metre apart produce different keys, so the hit rate would be close to zero.

5Follow-up questions

  • A user searches with a 50 km radius in a rural area. How does your precision choice change, and what stops it from scanning a 156 km cell in a dense region?
  • How would you add full-text search ("vegan ramen open now") on top of the geo filter?
  • Owners complain that edits take a day to appear. What changes if freshness must be under 5 seconds?
  • How would the design change for moving objects that update their location every 4 seconds, such as delivery drivers?
  • How do you handle a search near the antimeridian or the poles, where geohash neighbours behave oddly?
