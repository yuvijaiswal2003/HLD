Top-K, heavy hitters and fan-out

"Top 10 trending hashtags", "most viewed videos this hour", "which cache keys are hot" and "which IPs send the most requests" are all Top-K problems: rank items by frequency and return the K most frequent. A heavy hitter is an item whose count exceeds some fraction of the whole stream, for example more than 0.1% of all events. The difficulty is never the ranking itself; it is counting billions of events over millions of distinct keys, across many machines and over sliding time windows.

Exact Top-K on one machine

Count with a hash map, then keep a min-heap of size K: push each item while the heap is small; once it holds K items, replace the root only when an item beats the current K-th best. That is O(D log K) for D distinct items instead of O(D log D) for a full sort, and it is what you write when the data fits on one box.

python
import heapq

def top_k(counts, k):
    heap = []                                  # min-heap of (count, key)
    for key, c in counts.items():
        if len(heap) < k:
            heapq.heappush(heap, (c, key))
        elif c > heap[0][0]:                   # beats the current k-th best
            heapq.heapreplace(heap, (c, key))
    return sorted(heap, reverse=True)

top_k({"#a": 5, "#b": 9, "#c": 1, "#d": 7}, 2)   # [(9, '#b'), (7, '#d')]

Distributed Top-K: partition by key

At scale, events are spread over many servers. The correct pattern is to partition the stream by the key being counted, for example a Kafka topic keyed by hashtag, so all events for one hashtag reach one aggregator. Each aggregator then holds exact counts for its share of keys, computes a local top-K, and a merger combines the local lists. Because no key is split across aggregators, the global top K is guaranteed to be among the union of the local top Ks.

Pitfall
Merging local top-K lists from unkeyed data is wrong
Suppose three web servers each count the hashtags they happened to receive. Server 1 sees #b 150 times, server 2 sees #c 150 times, server 3 sees #d 150 times, and every server sees #a 100 times. Each local top-1 omits #a, so the merged answer is a 150-count tag, yet #a has 300 in total and is the true winner. Merging is only correct after a shuffle by key, or if every server sends its full counts rather than just its top K.

Approximate Top-K in bounded memory

When there are too many distinct keys to count exactly, two techniques bound memory. Count-Min Sketch plus a heap: add every event to a sketch, read back its estimate, and keep a heap of the best candidates; memory is the sketch plus the heap. Because estimates never undercount, a frequency threshold never filters out a real heavy hitter. The risk runs the other way, a light item inflated by collisions, so keep a few more candidates than K (say 2K) and rank them by exact counts kept just for those candidates. Space-Saving (a relative of Misra-Gries) keeps exactly m counters: an item already tracked is incremented, while a new item replaces the item with the smallest counter and inherits that count plus 1. Any item that occurs more than N/m times in a stream of N events is guaranteed to be tracked, and each count is overestimated by at most the smallest counter.

For time windows, keep one bucket per minute: a hash map, a sketch or both. The last hour is the sum of the last 60 minute buckets, and sliding the window drops the oldest bucket. Count-Min Sketches with identical dimensions and hash functions can be added cell by cell, so per-minute sketches combine cheaply; heaps cannot be added or subtracted, so a top-K is recomputed from the combined counts. Windowing, event time and watermarks are covered in Chapter 10.

Tip
Redis sorted sets for modest Top-K
For up to a few million keys, a Redis sorted set per minute does the job: ZINCRBY trend:10:15 1 "#worldcup" on each event, ZUNIONSTORE the last 60 minute keys for the hour, then ZREVRANGE trend:hour 0 9 WITHSCORES. Each ZINCRBY is O(log n). The catch is that every event is a network round trip to one node, so batch or pre-aggregate counts in the application before sending them.

Fan-out strategies: a preview

Fan-out means one action triggering work on many targets. It is central to news feeds, notifications and chat (Chapter 16 covers those in depth), and the choice is usually between doing the work on write or on read.

Fan-out on write (push)

Strengths
  • Reads are one cache lookup: the feed is precomputed
  • Predictable read latency
Weaknesses
  • Write cost scales with follower count: 50M writes for an account with 50M followers
  • Wasted work for inactive followers
Use whenMost users, who have modest follower counts and readers who read far more often than they post.

Fan-out on read (pull)

Strengths
  • Writes are a single insert
  • No wasted work; always fresh
Weaknesses
  • Each read gathers from every followee and merges, so read cost grows with following count
  • Higher and more variable read latency
Use whenCelebrity accounts and rarely read feeds.

Hybrid

Strengths
  • Push for normal accounts, pull for accounts above a follower threshold
  • Bounds both write amplification and read cost
Weaknesses
  • Two code paths to build and keep consistent
  • The threshold needs tuning
Use whenThe standard answer for social feeds at scale.

Fan-out on read has a statistical trap: tail latency amplification. If one request fans out to 100 shards and each shard is slow 1% of the time, then 1 − 0.99^100 ≈ 63% of requests wait for at least one slow shard. Mitigations include hedged requests (send a duplicate to another replica if the first has not answered by about the p95 latency), returning partial results after a deadline, and fanning out to fewer, larger partitions.

In the interview
Top-K signals interviewers look for
Clarify the window (all time, last hour, sliding) and whether approximate counts are acceptable. Partition by key before aggregating, pre-aggregate hot keys on the producer side, and keep the serving path separate: a precomputed list in a cache, refreshed every few seconds, not a query that scans counts on demand.
