Probabilistic data structures

Some questions are expensive to answer exactly at scale: have we seen this URL before?, how many times did this hashtag appear?, how many distinct users visited today? An exact answer needs memory proportional to the number of distinct items, which can be billions. Probabilistic data structures (often called sketches) answer with a small, mathematically bounded error in a fixed amount of memory, often kilobytes. Most are also mergeable: you can build one per server or per minute and combine them, which is what makes them fit distributed systems so well.

Bloom filters

A Bloom filter is a bit array of m bits, all initially 0, plus k hash functions that each map an item to a position in the array. To add an item, hash it k times and set those k bits to 1. To query, hash it the same way: if any of the k bits is 0, the item was definitely never added; if all are 1, it was probably added, because other items may have set those bits. So a Bloom filter never gives a false negative, only false positives, and it works as a cheap gatekeeper in front of an expensive lookup.

After inserting n items, the false-positive probability is approximately p ≈ (1 − e^(−kn/m))^k. For a given m and n it is minimised at k = (m/n) · ln 2, which gives the sizing formula m = −n · ln p / (ln 2)², about 1.44 · log2(1/p) bits per item. Worked example: 100M usernames at 1% need m = 10^8 × 4.605 / 0.4805 ≈ 958M bits ≈ 120 MB, with k = 9.6 × 0.693 ≈ 7 hash functions. Two consequences: the filter size depends only on n and p, not on item size (a 2 KB URL costs the same 9.6 bits as an 8-byte ID), and every 10x reduction in false positives costs another 4.8 bits per item.

python
import hashlib, math

class BloomFilter:
    def __init__(self, n, p):
        self.m = math.ceil(-n * math.log(p) / math.log(2) ** 2)   # bits
        self.k = max(1, round(self.m / n * math.log(2)))          # hashes
        self.bits = bytearray((self.m + 7) // 8)

    def _positions(self, item):
        # Kirsch-Mitzenmacher trick: k positions from two hashes, h1 + i*h2
        d = hashlib.sha256(item.encode()).digest()
        h1 = int.from_bytes(d[:8], "big")
        h2 = int.from_bytes(d[8:16], "big") | 1
        return [(h1 + i * h2) % self.m for i in range(self.k)]

    def add(self, item):
        for pos in self._positions(item):
            self.bits[pos // 8] |= 1 << (pos % 8)

    def might_contain(self, item):
        return all(self.bits[pos // 8] & (1 << (pos % 8))
                   for pos in self._positions(item))

bf = BloomFilter(n=1_000_000, p=0.01)   # m = 9,585,059 bits (~1.2 MB), k = 7
bf.add("user:42")
bf.might_contain("user:42")   # True, always
bf.might_contain("user:43")   # False, or True about 1% of the time
Pitfall
Bloom filter pitfalls
No deletes: clearing a bit could erase other items, so use a counting Bloom filter (small counters instead of bits) or a cuckoo filter if you need removal. No resizing: the false-positive rate climbs steeply past the planned n; a filter sized for 1% at n items is at about 44% after 3n insertions, so size for growth or rebuild periodically. No enumeration: you cannot list what is inside, only test membership.

Count-Min Sketch

A Count-Min Sketch estimates how often each item has appeared in a stream. It is a grid of counters with d rows and w columns, and each row has its own hash function. To count an item, hash it once per row and increment one counter in each row. To estimate its count, read the same d counters and take the minimum. Collisions only ever add other items' counts to a counter, so with non-negative increments every counter is at least the true count and the estimate can only overestimate, never underestimate. Taking the minimum picks the row with the least collision noise.

Sizing: with w = ⌈e/ε⌉ and d = ⌈ln(1/δ)⌉, the estimate is at most true count + εN with probability at least 1 − δ, where N is the total of all increments. For ε = δ = 0.001 that is 2,719 columns × 7 rows = 19,033 counters, about 76 KB with 4-byte counters, whether the stream holds a thousand distinct keys or a billion. The bound is relative to N, though: over 1 billion events the overestimate can reach 1 million. That is noise for a hashtag seen 50 million times and meaningless for one seen 40 times, which is why Count-Min Sketches are used to find heavy hitters, not to report long-tail counts.

HyperLogLog

HyperLogLog (HLL) estimates cardinality, the number of distinct items. The intuition: hash every item to a uniformly random bit string. Half the hashes start with a 0 bit, a quarter with 00, one in 2^k with k zeros, so if the longest run of leading zeros you have seen is 20, you have probably seen around 2^20 distinct items. One such observation is very noisy, so HLL uses the first p bits of each hash to pick one of m = 2^p registers, keeps the maximum leading-zero rank seen in each register, and combines them with a harmonic mean plus bias corrections. The standard error is 1.04 / √m. A duplicate hashes identically and cannot raise a register twice, which is why HLL counts distinct items rather than events.

Redis implements HLL with p = 14: 16,384 registers of 6 bits each is 12,288 bytes, the well-known 12 KB, and 1.04 / √16384 gives 0.81% standard error whether the set holds a thousand or a billion members (small sets use a compact sparse encoding). The commands are PFADD, PFCOUNT and PFMERGE. Merging takes the register-wise maximum, so merging seven daily HLLs gives an HLL of the week's distinct visitors, but intersections cannot be computed reliably and you must never sum daily counts to get weekly uniques. Counting 1 billion distinct 8-byte user IDs exactly as a plain set needs about 8 GB; an HLL needs 12 KB.

In production
Where these show up in real systems
Cassandra, HBase and RocksDB keep a Bloom filter per on-disk data file so a read for a missing key skips that file without touching disk (Cassandra exposes this as the per-table bloom_filter_fp_chance). Redis ships HyperLogLog natively, and the RedisBloom module adds Bloom filters and Count-Min Sketches. BigQuery's HLL_COUNT functions implement HyperLogLog++. The Java cache Caffeine decides which entries to admit using a compact Count-Min-style frequency sketch (TinyLFU).
In the interview
When to reach for a sketch
Ask whether the answer must be exact. Unique visitors on a dashboard, trending topics and already-crawled checks tolerate 1% error; billing, inventory and account balances do not. When you propose a sketch, name the error type (Bloom: false positives only; Count-Min: overestimates only; HLL: symmetric, about ±0.81%) and the memory saved, for example 12 KB instead of 8 GB.
