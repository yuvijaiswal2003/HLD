Design a Top-K trending hashtags system

Design the service behind a 'Trending now' panel for a Twitter-like social network. Show the top 10 hashtags globally and per country, based on activity over the last hour, refreshed at least every minute. Assume 500M posts per day, and that roughly 30% of posts contain hashtags.

45:00Mock interview timer. Start it when you begin talking.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • Is trending simply the highest count in the window, or what is growing fastest compared with normal? A tag like #love is always popular but rarely trending.
  • Which windows matter: a sliding last hour, last 24 hours? How fresh must the panel be?
  • Global and per-country only, or also per city and per topic?
  • Are approximate counts acceptable, or does this feed anything that must be exact, such as ad billing?
  • What do we do about spam and bots inflating a hashtag?
  • Do we need historical trends (what was trending at 9 pm yesterday) or only the current list?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1Separate the pipeline that counts from the API that serves; the panel should read a precomputed list.
H2Counting needs all events for a hashtag in one place. What should the Kafka partition key be, and what happens to a partition when one tag goes viral?
H3A sliding 1-hour window can be built from 60 one-minute buckets. Which data structures can be added together across buckets?
H4The number of distinct hashtags is huge but the top 10 are heavy hitters. Consider Count-Min Sketch or Space-Saving to bound memory, and keep exact counts only for candidates.
H5Raw count favours always-popular tags. Score the current window against a baseline from previous days, and count distinct users per tag so one bot cannot fake a trend.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: top 10 trending hashtags globally and for each of about 200 countries over a sliding 1-hour window; refreshed every minute; trending means unusually high activity relative to the tag's normal level, not only high volume.
  • Non-functional: freshness within 1 to 2 minutes; serving p99 under 50 ms at very high read QPS; approximate counts are fine; resilient to bot manipulation; the counting pipeline survives node failures without double counting enough to change rankings.
  • Out of scope: personalised trends, text topic clustering, ad billing.

Estimates

  • Events: 500M posts × 30% with tags × ~2 tags = 3 × 10^8 hashtag events per day ≈ 3,500 per second on average, so assume ~10k per second at peak and 50k per second during a global event.
  • Event size: ~100 bytes (tag, country, user ID, timestamp), so 10k/s × 100 B = 1 MB/s; trivial for Kafka.
  • Distinct tags: maybe 5M distinct tags per hour, but the long tail is huge (most appear once). An exact hash map for one minute holds well under 1M entries, about 100 MB; fine on one aggregator, larger if country breakdowns are exact.
  • Reads: the panel is loaded on many app opens: say 200M DAU × 10 views = 2 × 10^9 per day ≈ 23k QPS on average, 70k at peak. All of it is served from a precomputed list in a cache or CDN.
  • Output: 201 lists (global plus 200 countries) × 50 candidates × ~50 bytes ≈ 500 KB per refresh. Tiny.

High-level design

  1. Emit
    When a post is created, the post service extracts and normalises hashtags (lowercase, Unicode NFKC normalisation so visually identical tags count together) and produces one event per tag to Kafka, keyed by tag. Keying by tag puts every event for a tag on one partition and one Flink task.
  2. Count
    A Flink job keyed by tag keeps, per tag and per one-minute event-time bucket, a total count, per-country counts and a HyperLogLog of user IDs. A watermark allowing about 30 s of lateness closes each minute. Flink checkpoints state and Kafka offsets together, so after a failure counts are restored exactly.
  3. Emit candidates
    When a minute closes, each Flink task sums the last 60 minutes for its tags, keeps a local top 50 globally and per country by score, and sends those lists to the ranker. Because the stream is partitioned by tag, the true global top 10 must appear in the union of these per-partition lists.
  4. Rank
    The ranker merges about 64 lists per scope, removes blocklisted tags and those below the distinct-user threshold, computes the final score and writes the top 50 per scope to Redis as one small JSON value. A standby ranker takes over through a lease if the active one dies.
  5. Serve
    The API reads trends:{scope} from Redis and returns the top 10; the CDN caches each scope for 30 s. 70k reads per second turn into a few hundred origin requests per second.

Deep dives

1. Trending is not the same as popular. Ranking by raw count shows #love and #photography forever. Instead compare the last hour with the tag's usual level for this hour, taken from Cassandra minute counts (the average for the same hour over the previous 7 days). A simple z-like score works well: score = (count_1h − expected) / sqrt(expected), with expected floored at a small number so brand-new tags do not divide by zero. Example: #love at 5,000 per hour against a baseline of 4,800 scores (5,000 − 4,800) / √4,800 ≈ 2.9; #earthquake at 2,500 against a baseline of 50 scores about 346 and trends. Add minimum volume and distinct-user thresholds, and optionally decay the score over the hour so the panel turns over.

python
import math

def trend_score(count_1h, baseline_1h, distinct_users):
    if count_1h < 200 or distinct_users < 100:     # too small or too few people
        return 0.0
    expected = max(baseline_1h, 5.0)               # floor for brand-new tags
    return (count_1h - expected) / math.sqrt(expected)

trend_score(5000, 4800, 3900)   # ~2.9:  always popular, not trending
trend_score(2500, 50, 2100)     # ~346:  a sudden spike, trending

2. Hot partitions when a tag goes viral. During a final, #worldcup can be 20% of all events, about 10k per second, all keyed to one Kafka partition and one Flink task. Two fixes compose well. First, pre-aggregate before Kafka: each post-service instance keeps a local map of tag counts for 1 to 5 seconds and emits (tag, country, count) deltas instead of single events, which collapses thousands of events into one message per instance per flush. Second, salt only known-hot keys: send #worldcup as #worldcup|0 to #worldcup|7, count each sub-key separately and add the 8 partial counts in the ranker. Pre-aggregation alone usually suffices; salting adds a second merge step and is reserved for the few tags a hot-key detector flags.

3. Memory for the long tail. Exact per-minute counts for millions of one-off tags waste state. Use two tiers: every event updates a per-minute Count-Min Sketch per partition (2,719 × 7 counters ≈ 76 KB, with error at most 0.1% of that minute's events), and a tag gets exact state only once its sketch estimate passes a threshold, say 20 per minute. Because the sketch only overestimates, no tag that truly crossed the threshold is missed; a few false candidates just cost a little extra exact state. Distinct-user HLLs are kept only for candidates for the same reason: at about 12 KB each in dense form, one per tag would cost 60 GB for 5M tags.

Trade-offs and bottlenecks

  • Exact vs approximate: exact keyed counts are affordable for candidate tags; sketches bound memory for the tail. The rankings tolerate small errors; billing would not.
  • Freshness vs stability: one-minute buckets with a 30 s watermark give trends within about 2 minutes. Shorter windows react faster but make the list jumpy; publish only when ranks change meaningfully, or smooth scores across minutes.
  • Global vs regional pipelines: one global pipeline is simpler; per-region pipelines with a global merge of candidate lists avoid shipping every event across oceans, at the cost of a second merge step.
  • Abuse: distinct-user HLLs, account-age weighting and a manual blocklist matter as much as the counting; a trending list is a target for spam.
  • Bottlenecks: hot partitions (fixed by pre-aggregation and salting), the single ranker (small and stateless, so a standby with a lease), and Flink state size (two-tier counting).

5Follow-up questions

  • How do you show 'what was trending at 9 pm last Friday' without replaying Kafka?
  • A bot network posts #buyXcoin from 50,000 new accounts. Which signals stop it from trending, and what is the cost of false positives?
  • How would you extend trends to every city in the world, roughly 10,000 scopes, without 50 times more ranker work?
  • If Flink is down for 10 minutes, what does the panel show, and how does it catch up?
  • How would you make trends personalised (relevant to accounts the user follows) at 70k reads per second?
