Real-time collaboration: OT vs CRDTs

In a collaborative editor every user edits a local copy so typing feels instant, and edits are exchanged in the background. The hard part is concurrency. Start with the text abc. Alice inserts X at position 0 while Bob, at the same moment, deletes position 2 (the c). If each side simply applies the other's operation, Alice applies delete 2 to Xabc and removes the b, ending with Xac; Bob applies insert X at 0 to ab and gets Xab. The replicas have diverged, and Alice lost a character Bob never deleted. Positions are only meaningful relative to the document version they were created against. The two families of solutions are operational transformation and CRDTs.

Operational transformation

OT keeps position-based operations and transforms each incoming operation against the concurrent operations already applied, so it still means what its author intended. Bob's delete 2, transformed past Alice's insert at 0, becomes delete 3, and both sides end with Xab. Production OT systems use a central server that assigns every operation a revision number, which creates one total order. A client sends each operation tagged with the revision it was based on; the server transforms it against everything committed since then, commits it as the next revision and broadcasts it. Clients transform incoming operations against their own pending ones in the same way.

python
# Transform op against an op that was applied concurrently before it.
# op = (kind, pos, char, site); site IDs break ties between equal positions.
def transform(op, other):
    kind, pos, ch, site = op
    o_kind, o_pos, _, o_site = other
    if o_kind == "ins":
        if o_pos < pos or (o_pos == pos and (kind == "del" or o_site < site)):
            pos += 1                      # text shifted right under us
    else:                                 # other was a delete
        if o_pos < pos:
            pos -= 1                      # text shifted left under us
        elif o_pos == pos and kind == "del":
            return None                   # both deleted the same char: no-op
    return (kind, pos, ch, site)

transform(("del", 2, "c", "bob"), ("ins", 0, "X", "alice"))
# -> ("del", 3, "c", "bob")

Even this two-operation case needs tie-break rules. Real editors also have rich-text formatting, multi-character ranges, undo and cursors, and every pair of operation types needs a transform function. Many published OT algorithms for the peer-to-peer case, with no central server, were later shown to diverge in some corner cases. The central server sidesteps most of that, because operations only ever need to be transformed against one agreed history.

CRDTs

A conflict-free replicated data type is designed so that concurrent updates can be applied in any order and replicas that have seen the same set of updates are guaranteed to end up in the same state, with no transformation and no central ordering. State-based CRDTs ship whole states and merge them with a function that is commutative, associative and idempotent, so duplicated or reordered messages are harmless. Operation-based CRDTs ship operations that commute, but need delivery that is reliable and in causal order. Text CRDTs (RGA, YATA as used by Yjs, Automerge's list type) avoid positions entirely: every character gets a unique ID such as (counter, replica) and an insert says "after the character with ID x". Concurrent inserts after the same character are ordered by a deterministic rule on their IDs, and deletes leave tombstones so later operations can still refer to the deleted character.

python
class GCounter:                       # grow-only counter, state-based CRDT
    def __init__(self, replica_id):
        self.id, self.counts = replica_id, {}

    def increment(self, n=1):
        self.counts[self.id] = self.counts.get(self.id, 0) + n

    def merge(self, other):           # element-wise max: order and repeats don't matter
        for rid, c in other.counts.items():
            self.counts[rid] = max(self.counts.get(rid, 0), c)

    def value(self):
        return sum(self.counts.values())

us, eu = GCounter("us"), GCounter("eu")
us.increment(3); eu.increment(5)
us.merge(eu); eu.merge(us)            # both now report 8

Operational transformation

Strengths
  • Small, position-based operations and little per-character metadata
  • Mature for text: Google Docs uses OT
  • Server can validate and reject edits and enforce permissions in one place
Weaknesses
  • Transform functions are subtle and grow with every operation type
  • Needs a central server for ordering in practice
  • Long offline sessions mean transforming large batches of operations on reconnect
Use whenAlways-online, server-mediated editing of text or rich text.

CRDTs

Strengths
  • Converge without a central authority: peer-to-peer, multi-region, offline-first
  • Merge is mathematically guaranteed; any sync order works
  • Libraries exist for counters, sets, maps, lists and JSON: Yjs, Automerge
Weaknesses
  • Unique IDs and tombstones add metadata; cleaning up tombstones needs coordination
  • Converging is not the same as preserving intent: semantic conflicts still need product rules
  • Invariants such as no cycles in a tree are hard to enforce without a server
Use whenOffline-first or peer-to-peer apps, multi-region replicated state, local-first software.
In production
Figma's middle path
Figma's engineering team has written that its multiplayer system is not a true CRDT but was inspired by CRDTs, and relies on a central server as the authority. A Figma file is a tree of objects with properties. Concurrent changes to different properties both survive, while concurrent changes to the same property resolve to the last value the server received. Child order uses fractional indexing, which gives each child a position between its neighbours, and the server rejects reparenting moves that would create a cycle. A design canvas suits this because users rarely edit the same property of the same object at the same moment, unlike two people typing in one paragraph.
Tip
The rest of a collaboration system
Persist an append-only operation log plus periodic snapshots, so a newly opened document loads the latest snapshot and replays only the operations after it. Route every editor of one document to the same server (consistent hashing on document ID) so ordering happens in one process. Send cursors and selections over the same WebSocket but never persist them; they are ephemeral presence data.
In the interview
How to choose in an interview
For "design Google Docs", OT with a central server per document, an op log and snapshots is the expected answer, and you should say why: low metadata and one place to enforce ordering and permissions. Pick CRDTs when the prompt says offline editing, peer-to-peer sync or multi-region writes without a single leader. Either way, name the cost: OT needs a server in the loop, and CRDTs carry metadata and tombstones.
