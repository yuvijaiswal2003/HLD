Merkle trees, gossip and failure detection

Large leaderless clusters such as Cassandra and other Dynamo-style stores (Chapter 7) have two housekeeping problems that no single coordinator should own. Replicas drift apart after missed writes, and they need to find which data differs without shipping terabytes around to compare. And every node needs to know which other nodes are alive. Merkle trees solve the first problem; gossip plus a failure detector solves the second.

Merkle trees

A Merkle tree (hash tree) summarises a dataset with hashes. Split the key space into ranges and hash the data in each range to form the leaves. Each parent is the hash of its children's hashes concatenated, up to a single root hash. Changing one value changes its leaf, every ancestor and the root, so two replicas with equal roots hold identical data; with a cryptographic hash, equal roots over different data are vanishingly unlikely.

To repair, two replicas exchange root hashes. If they match, stop. If not, exchange the children's hashes and recurse only into the children that differ. With 1 million leaf ranges the tree is 20 levels deep, so a single divergent range is located in about 20 steps of comparing two hashes, and then only that range's keys are streamed. Without the tree, replicas would exchange a hash per key or ship the data itself. Leaf size is the main knob: smaller ranges re-send less data per mismatch but make the tree bigger to build and store.

  • Anti-entropy repair in Dynamo, Cassandra (nodetool repair builds trees per token range) and Riak.
  • Git: a commit points to a tree object whose hash covers its subtrees and file blobs, so diffing two commits skips every subtree whose hash is unchanged.
  • Inclusion proofs: Certificate Transparency logs and Bitcoin blocks let a client verify that an item belongs to a set of n items with only log2(n) sibling hashes, about 20 hashes for a million entries.
  • Sync and backup tools: comparing per-directory or per-chunk hash trees tells a client which parts of a large tree changed.
Pitfall
Merkle trees are not free
Both replicas must bucket keys into exactly the same ranges, which is natural when ranges follow the token ring but breaks if replicas own different ranges. Building a tree means reading and hashing every row in the range, which is why Cassandra repairs are scheduled, throttled operations rather than continuous ones. Systems that keep the tree current on every write move that hashing cost onto the write path instead.

Gossip protocols

In a gossip (epidemic) protocol, every node wakes up periodically, say once per second, picks one or a few random peers, and exchanges a digest of its state: for example a table of node, heartbeat counter, status and version. Each side keeps whichever entry has the higher version. A fact known to one node reaches all N nodes in O(log N) rounds, roughly 10 to 20 one-second rounds for 1,000 nodes, while each node sends a constant number of messages per round regardless of cluster size. There is no coordinator to fail, and a lost message is repaired in the next round. The price is that membership is eventually consistent: different nodes briefly disagree about who is in the cluster.

In production
Gossip in the wild
Cassandra's gossiper runs every second and exchanges state with up to three other nodes, which is how nodes learn about joins, departures, schema versions and token ownership. Redis Cluster nodes ping each other over a dedicated cluster bus and piggyback information about other nodes on those messages. HashiCorp Consul and Serf use the memberlist library, an implementation of the SWIM protocol.

Failure detection

A node cannot tell a crashed peer from a slow one or from a broken network link; all it sees is missing messages. A failure detector therefore only ever suspects, and every design trades detection speed against false alarms.

Fixed-timeout heartbeats

Strengths
  • Trivial to implement and reason about
  • Detection time is predictable: timeout plus one interval
Weaknesses
  • One threshold for every network: too short gives false alarms during GC pauses, too long delays failover
  • All-to-all heartbeats cost O(N²) messages
Use whenSmall clusters and leader-to-follower checks, such as Raft election timeouts.

SWIM-style probing

Strengths
  • Each node probes one random peer per period, so load per node is constant
  • Indirect probes through k other nodes filter out a single bad link
  • A suspect state lets a slow node refute the accusation
Weaknesses
  • More protocol states and tuning knobs
  • Detection time is probabilistic
Use whenLarge, dynamic memberships: Consul, Serf, service discovery agents.

Phi accrual

Strengths
  • Learns each peer's heartbeat inter-arrival distribution
  • Outputs a suspicion level, so each consumer picks its own threshold
Weaknesses
  • Needs a window of heartbeat history per peer
  • Thresholds are less intuitive than seconds
Use whenCassandra and Akka cluster membership, on noisy networks.

The phi accrual detector (Hayashibara et al., 2004) records the arrival times of a peer's recent heartbeats and models the gaps between them as a probability distribution. At any moment it outputs φ = −log10(P), where P is the probability that a heartbeat would arrive even later than now given that history. φ = 1 means roughly a 10% chance that suspecting the peer is a mistake, φ = 2 means 1%, φ = 3 means 0.1%. A peer whose heartbeats are normally regular gets suspected quickly; one on a jittery link automatically gets more slack. Cassandra convicts a node when φ exceeds phi_convict_threshold, which defaults to 8.

In the interview
Say suspected, then fence
Interviewers like to hear that no failure detector is perfect in an asynchronous network: a node declared dead may still be running and writing. Pair detection with a safety mechanism, such as leases with fencing tokens (Chapter 8) or quorum writes, so a falsely suspected node cannot corrupt data. Then quote the knobs: heartbeat interval, timeout or φ threshold, and the expected detection time.
