Unique ID generation

On a single database, AUTO_INCREMENT or a PostgreSQL BIGSERIAL hands out IDs and you never think about it. Once data is sharded across many databases or written in several regions, there is no single counter to ask. You need IDs that are unique without coordinating on every insert, and you usually want more than uniqueness: a compact size (64 vs 128 bits), rough ordering by creation time so the newest rows sort last, high throughput, and no leakage of business data such as how many orders you took today.

Auto-increment, step offsets and ticket servers

The cheapest distributed scheme reuses the database counter. With two MySQL masters you set auto_increment_increment = 2 on both and auto_increment_offset to 1 and 2, so one issues odd IDs and the other even IDs. A ticket server takes this further: a dedicated database whose only job is to hand out numbers, which application servers call before inserting rows anywhere. Both give compact 64-bit integers, but each ID (or batch) costs a network round trip to a component you now have to keep highly available. A common refinement is segment allocation: each app server reserves a block of, say, 1,000 IDs with one UPDATE ... SET max_id = max_id + 1000 and hands them out from memory, cutting database traffic by 1,000x at the cost of gaps when a server restarts.

In production
Flickr's ticket servers
Flickr generated primary keys for its sharded MySQL databases with two dedicated ticket servers. Getting an ID meant running REPLACE INTO Tickets64 (stub) VALUES ('a') followed by SELECT LAST_INSERT_ID() on a ticket server. One server issued odd numbers and the other even numbers, so either could fail without stopping ID generation.

UUIDs and ULIDs

A UUID v4 is 128 bits, 122 of them random, so any machine can generate one with no coordination. Collisions are a non-issue in practice: by the birthday bound you need about 2.7 × 10^18 UUIDs for a 50% chance of a single collision, which is a billion IDs per second for 86 years. The costs are size (16 bytes, often stored as a 36-character string) and randomness: consecutive v4 IDs land in unrelated places in an index. UUID v7 (RFC 9562, 2024) fixes the ordering by putting a 48-bit Unix millisecond timestamp in the high bits, followed by random bits, so IDs generated later sort later. ULID is the same idea from before v7 existed: 48 bits of milliseconds plus 80 random bits, written as 26 characters of Crockford base32 that sort lexicographically in time order.

Twitter Snowflake

Snowflake, which Twitter built in 2010, generates IDs inside each worker process from three ingredients. The top bit stays 0 so the value is positive in signed 64-bit types (Java long, PostgreSQL BIGINT). The next 41 bits are milliseconds since a custom epoch: 2^41 ms is about 69.7 years, and choosing a recent epoch (Twitter's is in November 2010, so its IDs last until about 2080) spends none of that range on the past. 10 bits identify the worker, allowing 1,024 generators (Twitter split them into 5 bits of data center and 5 of worker). The last 12 bits are a sequence that counts up within one millisecond, so each worker can issue 4,096 IDs per millisecond, about 4.1 million per second. If the sequence overflows, the generator waits for the next millisecond. IDs are k-sorted: ordered by millisecond across the fleet, as far as worker clocks agree, but within one millisecond they order by worker ID, not by true creation time.

python
import threading, time

EPOCH_MS = 1767225600000               # custom epoch: 2026-01-01T00:00:00Z
MACHINE_BITS, SEQ_BITS = 10, 12
MAX_SEQ = (1 << SEQ_BITS) - 1          # 4095

class Snowflake:
    def __init__(self, machine_id):
        if not 0 <= machine_id < (1 << MACHINE_BITS):    # 0..1023
            raise ValueError("machine_id out of range")
        self.machine_id, self.last_ms, self.seq = machine_id, -1, 0
        self.lock = threading.Lock()

    def next_id(self):
        with self.lock:
            now = time.time_ns() // 1_000_000
            if now < self.last_ms:                       # clock went backwards
                raise RuntimeError("clock moved back; refusing to issue IDs")
            if now == self.last_ms:
                self.seq = (self.seq + 1) & MAX_SEQ
                if self.seq == 0:                        # 4,096 used this ms:
                    while now <= self.last_ms:           # spin to the next ms
                        now = time.time_ns() // 1_000_000
            else:
                self.seq = 0
            self.last_ms = now
            return (((now - EPOCH_MS) << (MACHINE_BITS + SEQ_BITS))
                    | (self.machine_id << SEQ_BITS) | self.seq)

def decode(sid):   # -> (unix_ms, machine_id, sequence)
    return (sid >> 22) + EPOCH_MS, (sid >> 12) & 1023, sid & MAX_SEQ
Pitfall
The two ways Snowflake produces duplicates
Snowflake is unique only if (1) no two live workers share a machine ID and (2) a worker's clock never runs backwards. Assign machine IDs from a lease in ZooKeeper or etcd rather than hand-edited config, and make the worker stop issuing IDs if it loses the lease. For clocks, run NTP in slew mode so corrections speed the clock up or slow it down instead of stepping it back, persist the last issued timestamp so a restart cannot reuse it, and on a backward jump either wait it out (a few milliseconds) or refuse and alert.

Sortable vs random IDs and index locality

In a B-tree primary key index (and especially a clustered one, like InnoDB's, where the rows live in the index), time-ordered keys always insert at the right-hand edge. The same few leaf pages stay hot in memory, pages fill completely before a new one starts, and range scans by time are cheap. Random UUID v4 keys insert into a random leaf every time: once the index outgrows the buffer pool, most inserts need a disk read first, pages split and stay partly empty, and write throughput can drop several-fold. That is why Snowflake, UUID v7 and ULID exist. The rule flips on range-partitioned distributed stores such as Bigtable, HBase and Spanner: a monotonically increasing key sends every new write to the one tablet that owns the newest range, creating a hot spot, so Spanner's documentation recommends UUID v4 or bit-reversed sequences. Hash-partitioned stores like Cassandra and DynamoDB hash the partition key, so its ordering does not affect how writes spread.

Tip
Send 64-bit IDs to browsers as strings
JavaScript numbers are doubles and represent integers exactly only up to 2^53 (about 9 × 10^15). A Snowflake ID exceeds that once its timestamp passes 2^31 ms, roughly 25 days after the epoch, and JSON.parse silently rounds it to a different ID. Twitter's API added an id_str field for this reason, and Discord sends its Snowflake IDs as strings.
In production
Snowflake variants in production
Discord uses Snowflake-style IDs with an epoch of 1 January 2015 for messages, users and channels. Instagram generated 64-bit IDs inside PostgreSQL with a PL/pgSQL function: 41 bits of milliseconds, 13 bits of logical shard ID and a 10-bit per-shard sequence, so the shard that owns a row can be read straight from its ID.
In the interview
How to answer the ID question
State the requirements first: must IDs fit in 64 bits, sort by time, be unguessable? Then pick: Snowflake for compact, time-sorted numeric IDs at high volume; UUID v7 when 128 bits is acceptable and you want zero coordination; UUID v4 or a random token for anything user-facing that must not be enumerable. Mention the two Snowflake risks (worker ID assignment and clock rollback) before the interviewer does.
