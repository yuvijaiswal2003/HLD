Design a distributed unique ID generator

Design a service that issues unique IDs for every entity in a large product (posts, messages, orders, users), used by dozens of internal services running in 5 regions. IDs must be 64-bit integers, roughly sortable by creation time, and available even if a region is cut off from the others. Peak demand is about 1 million IDs per second globally.

1Clarify first

Write down what you would ask the interviewer before designing anything, then compare.

  • Must IDs fit in 64 bits, or is a 128-bit UUID acceptable to the databases and clients that store them?
  • How strict is the ordering: strictly increasing across the whole system, or roughly time-sorted (k-sorted) to within a few milliseconds?
  • What is the peak rate per region, and how many regions and generator processes might exist in 5 years?
  • Will IDs appear in public URLs or APIs? Is it a problem if they reveal creation time or allow guessing neighbouring IDs?
  • What latency budget does a caller have to obtain an ID, and may callers fetch IDs in batches?
  • How many years must the scheme last without changing format?

2Your answer

3Hints 0/5

Stuck? Each hint gives a little more away than the last.

H1Rule out the simple options first: why do auto-increment and UUID v4 each break one of the requirements?
H2Split 64 bits into time, generator identity and a counter. Work out how long 41 bits of milliseconds last and how many IDs per millisecond 12 bits give.
H3Uniqueness now depends entirely on no two live generators sharing an identity. How do you hand out generator IDs in an autoscaling fleet, and take them back from crashed nodes?
H4Put region bits in the generator ID so regions never coordinate. Then deal with clocks: what does a generator do when its clock jumps backwards, and what if a reused generator ID runs on a machine whose clock is behind?
H5Consider whether generation belongs in a library inside every service or in a small dedicated service, and what batching does to latency and ordering.

4Model solution

Try your own answer first. The solution follows seven steps: requirements, estimates, API, data model, architecture, deep dives, trade-offs.

Requirements

  • Functional: issue unique 64-bit IDs, singly or in batches up to 1,000; decode an ID into its timestamp and generator for debugging.
  • Non-functional: never a duplicate, even across crashes, restarts and clock problems; roughly time-ordered (IDs created more than a few milliseconds apart sort correctly); 1M IDs/s global peak; p99 under 2 ms in-region; each region keeps issuing IDs while partitioned from the others; at least 50 years of range.
  • Not required: strictly increasing IDs across the system or gap-free sequences, which would need a single sequencer.

Estimates

  • Rate: 1M IDs/s global peak; the largest region carries 40%, so 400k IDs/s.
  • Per-generator capacity: 4,096 IDs per ms is about 4.1M IDs/s, far above demand, so the sequence field is not the limit. The limit is RPC handling: with batching averaging 10 IDs per request, the largest region sees 40k requests/s, and a generator node comfortably serves 50k gRPC requests/s, so 2 nodes would do; run 6 per region (2 per availability zone), which still leaves N+2 after losing a whole zone.
  • Lifetime: 2^41 ms ≈ 69.7 years; with a custom epoch of 2026-01-01 the IDs last until 2095.
  • Generator IDs: 10 bits = 3 bits region (8 regions) + 7 bits worker (128 per region); 6 nodes per region, plus new nodes started during deploys, is far below 128.
  • State: none per ID. Coordination state is two etcd keys per active worker (owner and reservation), about 60 keys across the 5 regions, refreshed once a second.

The only stored state lives in a 3- or 5-node etcd cluster per region, two keys per worker ID: an owner key attached to a lease, which disappears if the holder stops renewing, and a reserved key with no lease, which survives the holder and records the latest timestamp it was allowed to use. etcd is chosen because it offers linearizable compare-and-set and leases that expire when the holder stops renewing them, which are exactly the primitives needed to hand out exclusive identities (ZooKeeper ephemeral nodes would work equally well).

High-level design

ID path: a service calls NextIds(count) through a thin client library; the load balancer picks a healthy generator, which runs the Snowflake loop in memory and returns the IDs. No disk and no coordination is involved, so latency is one in-region round trip, well under 1 ms. If a generator is unhealthy, the client retries on another; since every worker has a distinct ID, retries can never produce duplicates. Control path: at startup and every second, each generator talks to etcd to hold its worker lease and extend its reservation, described next.

Deep dives

1. Leasing worker IDs safely. Uniqueness depends on no two live processes sharing a (region, worker) pair. Static config files fail in autoscaling fleets, so worker IDs are leased: a starting node grants itself a 10-second etcd lease and tries worker IDs 0 to 127 with a transaction that creates /idgen/region-2/owner/n, attached to the lease, only if it does not exist. It renews the lease every second, together with the reservation described below. If renewal has not succeeded for 7 seconds by its own clock, it stops serving IDs and reports unhealthy before etcd can expire the lease and hand the ID to someone else. A crashed node's key disappears when its lease expires, so the worker ID returns to the pool automatically.

The reservation closes a subtle hole. Suppose worker 17's previous holder died and its clock was 50 ms ahead of the new node's. Without a reservation, the new holder could issue IDs in milliseconds the old one already used, with the same worker ID, and produce duplicates. Each holder therefore sets reserved/17 to now + 2 s every second, using a transaction that succeeds only while owner/17 is still attached to its own lease ID, and never issues an ID with a timestamp beyond the reservation. A new holder waits until its own clock passes the stored value before serving. Since the old holder's IDs carry timestamps no later than T by its own clock and the new holder's carry timestamps after T by its clock, the two can never overlap, whatever the skew between them. A paused zombie that wakes up after losing the lease cannot extend the reservation, so it runs out of usable milliseconds almost immediately. Restarts on the same machine work the same way, so no local disk state is needed.

2. Clocks. Run chrony in slew mode with a maximum offset alarm: if a node's offset from its time sources exceeds 20 ms, it marks itself unhealthy and drains. In the generator, read time as the wall clock captured at startup plus a monotonic clock's elapsed time, so NTP steps and leap-second handling cannot make time go backwards while the process runs; re-anchor gradually if the two diverge. If time still appears to go backwards, wait when the gap is under 10 ms and refuse with an error above that; the client simply retries on another node. Ordering across regions is only as good as clock agreement, a few milliseconds, which is why the requirement says roughly time-ordered.

3. Library or service. Embedding the generator as a library in every service removes the network hop, but then every pod needs a worker ID: a few thousand pods per region and frequent autoscaling would exhaust 128 IDs and hammer etcd with lease churn. A dedicated service keeps the generator count small and stable and the bit budget comfortable, at the cost of about 0.5 ms per call, which batching hides. Services with extreme rates, such as the chat service issuing message IDs, can still embed the library with a reserved block of worker IDs. Batching does not break ordering in any way that matters: a batch of 100 IDs is generated at one moment and handed out over the next few milliseconds, well within the roughly ordered guarantee.

  • etcd is off the per-ID path but not off the critical path: no ID request touches etcd, but a generator that cannot extend its reservation stops within about 2 s, which is the price of safety. To ride out short etcd outages, reserve further ahead (say 30 s) with a longer lease. The cost is that a node taking over a recently used worker ID may wait up to 30 s, so new nodes should prefer worker IDs that have been idle longest. Run etcd as 5 nodes across AZs.
  • Information leakage: IDs reveal creation time, and the sequence hints at volume. For public URLs, expose a separate random token or encrypt the ID with a fixed-key 64-bit block cipher.
  • Bit budget is a one-way door: changing the layout later breaks ordering and decoding, so leave headroom (128 workers per region, 4,096 per ms) and document the epoch.

5Follow-up questions

  • A product team needs 2,000 generator processes in one region. How would you re-split the 64 bits, and what do you give up?
  • Finance requires order IDs that are strictly increasing with no gaps. Can this design provide that? What would?
  • A VM live-migrates and its clock comes back 2 seconds behind. Walk through exactly what your generator does.
  • How would you migrate an existing system that uses auto-increment IDs to this scheme without breaking clients that sort by ID?
  • Your IDs appear in public URLs, and a competitor is estimating your daily order volume from them. What do you change?
